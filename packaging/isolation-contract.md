# Maknae Isolation Contract

This file is the **normative** isolation contract. Its source is §4 of the topology design
spec (`2026-08-03-maknae-rust-workspace-topology-design.md` (out-of-repo design spec; specs never live in this repository)).
Two tables follow: the **property × profile** table (which `ci/gates/isolation-contract-lint.sh`
checks — every non-`deferred` cell must carry a `✓<check>` token) and the **crate × binary
matrix** (the human-readable statement of the P1/P2 capability-separation property).

Profiles not yet enabled (K8s) carry `deferred` cells and are exempt from the lint until enabled.

> **CORRECTED 2026-08-30 (operator ruling): host-native macOS is a DEPLOYMENT TARGET, not a dev convenience.** The column below read *"Host-native macOS (dev; reduced)"* and every downstream decision inherited that framing — including, on the day this was corrected, an argument that an unverified macOS lane was acceptable because *"macOS is a dev host anyway"*. It is not. The operator's statement of intent: **the Mac mini fleet bought when OpenClaw shipped is a market Maknae intends to serve.** The column is renamed accordingly.
>
> **What this changes, concretely:** a macOS delta is now a *supported-platform gap*, not a reduced-profile footnote. `launchd (no seccomp)` stays an honest delta because it is a platform fact with no macOS equivalent; *"we have not tested it there"* is not a delta, it is an unmet obligation. **Anything the Linux profile enforces needs a macOS answer or a recorded, ratified reason there is none** — and the reason may not be "dev host".

A `macos-26` CI job now runs the covered crates' suites on every relevant PR, and **Wrathion runs macOS 26 on Apple Silicon — OS-version and architecture parity.** CI is therefore an equivalent lane for that surface, not a weaker one, and it repeats per-change instead of once. *(Corrected 2026-09-11, #198: the job runs the whole workspace now, not "the covered crates' suites" — see the correction two lines down.)*

> **The lane does not cover everything.** `maknae-vault` and above pull `aws-lc-fips-sys` and `ring`, whose build scripts need a macOS SDK unavailable on a hosted runner. *(Corrected 2026-09-19, #320: `ring` is no longer among them — `cargo tree -i ring --target all` prints no tree on either `main` or this branch; it left when reqwest moved 0.12→0.13 under `rustls-no-provider`, and survives in `Cargo.lock` only as `rustls-webpki`'s unselected optional edge. What remains true: those crates cannot be **cross-checked from Linux**, and FIPS-140-3 *validation* of `aws-lc-fips` on macOS arm64 is a separate open question.)* Separately, whether `aws-lc-fips` is FIPS-140-3 *validated* on macOS arm64 — not merely compilable — is open, and for a FIPS-posture product that question outranks the tooling one. **RESOLVED 2026-09-11 (#200, maintainer ruling).** It is not. The AWS-LC FIPS 3.x line Maknae pinned until 2026-09-19 (`aws-lc-fips-sys` 0.13.x) *(present tense struck, #320: the pin is gone and the tree is on 0.14.x / the 4.x line — the sentence describes what was, and the dated correction below gives what is)* is the line CMVP validated as **certificate #5314** (static; #5298 dynamic — **on macOS the applicable line is #5298; see the 2026-09-12 correction below**) — at module version **3.1.0**. **MAINTAINER RULING 2026-09-13 (restated; first given 2026-09-12): ANY 3.x implementation is approved. The AWS-LC-FIPS **3.x line** is what CMVP validated and what an assessor evaluates; that the certificate was issued at 3.1.0 while the pinned crate vendors 3.6.0 is NOT a finding and is not tracked. Earlier prose here treated it as an unresolved 'version mapping' that barred citing the certificate — that was wrong, it is struck, and it must not be reintroduced.** What #5314 establishes independent of that mapping is the environment list: its security policy, Table 3 *Tested Operational Environments*, lists exactly: **Amazon Linux 2023 on Graviton4 (ARMv9, r8g.metal-24xl) and on Intel Xeon Platinum 8375C (c6i.metal), each with and without PAA** — vendor-affirmed environments: *N/A*. The policy's own words: *"CMVP makes no statement as to the correct operation of the module or the security strengths of the generated keys when so ported if the specific operational environment is not listed on the validation certificate."* macOS on Apple Silicon is therefore a **ported**, unvalidated operational environment: the module compiles and its self-tests and our suites pass there in CI (`darwin-native`, observed green 2026-09-11), and Maknae does **not** claim FIPS 140-3 validation on macOS. Note the same table for the Linux profile: RHEL/Rocky 9 on generic x86_64/aarch64 is not a listed environment either — the validated deployment is Amazon Linux 2023 on those two CPUs; everything else runs the module *line* that was validated, outside its tested *environments*. The honest form of the claim on every platform Maknae ships today concerns the ENVIRONMENT, not the version: the module line is validated, and the operational environment Maknae ships on is not one the certificate lists. The ruling: macOS stays a production target; a deployment with a FIPS compliance obligation will not be on macOS regardless (there is a macOS STIG, but a STIG'd host is still an unlisted environment for this module), so the posture statement is the fact above, not a plan to change it.

> **CORRECTED 2026-09-12 (#227, from upstream AWS-LC source — this is the macOS build's own linkage, not an inference).** The paragraph above cites **#5314** as the certificate Maknae's FIPS line maps to. **#5314 is the STATIC module, and macOS cannot use it.** Upstream forbids a static FIPS build outside Linux — `aws-lc/CMakeLists.txt:842`: `if(NOT BUILD_SHARED_LIBS AND NOT (UNIX AND NOT APPLE)) message(FATAL_ERROR "Static FIPS build of AWS-LC is suported only on Linux")` (verified by running `AWS_LC_FIPS_SYS_STATIC=1 cargo build --target aarch64-apple-darwin`, which fails on exactly that line) — and `aws-lc-fips-sys/README.md:143` states plainly that a shared `libcrypto` is *"the required form for FIPS on macOS and Windows"*. **So on macOS the applicable validation line is #5298 (dynamic), not #5314 (static).** Every Maknae document that cited #5314 in a macOS context named the wrong line of the wrong module; corrected here and in `packaging/macos/README.md`, `design/adr/ADR-0002-kernel-is-rust.md` and `design/adr/ADR-0009-subject-side-os-dac-evaluation.md` on the same date.
>
> **This is not a macOS deficiency.** Shared is a first-class upstream FIPS mode, not a fallback: `aws-lc/crypto/CMakeLists.txt:621-623` — *"Rewrite libcrypto.so, libcrypto.dylib, or crypto.dll to inject the correct module hash value. For now we support the FIPS build only on Linux, macOS, iOS, and Windows"* — with a dedicated `-apple` flag for `inject_hash.go`, and `aarch64_apple_darwin` carrying pregenerated bindings. The two modes differ only in how the module's self-integrity region is made hashable: shared treats the dylib itself as the module boundary, while static must synthesise one with **delocate**, which rewrites the module's assembly to lay text and rodata contiguously — ELF-specific machinery, which is exactly what the guard above encodes. Upstream's own README speaks of *"the static **or** dynamic AWS-LC Cryptographic Module"*: two separately validated modules, neither weaker. *(Corrected 2026-09-19, #320: true of the 3.x pair this sentence was written about; under 4.x **neither** is validated — both v4.0 static and v4.0 dynamic are Modules In Process. The structural point survives intact: shared is a first-class upstream FIPS mode, not a fallback, and the two forms are peers.)*
>
> **What DOES change, and it is a packaging obligation with a fail-open edge.** `aws-lc-fips-sys/README.md:141-149` warns that a shared install's library directory is not embedded in the consumer binary, so *"a different `libcrypto` may be loaded — on macOS the build-host's `@rpath` install name can resolve to an unrelated library."* Measured on `main` 2026-09-12: `otool -L target/debug/maknaed` shows `@rpath/libaws_lc_fips_0_13_17_crypto.dylib` *(the basename carries the `aws-lc-fips-sys` crate version, so on and after 2026-09-19 (#320) it is `libaws_lc_fips_0_14_2_crypto.dylib`; the measurement is left at its observed value, and packaging is version-independent — `build-pkg.sh` globs it, `smoke.sh` normalises it)* and `otool -l` shows **zero `LC_RPATH`**; the binaries run under `cargo` only because cargo injects `DYLD_*`. The hazard is therefore not merely "the installed binary fails to start" — it is that an unresolved `@rpath` **searches**, and can bind a `libcrypto` nobody chose while the posture claims otherwise. *(Corrected 2026-09-19, #320 — the same strike applied in `packaging/macos/README.md`: the hazard was never about the CMVP list. An unresolved `@rpath` binds **some other `libcrypto` entirely** — one nobody chose, self-tested or shipped. Maknae's own module is no longer on the validated list either ([ADR-0025](../design/adr/ADR-0025-fips-validation-is-a-goal-not-a-constraint.md)), which is exactly why the old wording now reads as a contradiction rather than a warning; the hazard is unchanged and just as serious.)* #227 pins the module by **absolute install name** (the pattern Cisco AnyConnect uses for its own crypto dylibs on this platform: `/opt/cisco/anyconnect/lib/libacciscocrypto.dylib`, zero `LC_RPATH`), so the loader can resolve exactly one file and no search occurs.

> **The certificate SPLIT is the real correction here, and it stands.** **MAINTAINER RULING 2026-09-13 (restated; first given 2026-09-12): ANY 3.x implementation is approved. The AWS-LC-FIPS **3.x line** is what CMVP validated and what an assessor evaluates; that the certificate was issued at 3.1.0 while the pinned crate vendors 3.6.0 is NOT a finding and is not tracked. Earlier prose here treated it as an unresolved 'version mapping' that barred citing the certificate — that was wrong, it is struck, and it must not be reintroduced.** What changes on macOS is *which certificate applies* — #5298, the dynamic line — not any question about the module's version.

> **CORRECTED 2026-09-19 (#320, maintainer ruling): Maknae is not on a CMVP-validated module line any more — deliberately, and that is now the recorded posture.** Everything above describes the AWS-LC-FIPS **3.x** line, which `maknae-vault` pinned (`aws-lc-rs >=1.17.3, <1.18.0`) until today. RUSTSEC-2026-0285 — TLS 1.3 handshake messages accepted across encryption-level boundaries, `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`, and the advisory states that *"the handshake transcript is still authenticated, so a network-position attacker cannot use this to alter or complete a handshake"*, so it is a confidentiality-only, low-severity defect rather than a handshake break — is fixed in rustls 0.23.45, which requires `aws-lc-rs >=1.18`, i.e. the AWS-LC-FIPS **4.x** module; upstream lists v4.0 static and v4.0 dynamic under *Modules In Process* ("Review"), not under validated (`aws-lc/crypto/fipsmodule/FIPS.md`, read 2026-09-19). **The pin made a published TLS vulnerability untakeable**, and `cargo deny check advisories` was red on `main` and on every branch with no fix available to an agent. The maintainer's ruling — recorded as **[ADR-0025](../design/adr/ADR-0025-fips-validation-is-a-goal-not-a-constraint.md)**, which is the decision of record; this document carries the normative platform statement and mirrors that decision, it does not replace it — in their words: *"Maknae does NOT have the same compliance posture as Microkosmos and it's silly to try and justify it otherwise. The design goal is the same (FIPS Validated), but it's a goal not a constraint."* It follows the same reasoning already standing here since 2026-09-12: keeping an older crypto library with known vulnerabilities is worse than moving within the vendor's supported channel.
>
> **The claim this document makes from today, on every platform: Maknae builds on the AWS-LC-FIPS 4.x module line, which is submitted and under CMVP review — never "validated", and (independently, exactly as before) never in a listed operational environment.** So the SC-13 evidence gap is now **two** axes, not one: the module's certificate *and* the operational environment. The 3.x certificate facts above are retained as the record of what was and because the environment reasoning is unchanged in kind — they are no longer a current claim about the shipped artifact. **What survives structurally:** the static/dynamic SPLIT (Linux static, macOS dynamic — upstream submitted v4.0 as the same two modules, so macOS remains the dynamic one), the absolute-install-name pinning obligation, and the runtime `.fips()` assertion, which proves the FIPS *build* and never proved a certificate. **What is struck:** every sentence in this file that reads as "Maknae ships a validated module", and the framing of the 3.x pin as a control in force. **The v4.0 certificate is NOT TRACKED** — maintainer, 2026-09-19: *"We don't need to be FIPS Validated because there is no CAT I."* No watch issue, no review date, nothing owed. If it issues, it licenses an upgrade to the claim above and nothing else. Do not file a watch and do not propose restoring the pin.
