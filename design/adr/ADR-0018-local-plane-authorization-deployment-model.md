> **Decision 1's client gate is superseded in target model (ADR-0006 Decisions 2 & 4).** For **local clients**, clause (a) — a verified `cli`-plane leaf — is retired along with the client certificate itself; the gate becomes **(b) *current* `maknae`-group membership + a live host-login session for that uid + the live peer-cred uid + the daemon-side uid-bound session** — the liveness factor platform-scoped and **config-driven** (deployment-mode key, fail-closed at boot and environment-cross-checked — mismatch refuses boot: the connecting **process's own** logind session — `sd_pid_get_session`, never a uid-scoped search — with `Class=user`/`State∈{active,online}` on Linux hosts; the two-part human-login + liveness check on macOS; **on this ADR's Kubernetes/container path no client listener is bound and the image ships no client binary** — human access is the gateway #117 — ADR-0006 Decision 4 §Platform scope) — with membership and session-liveness **re-resolved from the host on every connection *and re-evaluated on every request over that connection*** (never trusted from the client process's snapshotted supplementary groups) — so **de-enrollment by group removal — and logout — terminates access at the next request, even over an already-open connection**, which is the local session-termination (AC-12) mechanism, and on Linux every request's **kernel-verified sender credentials** (`SO_PASSCRED`/`SCM_CREDENTIALS`) must match the session uid — a delegated fd transfers nothing (#115). **Disambiguation, 2026-08-30 ([ADR-0009](ADR-0009-subject-side-os-dac-evaluation.md)):** this governs the **connection** fd (T13). It does **not** forbid delegating a **file** fd, which ADR-0009 makes the REQUIRED mechanism for `fs.read` — the client opens the object as the subject so the kernel decides object access, and `SO_PASSCRED` is what makes it safe. **A file fd carries object authority, never identity.** `maknaed` additionally owns a **visit clock** — an idle timeout (SC-10) and an absolute maximum connection lifetime (AC-12), client-independent termination authority (ADR-0006 Decision 4): expiry is the disconnect event, and re-establishment re-runs the full gate with a fresh kernel peer-cred capture; timer values are #115's to fix and MUST be stated. This also supersedes, **for the enrollment gate only**, this ADR's "gates *connections*, not *operations*" scope line: the AuthN re-check is per-request in the target model, while the per-request PDP *authorization* decision remains out of this ADR's scope as before. Clause (a) survives for **machine planes** (the daemon's own identity; the gateway's internal channel later). The enforcement posture is unchanged: a non-`maknae`-group peer is refused, fail-closed, with an AU-3 audit event (ADR-0019); the channel remains TLS 1.3 with the daemon server-authenticated (`plane/kernel`). (The **remote** path is out of scope for this local-plane ADR — a remote client reaches the gateway, never `maknaed`.) **The "mTLS plane cert is the real per-user credential" framing is superseded everywhere it appears in this ADR** — decision 1's body, the Consequences echo of it, the acceptance-test framing built on "a valid `cli` plane cert" (client channel only; machine-channel tests stand, #114), and **both** control-mapping rows that cast the cert as the client authenticator: the per-user credential is the **OS login, attested per connection by `SO_PEERCRED`** — the per-request authorization principal is that uid (local) or the gateway-asserted OIDC principal (remote), never a certificate. This ADR's body below states the pre-ADR-0006 steady state; this banner governs the target model.

## Context

Stage 2 established a mutually-authenticated mTLS channel over a local UDS and deliberately deferred (Boundary A) the daemon-side *authorization* decision and the daemon *lifecycle* — who may be served, and how the daemon stays authenticated to Vault without operator babysitting. Stage 3a must decide both, and the decision is shaped by two facts:

1. **Deployment reality.** The common case (an OpenClaw-style single-user local agent on a dedicated host) is single-user; multi-user only arises on shared infrastructure, where the realistic deployment is **Kubernetes**, which supplies its own platform identity and changes the trust model entirely. So a heavyweight per-user authorization apparatus is over-built for the deployments that actually occur.

> **Amendment (2026-09-10, via [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) — Accepted).** **One sentence of this fact is superseded: *"multi-user only arises on shared infrastructure, where the realistic deployment is Kubernetes."*** It does not. Maknae is multi-tenant on a single host — several humans, several agent personas, one kernel — and the **local** plane separates their authority, rather than deferring the case to a gateway or an orchestrator.
>
> **The rest of this fact stands, and ADR-0024 reinforces it.** Most deployments will still have one subject, and the anti-friction conclusion is explicitly honoured: ADR-0024 adds **no new mechanism** and adopts **no per-uid allowlist**. Multi-tenancy is structural, never ceremonial — a single-subject install must feel single-subject — which is possible precisely because the per-request uid principal this ADR established already distinguishes subjects at no cost. Decision 1's "a per-uid allowlist is not adopted" is unchanged.
2. **Availability is High.** For an HHH system a daemon that shuts itself down on a fixed schedule (e.g. when its Vault token hits `token_max_ttl`) is a self-inflicted availability vector. "Vault is unreachable" is a legitimate fail-closed trigger; "I let my own credential expire" is negligence, not a failure mode — especially when Vault provides a mechanism to hold authentication indefinitely.

## Decision

**1. Authorization gate = mTLS plane cert **AND** `maknae`-group membership; no per-uid allowlist.** A connection is served only if (a) the transport verified the peer's `cli`-plane URI-SAN (ADR-0005), **and** (b) the peer's kernel-reported `uid` is a member of the `maknae` group (the same group that gates the `0660` socket). The **mTLS plane cert is the real per-user credential**; the group gate is the cheap outer fence. A per-uid allowlist is **not** adopted — on a single-user host it is friction with no benefit, and multi-user hardening collapses into the Kubernetes/gateway case. The group-membership predicate is pure decision logic (ADR-0016 **T1**, 0-missed). A non-member connection fails closed with an audit event (ADR-0019).

**2. Enrollment = `maknae enroll`, a one-time elevated event.** Package installation performs only the root-only, no-secret setup (create the `_maknae` service account and `maknae` group via `sysusers.d`; create `/etc/maknae{,/tls,/private}`; install the `maknaed` systemd unit with `RuntimeDirectory=maknae`). The operator then authenticates to Vault *as themselves* and runs `maknae enroll`, which — **using the operator's Vault authority** — provisions the daemon's and the operator's credentials (decision 4) and adds the operator to the `maknae` group. `maknae enroll` is a thin, inspectable wrapper over the equivalent `vault` commands.

**3. Continuous operation = a periodic Vault token; no scheduled re-auth.** The `maknaed` AppRole role sets **`token_period`**, making the daemon's token a **periodic token** with no `max_ttl` ceiling: the existing background renewal loop (ADR-0005 / Stage 1) renews it indefinitely. **A failed renewal is retried within the token's remaining validity window** — renewal is attempted well before expiry (≈⅔ of the lease), so a *transient* Vault outage at renewal time is retried and does **not** stop service. The daemon fails closed **only** when the token can no longer be renewed **before it would expire** (retries exhausted / sustained outage) or the token is **revoked**. So "lost Vault connectivity" is a legitimate fail-closed trigger, but a brief blip is absorbed by the retry window rather than taking the plane down. A new **leaf-rotation loop** re-mints the plane leaf before its `leaf_ttl` (~72h) using the valid token, so certificate delivery is continuous. The daemon never re-authenticates on a schedule and never shuts itself down for cause other than genuine Vault failure. Periodic tokens are chosen over daemon-side SecretID self-rotation **specifically to preserve custody-by-secret-absence**: self-rotation would require granting the daemon `create` on `.../secret-id`, handing a compromised daemon a persistence/self-escalation primitive; a periodic token needs no such grant.

**4. Secure introduction (boot bootstrap) is deployment-specific.** The token and leaf are memory-only, so a reboot is a re-authentication event requiring a bootstrap credential:
   - **Bare-metal (single-user):** a **standing SecretID**, provisioned by `maknae enroll` with the operator's authority and **sealed at rest to the platform hardware root of trust (HRoT), decrypted only into memory at startup** (never written in plaintext):
     - **Linux:** `maknae enroll` runs `systemd-creds encrypt` **TPM2-anchored** (`--with-key=tpm2`, i.e. the sealing key is bound to the TPM — *not* the host-key-only fallback, which would put the key on disk) → a `.cred` file; the `maknaed` unit declares `LoadCredentialEncrypted=`, so systemd decrypts it at service start into `$CREDENTIALS_DIRECTORY` — a per-service **memory-backed tmpfs**, `0400`, `_maknae`-only. No crypto code lives in Maknae; systemd + the TPM do it, and the `.cred` is bound to that TPM.
     - *(Superseded 2026-09-27 by decision 6: a launchd daemon cannot use the data protection keychain a Secure Enclave key requires — Apple-documented in TN3137; the probes on #76 measured the failures that follow from it.)* **macOS: envelope encryption with a non-exportable Secure Enclave key** (a Keychain password item is *not* SEP-sealed — the SEP protects keys, not arbitrary data). `maknae enroll` generates a **non-exportable EC key inside the Secure Enclave** (`SecKeyCreateRandomKey` with `kSecAttrTokenIDSecureEnclave`), encrypts the SecretID to that key's public half (ECIES), and stores the **ciphertext** on disk (or as a Keychain blob — it is already encrypted). At startup the daemon calls `SecKeyCreateDecryptedData` with the SEP-resident private key to recover the SecretID **into memory**. The SEP private key **never leaves the enclave**, so the ciphertext is bound to that Mac's SEP.
     The role sets `secret_id_num_uses = 0` so the daemon re-logs-in on every boot; the **daemon holds no SecretID-minting capability** — it only *reads* the decrypted-in-memory credential and consumes it. Reboots are hands-free *(on a FileVault Mac, once the disk is unlocked — decision 6, delta 4)*. **Copying the sealed artifact to another host is useless** (the HRoT-sealed key does not travel) — disk-at-rest exfiltration is defeated *(On macOS this holds against a non-administrator only: root can copy the System keychain and `/var/db/SystemKey` — decision 6.)*; the remaining residual is a *live-compromised* `_maknae`, which can ask the HRoT to unseal exactly as the daemon does *(on macOS also root, and a live-compromised `_maknae-egress` for its own item — decision 6)*. Rotatable via `maknae enroll --rotate`. A plaintext-at-rest form exists **only** behind an explicit, loudly-audited `maknae enroll --insecure-plaintext-secret` opt-out for hosts with no HRoT — never the default.
   - **HARDWARE PREREQUISITE (explicit).** *(Narrowed 2026-09-27: on macOS the prerequisite is a Developer ID-signed install, not a Secure Enclave, and the `--insecure-plaintext-secret` opt-out below does not apply there — decision 6, delta 3.)* Bare-metal deployment **requires a hardware root of trust**: a **TPM 2.0** on Linux (physical or a hypervisor **vTPM** — VMware/Hyper-V/KVM-swtpm/cloud all provide one) or a **Secure Enclave** on macOS (Apple Silicon). A host or VM without an HRoT is a supported deployment **only** via the explicit `--insecure-plaintext-secret` opt-out (which reverts to the `_maknae:_maknae 0400` plaintext residual and is audited as a degraded posture). **Kubernetes needs no HRoT** — it uses SA auth with no secret at rest.
   - **Kubernetes:** the **Vault Kubernetes auth method** (the pod's service-account token as platform identity) — hands-free, **no** secret at rest, survives reschedule/reboot. This is the production path and needs no enrollment secret or HRoT.
   - `maknae enroll` also provisions the **operator's own `cli`-plane standing SecretID** (operator-owned; HRoT-sealed) so the CLI can mint its `cli` leaf. On **macOS** the operator's login Keychain (Secure-Enclave-backed — *corrected 2026-09-27: not so; the login keychain is a file-based keychain, and Secure Enclave protection needs the data protection keychain (TN3137). Decision 6 does not cover the CLI store, which #116 removes*) is the natural CLI store. On **Linux** the daemon's `systemd-creds` + `LoadCredentialEncrypted=` path is a *service-unit* mechanism that does not apply to an interactive CLI (no unit, no `$CREDENTIALS_DIRECTORY`); the operator-CLI seal mechanism there (a systemd *user* credential, a kernel keyring TPM-*trusted* key, or a libsecret store) is **resolved in the implementing spec**, not implied identical to the daemon path.

**5. Full-lifecycle intervention posture.** Across the daemon's life, the only operator touches are **first enroll** and **intentional** acts (rotate the standing credential; revoke on compromise). Steady-state operation, leaf rotation, transient Vault outages, and **reboots** are all hands-free. *(macOS, 2026-09-27: on a FileVault Mac neither plane starts until the disk is unlocked after a reboot; `fdesetup authrestart` covers planned restarts — decision 6, delta 4.)*

**6. macOS plane-secret custody: the System keychain, bound to the signed binary (2026-09-27, #76).** *Prospective (see the banner): the sentences below are requirements on #76's implementation.* On macOS each bare-metal plane's standing SecretID — `maknaed`'s, and `maknae-egress`'s since #240b — is a generic-password item in `/Library/Keychains/System.keychain` (service `io.maknae.maknaed` or `io.maknae.maknae-egress`, account `secret-id`) whose access-control list trusts only that plane's binary, by its designated requirement: signing identifier, Developer ID chain and Team ID. `maknae enroll` writes both items as root. Each process reads only its own item, with keychain user interaction disabled, and only after confirming it runs as its own account (`_maknae` or `_maknae-egress`). A root-owned pointer file (`private/maknaed-secret-id.keychain`, `egress/maknae-egress-secret-id.keychain`) names the item; the reader refuses a pointer that names any other keychain, service or account, so the file cannot redirect the read. The boot posture record reports `code_bound`, never `hrot_sealed`.

*Why not the Secure Enclave.* Measured on Apple Silicon, macOS 26.6.2 (#76): persisting a Secure Enclave key to the keychain fails `-34018` unsigned, as root, and with a Developer ID signature and no entitlement; claiming `keychain-access-groups` without a matching provisioning profile is killed at exec (SIGKILL). Per Apple's documentation (not measured here), a provisioning profile would authorize the entitlement, but TN3137's execution-context limit still excludes a launchd daemon. There is no Secure Enclave path for a system daemon.

*What was measured* (Wrathion, macOS 26.6.2, with a Developer ID-signed probe binary standing in for `maknaed`; the scratch items, users and jobs were removed and verified gone). Rows marked † were measured on a scratch file-based keychain in user context (2026-09-25); the rest on `/Library/Keychains/System.keychain`, as root, an administrator and a non-administrator, and from a launchd daemon (2026-09-27). Still unmeasured: the real `maknaed` and `maknae-egress` designated requirements, and a reader over ssh.

*The delta from Linux, stated.*
1. **Bound to code identity with a root-held key, not to hardware.** The System keychain's *"unlocking is automatically handled by the system"* (`systemkeychain(8)`), observed in the boot row above; `/var/db/SystemKey` is `root:wheel 0400` (measured). Inferred, not measured: that file is the unlock key, so a non-administrator who copies the keychain off the host gets nothing, and **root can copy the keychain and `SystemKey` and decrypt them off the host**, which a TPM-sealed `.cred` does not allow. Offline access to both files — a disk image or backup that holds `/var/db/SystemKey` — is equivalent to root; FileVault is what protects an offline disk.
2. **The ACL checks the calling code, not the user** (measured: the trusted binary read as a non-admin user). Any local user who can execute the signed daemon gets a process the keychain would serve, so each process refuses the read unless it runs as its own account; that account check, not the ACL, is what keeps another user out. Hardened Runtime refuses debugger attach and library injection into the running daemon (Apple-documented). **This holds only if every binary that satisfies the requirement carries both, so it is a requirement on signing:** every Developer ID signature of `maknaed` or `maknae-egress` carries Hardened Runtime and an empty entitlement set — in particular no `get-task-allow` and no Hardened Runtime exception (`com.apple.security.cs.*`, which includes `disable-library-validation` and `disable-executable-page-protection`) — and the account check; a build that needs any entitlement stays ad hoc and cannot read the item, and adding one to a signed build needs its own recorded decision. (One Developer ID signature over the binary and the FIPS dylib passes library validation with no entitlement — measured 2026-09-19, #227.) The invariant holds from the first build that carries the account check. Developer ID builds signed before that (the #227 verification, and any `build-pkg.sh` run with a signing identity before #76's implementation lands) satisfy the requirement without the check; they are not distributed and must not run on a host shared with another user — an accepted dependency on artifact custody. Rotating the SecretID does not exclude them, because the item's ACL is keyed to the requirement, not to the value. No signed release exists as of this amendment. The implementation owes a test that goes red if the check is removed.
3. **An ad-hoc build cannot read the item.** Enrollment requires Developer ID-signed `maknaed` and `maknae-egress`, and refuses otherwise, so a development build and a packaged install diverge on the Mac. The `--insecure-plaintext-secret` opt-out does not waive the signature requirement on macOS: it exists for hosts without a hardware root of trust, and every supported Mac has the System keychain.
4. **FileVault gates start.** Inferred, not separately measured: on the boot above the daemon ran about 12 minutes after kernel start, consistent with the FileVault pre-boot unlock gating the Data volume the job lives on. A FileVault Mac that reboots unattended leaves both planes down until the disk is unlocked; `fdesetup authrestart` covers planned restarts.

## Security criteria / acceptance tests

- A connection from a `uid` **not** in the `maknae` group is refused, fail-closed, with an audit event (ADR-0019) — even when the peer presents a valid `cli` plane cert. (The group predicate is T1, 0-missed.)
- A daemon left running past the former `token_max_ttl` keeps serving (periodic token renews). A **transient** Vault outage at renewal time is retried within the token's validity window and does **not** stop service; a **sustained** outage causes fail-closed once the token can no longer be renewed before expiry; a **revoked** token causes fail-closed.
- After a reboot with no operator action *(on a FileVault Mac, after the disk is unlocked — decision 6)*, `maknaed` re-authenticates from the HRoT-sealed standing SecretID (decrypted only into the memory-backed credential store *— on macOS, into process memory; decision 6*) and resumes serving.
- The standing SecretID is **never present in plaintext at rest** (default path) — it exists only as **HRoT-sealed ciphertext** (Linux: a TPM2-anchored `systemd-creds` `.cred`; macOS: SEP-encrypted ciphertext, wherever stored *(2026-09-27: on macOS a System-keychain item, not SEP ciphertext — decision 6)*) plus, transiently, the in-memory decrypted form. Copying the sealed artifact to a **different host fails to yield a usable SecretID** (HRoT-bound). *(The test asserts these two properties — no plaintext at rest, ciphertext host-bound — not a specific storage location.)* *(macOS, 2026-09-27: "no plaintext at rest" holds; "ciphertext host-bound" holds against a non-administrator only — decision 6.)*
- The operator's own uid **cannot** retrieve the daemon's sealed SecretID. *(2026-09-27: an operator with administrator rights — `sudo`, or on macOS approving the keychain's administrator dialog — is root-equivalent and outside this property on both platforms — decision 6.)*
- The daemon's Vault policy grants **no** `create` on any `.../secret-id` path (verified against the role policy).

## Scope boundary

This ADR covers the **local-plane** authorization and the daemon lifecycle for the single-user bare-metal and Kubernetes deployments, **including** HRoT-sealed at-rest protection of the bootstrap SecretID (TPM 2.0 / Secure Enclave *— on macOS the System keychain, code-bound, decision 6*). It does **not** cover: the **per-request PDP** decision (deferred to the authorization-seam/PDP work — this ADR gates *connections*, not *operations*); **remote / cross-host** authorization and the channel bridges (the **gateway**, issue #117); **TPM measured-boot / remote attestation** binding the seal to boot state (a further hardening beyond sealing); and the **audit record model** (ADR-0019).

## Consequences

- **Positive:** hands-free steady-state + reboot lifecycle (Availability) *(on a FileVault Mac, after the disk is unlocked — decision 6)*; custody-by-secret-absence preserved for the daemon runtime (no SecretID minting); the bootstrap SecretID is HRoT-sealed at rest and decrypted only into memory, so disk-at-rest exfiltration is defeated *(on macOS against a non-administrator, not against root — decision 6)*; minimal authorization surface that matches real deployments; a single, inspectable enrollment command.
- **Negative / accepted:** a **hardware prerequisite** (TPM 2.0 / Secure Enclave) for bare-metal *(on macOS a Developer ID-signed install instead, with a root-held key — decision 6)* — accepted and made explicit (VMs need a vTPM); the `--insecure-plaintext-secret` opt-out reintroduces the plaintext residual for no-HRoT hosts and is audited as degraded; no per-user granularity below group membership on the local plane (accepted; the mTLS cert is the per-user credential, and finer control is a gateway/PDP concern).
- **Custody-by-secret-absence, precisely.** The property holds for the daemon's runtime **token** and its **minting capability**: the daemon can neither mint SecretIDs (no `create` grant) nor hold a durable off-host token (the memory-only periodic token dies with the process and within one period if unrenewed). With HRoT sealing (the default), the bare-metal standing SecretID **no longer yields to disk theft** — the sealed artifact is useless off-host *(on macOS, to a non-administrator; root can take the System keychain and its key — decision 6)*. The remaining residual is a **live-compromised `_maknae`** *(on macOS also root, and a live-compromised `_maknae-egress` for its own item — decision 6)*, which can request an HRoT unseal exactly as the daemon does — and because the SecretID is `num_uses = 0`, once unsealed into a compromised process it is **durably replayable off-host until `--rotate`** (unlike the memory-only periodic token, which dies with the process). So HRoT sealing narrows the exposure to *runtime* compromise but does not bound the *durability* of what such a compromise yields; that is accepted under the single-user threat model and rotation. The plaintext residual returns only under the explicit `--insecure-plaintext-secret` opt-out. None of this exists on the k8s path (no secret at rest). The operator's `cli`-plane standing SecretID is the same class, HRoT-sealed on the operator's uid *(on Linux; on macOS its login-keychain store is file-based, not HRoT-sealed — see decision 4's CLI sentence; #116 removes it)* and subsumed by operator-uid compromise (which ADR-0005 already treats as fatal to that plane).
- **Terraform (`deploy/vault-pki`, its own change):** the `maknaed` role gains **`token_period`** (periodic token) **+** `secret_id_num_uses = 0` (standing bootstrap). The `maknae` CLI role keeps its **short-lived token** (per-invocation, dies fast — no `token_period`) but its **SecretID becomes standing** (`secret_id_num_uses = 0`, operator-owned) so the CLI can mint per invocation without re-seeding. Both SecretID changes supersede ADR-0005's single-use-response-wrapped model (bootstrap is a local `_maknae`/operator-owned file, not an untrusted-channel delivery, so response-wrapping adds nothing here).
