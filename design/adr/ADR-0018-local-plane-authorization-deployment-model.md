# ADR-0018: Local-plane authorization & deployment model — group+cert gate, `maknae enroll`, periodic-token continuous operation

- **Status:** Accepted (operator-ratified 2026-08-11)
- **Date:** 2026-08-11
- **Deciders:** Alex Ackerman (operator), Claude (pair)
- **Addresses:** the Stage-3a "make it respond" harness — how an operator stands Maknae up, which gates authorize the local plane, and how the daemon maintains continuous authentication across its full lifecycle.
- **Relates to:** ADR-0005 (the mTLS plane transport + plane-cert identity this authorizes over); ADR-0007 (key & signature model); ADR-0019 (audit model — records the decisions here); issue #66 (the gateway / remote-client boundary this defers to); the merged Vault PKI (`deploy/vault-pki/`) whose AppRole roles this amends.
- **Supersedes (clauses of the *Accepted* ADR-0005 — see the amendment appended to ADR-0005):** three ratified clauses are intentionally changed here, adjudicated in the Stage-3a brainstorm — (1) the **single-operator principal model** (principal = peer-cred uid resolved against the single Tier-0 operator record; any other uid denied) → **`maknae`-group membership + the mTLS plane cert**; (2) **"background token renewal → fail-closed at `token_max_ttl` (re-auth with a fresh SecretID)"** → **periodic token, renewed indefinitely, fail-closed only on genuine Vault failure**; (3) the plane SecretID as **"out-of-band single-use response-wrapped"** → a **standing SecretID** (daemon `_maknae`-only; operator-owned for the CLI). These are not silent drift; they are deliberate supersessions with the rationale below.
- **Source spec:** `~/claude-memory/maknae/specs/2026-08-11-maknae-stage3a-it-responds.md`.

> **Amendment (2026-08-22, via [ADR-0006](ADR-0006-client-authentication-model.md) — Accepted).** The **operator-CLI** half of the standing-SecretID clause is superseded *in target model*: the operator CLI will hold **no credential at rest at all** — no Vault SecretID and no client certificate. Client authentication moves to the trust plane as the sole door — on-host via OS login + root-gated `maknae`-group + kernel-attested peer-cred uid, carried in a **short-TTL session bound to that uid**; remotely via enrolled-subject OIDC through the gateway (#66). X.509 becomes **machine identity only** (ADR-0006 Decision 2); no new Vault signing capability is granted to anyone. **This is prospective, not yet in force:** until the session path lands, the standing operator-CLI SecretID and its el9 `0400` residual (#73, OPEN) **remain in effect** — do not treat #73 as closed. #89 (`--user` cannot use `--with-key=tpm2`) was separately **patched** (`--with-key=auto`) and closed 2026-08-16. The **daemon's** machine identity below — a standing AppRole SecretID, HRoT-sealed, periodic-token — is unchanged.
>
> **Decision 1's client gate is superseded in target model (ADR-0006 Decisions 2 & 4).** For **local clients**, clause (a) — a verified `cli`-plane leaf — is retired along with the client certificate itself; the gate becomes **(b) `maknae`-group membership + the live peer-cred uid + the uid-bound session** (the daemon re-verifies live peer-cred against the session on every connection). Clause (a) survives for **machine planes** (the daemon's own identity; the gateway's internal channel later). The enforcement posture is unchanged: a non-`maknae`-group peer is refused, fail-closed, with an AU-3 audit event (ADR-0019); the channel remains TLS 1.3 with the daemon server-authenticated (`plane/kernel`). (The **remote** path is out of scope for this local-plane ADR — a remote client reaches the gateway, never `maknaed`.) **Decision 1's phrase "the mTLS plane cert is the real per-user credential" is superseded:** the per-user credential is the **OS login, attested per connection by `SO_PEERCRED`** — the per-request authorization principal is that uid (local) or the channel-bound OIDC principal (remote), never a certificate. Decision 1's body and its §-control-mapping row state the pre-ADR-0006 steady state; this banner governs the target model.

## Context

Stage 2 established a mutually-authenticated mTLS channel over a local UDS and deliberately deferred (Boundary A) the daemon-side *authorization* decision and the daemon *lifecycle* — who may be served, and how the daemon stays authenticated to Vault without operator babysitting. Stage 3a must decide both, and the decision is shaped by two facts:

1. **Deployment reality.** The common case (an OpenClaw-style single-user local agent on a dedicated host) is single-user; multi-user only arises on shared infrastructure, where the realistic deployment is **Kubernetes**, which supplies its own platform identity and changes the trust model entirely. So a heavyweight per-user authorization apparatus is over-built for the deployments that actually occur.
2. **Availability is High.** For an HHH system a daemon that shuts itself down on a fixed schedule (e.g. when its Vault token hits `token_max_ttl`) is a self-inflicted availability vector. "Vault is unreachable" is a legitimate fail-closed trigger; "I let my own credential expire" is negligence, not a failure mode — especially when Vault provides a mechanism to hold authentication indefinitely.

## Decision

**1. Authorization gate = mTLS plane cert **AND** `maknae`-group membership; no per-uid allowlist.** A connection is served only if (a) the transport verified the peer's `cli`-plane URI-SAN (ADR-0005), **and** (b) the peer's kernel-reported `uid` is a member of the `maknae` group (the same group that gates the `0660` socket). The **mTLS plane cert is the real per-user credential**; the group gate is the cheap outer fence. A per-uid allowlist is **not** adopted — on a single-user host it is friction with no benefit, and multi-user hardening collapses into the Kubernetes/gateway case. The group-membership predicate is pure decision logic (ADR-0016 **T1**, 0-missed). A non-member connection fails closed with an audit event (ADR-0019).

**2. Enrollment = `maknae enroll`, a one-time elevated event.** Package installation performs only the root-only, no-secret setup (create the `_maknae` service account and `maknae` group via `sysusers.d`; create `/etc/maknae{,/tls,/private}`; install the `maknaed` systemd unit with `RuntimeDirectory=maknae`). The operator then authenticates to Vault *as themselves* and runs `maknae enroll`, which — **using the operator's Vault authority** — provisions the daemon's and the operator's credentials (decision 4) and adds the operator to the `maknae` group. `maknae enroll` is a thin, inspectable wrapper over the equivalent `vault` commands.

**3. Continuous operation = a periodic Vault token; no scheduled re-auth.** The `maknaed` AppRole role sets **`token_period`**, making the daemon's token a **periodic token** with no `max_ttl` ceiling: the existing background renewal loop (ADR-0005 / Stage 1) renews it indefinitely. **A failed renewal is retried within the token's remaining validity window** — renewal is attempted well before expiry (≈⅔ of the lease), so a *transient* Vault outage at renewal time is retried and does **not** stop service. The daemon fails closed **only** when the token can no longer be renewed **before it would expire** (retries exhausted / sustained outage) or the token is **revoked**. So "lost Vault connectivity" is a legitimate fail-closed trigger, but a brief blip is absorbed by the retry window rather than taking the plane down. A new **leaf-rotation loop** re-mints the plane leaf before its `leaf_ttl` (~72h) using the valid token, so certificate delivery is continuous. The daemon never re-authenticates on a schedule and never shuts itself down for cause other than genuine Vault failure. Periodic tokens are chosen over daemon-side SecretID self-rotation **specifically to preserve custody-by-secret-absence**: self-rotation would require granting the daemon `create` on `.../secret-id`, handing a compromised daemon a persistence/self-escalation primitive; a periodic token needs no such grant.

**4. Secure introduction (boot bootstrap) is deployment-specific.** The token and leaf are memory-only, so a reboot is a re-authentication event requiring a bootstrap credential:
   - **Bare-metal (single-user):** a **standing SecretID**, provisioned by `maknae enroll` with the operator's authority and **sealed at rest to the platform hardware root of trust (HRoT), decrypted only into memory at startup** (never written in plaintext):
     - **Linux:** `maknae enroll` runs `systemd-creds encrypt` **TPM2-anchored** (`--with-key=tpm2`, i.e. the sealing key is bound to the TPM — *not* the host-key-only fallback, which would put the key on disk) → a `.cred` file; the `maknaed` unit declares `LoadCredentialEncrypted=`, so systemd decrypts it at service start into `$CREDENTIALS_DIRECTORY` — a per-service **memory-backed tmpfs**, `0400`, `_maknae`-only. No crypto code lives in Maknae; systemd + the TPM do it, and the `.cred` is bound to that TPM.
     - **macOS: envelope encryption with a non-exportable Secure Enclave key** (a Keychain password item is *not* SEP-sealed — the SEP protects keys, not arbitrary data). `maknae enroll` generates a **non-exportable EC key inside the Secure Enclave** (`SecKeyCreateRandomKey` with `kSecAttrTokenIDSecureEnclave`), encrypts the SecretID to that key's public half (ECIES), and stores the **ciphertext** on disk (or as a Keychain blob — it is already encrypted). At startup the daemon calls `SecKeyCreateDecryptedData` with the SEP-resident private key to recover the SecretID **into memory**. The SEP private key **never leaves the enclave**, so the ciphertext is bound to that Mac's SEP.
     The role sets `secret_id_num_uses = 0` so the daemon re-logs-in on every boot; the **daemon holds no SecretID-minting capability** — it only *reads* the decrypted-in-memory credential and consumes it. Reboots are hands-free. **Copying the sealed artifact to another host is useless** (the HRoT-sealed key does not travel) — disk-at-rest exfiltration is defeated; the remaining residual is a *live-compromised* `_maknae`, which can ask the HRoT to unseal exactly as the daemon does. Rotatable via `maknae enroll --rotate`. A plaintext-at-rest form exists **only** behind an explicit, loudly-audited `maknae enroll --insecure-plaintext-secret` opt-out for hosts with no HRoT — never the default.
   - **HARDWARE PREREQUISITE (explicit).** Bare-metal deployment **requires a hardware root of trust**: a **TPM 2.0** on Linux (physical or a hypervisor **vTPM** — VMware/Hyper-V/KVM-swtpm/cloud all provide one) or a **Secure Enclave** on macOS (Apple Silicon). A host or VM without an HRoT is a supported deployment **only** via the explicit `--insecure-plaintext-secret` opt-out (which reverts to the `_maknae:_maknae 0400` plaintext residual and is audited as a degraded posture). **Kubernetes needs no HRoT** — it uses SA auth with no secret at rest.
   - **Kubernetes:** the **Vault Kubernetes auth method** (the pod's service-account token as platform identity) — hands-free, **no** secret at rest, survives reschedule/reboot. This is the production path and needs no enrollment secret or HRoT.
   - `maknae enroll` also provisions the **operator's own `cli`-plane standing SecretID** (operator-owned; HRoT-sealed) so the CLI can mint its `cli` leaf. On **macOS** the operator's login Keychain (Secure-Enclave-backed) is the natural CLI store. On **Linux** the daemon's `systemd-creds` + `LoadCredentialEncrypted=` path is a *service-unit* mechanism that does not apply to an interactive CLI (no unit, no `$CREDENTIALS_DIRECTORY`); the operator-CLI seal mechanism there (a systemd *user* credential, a kernel keyring TPM-*trusted* key, or a libsecret store) is **resolved in the implementing spec**, not implied identical to the daemon path.

**5. Full-lifecycle intervention posture.** Across the daemon's life, the only operator touches are **first enroll** and **intentional** acts (rotate the standing credential; revoke on compromise). Steady-state operation, leaf rotation, transient Vault outages, and **reboots** are all hands-free.

## Security criteria / acceptance tests

- A connection from a `uid` **not** in the `maknae` group is refused, fail-closed, with an audit event (ADR-0019) — even when the peer presents a valid `cli` plane cert. (The group predicate is T1, 0-missed.)
- A daemon left running past the former `token_max_ttl` keeps serving (periodic token renews). A **transient** Vault outage at renewal time is retried within the token's validity window and does **not** stop service; a **sustained** outage causes fail-closed once the token can no longer be renewed before expiry; a **revoked** token causes fail-closed.
- After a reboot with no operator action, `maknaed` re-authenticates from the HRoT-sealed standing SecretID (decrypted only into the memory-backed credential store) and resumes serving.
- The standing SecretID is **never present in plaintext at rest** (default path) — it exists only as **HRoT-sealed ciphertext** (Linux: a TPM2-anchored `systemd-creds` `.cred`; macOS: SEP-encrypted ciphertext, wherever stored) plus, transiently, the in-memory decrypted form. Copying the sealed artifact to a **different host fails to yield a usable SecretID** (HRoT-bound). *(The test asserts these two properties — no plaintext at rest, ciphertext host-bound — not a specific storage location.)*
- The operator's own uid **cannot** retrieve the daemon's sealed SecretID.
- The daemon's Vault policy grants **no** `create` on any `.../secret-id` path (verified against the role policy).

## Scope boundary

This ADR covers the **local-plane** authorization and the daemon lifecycle for the single-user bare-metal and Kubernetes deployments, **including** HRoT-sealed at-rest protection of the bootstrap SecretID (TPM 2.0 / Secure Enclave). It does **not** cover: the **per-request PDP** decision (deferred to the authorization-seam/PDP work — this ADR gates *connections*, not *operations*); **remote / cross-host** authorization and the channel bridges (the **gateway**, issue #66); **TPM measured-boot / remote attestation** binding the seal to boot state (a further hardening beyond sealing); and the **audit record model** (ADR-0019).

## Consequences

- **Positive:** hands-free steady-state + reboot lifecycle (Availability); custody-by-secret-absence preserved for the daemon runtime (no SecretID minting); the bootstrap SecretID is HRoT-sealed at rest and decrypted only into memory, so disk-at-rest exfiltration is defeated; minimal authorization surface that matches real deployments; a single, inspectable enrollment command.
- **Negative / accepted:** a **hardware prerequisite** (TPM 2.0 / Secure Enclave) for bare-metal — accepted and made explicit (VMs need a vTPM); the `--insecure-plaintext-secret` opt-out reintroduces the plaintext residual for no-HRoT hosts and is audited as degraded; no per-user granularity below group membership on the local plane (accepted; the mTLS cert is the per-user credential, and finer control is a gateway/PDP concern).
- **Custody-by-secret-absence, precisely.** The property holds for the daemon's runtime **token** and its **minting capability**: the daemon can neither mint SecretIDs (no `create` grant) nor hold a durable off-host token (the memory-only periodic token dies with the process and within one period if unrenewed). With HRoT sealing (the default), the bare-metal standing SecretID **no longer yields to disk theft** — the sealed artifact is useless off-host. The remaining residual is a **live-compromised `_maknae`**, which can request an HRoT unseal exactly as the daemon does — and because the SecretID is `num_uses = 0`, once unsealed into a compromised process it is **durably replayable off-host until `--rotate`** (unlike the memory-only periodic token, which dies with the process). So HRoT sealing narrows the exposure to *runtime* compromise but does not bound the *durability* of what such a compromise yields; that is accepted under the single-user threat model and rotation. The plaintext residual returns only under the explicit `--insecure-plaintext-secret` opt-out. None of this exists on the k8s path (no secret at rest). The operator's `cli`-plane standing SecretID is the same class, HRoT-sealed on the operator's uid and subsumed by operator-uid compromise (which ADR-0005 already treats as fatal to that plane).
- **Terraform (`deploy/vault-pki`, its own change):** the `maknaed` role gains **`token_period`** (periodic token) **+** `secret_id_num_uses = 0` (standing bootstrap). The `maknae` CLI role keeps its **short-lived token** (per-invocation, dies fast — no `token_period`) but its **SecretID becomes standing** (`secret_id_num_uses = 0`, operator-owned) so the CLI can mint per invocation without re-seeding. Both SecretID changes supersede ADR-0005's single-use-response-wrapped model (bootstrap is a local `_maknae`/operator-owned file, not an untrusted-channel delivery, so response-wrapping adds nothing here).
