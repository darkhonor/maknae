# ADR-0033: Agent identity, admission and tasks — enrollment under `/etc/maknae/agents/<id>/`, the agent socket, and kernel-signed task objects

- **Status:** Accepted (maintainer-ruled 2026-11-07 and 2026-11-08)
- **Date:** 2026-11-08
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#609](https://github.com/darkhonor/maknae/issues/609), part of the Agent Daemon work in [#472](https://github.com/darkhonor/maknae/issues/472)

## Context

[ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 makes the Agent Daemon a subject with its own account, and [ADR-0006](ADR-0006-client-authentication-model.md) decision 9 decides how it authenticates: its own plane leaf, on a machine channel of its own, bound to its enrolled uid, with its enrollment decided on every request. [ADR-0032](ADR-0032-per-subject-restrictions.md) decision 9 adds that an agent never holds `admin`, in code. None of it was built. #561 had written an enrollment record at `/etc/maknae/agents/<id>.yaml` and sealed the agent's SecretID, but `maknaed` read nothing of it: an enrolled agent had no role, no policy, no socket and no way to be given work.

#609 builds identity, admission, the agent's own policy, the task object, the decision on giving a task, the task store, kernel signing of tasks with their verification, and the task id carried by agent requests and audit records. Delivering a task into the agent's loop, calling `verify_task` there, the user-facing tasking verb's behaviour and per-tasker work separation inside the agent are [#610](https://github.com/darkhonor/maknae/issues/610)'s. Scheduled tasks are [#611](https://github.com/darkhonor/maknae/issues/611)'s.

## Decision

### 1. Each agent is a directory: `agents/<id>/enrollment.yaml` and `policy.yaml`

An agent's configuration lives under `/etc/maknae/agents/<id>/`. `enrollment.yaml` is written by `sudo maknae enroll agent` and names the agent id, the account, its uid and the agent's role, beside the CLI's own fields (mount, AppRole role, RoleID, bound CIDRs, custody source). `policy.yaml` is written by hand (decision 4). An agent id is 1 to 32 bytes of `[a-z0-9._-]`, starting and ending with `[a-z0-9_]`, and not `data`. The directory and both files must be root-owned, not group- or world-writable and not world-readable; each file is a regular, single-link file of at most 64 KiB, read through `maknae-io` like every configuration file.

`maknaed` reads the directory at every start and reload, beside `authz.yaml` and `bindings.yaml`, as one policy. **Removing `enrollment.yaml` is the de-enrollment act.** A directory without it, a directory whose name is not an agent id, and a non-directory entry in `agents/` are skipped and reported as `graph.identity` problems (`agents/<entry> is skipped: <why>`), never a load refusal. An `enrollment.yaml` or `policy.yaml` that does not parse, or whose `agent_id` is not its directory's, refuses the load, so the previous snapshot stands. A `policy.yaml` with no `enrollment.yaml` beside it is not compiled. #561's `/etc/maknae/agents/<id>.yaml` is not migrated (pre-release). *Failure it prevents:* one file holding several agents would make removing one agent an edit of a shared document; a directory per agent puts its enrollment, policy and later its persona and provider configuration side by side, and makes de-enrollment the removal of one file.

### 2. An agent's role comes only from its enrollment; `admin` is refused everywhere

An enrollment binds the agent to `user` (the default) or `guest`; `admin` is not a value the record, the CLI or the parser accepts. `bindings.yaml` may name an agent's account only under `adversary`, which contains it. The `admin` refusal is made three times, by independent code:

- **the CLI:** `maknae enroll agent --role` offers `user` and `guest`, and enrollment refuses an account `bindings.yaml` binds under `admin`, `user` or `guest`, by name, by uid or by another name for its uid. It decides the binding with `maknae_config::bindings_conflict`, the predicate the rebuild runs;
- **the rebuild:** an enrollment refused only because `bindings.yaml` binds its account, where the account passes every other check (decision 3), is a load refusal when the binding is under `admin`, by name or by uid alias (`AuthzBasicError::AgentAccountAdmin`; the previous snapshot stands). This holds on a reload and on a live identity edit alike (maintainer, 2026-11-08, #609). Under `user` or `guest` that enrollment is ignored (decision 3); under `adversary` it is enrolled and contained;
- **the graph:** the identity layer persists each enrolled agent as an `Agent` node with one `enrolls` edge to its `Subject`, and refuses a layer in which that subject is bound to `admin` (`IdentityError::AgentAdmin`), on write and on load ([ADR-0029](ADR-0029-kernel-enforcement-state-graph.md) decision 7's amendment).

*Failure it prevents:* an agent is driven by model output, so an agent holding `admin` could be steered into disclosing the configuration or releasing a contained subject. A refusal in only one of these places leaves a route through the others: a hand-written `enrollment.yaml`, a `bindings.yaml` edit after enrollment, or a store written by a defective build.

### 3. The rebuild runs the CLI's predicate; a refused enrollment is ignored

`maknae_config::service_account_check` is the one predicate both the CLI and the rebuild run. It refuses an account that does not exist, root, the principal, a Maknae daemon account or a member of a daemon group (primary or supplementary, `_maknae` and `_maknae-egress` by name), a `maknae`-group member, an account whose shell is not in `NON_LOGIN_SHELLS`, and an account another agent already holds. The rebuild also refuses an enrollment whose recorded uid now names a different account, and one whose account `bindings.yaml` binds (decision 2). Host lookups run once per file load; a live identity edit reuses that load's result and can only drop an agent its new bindings name.

**A refused enrollment is ignored, not a load refusal.** The uid keeps its ordinary standing: its `bindings.yaml` role and client-socket admission, exactly as before the enrollment existed. It is never admitted on the agent socket, and the refusal is reported as a `graph.identity` problem (`agent '<id>' (uid <n>) is not enrolled: <why>`). The one exception is decision 2's `admin` binding of an otherwise valid service account. **A removed or ignored enrollment returns the uid to an ordinary account and purges the agent's tasks** at the next snapshot install (decision 7). *(Corrected 2026-11-11, #628: the tasks are no longer purged. Each open task is closed `AgentGone` and kept as a tombstone its tasker collects; see the amendment of that date.)* *Failure it prevents:* root writing an `enrollment.yaml` that names a person's account must not lock that person out of Maknae; and an account that later gains a login shell or joins `maknae` must stop being an agent at the next reload rather than carry agent standing as a human.

### 4. The agent's policy is its own file, in #608's grammar, with one source

`policy.yaml` carries `schema_version: 1` and the `subjects:` entry keys of ADR-0032 (`permissions`, `actions`, `models`), compiled into the same snapshot under the same rules: the site deny floor, deny beats allow, inert when the account is absent, and the `admin` ban (decision 5). An enrolled agent whose account `authz.yaml` `subjects:` also names refuses the load (`AgentPolicyTwice`). An agent with no `policy.yaml`, or one without `permissions`, holds no file access through Maknae's tools. Its digest is a section of the snapshot's change detection (`agents.<id>`).

`policy.yaml` may also carry `taskers:`, a list of `uid:<n>`, account names and `agent:<id>` entries naming who may task this agent. **Absent, only people may task it**, still subject to the PDP permitting `session.task`; an agent may task it only when the list names that agent (`taskers: [agent:hobi]`), and `taskers: []` admits nobody (maintainer, #609). One function, `taskers_admit`, holds this default. An entry naming no account, or an agent this load did not enroll, is inert.

**`session.new` is denied to an enrolled agent by default** (maintainer, 2026-11-07, #609). The agent holds it only when its own `policy.yaml` `actions.allow`, expanded, contains it and `actions.deny` does not; `session.*` counts. It is a default the agent's policy overrides, not an absolute ban like `admin.*`, and it never grants: the role still decides. `session.new` enters the action vocabulary as subject-limitable only; no role may grant it until #170 builds it. *Failure it prevents:* an agent's permission set in `authz.yaml` beside the humans' would make removing an agent an edit of the site policy, and two sources for one subject's limits would leave a reader unable to say which applies. A conversation an agent opens on its own initiative is a new channel to a model, so it is withheld until the agent's own policy asks for it.

### 5. The PDP decides the channel binding and the `admin` ban from one snapshot

The kernel stamps every request with its channel (`channel`: `client` or `agent`) and, on the agent channel, the agent id from the verified leaf (`agent`); a request never supplies them. In `maknae-authz-basic`'s prelude, before role resolution, `channel_refusal` denies an agent-channel request whose uid is not that agent's enrolled uid in this snapshot, and a client-channel request from an enrolled agent's uid. It runs before role resolution, so a uid that resolves to no role cannot skip it; `containment-ordering.sh` admits exactly that statement. In the role match, `agent_arm` then denies every `admin.*` action for an enrolled agent's uid except `admin.whoami`, which a following arm permits for an enrolled agent, and applies the `session.new` default (decision 4), before `action_limit` and every role arm. An agent bound to `adversary` stays contained. All of this, the agent's subject entry and its `taskers:` come from one installed snapshot.

`admin.subject.list` lists each enrolled agent, with its agent id, whether or not `bindings.yaml` is explicit. When it is not, the list also carries the principal as an `admin` row marked as the principal, because that is what the PDP decides (maintainer, 2026-11-08, #609). *Failure it prevents:* an admission check made at connect against one snapshot and a decision made later against another can disagree after a reload; deciding the binding in the PDP, per request, from the snapshot the decision uses, closes that gap without a second check that could drift.

### 6. Admission: a socket, group and semaphore of its own, the agent SAN, and the enrolled uid

On `linux-host` and `macos-host`, `maknaed` binds a second listener at `transport.agent_socket_path` (`/run/maknae-agent/maknaed.sock` on Linux, `/usr/local/var/run/maknae-agent/maknaed.sock` on macOS), group-owned by `maknae-agents`, a group that holds no human, and refuses to start when that group does not exist. `container` mode binds no agent listener. The agent listener has its own connection semaphore of `transport.max_connections`, so agents at capacity do not take client slots.

- **The channel:** mutual TLS 1.3. The verifier's `SanRule::Agent` accepts only a leaf whose one SAN is `spiffe://<trust_domain>/plane/agent/<id>` with a valid agent id; a `plane/cli` or `plane/kernel` leaf, a second SAN of any kind and every malformed form are refused.
- **At connect:** the peer-cred uid must equal the uid enrolled for the agent the leaf names in the installed snapshot. An enrolled agent's uid is refused on the client socket, and a `maknae` member presenting an agent's leaf is refused on the agent socket.
- **On every request:** the account must still exist and must not be a `maknae` member (a member is refused as a human account), read from the host user database as for a human client, and the PDP decides the binding (decision 5). A de-enrolled agent is refused at its next request after the reload that removes it, over an open connection too.
- **Ending:** a connection ends at the visit clock or at the leaf's `not_after`, whichever comes first; a leaf already expired opens no session.

*Failure it prevents:* an agent on the client socket would be admitted by `maknae` membership, the human factor, and an agent socket shared with humans would make the leaf the only thing between a person's process and an agent's standing. Each fact is necessary: the leaf names the agent, the uid binds it to the account, and the group keeps humans off the socket.

### 7. Tasks: a fixed, versioned CBOR object, decided at submission, held in memory, cited by id

*(Amended 2026-11-11, #628: tasks are no longer held in memory only. They persist, sealed under the graph key, in `STATE_DIR/tasks`, and survive a restart; only the agent's own working task is citable; the kernel closes a task by tombstone and never purges it. The amendment of that date at the end of this ADR is current where it differs from this decision.)*

A task is `maknae_proto::TaskObject` (`schema: "maknae.task"`, `version: 1`): a kernel-assigned 16-byte random `task_id`, the `tasker`, an optional `parent`, the target `agent`, the `ask` (v1: `Prompt`, a `SecretText`) and `labels`. A tasker sends a `TaskSubmission`, which carries no id, tasker or parent: the kernel derives the tasker from the authenticated session (`uid:<n>`, or `agent:<id>` with its uid) and the parent from the task the submitting agent's request cited, already resolved; `None` is a person's task or an agent's own initiative. `Labels` is reserved for classification and releasability and v1 refuses any label, because a label carried but never evaluated would read as enforced.

- **The decision.** A submission is decided once, as `session.task`, by the PDP: the role's own grant (`admin` and `user` may hold it; the shipped `authz.yaml` grants it to both, by maintainer ruling on #609), the target being an enrolled agent in this snapshot (resource attribute `agent`), the target's `taskers:` admitting the submitter, and the submitter's own action limit. Agents task agents through the same path (maintainer, #609). There is no later per-request "is the tasker still allowed" check (maintainer, #609). The decision runs under the request path's decision breaker and timeout, through the one shared `admit_blocking`.
- **The store.** A permitted task is signed (decision 8), then stored in memory for `maknaed`'s life, at most 256 live tasks per agent, bound to the agent id and the uid enrolled when it was minted. Every snapshot install reconciles the store against the installed enrollment: an agent that is no longer enrolled, or whose uid changed, is purged, and its generation is bumped first, so a submission decided before the install and stored after it is refused. A task whose submission record cannot be audited is withdrawn. *(Corrected 2026-11-11, #628: the store is on disk, not in memory; the 256 counts open tasks only, beside two per-tasker caps; and a de-enrolled agent's or re-bound uid's open tasks are closed `AgentGone`, not purged. See the amendment of that date.)*
- **Citing a task.** A request carries an optional `task` id (additive on the wire). On the agent channel the kernel resolves it against the store, bound to that agent and uid, before the PDP; an unknown task or another agent's task is refused and ends the session, and the refusal's audit reason names the cited id (`task-unknown:<id>`, `task-other-agent:<id>`). A task id on the client channel is refused. The resolved task's id and tasker are stamped on the request (`task`, `tasker`) and on its audit record (`subject.task_id`, `subject.tasker`), with `subject.agent`; the submission record also carries `subject.parent_task_id`. *(Corrected 2026-11-11, #628: only the agent's own `Working` task resolves. Another agent's task is still `task-other-agent:<id>`; an unknown id, or the agent's own task in any other state, is `task-not-working:<id>`. Both end the session. The resolved task also stamps `root_tasker`, the partition key the partition operand decides on ([ADR-0008](ADR-0008-authorization-composition-contract.md), amendment 2026-11-11).)*

`Verb::TaskSubmit` and `session.task` exist in #609 so the decision can be built and its grant checked by `verb-vocabulary-drift.sh`. The verb dispatches as `NoBehaviour` and answers refused until #610 wires the submission path to it. *(Corrected 2026-11-11, #628: every task verb is now built in the kernel, `TaskSubmit` included, with eight more: `TaskAdd`, `TaskStatus`, `TaskList`, `TaskStop`, `TaskDrop` and `TaskCollect` for a tasker, `TaskClaim` and `TaskReport` for the holding agent. The CLI that sends them is #630 and the agent process that claims is #629.)* `PROTOCOL_VERSION` and the graph's `SCHEMA_VERSION` are unchanged. *Failure it prevents:* a task identified by its text, or by a name the agent supplies, could be replayed or claimed by another agent; a kernel-assigned id bound to the agent and uid, and resolved by the kernel, ties every message of a task to the decision that authorized it.

### 8. Kernel-signed tasks

The kernel signs every task it authorizes with its current `plane/kernel` leaf key (maintainer, #609: "kernel signed for now"). The signature covers the context `maknae.task.v1\0` followed by the task object's canonical CBOR, encoded into one zeroizing buffer bounded by the prompt's length plus `TASK_ENVELOPE_MARGIN` (4096). `TaskSignature` carries `alg` (the `vault.plane_key` name), the `leaf`, a `chain` of at most `TASK_CHAIN_MAX` (2) intermediates and the `sig`, each as a CBOR byte string; together they may hold at most `TASK_SIGNATURE_MAX_BYTES` (32 KiB), which fits an ML-DSA-87 signature and leaf.

- **Verification.** `maknae_vault::task_sig::verify_task` takes the CA bundle, the trust domain, the expected agent and a time. It refuses a task for another agent, then requires the leaf to chain to the bundle as a `plane/kernel` leaf valid at that time, the leaf's key to be the named algorithm, and the signature to verify. It accepts any `PlaneKey` whose kernel leaf the CA issued, which is no wider than the trust TLS already places in that leaf.
- **What it proves.** Origin, not liveness. A signature stays valid until its leaf expires, so the kernel's store, not the signature, decides whether a task is still live.
- **Rotation.** A task is re-signed per task, when it is handed out, if its signing leaf is not the signer's current one (`resign_if_stale`), after the same ownership check `resolve` makes, outside the store lock, and at most twice; otherwise nothing is handed out. `resign_if_stale` is built and tested; #610's delivery path is its caller. *(Corrected 2026-11-11, #628: its caller is the kernel's `TaskClaim` hand-out. A re-sign that fails hands nothing out and leaves the task queued; it never closes the task. When the store refused the re-signed record's write, or its write is "outcome unknown", the task is also held back from the next claims for 1 s, doubling to 60 s, and is never read as unsigned.)* Signing at mint is also outside the store lock, and an unsigned task is never stored.
- **The frame bound #610 must use.** A delivery frame for a signed task needs `prompt_max_bytes + TASK_ENVELOPE_MARGIN + TASK_SIGNATURE_MAX_BYTES`. The decoder's own size check on a `SignedTask` runs after ciborium has allocated, so that frame cap, not the decoder, is the real memory bound.

Sealing a task to the agent's key and tasker-held keys are not built: the store is in memory and nothing relays a task past the kernel, so sealing is raised when #611's schedule storage is designed. *(Amended 2026-11-11, #628: the store is no longer in memory. Each task record is sealed at rest under the graph key, in `STATE_DIR/tasks`, as the conversation store is. Sealing to the agent's key is still not built: the kernel hands the task to the agent itself, over the agent channel, and nothing relays a task past the kernel. It is still raised with #611.)* *Failure it prevents:* an agent that worked any well-formed task would work one injected into its input by another path; requiring the kernel's signature means only a task the PDP authorized is worked.

### 9. Revocation by entity disable; the Vault objects an agent needs

Each agent needs these Vault objects, however the deployment manages Vault:

- the AppRole role `agent-<id>` on an agent mount separate from `maknaed`'s, issuing a bounded, non-periodic token (`token_max_ttl`, also the explicit maximum, never 0);
- the policy `maknae-agent-<id>`: its own credential subtree, `update` on `<int_mount>/sign/maknae-agent-<id>` with `not_after` denied, token self-management including `revoke-self`, and no `revoke` path;
- the PKI role `maknae-agent-<id>` on the intermediate mount: client-only, admitting only `spiffe://<trust_domain>/plane/agent/<id>`, `no_store`, and a TTL of at most `leaf_ttl_seconds`;
- the identity entity `maknae-agent-<id>` with one alias on the agent mount whose name is the role's RoleID;
- for the operator, the policy `maknae-enroll-agent`: on the agent mount only, read a role's RoleID, create, list and destroy SecretIDs, and `read` and `update` on `identity/entity/name/maknae-agent-*`, where `update` may set only `disabled`.

`deploy/vault-pki` is one way to create them. It is an aid, not a requirement: operators manage Vault their own way, and Maknae checks the objects, not how they were made (maintainer, 2026-11-08). Every sign grant, the kernel's and the CLI's included, denies `not_after`, so the role's TTL bounds every leaf. A `maknae_users` key may not start with `agent-`, because its entity `maknae-<user>` would fall under `maknae-enroll-agent`'s `maknae-agent-*` grant.

**Revocation is entity disable, never a lease prefix.** `maknae enroll remove-agent` removes `enrollment.yaml` first, so the next reload drops the agent whatever Vault does. It then disables the entity, which makes Vault refuse that agent's existing tokens, and destroys every SecretID accessor it records or Vault lists. It treats the Vault side as gone only when the role and the entity both read not-found; a role that is not found while the entity exists may mean a wrong mount, so it refuses and changes nothing in Vault. Enrollment reads the entity before it mints anything and re-enables it last, only when every earlier SecretID was destroyed.

One residual is stated, not closed. **Disabling does not revoke:** `remove-agent` records no token accessor, so a login token the agent already holds stays valid until `agent_token_max_ttl`, refused by Vault only while the entity stays disabled. When the role and the entity were both already absent, nothing is disabled, and a held token lives until `agent_token_max_ttl`. Re-enabling the entity at re-enrollment makes tokens issued before it was disabled usable again until `agent_token_max_ttl`. That is expected, not a residual: re-enrolling a removed agent is intentional, and Vault's token handling governs. *Failure it prevents:* `revoke-prefix` on the agent mount would revoke every agent's tokens, and on `maknaed`'s mount the daemon's own (ADR-0018); a mechanism scoped to one entity revokes one agent. A document that made the Terraform the only route would leave a deployment that manages Vault otherwise with no statement of what to create.

## Consequences

- An agent is configured, admitted and decided end to end on a host, but it cannot yet be given work: the submission path is built and tested and reaches the wire only with #610, which also delivers the task, calls `verify_task` in the agent's loop and separates per-tasker work. *(Corrected 2026-11-11, #628: the kernel half of #610 is built. The kernel takes, stores, hands out and closes tasks over the wire, and the partition operand separates per-tasker work for file verbs. What remains is the agent process that claims and calls `verify_task` (#629) and the CLI that tasks (#630).)*
- A failed reload after `enrollment.yaml` was removed keeps the previous snapshot, so the agent stays admitted until a reload succeeds (ADR-0029); `remove-agent` tells the operator to reload.
- An agent's actions are distinguishable from a person's in the trail by its uid, its agent SAN in `plane_uri_san`, the agent socket in `where.socket`, and `subject.agent`; each in-task record names its task and tasker. This closes ADR-0024's origin gap for the Agent Daemon; the interactive runtime's gap stays [#549](https://github.com/darkhonor/maknae/issues/549).
- macOS and Linux share every decision here. The macOS agent socket and directory rows of `packaging/macos/smoke.sh` are not yet run on a host.

## Amendment 2026-11-11 (#628): tasks persist, and the kernel closes what cannot finish

Dated as-built amendment; rides the #628 PR. It replaces decision 7's in-memory store and settles decision 8's sealing at rest. Ten statements.

1. **Tasks persist, sealed, and survive a restart.** Each task is one `.task` record in `STATE_DIR/tasks` (`/var/lib/maknae/tasks` on Linux, `/usr/local/var/db/maknae/state/tasks` on macOS), beside one `counters.task` file. Each is sealed under a fresh data key wrapped by the graph key, as the conversation store is. A record holds the signed task, the agent and its uid at mint, the tasker, the root tasker of the task's chain, the parent, the state and close, the follow-ups, the report and the last stored action counts. A change is written before memory shows it. A submission is written pending, then confirmed after its decision record lands; at boot a pending record is discarded, and an unreadable or oversized one is moved aside as `.task.quarantine`, each after its trail record. The counters file holds the store's submission sequence and each tasker's own submission and report ordinals. A value is written there before it is issued and never goes back, and a missing, unreadable or lagging counters file beside stored tasks refuses boot. *Failure it prevents:* a restart that forgot every task would drop queued work and every held report without a word to the taskers.

2. **Caps.** These are checked when a task is stored:
   - at most 256 open tasks (queued or working, pending included) per agent; a held report or a close does not count;
   - at most 32 open tasks per tasker with one agent;
   - at most 256 records per tasker over every agent, open tasks, held reports and closes together;
   - each prompt, follow-up and report at most `transport.prompt_max_bytes`, and a task's follow-ups at most 32 and at most `prompt_max_bytes` in total.

3. **The lease and the hold.** A claimed task is held under `CLAIM_LEASE` (15 minutes). Each request that cites it, and each heartbeat (`TaskClaim` with `seen_follow_ups`), renews the lease. The lease is never stored; at boot every working task's lease starts afresh. A report, a stop and a close are held for the tasker for `REPORT_HOLD` (30 days) and then expire. The kernel sweeps at start, every 60 seconds and once more at stop, and stores the running action counts on each sweep, so a crash loses at most a minute of them.

4. **The kernel gives a definite answer only when the disk durably agrees.** Otherwise it answers "outcome unknown". A store step the kernel could not prove removed or rewritten is owed: it stays in memory and every later store write retries it before its own work. On the wire every refusal is `Unauthorized`; the trail says `outcome unknown: <cause>` where the change may or may not stand, `not done: <cause>` where nothing was written and nothing will be, and `not stored: <cause>` for a submission the store definitely refused. *Failure it prevents:* a write that reached the disk unsynced can return after a crash. A refusal over it can revive a task the tasker was told was refused, and a "done" over a drop can revive a task that an agent then claims.

5. **The kernel closes by tombstone.** A de-enrolled agent's open tasks, and those of an agent whose uid changed, close `AgentGone`; a working task whose lease lapsed closes `AgentLost`. The record is rewritten `Closed`, with a report ordinal issued for that attempt (a retried close takes a fresh one, so it never lands below a cursor its tasker has already acknowledged), and the tasker collects the close as it collects a report. Nothing is deleted, so the close never depends on an unlink. The close is shown to the tasker only once stored: until then the task keeps its prior state for the tasker and the agent is refused it, at every claim, citation and report. De-enrollment marks the tasks without I/O when the snapshot is installed, so no agent is handed one after that. A tasker's `stop` closes `Stopped` in the same way; a `drop` of a queued task removes it, through the same pending-then-unlink steps as a withdrawal. Expiry removes a held report or close the same way. *Failure it prevents:* a purge that deletes records depends on the unlink. An unlink that fails, or lands unsynced, leaves the open record on disk, and a later boot could hand it to an agent enrolled again under the same uid.

6. **A kernel close is recorded first.** A close and an expiry are each appended to the trail before the store performs them, and a refused record leaves the task open and due. The record is at least once:
   - a crash between the record and the close leaves the task open; the next boot finds it due and records it again, so a second record is accepted;
   - a record whose close never happens is accepted too. That happens when the task stops being due between the record and the close: its lease is renewed, or its tasker stops it first.
   No close happens without a record. The record is `event: task` ([ADR-0019](ADR-0019-audit-record-model.md), amendment 2026-11-11). Boot marks every task of an agent it does not enroll and closes what one bounded pass allows; what remains is recorded and left to the sweep, and no agent is handed those tasks meanwhile.

7. **The verbs.** A tasker's verbs (`submit`, `add`, `status`, `list`, `stop`, `drop`, `collect`) are decided as `session.task`, with the operation stamped as `task_op`. Each acts only on the caller's own tasks, in the state it needs; another tasker's task and an unknown task are refused alike. `list` and `collect` need a well-formed agent id and not an enrolled agent, so a tasker can collect what a removed agent left. Cursors count each tasker's own tasks and reports, never another's. `claim` and `report` come with holding the task: an enrolled agent on the agent channel may claim, and may report only the working task it cites, whatever its role grant or `actions:` limits say. An agent that holds a working task submits only under it, by citing it, so the sub-task links back to the person at the root and works in that person's partition; an uncited submission from such an agent is refused. An agent holding no working task may submit on its own initiative, rooted at `agents/<id>`. A hand-out the store or the signer refuses holds that task back from the agent's claims, 1 second doubling to 60, and the claims are answered idle meanwhile; an `Unauthorized` on a claim is therefore retryable. Task answers are bounded by the 16 MiB ceiling of `prompt_max_bytes`, not its current value. *(Amended 2026-11-13, #629: a report carries `seen_follow_ups`, the follow-ups its answer has seen. Under the store's writer the kernel refuses it, changing nothing, while the task holds more, so a follow-up added between the agent's last heartbeat and its report is never answered past; `None` skips the check. The field is additive; `PROTOCOL_VERSION` is unchanged.)*

8. **Named residuals.**
   - **Same-uid re-enrollment across a crash.** If the disk refuses a tombstone, the process stops before a retry lands, and the agent is enrolled again under the same uid before the next boot, the task reloads open for that agent. Boot cannot tell it from a live task, because the agent is enrolled.
   - **The owed and stale retry lists live in memory only.** A crash before a retry lands can bring back a record whose removal or rewrite was owed: a dropped task, an acknowledged report or an expired one. Each of these was answered "outcome unknown", or is a held report that expires again.
   - **An acknowledged report may be delivered at least once.** An acknowledgement whose removal is not proven is answered "outcome unknown", and the report can be collected again after a crash.
   - **The counters file keeps tasker ids.** It holds one entry per tasker that ever submitted, and never forgets one. Today that grows with distinct local uids and agents, because a remote tasker is refused at submission.
   - **The runtime's own uid.** The partition operand bounds what the kernel releases to the model. It does not bound the agent process, whose account owns its whole home, every partition included; bounding the process is #629's confinement.

9. **Containment holds tasks** (maintainer, 2026-11-11: "If a person or agent is moved to a contained state, all work ceases and all tasks placed on hold. They become potential evidence of a breach or malicious behavior." and "they need an admin to release the tasks from hold status"). `TaskState::Held` is an additive state; the record keeps the state it was held from.
   - **Who.** A contained person (role `adversary`) has every task they gave, and every task rooted at them, held, whether open, reported or closed. A contained agent has every open task it holds held, and also every task it gave and every task in a chain rooted at it, whoever gave that task. *(Corrected 2026-11-11, branch review: this named only the open tasks it holds; the code already held the tasks it gave, and the chain rooted at it is held by ruling.)* A contained agent is given no new task: the submit arm refuses a target that is contained. *(Added 2026-11-11, codex review.)* Containment is checked again when a submission is stored: under the writer, a submission whose tasker, root or agent is contained is refused and its record unlinked; one that was already written and is waiting for its audit is marked like any other task, and its confirm then records the hold and stores it `Held`, never `Queued`. A sub-task is taken only under a parent that is still working and due neither a hold nor a close. An expiry never removes a held task, however old the selection it came from.
   - **When.** At the points a de-enrollment is handled: boot, a reload, a live edit and `admin.contain`. The tasks are marked without I/O when the snapshot is installed, and from that moment none is handed out, cited, reported on or added to. The hold is then recorded (`task held: contained`) and written, record first and at least once, exactly as a close is; a crash between the two holds again at the next boot while the subject is still contained.
   - **While held.** A held task is never handed out; a heartbeat answers `Held`, so the agent stops; it is never closed, expired or lapsed; drop, stop, add, report, collect and acknowledge leave it as it is. `status` and `list` show `Held` to the tasker.
   - **Release.** `admin.release` lifts the containment only. A held task stays held until an admin releases it, which is #632 and is not built here.
   *Failure it prevents:* a contained subject's work kept running, and its queued tasks, partitions and reports kept changing or expiring, after the moment they became evidence.

10. **Withdrawn authority closes queued tasks at hand-out** (maintainer, 2026-11-11). Before a claim hands out a queued task, the kernel decides its tasker's submission again, on the submit arm, under the policy in force: the role's grant, the target's `taskers:` and its enrollment. A decided refusal answers the claim idle, with the reason in that claim's record, marks the task so it is never handed out, and closes it `TaskClose::Withdrawn` by the same record-first tombstone as the other kernel closes. A tasker who still holds the role's grant (one only removed from the agent's `taskers:`) collects the close; a tasker whose role lost `session.task`, or who has no role, cannot `collect`, `status` or `list`, so the close they were owed expires after 30 days unless the grant returns. *(Corrected 2026-11-11, maintainer ruling: this said "the tasker collects the close" without the limit; `collect` stays gated by the role's grant.)* A working task is not decided again and finishes. Only a decided refusal withdraws: the identity resolves and its role lacks `session.task`, or the agent's `taskers:` excludes it. An identity that could not be resolved is undecided (maintainer, 2026-11-11: "We don't need a DoS on ourselves because of a network glitch"): a tasker with no role, in a load that could not resolve every name it binds, may be one of those names. A refusal stands only when the load it was decided on is the one read before and after it: the tasker's containment and resolution, and the agent's containment, are read again after a refusal, and a load replaced during the decision makes it undecided. A decision that could not be reached, or came back indeterminate, withdraws nothing: the claim is answered idle and recorded `idle: the tasker's standing could not be decided: <cause>`, and the next claim decides again. *(Added 2026-11-11, codex review.)* A permit is bound to the policy load it was decided on as well as to the task: the store compares that load with the installed one under the writer and answers idle when a new policy was installed in between, so the next claim decides again. The decision is bound to the hand-out: the store starts a queued task only when it is the one just decided, so a head that changed after the decision, or a queued task that became the head after a working one finished, is not started on a decision made for another. A contained tasker's tasks are held (statement 9), never withdrawn. *Failure it prevents:* a task queued by someone who has since lost the right to task the agent being handed out and run on that stale authority.

## Amendment 2026-11-14 (#629): the Agent Daemon's confinement and custody

Dated as-built amendment; rides #629 PR B. It narrows amendment 2026-11-11's residual "the runtime's own uid" and records the custody residuals the maintainer accepted for the daemon.

1. **The process is confined, per agent account.** On Linux each agent runs as `maknae-agent@<id>.service` under its own account. Under SELinux it runs in `maknae_agentd_t`, which reads only `maknae_agent_etc_t` and `maknae_tls_t` among Maknae's configuration, writes files only in `maknae_agent_home_t` (the homes under `/var/lib/maknae-agents`), connects by unix socket only to `maknaed_t`, and executes nothing but itself; enroll refuses a home of any other type on an SELinux host, and, on a host where the rpm installed the policy package, refuses unless SELinux is enforcing. The control is the absence of other allows: the module's `neverallow` rules are not enforced at load (`expand-check=0` on EL9 and EL10). Under AppArmor every instance shares the profile `maknae-agentd`, whose home rules are `owner` rules over the homes enroll names in `/etc/apparmor.d/tunables/maknae-agents.d/<id>.home`; enroll refuses on a host whose kernel does not enforce AppArmor. Both leave the agent no write to the mail spool, a terminal or a journal socket, and the unit sets `SyslogLevelPrefix=no`, so an agent cannot raise a message to journald's wall forwarding; within a Linux host it reaches a person only through `TaskReport`. macOS has no MAC layer; the account's DAC is the bound there. Named residuals: **network egress** on every platform. Under SELinux the name-resolution interface (`sysnet_dns_name_resolve`) lets the agent send UDP to any host and port and open TCP to port 53 on any host, beside TCP to the labeled Vault port; under AppArmor and on macOS it can open TCP and send UDP anywhere. The unit's `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK` removes the other socket families and bounds no destination; the operator bounds egress with an nftables rule on the agent's uid (`meta skuid <uid>`) or a drop-in setting `IPAddressDeny=any` and `IPAddressAllow=<Vault>,<DNS>`, or a `pf` rule on macOS. **On macOS, people reachable without the kernel:** a terminal through the setgid `/usr/bin/write`; a mailbox through local mail (the setgid `postdrop` that `sendmail` hands to, delivered to `/var/mail/<person>`); and every logged-in terminal through a syslog emergency message, which `/etc/asl.conf` configures macOS to broadcast (configured, not measured). *(Corrected 2026-11-14, #629 PR B whole-branch review: this item said the domain "connects only to `maknaed_t` and the labeled Vault port" and named outbound TCP as the only egress residual, unrestricted only on Debian and macOS; the DNS interface's UDP and port-53 TCP grants, and macOS's mail and syslog broadcast routes to a person, were missing.)* The amendment 2026-11-11 residual stands as narrowed: the confinement bounds which homes an agent process writes, not which partition within its own home.
2. **macOS shares one keychain trust across agents.** The SecretID item (service `io.maknae.maknae-agentd`, account `<id>`) trusts the one signed `maknae-agentd` binary, so agent A's process could read agent B's SecretID; on Linux the credential is scoped to its unit. Bounded by the SecretID's CIDR binding and by decision 6's peer-credential uid check, which refuses a leaf minted for B on A's uid.
3. **A failed revoke fails the agent's exit** (maintainer, 2026-11-13). The daemon exits non-zero when revoking its own login fails or outlives `PLANE_SHUTDOWN_BOUND`; `maknaed` and the CLI log it and exit 0.
4. **Orphaned login** (maintainer, 2026-11-13, accepted). If the 30 s wait for the leaf supervisor lapses while it is mid re-login, a token Vault minted but the client never stored is not revoked and lives to its TTL.

*Failure it prevents:* an agent process that could write another agent's home, or a person's terminal or mailbox, would bypass the kernel's decisions on everything it can reach; and residuals stated only in an issue are lost to the next reader of this ADR.
