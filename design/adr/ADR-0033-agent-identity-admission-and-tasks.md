# ADR-0033: Agent identity, admission and tasks — enrollment under `/etc/maknae/agents/<id>/`, the agent socket, and kernel-signed task objects

- **Status:** Accepted (maintainer-ruled 2026-11-07 and 2026-11-08)
- **Date:** 2026-11-08
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#609](https://github.com/darkhonor/maknae/issues/609), part of the Agent Daemon work in [#472](https://github.com/darkhonor/maknae/issues/472)

## Context

[ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 makes the Agent Daemon a subject with its own account, and [ADR-0006](ADR-0006-client-authentication-model.md) decision 9 decides how it authenticates: its own plane leaf, on a machine channel of its own, bound to its enrolled uid, with its enrollment decided on every request. [ADR-0032](ADR-0032-per-subject-restrictions.md) decision 9 adds that an agent never holds `admin`, in code. None of it was built. #561 had written an enrollment record at `/etc/maknae/agents/<id>.yaml` and sealed the agent's SecretID, but `maknaed` read nothing of it: an enrolled agent had no role, no policy, no socket and no way to be given work.

#609 builds identity, admission, the agent's own policy, the task object, the decision on giving a task, the task store, kernel signing of tasks with their verification, and the task id carried by agent requests and audit records. Delivering a task into the agent's loop, calling `verify_task` there, the user-facing tasking verb's behaviour and per-tasker work separation inside the agent are [#610](https://github.com/darkhonor/maknae/issues/610)'s. Scheduled tasks are [#611](https://github.com/darkhonor/maknae/issues/611)'s.

## Decision

### 1. Each agent is a directory: `agents/<id>/enrollment.yaml` and `policy.yaml`

An agent's configuration lives under `/etc/maknae/agents/<id>/`. `enrollment.yaml` is written by `sudo maknae enroll agent` and names the agent id, the account, its uid and the agent's role, beside the CLI's own fields (mount, AppRole role, RoleID, bound CIDRs, custody source). `policy.yaml` is written by hand (decision 4). An agent id is 1 to 32 bytes of `[a-z0-9._-]`, starting and ending with `[a-z0-9_]`, and not `data`. The directory and both files must be root-owned, not group- or world-writable and not world-readable; each file is a regular, single-link file of at most 64 KiB, read through `maknae-io` like every configuration file.

`maknaed` reads the directory at every start and reload, beside `authz.yaml` and `bindings.yaml`, as one policy. **Removing `enrollment.yaml` is the de-enrollment act.** A directory without it, a directory whose name is not an agent id, and a non-directory entry in `agents/` are skipped and reported as `graph.identity` problems (`agents/<entry> is skipped: <why>`), never a load refusal. An `enrollment.yaml` or `policy.yaml` that does not parse, or whose `agent_id` is not its directory's, refuses the load, so the previous snapshot stands. A `policy.yaml` with no `enrollment.yaml` beside it is not compiled. #561's `/etc/maknae/agents/<id>.yaml` is not migrated (pre-release). *Failure it prevents:* one file holding several agents would make removing one agent an edit of a shared document; a directory per agent puts its enrollment, policy and later its persona and provider configuration side by side, and makes de-enrollment the removal of one file.

### 2. An agent's role comes only from its enrollment; `admin` is refused everywhere

An enrollment binds the agent to `user` (the default) or `guest`; `admin` is not a value the record, the CLI or the parser accepts. `bindings.yaml` may name an agent's account only under `adversary`, which contains it. The `admin` refusal is made three times, by independent code:

- **the CLI:** `maknae enroll agent --role` offers `user` and `guest`, and enrollment refuses an account `bindings.yaml` binds under `admin`, `user` or `guest`, by name, by uid or by another name for its uid. It decides the binding with `maknae_config::bindings_conflict`, the predicate the rebuild runs;
- **the rebuild:** an enrollment refused only because `bindings.yaml` binds its account, where the account passes every other check (decision 3), is a load refusal when the binding is under `admin`, by name or by uid alias (`AuthzBasicError::AgentAccountAdmin`; the previous snapshot stands). This holds on a reload and on a live identity edit alike (maintainer, 2026-11-08, #609). Under `user` or `guest` that enrollment is ignored (decision 3); under `adversary` it is enrolled and contained;
- **the graph:** the identity layer persists each enrolled agent as an `Agent` node with one `enrolls` edge to its `Subject`, and refuses a layer in which that subject is bound to `admin` (`IdentityError::AgentAdmin`), on write and on load ([ADR-0029](ADR-0029-kernel-enforcement-state-graph.md) decision 7's amendment).

*Failure it prevents:* an agent is driven by model output, so an agent holding `admin` could be steered into disclosing the configuration or releasing a contained subject. A refusal in only one of these places leaves a route through the others: a hand-written `enrollment.yaml`, a `bindings.yaml` edit after enrollment, or a store written by a defective build.

### 3. The rebuild runs the CLI's predicate; a refused enrollment is ignored

`maknae_config::service_account_check` is the one predicate both the CLI and the rebuild run. It refuses an account that does not exist, root, the principal, a Maknae daemon account or a member of a daemon group (primary or supplementary, `_maknae` and `_maknae-egress` by name), a `maknae`-group member, an account whose shell is not in `NON_LOGIN_SHELLS`, and an account another agent already holds. The rebuild also refuses an enrollment whose recorded uid now names a different account, and one whose account `bindings.yaml` binds (decision 2). Host lookups run once per file load; a live identity edit reuses that load's result and can only drop an agent its new bindings name.

**A refused enrollment is ignored, not a load refusal.** The uid keeps its ordinary standing: its `bindings.yaml` role and client-socket admission, exactly as before the enrollment existed. It is never admitted on the agent socket, and the refusal is reported as a `graph.identity` problem (`agent '<id>' (uid <n>) is not enrolled: <why>`). The one exception is decision 2's `admin` binding of an otherwise valid service account. **A removed or ignored enrollment returns the uid to an ordinary account and purges the agent's tasks** at the next snapshot install (decision 7). *Failure it prevents:* root writing an `enrollment.yaml` that names a person's account must not lock that person out of Maknae; and an account that later gains a login shell or joins `maknae` must stop being an agent at the next reload rather than carry agent standing as a human.

### 4. The agent's policy is its own file, in #608's grammar, with one source

`policy.yaml` carries `schema_version: 1` and the `subjects:` entry keys of ADR-0032 (`permissions`, `actions`, `models`), compiled into the same snapshot under the same rules: the site deny floor, deny beats allow, inert when the account is absent, and the `admin` ban (decision 5). An enrolled agent whose account `authz.yaml` `subjects:` also names refuses the load (`AgentPolicyTwice`). An agent with no `policy.yaml`, or one without `permissions`, holds no file access through Maknae's tools. Its digest is a section of the snapshot's change detection (`agents.<id>`).

`policy.yaml` may also carry `taskers:`, a list of `uid:<n>`, account names and `agent:<id>` entries naming who may task this agent. **Absent, only people may task it**, still subject to the PDP permitting `session.task`; an agent may task it only when the list names that agent (`taskers: [agent:hobi]`), and `taskers: []` admits nobody (maintainer, #609). One function, `taskers_admit`, holds this default. An entry naming no account, or an agent this load did not enroll, is inert.

**`session.new` is denied to an enrolled agent by default** (maintainer, 2026-11-07, #609). The agent holds it only when its own `policy.yaml` `actions.allow`, expanded, contains it and `actions.deny` does not; `session.*` counts. It is a default the agent's policy overrides, not an absolute ban like `admin.*`, and it never grants: the role still decides. `session.new` enters the action vocabulary as subject-limitable only; no role may grant it until #170 builds it. *Failure it prevents:* an agent's permission set in `authz.yaml` beside the humans' would make removing an agent an edit of the site policy, and two sources for one subject's limits would leave a reader unable to say which applies. A conversation an agent opens on its own initiative is a new channel to a model, so it is withheld until the agent's own policy asks for it.

### 5. The PDP decides the channel binding and the `admin` ban from one snapshot

The kernel stamps every request with its channel (`channel`: `client` or `agent`) and, on the agent channel, the agent id from the verified leaf (`agent`); a request never supplies them. In `maknae-authz-basic`'s prelude, before role resolution, `channel_refusal` denies an agent-channel request whose uid is not that agent's enrolled uid in this snapshot, and a client-channel request from an enrolled agent's uid. It runs before role resolution, so a uid that resolves to no role cannot skip it; `containment-ordering.sh` admits exactly that statement. In the role match, `agent_arm` then denies every `admin.*` action for an enrolled agent's uid except `admin.whoami`, which a following arm permits for an enrolled agent, and applies the `session.new` default (decision 4), before `action_limit` and every role arm. An agent bound to `adversary` stays contained. All of this, the agent's subject entry and its `taskers:` come from one installed snapshot.

`admin.subject.list` lists each enrolled agent, with its agent id, whether or not `bindings.yaml` is explicit. When it is not, the list also carries the principal as an `admin` row marked as the principal, because that is what the PDP decides (maintainer, 2026-11-08, #609). *Failure it prevents:* an admission check made at connect against one snapshot and a decision made later against another can disagree after a reload; deciding the binding in the PDP, per request, from the snapshot the decision uses, closes that gap without a second check that could drift.

### 6. Admission: a socket, group and semaphore of its own, the agent SAN, and the enrolled uid

On `linux-host` and `macos-host`, `maknaed` binds a second listener at `transport.agent_socket_path` (`/run/maknae-agent/maknaed.sock` on Linux, `/usr/local/var/run/maknae-agent/maknaed.sock` on macOS), group-owned by `maknae-agents`, a group that holds no human, and refuses to start when that group does not exist. `container` mode binds no agent listener. The agent listener has its own connection semaphore of `transport.max_connections`, so agents at capacity do not take client slots.

- **The channel:** mutual TLS 1.3. The verifier's `SanRule::Agent` accepts only a leaf whose one SAN is `spiffe://<trust_domain>/plane/agent/<id>` with a valid agent id; a `plane/cli` or `plane/kernel` leaf, a second SAN of any kind and every malformed form are refused.
- **At connect:** the peer-cred uid must equal the uid enrolled for the agent the leaf names in the installed snapshot. An enrolled agent's uid is refused on the client socket, and a `maknae` member presenting an agent's leaf is refused on the agent socket.
- **On every request:** the account must still exist and must not be a `maknae` member (a member is refused as a human account), read from the host user database as for a human client, and the PDP decides the binding (decision 5). A de-enrolled agent is refused at its next request after the reload that removes it, over an open connection too.
- **Ending:** a connection ends at the visit clock or at the leaf's `not_after`, whichever comes first; a leaf already expired opens no session.

*Failure it prevents:* an agent on the client socket would be admitted by `maknae` membership, the human factor, and an agent socket shared with humans would make the leaf the only thing between a person's process and an agent's standing. Each fact is necessary: the leaf names the agent, the uid binds it to the account, and the group keeps humans off the socket.

### 7. Tasks: a fixed, versioned CBOR object, decided at submission, held in memory, cited by id

A task is `maknae_proto::TaskObject` (`schema: "maknae.task"`, `version: 1`): a kernel-assigned 16-byte random `task_id`, the `tasker`, an optional `parent`, the target `agent`, the `ask` (v1: `Prompt`, a `SecretText`) and `labels`. A tasker sends a `TaskSubmission`, which carries no id, tasker or parent: the kernel derives the tasker from the authenticated session (`uid:<n>`, or `agent:<id>` with its uid) and the parent from the task the submitting agent's request cited, already resolved; `None` is a person's task or an agent's own initiative. `Labels` is reserved for classification and releasability and v1 refuses any label, because a label carried but never evaluated would read as enforced.

- **The decision.** A submission is decided once, as `session.task`, by the PDP: the role's own grant (`admin` and `user` may hold it; the shipped `authz.yaml` grants it to both, by maintainer ruling on #609), the target being an enrolled agent in this snapshot (resource attribute `agent`), the target's `taskers:` admitting the submitter, and the submitter's own action limit. Agents task agents through the same path (maintainer, #609). There is no later per-request "is the tasker still allowed" check (maintainer, #609). The decision runs under the request path's decision breaker and timeout, through the one shared `admit_blocking`.
- **The store.** A permitted task is signed (decision 8), then stored in memory for `maknaed`'s life, at most 256 live tasks per agent, bound to the agent id and the uid enrolled when it was minted. Every snapshot install reconciles the store against the installed enrollment: an agent that is no longer enrolled, or whose uid changed, is purged, and its generation is bumped first, so a submission decided before the install and stored after it is refused. A task whose submission record cannot be audited is withdrawn.
- **Citing a task.** A request carries an optional `task` id (additive on the wire). On the agent channel the kernel resolves it against the store, bound to that agent and uid, before the PDP; an unknown task or another agent's task is refused and ends the session, and the refusal's audit reason names the cited id (`task-unknown:<id>`, `task-other-agent:<id>`). A task id on the client channel is refused. The resolved task's id and tasker are stamped on the request (`task`, `tasker`) and on its audit record (`subject.task_id`, `subject.tasker`), with `subject.agent`; the submission record also carries `subject.parent_task_id`.

`Verb::TaskSubmit` and `session.task` exist in #609 so the decision can be built and its grant checked by `verb-vocabulary-drift.sh`. The verb dispatches as `NoBehaviour` and answers refused until #610 wires the submission path to it. `PROTOCOL_VERSION` and the graph's `SCHEMA_VERSION` are unchanged. *Failure it prevents:* a task identified by its text, or by a name the agent supplies, could be replayed or claimed by another agent; a kernel-assigned id bound to the agent and uid, and resolved by the kernel, ties every message of a task to the decision that authorized it.

### 8. Kernel-signed tasks

The kernel signs every task it authorizes with its current `plane/kernel` leaf key (maintainer, #609: "kernel signed for now"). The signature covers the context `maknae.task.v1\0` followed by the task object's canonical CBOR, encoded into one zeroizing buffer bounded by the prompt's length plus `TASK_ENVELOPE_MARGIN` (4096). `TaskSignature` carries `alg` (the `vault.plane_key` name), the `leaf`, a `chain` of at most `TASK_CHAIN_MAX` (2) intermediates and the `sig`, each as a CBOR byte string; together they may hold at most `TASK_SIGNATURE_MAX_BYTES` (32 KiB), which fits an ML-DSA-87 signature and leaf.

- **Verification.** `maknae_vault::task_sig::verify_task` takes the CA bundle, the trust domain, the expected agent and a time. It refuses a task for another agent, then requires the leaf to chain to the bundle as a `plane/kernel` leaf valid at that time, the leaf's key to be the named algorithm, and the signature to verify. It accepts any `PlaneKey` whose kernel leaf the CA issued, which is no wider than the trust TLS already places in that leaf.
- **What it proves.** Origin, not liveness. A signature stays valid until its leaf expires, so the kernel's store, not the signature, decides whether a task is still live.
- **Rotation.** A task is re-signed per task, when it is handed out, if its signing leaf is not the signer's current one (`resign_if_stale`), after the same ownership check `resolve` makes, outside the store lock, and at most twice; otherwise nothing is handed out. `resign_if_stale` is built and tested; #610's delivery path is its caller. Signing at mint is also outside the store lock, and an unsigned task is never stored.
- **The frame bound #610 must use.** A delivery frame for a signed task needs `prompt_max_bytes + TASK_ENVELOPE_MARGIN + TASK_SIGNATURE_MAX_BYTES`. The decoder's own size check on a `SignedTask` runs after ciborium has allocated, so that frame cap, not the decoder, is the real memory bound.

Sealing a task to the agent's key and tasker-held keys are not built: the store is in memory and nothing relays a task past the kernel, so sealing is raised when #611's schedule storage is designed. *Failure it prevents:* an agent that worked any well-formed task would work one injected into its input by another path; requiring the kernel's signature means only a task the PDP authorized is worked.

### 9. Revocation by entity disable; the Vault objects an agent needs

Each agent needs these Vault objects, however the deployment manages Vault:

- the AppRole role `agent-<id>` on an agent mount separate from `maknaed`'s, issuing a bounded, non-periodic token (`token_max_ttl`, also the explicit maximum, never 0);
- the policy `maknae-agent-<id>`: its own credential subtree, `update` on `<int_mount>/sign/maknae-agent-<id>` with `not_after` denied, token self-management including `revoke-self`, and no `revoke` path;
- the PKI role `maknae-agent-<id>` on the intermediate mount: client-only, admitting only `spiffe://<trust_domain>/plane/agent/<id>`, `no_store`, and a TTL of at most `leaf_ttl_seconds`;
- the identity entity `maknae-agent-<id>` with one alias on the agent mount whose name is the role's RoleID;
- for the operator, the policy `maknae-enroll-agent`: on the agent mount only, read a role's RoleID, create, list and destroy SecretIDs, and `read` and `update` on `identity/entity/name/maknae-agent-*`, where `update` may set only `disabled`.

`deploy/vault-pki` is one way to create them. It is an aid, not a requirement: operators manage Vault their own way, and Maknae checks the objects, not how they were made (maintainer, 2026-11-08). Every sign grant, the kernel's and the CLI's included, denies `not_after`, so the role's TTL bounds every leaf. A `maknae_users` key may not start with `agent-`, because its entity `maknae-<user>` would fall under `maknae-enroll-agent`'s `maknae-agent-*` grant.

**Revocation is entity disable, never a lease prefix.** `maknae enroll remove-agent` removes `enrollment.yaml` first, so the next reload drops the agent whatever Vault does. It then disables the entity, which makes Vault refuse that agent's existing tokens, and destroys every SecretID accessor it records or Vault lists. It treats the Vault side as gone only when the role and the entity both read not-found; a role that is not found while the entity exists may mean a wrong mount, so it refuses and changes nothing in Vault. Enrollment reads the entity before it mints anything and re-enables it last, only when every earlier SecretID was destroyed.

Two residuals are stated, not closed. **Disabling does not revoke:** `remove-agent` records no token accessor, so a login token the agent already holds stays valid until `agent_token_max_ttl`, refused by Vault only while the entity stays disabled. When the role and the entity were both already absent, nothing is disabled, and a held token lives until `agent_token_max_ttl`. **Re-enabling revives:** re-enabling the entity at re-enrollment makes tokens issued before it was disabled usable again until `agent_token_max_ttl`; an operator who must avoid that waits out `agent_token_max_ttl` before re-enrolling. *Failure it prevents:* `revoke-prefix` on the agent mount would revoke every agent's tokens, and on `maknaed`'s mount the daemon's own (ADR-0018); a mechanism scoped to one entity revokes one agent. A document that made the Terraform the only route would leave a deployment that manages Vault otherwise with no statement of what to create.

## Consequences

- An agent is configured, admitted and decided end to end on a host, but it cannot yet be given work: the submission path is built and tested and reaches the wire only with #610, which also delivers the task, calls `verify_task` in the agent's loop and separates per-tasker work.
- A failed reload after `enrollment.yaml` was removed keeps the previous snapshot, so the agent stays admitted until a reload succeeds (ADR-0029); `remove-agent` tells the operator to reload.
- An agent's actions are distinguishable from a person's in the trail by its uid, its agent SAN in `plane_uri_san`, the agent socket in `where.socket`, and `subject.agent`; each in-task record names its task and tasker. This closes ADR-0024's origin gap for the Agent Daemon; the interactive runtime's gap stays [#549](https://github.com/darkhonor/maknae/issues/549).
- macOS and Linux share every decision here. The macOS agent socket and directory rows of `packaging/macos/smoke.sh` are not yet run on a host.
