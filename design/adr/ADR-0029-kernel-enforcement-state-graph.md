# ADR-0029: The kernel enforcement-state graph

- **Status:** Accepted (maintainer-ruled 2026-10-07, issue #485). The decisions below are the maintainer's rulings. They are built in five pull requests: #487 builds only the `maknae-graph` crate and format v1, and is not wired into `maknaed`; encryption at rest, rollback anchoring and `maknaed --reseed` (#488), seeding and the PDP walking the graph (#489), the baseline layer and `admin.baseline.accept` (#490) and sync back (#491) are decided here and built there. Until a slice lands, the behaviour it describes does not exist. Mechanism details not stated here belong to those pull requests. *(Corrected 2026-10-07, #489: this named #487 "S1", an internal label.)*
- **Date:** 2026-10-07
- **Deciders:** Alex Ackerman (maintainer)

## Context

Total containment (#165) needs state that survives a restart: a subject contained by an operator or by the kernel must still be contained after `maknaed` restarts. The daemon has nowhere to keep it. `authz.yaml` is `root:_maknae 0640`, so the daemon cannot write it, and under `ProtectSystem=strict` the Linux unit can write only `/run/maknae` and `/var/log/maknae`. There is no state directory.

Holding the state in memory alone would not be enough either. `maknae-authz-basic` re-reads `authz.yaml` on every request, so any state the daemon held would sit beside a second, unmodelled path to a decision: the file as it stands at that moment. A containment held in the daemon and a binding read fresh from the file could disagree, and nothing would record which one decided. *(Corrected 2026-10-07, #489: this describes the PDP before #489, which removed the per-request re-read; see decision 1's amendment.)*

A decision that crosses policy, role, classification and containment also has no single place to read from, and so cannot name the rule and the source section that decided it. The lake and user graphs (`design/graph-native-memory-idea.md`, `design/plan-as-graph.md`) need a record envelope, a binary format, atomic commit, encryption, recovery and migration. This graph is small (hundreds to a few thousand nodes) and its blast radius is bindings and containment, which makes it the place to settle those choices first.

## Decision

### 1. One kernel-owned graph holds the running configuration, policy and live enforcement state, and the PDP decides by walking it

`maknaed` keeps one graph, `GraphSpace::Kernel` in the `maknae-graph` crate. It is seeded from `/etc/maknae`, persisted, and the reference monitor decides every request by bounded walks over one immutable snapshot of it (`Arc<Graph>`, swapped atomically, so a request never sees a half-applied change). Rules are nodes, so a verdict names the deciding rule's node and, through `declared_by` and `part_of`, the file section it came from; that path goes to the audit record only, never on the wire. Every walk has a fixed depth; the only transitive edge, `dominates`, runs over a total order of at most six levels, and start nodes come from sorted key indexes stored in the file, so no decision searches or scans the graph. The `contained` check is the walk's first hop, before any role can be reached, which keeps today's pre-class containment ordering and gives #165 one site to mutation-test. Composition is unchanged: the `-basic` walks and the classification-ceiling operand still combine deny-overrides (ADR-0008, ADR-0020), and `maknaed` remains the sole PDP (ADR-0005). The acceptance bar for the PDP switch (#489) is equivalence: for every (role, term, path) cell the shipped policy can express, the walks give the same verdict as today's file-based `-basic`. The per-request re-read of `authz.yaml` is removed in the same change. *Failure it prevents:* the re-read is a second path around any state the daemon holds, and a decision with no single source cannot cite what decided it.

*Amended 2026-10-07 (#489): "walking the graph" is built as a compiled snapshot, not a literal walk per request. At each start and each `SIGHUP` reload, `maknaed` compiles the persisted identity layer and `authz.yaml` into one immutable in-memory snapshot (rule nodes, the sections that declare them, and an index from each rule to its node), held as `RwLock<Arc<Snapshot>>` and replaced whole, so a request decides from exactly one snapshot; an `fs.mkdir` that decides several paths decides them all from one, through `Authorizer::decide_cited_all`. Only identity is resolved by graph hops at decision time (`Subject`, then `contained`, checked first, then `binds`, then `Role`); the evaluator that matches terms, paths and destinations is `-basic`'s existing one, unchanged in its verdicts and reasons, which its golden vectors pin. A verdict decided by a policy rule names that rule's key, its node and its section (`<source>#<section>`) in the audit record's `rule` block; a structural or deny-by-default decision carries none. The store persists only the identity layer, the four compiled `Role` nodes and a digest of the binary's vocabulary (a `ConfigSource` node keyed `binary:vocabulary`, attribute `sha256`); terms, classes, rules and policy edges live only in memory and are rebuilt at every compile. Equivalence is held by two controls: a golden matrix over the shipped policy and its variants asserts that roles resolved from the file and roles resolved through the graph give identical verdicts and reasons, and the evaluator's own golden vectors are unchanged.*

### 2. Three layers, each with its own lifetime

- **Baseline** (classification system, daemon configuration, from `maknae.yaml` and `config.d/`): persistent. A detected change to a baseline source is held as a pending change; the persisted baseline keeps running, the change is audited and reported in `admin.status`, and it applies only when an operator accepts it with **`admin.baseline.accept`**. A restart does not accept it. The verb is a new grantable term, granted separately and not in the shipped default; its operand is the canonical hash of the pending change, so an accept that names any other hash is refused and nobody accepts a change they did not see. Root edits the file and a granted operator accepts it, which separates the duties.

  *(Noted 2026-10-09, #490: this said the verb is granted separately and not in the shipped default. The maintainer ruled that the shipped `authz.yaml` grants `admin` `admin.status`, `admin.subject.list`, `admin.baseline.show` and `admin.baseline.accept`, in the file, never in code; an install's own `authz.yaml` decides. A second verb, `admin.baseline.show`, displays the pending change set, rendered through `admin.config.show`'s disclosure rules, and the hash an accept names; that reply is the only place the full hash appears, and the audit trail carries its first 12 hex digits. `vault` and `audit` follow the file at start, with a moved trail recorded in the old trail first and a back-link in the new one, which root must have prepared append-only. A pending set is recomputed from the files at every start, reload, show and accept, and is not persisted; the `PendingChange` kind stays reserved for sources whose content cannot be recomputed from a file. The first start over a store without a baseline takes the files as the baseline, audited, with no accept.)* *(Noted 2026-10-09, #490: `audit.readers` is the one `audit` key that does not follow the file at start. No code is swapped, so ADR-0002's static TCB is unchanged. Every accept runs the validator a start runs. Root can always replace an accepted baseline from the files with `sudo maknae reseed`. The live class is `principal`, the root `providers` allow-list while it stays non-empty, and `audit.readers`.)*
- **Policy** (grants, denies, action grants, from `authz.yaml`): not persisted. It is rebuilt from the file at an explicit reload (`SIGHUP`, later #164's `admin.policy.reload`) or at a restart, both safe transitions, as one audited transition that applies completely or not at all. Policy stays visible in files and reloadable.
- **Identity and live state** (bindings and containment): persistent. A root edit applies at reload or restart; live transitions persist and are synced back (decision 5).

*Failure it prevents:* a single lifetime for everything would either let a classification-system change take effect on the next restart without anyone accepting it, or freeze policy that operators expect to edit and reload.

### 3. Change detection uses a canonical hash per source section

Each source section is a node that stores `sha256` of the section's canonical form: the YAML parsed to its value tree and encoded as deterministic CBOR (RFC 8949 §4.2.1). A comment or whitespace edit is therefore not a change. At reload or restart, a section whose hash differs from its node's is a change. *Failure it prevents:* comparing file bytes or modification times would turn every cosmetic edit, and the daemon's own synced write, into a transition.

*Amended 2026-10-07 (#489): the canonical form is the parsed YAML value serialized as JSON with bytewise-sorted keys and no insignificant whitespace, not deterministic CBOR; `canonical_json` in `maknae-config` is the encoder.*

*(Noted 2026-10-09, #490: the baseline stores each section's canonical JSON as its value, not a per-section hash, because running the accepted baseline needs the values; one digest over all sections is held on the baseline's source node. Every node kind, edge and attribute it uses already existed, so the schema version is unchanged.)*

*(Noted 2026-10-10, #491: this decision says the daemon's own synced write is kept from reading back as a root edit, and decision 5 says that is done by recording the mirror's hash. As built, the synced write is recognised per entry instead: at a load, an entry whose value in `bindings.yaml` equals its live value is taken as it is, with no root edit, and a file whose whole section equals the live section is an adoption (decision 4's note). The mirror's hash is written to the journal when the mirror is published and is not persisted anywhere.)*

### 4. Every change is a transition with a recorded initiator

Every change to graph state is a transition, recorded with exactly one initiator: `seed` (first boot or an explicit reseed), `root-file` (an `/etc/maknae` edit detected at reload or restart), `operator` (a decided verb such as `admin.baseline.accept`, and later #165's and #164's verbs) or `kernel` (#165's kernel-initiated containment). Each transition runs in one order: audit intent written ahead (ADR-0019, reusing the type-state that enforces the order at compile time), build and validate the new graph, persist, swap, audit outcome. Nothing swaps until the persist succeeds, and a failed audit intent means no transition. Neither the graph nor a file silently wins: if, at reload or restart, `bindings.yaml` changed for a subject that also has an unsynced live transition, that subject fails closed (containment wins; a binding conflict leaves the subject unbound, which denies), and the conflict is audited and shown in `admin.status` until it is resolved. *Failure it prevents:* a store and a file that can each overwrite the other without a record give no answer to "why is this subject contained", and a silent last-writer-wins could release a contained subject.

*(Noted 2026-10-10, #491: the collision rule is built as a three-way merge per entry. An entry is a name or a `uid:` id and its value is the set of roles that list it; the store keeps the base (the `bindings:` section of the last `bindings.yaml` the daemon applied or adopted), the live section (the base with every live edit applied, which is what is enforced) and the conflict list. At every start and reload: a file value equal to the base keeps the live value; a live value equal to the base takes the file's; a file value equal to the live value takes it; any other entry is a conflict, which fails closed (contained if either side contains it, otherwise no role), goes on the conflict list, is audited as `graph.sync` and counted in `admin.status`. Conflicts persist in the store across restarts. One clears when root changes that entry again, and root's value wins, or when the file comes to hold the fail-closed value, as a sync installs it. An adoption (the file now holding the live section) and the first sync base a store receives are `kernel` transitions; a load that applies a root edit is `root-file`. A live edit follows this decision's order: `graph.sync` intent written ahead with the `operator` or `kernel` transition intent, persist, swap, then the outcome `live applied: revision <n>` with anchor `live-applied`. A live edit needs explicit bindings: while base or live holds no `bindings:` key, it is refused and nothing changes. The section-level rule for a missing file or an absent key is decision 5's #491 note.)*

*(Noted 2026-10-10, #491 review: a live edit that changes an entry on the conflict list also clears it, recorded `conflict resolved: <entry>: a live edit changed it`. The store accepts that as the only change a live edit may make to the conflict list. Root's next edit of the entry is then merged against the new live value, so an edit made without seeing the live edit is a new conflict and cannot release a containment root never saw.)*

### 5. The daemon never writes `/etc/maknae`; sync back writes only `/etc/maknae/bindings.yaml`

Bindings and containment move out of `authz.yaml` into their own file, `/etc/maknae/bindings.yaml`; `authz.yaml` keeps grants, denies and roles, nothing ever writes it, and it no longer accepts a `bindings:` key (a hard move with no compatibility shim, per the 2026-08-31 standing ruling that nothing is a breaking change while Maknae is pre-release). The `adversary:` list in `bindings.yaml` seeds `contained` edges, never `binds` edges. After each committed live transition, `maknaed` renders the identity layer to a mirror in its own state directory (`_maknae 0600`) and records the mirror's hash, so its own synced write never reads back as a root edit. Root installs it: `sudo maknae policy sync` validates the mirror against the `bindings.yaml` schema, shows the diff and installs it atomically as `/etc/maknae/bindings.yaml` (`root:_maknae 0640`), or an opt-in service does the same validated install. The service ships disabled: a systemd `maknae-policy-sync.path` and `.service` pair on Linux, a `launchd` job that is not loaded on macOS. Local policy decides how much a human stays in the loop. The mirror carries usernames, roles and the contained list only; containment reasons stay in the encrypted graph and the audit trail. Unsynced transitions are shown in `admin.status`. *Failure it prevents:* a daemon that writes its own policy file is a runtime-patchable policy path (ADR-0002, core principle 3); restricting the installer to exactly one path, never `authz.yaml`, is the whole privilege boundary.

### 6. A custom binary format, format v1, accepted only in its canonical encoding

The store is a custom binary format, because this graph baselines the lake's format: a header with the magic `MKNG`, format version 1, schema version, graph space, flags and store revision, followed by a section table, an interned string table, fixed-width node and edge tables, key indexes and an attribute heap, with integers little-endian. Every record carries `space` and `label` from day one, even though the kernel graph has one space and one partition, so the lake extends this envelope rather than replacing it.

- **Reading is a complete, bounds-checked parse into owned memory, with no `mmap`.** `mmap` would need `unsafe`, which is confined to `maknae-sys` (ADR-0027); the lake can revisit that with measurements in hand. The crate depends on the standard library only.
- **A store is accepted only if it is the canonical encoding of the graph it decodes to:** decode rebuilds the graph and re-encodes it, and refuses the store unless the bytes are identical. The same logical graph encodes to identical bytes regardless of insertion order. The parser also refuses an offset or length out of bounds, a dangling edge endpoint, an edge triple outside the compiled permitted-triple table, a record whose space differs from the header's, a store whose space differs from the one the caller asked for, an edge carrying compiled provenance, a compiled-in node that disagrees with the binary, a duplicate id or key, and an unknown format version, schema version, flag or tag.
- **The string bytes a store's references clone are bounded at build time and at decode time to four times the encoded length.** A graph whose strings would exceed it is refused when built, and a store whose string references would expand past it is refused when decoded, so peak decode memory is a small constant multiple of the input. No allocation is sized from a count read from the bytes.
- **Writing** serializes the whole graph and replaces the file atomically through `maknae-io` (temporary file, `fsync`, rename, directory `fsync`). There is no journal: rename atomicity is the crash safety, and transitions are rare, operator-paced events.
- **Versions:** a format newer than the binary is refused; an older one is migrated under #268's discipline. Format v1 has no migrations.

*Failure it prevents:* the parser is TCB code that consumes bytes an attacker may have shaped. If two byte strings could decode to the same graph, a modified store could carry hidden or ambiguous content past every semantic check, and the rollback anchor's same-revision hash comparison (decision 8) would stop meaning "same content". A small file whose many records reference one long string would otherwise expand into an allocation far larger than the file.

### 7. `Term`, `Class` and, for now, `Role` are compiled in; `guest` and `adversary` stay structural

The vocabulary (`Term`), the action classes (`Class`) and, for the MVP, the roles (`admin`, `user`, `guest`, `adversary`) are compiled in. They are stored so that edges can reach them, and on load each one is compared field by field with the binary's compiled set and the store is refused on any difference. A homelab or small business gets a workable set out of the box. When enterprise-defined roles arrive they will be declared nodes, distinguished by provenance, but `guest` and `adversary` stay structural whatever is declared. Containment is only the `contained` edge from a subject to a containment node; `Subject`–`binds`–`Role` is a permitted triple, but a `binds` edge whose target is the `adversary` role is refused as a forbidden target, by the target's key, even in an otherwise valid graph. *Failure it prevents:* a redefinable `adversary`, or a binding into it, would be a second route into containment that bypasses the transition and audit discipline of decision 4.

*Amended 2026-10-07 (#489): a store written by an older binary is migrated, not refused. The store records the digest of its compiled nodes. A store whose digest covers its own nodes but differs from the binary's, including a #488 store that has neither, is migrated at start as an audited `graph.migrate` transition; a `binds` edge to a role the binary no longer has is dropped and reported in that record. A store whose nodes differ from the digest it claims, or whose digest does not cover them, is refused as forged. The compiled `Role` nodes carry the selected classification system's lowest level as their label, so changing the classification system is also a migration. The `adversary` members of `authz.yaml`'s `bindings:` are persisted as `contained` edges already, ahead of the file move in decision 5.*

### 8. Encryption at rest from day one, with algorithm identifiers and rollback anchored to the audit trail

The format-v1 payload is encrypted with **AES-256-GCM** under a random 256-bit data key, through `aws-lc-rs` (built on the AWS-LC-FIPS 4.x module line, which is submitted and under CMVP review, per ADR-0025). The data key is wrapped by a platform-sealed daemon key behind a key-wrapping provider trait: on Linux a systemd encrypted credential (`LoadCredentialEncrypted=`), sealed to the TPM2; on macOS a System keychain item whose ACL trusts only `maknaed` (the custody pattern of ADR-0028). The envelope header carries an envelope version and **algorithm identifiers** for the AEAD and the wrap, bound as associated data, so a post-quantum or hybrid wrap is a new identifier, not a format break. Every write uses a fresh nonce; the data key is rotated at reseed, and every buffer holding it is zeroizing from allocation and never grows (ADR-0026). The AEAD tag is the store's integrity check.

*Amended 2026-10-07 (#488): enroll requires TPM2 for this key as for every sealed credential, so there is no host-key fallback; this decision said that without a TPM the Linux credential fell back to the host key, and that sentence and the qualifier "where one is present" are struck. The key-wrapping provider trait is deferred until a second provider exists; in #488 the wrap-algorithm identifier is the seam. (Corrected 2026-10-07, #489: this said "S2", an internal label for #488.) Enroll creates the key only when none is present and never rotates it, since a new key cannot read the existing store. A fresh data key is generated on every write, not only at reseed.*

*Amended 2026-10-07 (#488): `admin.status` reports `rollback-anchor-unavailable` until the next restart, not until the next checkpoint. The start that records it also writes a checkpoint, but the status is fixed for the life of the process; the next start finds that checkpoint and reports `verified`.*

Every committed transition and every start emits a `graph.checkpoint` audit record carrying the store revision and the `sha256` of the ciphertext. At start, a store whose revision is older than the latest checkpoint's, or whose ciphertext hash differs at the same revision, is refused. When no checkpoint is found (for example after a manual rotation or restore of the audit file) the daemon starts, records `rollback-anchor-unavailable`, and `admin.status` reports it until the next checkpoint: visible, not closed, because refusing would turn every manual rotation into an outage. *Failure it prevents:* a store left in plaintext gives a stolen disk, backup or snapshot the whole enforcement state; and an older store restored from a backup taken before a subject was contained decrypts cleanly and passes every other check.

### 9. A corrupt, rolled-back or missing store refuses to start; `maknaed --reseed` is the explicit recovery

`maknaed` refuses to start when the store fails decryption, parsing or validation; when rollback is detected; when the wrapping key is unavailable; when the store's format is newer than the binary; and when the store is missing but the audit trail holds a checkpoint. Each refusal names its cause. Recovery is `maknaed --reseed`, run by root: it moves the old file aside for forensics, seeds afresh from `/etc/maknae` with a new data key, and is audited as a `seed` transition; if sync has been running, the reseed restores containment from `bindings.yaml`. Only a first boot (no store and no checkpoint) seeds automatically. *Failure it prevents:* an automatic reseed after a lost or damaged store would silently drop every containment that had not yet been synced.

*Amended 2026-10-07 (#488): recovery is `sudo maknae reseed`, which writes a root-owned authorization marker into the state directory; `maknaed` performs the move-aside and the seed at its next start, so root never handles key material. It is not a `maknaed` flag, because the daemon's AppArmor profile confines root there. Wherever this ADR names `maknaed --reseed`, read `sudo maknae reseed`. A readable old store is kept as `kernel.graph.rejected.<unix-seconds>.<16 hex digits>` and never replaced; a store written by a newer `maknaed` refuses with a hint to reinstall that version, never to reseed. Under #488 the seed is an empty graph; seeding from `/etc/maknae` arrives with #489.*

## Consequences

- **This graph sets the shape the lake and user graphs extend:** the record envelope (with `space` and `label`), the format-v1 codec and its canonical-encoding rule, atomic commit, encryption, recovery and migration. `maknae-graph` owns the envelope, schema machinery and codec; the kernel vocabulary sits in its own module, the seam the lake and user vocabularies will sit beside.
- **What ships now and what does not.** #487 delivers the crate, the compiled kernel schema and permitted-triple table, format v1, key indexes and validation, with no other crate depending on it and no behaviour change. Until #489 lands, the PDP still re-reads `authz.yaml` per request and nothing decides from the graph; until #488, nothing is encrypted or persisted; until #490 and #491, there is no `admin.baseline.accept` and no sync. Total containment (#165) lands on #489, and its "the stop survives a reinstall" property needs #491. Scoped carves (#486) also depend on this graph.

  *Amended 2026-10-07 (#489): #489 has landed. The PDP decides from the compiled snapshot of decision 1, the store is seeded from `authz.yaml`'s identity layer, and the per-request re-read is gone.*
- **Reload replaces the per-request re-read.** An edit to `authz.yaml` takes effect at reload or restart, not on the next request. An invalid file at reload is refused and the current graph stands; an invalid `authz.yaml` at start leaves the policy layer absent and every decision except liveness fails closed, as today. A username in `bindings.yaml` that does not resolve fails closed for that subject only, where today one bad username fails the whole policy.

  *(Noted 2026-10-09, #490: the amendment below says the principal, the classification ceiling and the providers are fixed at start. From #490 an accepted change to the ceiling level, the principal or the providers list applies live; the classification system, the transport and the audit path still apply at a start.)* *(Noted 2026-10-09, #490: by the maintainer's ruling the ceiling, its level included, applies only at the start that follows its accept; the principal and the providers list apply live.)*

  *Amended 2026-10-07 (#489): as built, an invalid `authz.yaml` at start still refuses to start (exit 3), which is what the daemon did before #489; starting with the policy layer absent would be a new state and is an open question for the maintainer. A reload re-reads `authz.yaml` only; the principal, the classification system and ceiling, the transport, the audit configuration and the providers are fixed at start. Until #496 moves bindings to `bindings.yaml`, a username in `authz.yaml`'s `bindings:` that does not resolve refuses the whole start or the whole reload, as before, and one uid bound under two names in two different roles is refused at load.*

  *Amended 2026-10-08 (#496): a reload now re-reads `authz.yaml` and `bindings.yaml` together, and identity is resolved per subject, as decision 5's amendment says; the two whole-policy refusals above are gone.*
- **`PROTOCOL_VERSION` is unchanged.** *(Noted 2026-10-09, #490: `admin.baseline.show` is a second additive variant beside it.)* `admin.baseline.accept` is an additive CBOR enum variant with manifest rows and a `verb_to_action` arm; `graph.checkpoint` is an audit pseudo-action, never a client verb; `SIGHUP` is a local signal, not a wire term.
- **Operators discover state through `maknaed`, never the file.** `admin.status` gains pending baseline changes, unsynced live transitions, per-subject conflicts and the rollback anchor's state; the store itself is never handed out.

  *Amended 2026-10-08 (#496): per-subject identity problems reach `admin.status` as counts by kind only, with no names or uids; the per-subject detail is `admin.subject.list`'s, a separate grant.*
- **In manual sync mode, a lost store still loses what was never synced,** but as a refusal to start followed by an explicit, audited reseed, never silently.
- **Named residual: root on a running host.** Root can read the daemon's memory and its wrapping credential. Encryption at rest protects a stolen disk, backup or snapshot and detects offline tampering; it does not protect against root on the live host, and nothing in this design can.
- **Named residual: a moved reseed marker is a bearer token** *(added 2026-10-07, #488)*. The marker lives in a directory `_maknae` owns, so a compromised `_maknae` can rename a root-written marker aside and put it back later, authorizing a reseed at a time of its choosing. Ownership and link-count checks cannot tell a replayed marker from a fresh one. Under #488 a reseed replaces an empty graph *(corrected 2026-10-07, #489: this said "In S2", an internal label for #488)*; from #489, when the store holds real content, a replayed marker can drop containment that was never synced.
- **Named residual: the store and the audit trail rolled back together.** An attacker controlling both the state directory and the audit trail (root, or a compromised `_maknae`) can roll back both, and the checkpoint check passes. A TPM NV monotonic counter would close it and is on the roadmap. On macOS, each checkpoint's copy in the unified log is a second record `_maknae` can write but not read or modify, which an investigator can compare.
- **Named residual: a persist whose outcome is uncertain** *(added 2026-10-07, #489)*. A persist that fails after its transition intent is written leaves that intent with no checkpoint, and the reload is refused, so nothing swaps. Nothing reached disk: sealing the store failed, or writing or renaming its temporary file failed. A directory `fsync` that fails after the rename is not such a failure: the publish is the point of no return, so the store's revision floor advances, the reload installs the new snapshot and records it as applied with the durability failure in its reason, and a boot-time seed, migration or transition carries on and logs it *(corrected 2026-10-07, #489: this said that case refused the reload although the new store was on disk, which left the store holding a revision the floor did not cover, so a later reload could reuse it)*. The next reload that changes the identity layer rewrites that revision, and the next start loads whatever store is on disk (as `advanced` if the new one landed) and reconciles it with the file. A transition intent with no checkpoint therefore says only that the persist outcome is unknown. Shutdown waits a bounded time for a reload that is committing, so such a reload can also append its records after the stop record.
- **Roadmap, not issues:** Vault Transit as a key-wrapping provider, and post-quantum wrapping, adopted when the AWS-LC-FIPS module line Maknae builds on supports it. The algorithm identifiers of decision 8 make either a new identifier rather than a format break.
- **No `cargo-fuzz` target yet.** `cargo-fuzz` needs a nightly toolchain, and the repository builds on a pinned stable toolchain with no nightly lane. #487 instead ships a deterministic, seeded mutation-corpus harness that runs in `cargo test` and puts every mutated input through the same refuse-or-canonical, never-panic property; coverage-guided discovery is deferred to #492.
- **Coverage.** The codec, schema validation and the permitted-triple check are T1 under ADR-0016 (95% region floor, zero missed mutants), as the walks and the rollback check will be when they land.

  *Amended 2026-10-07 (#489): the identity layer, the snapshot compiler with its graph-hop identity resolution, the vocabulary digest and migration rule, and the reload ordering landed as T1.*
