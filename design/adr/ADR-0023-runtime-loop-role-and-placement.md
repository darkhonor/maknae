# ADR-0023: Maknae's runtime loop is the ACP Agent and the kernel is the Client — a Rust loop on the untrusted side, model egress decided by the kernel and executed by a separate Rust egress process

- **Status:** Proposed (operator-directed 2026-09-07, issue #239; milestone Cooky, epic Begin #244). Five of its decisions are operator **rulings** recorded verbatim — 1 (Maknae ships its OWN agent; the MCP-tool-surface framing was withdrawn in discussion), 3's egress process (2026-09-07: *"a self contained process that Maknae calls"*, Rust, not a host proxy such as Traefik), 5 (Rust loop), 6 (two tools, read first) and 7's small-MVP bound (*"Keep the MVP small for now"*) — and the rest is the author's proposal for ratification. Cooky's implementation issues cite this ADR as their authority while it is Proposed, the way ADR-0010 is cited; ratification is the operator's, at or after #242.
- **Date:** 2026-09-07
- **Deciders:** Alex Ackerman (operator)
- **How to read this while Proposed (operator direction 2026-09-07: *"It will be refined as we work through the milestone. Expect changes."*).** The **decisions** are settled and the implementation issues cite them. The **mechanisms** named inside decisions 3 and 7 — socket creation and ownership, the direction of the peer-credential check, the provider-block ownership predicate, what the loop can conclude from a silent close, the bounds enumeration — are the author's proposals for things not yet built, and eight rounds of adversarial review showed that prose about unbuilt mechanisms keeps being wrong in ways only a prototype settles. **Six corrections are owed, recorded here so nobody builds the wrong thing from the text below:** (1) a client-side peer check on an init-system-created socket reads the init system's uid, not `_maknae-egress` — the property stands (each side must establish the other's identity), the mechanism is #240's to prototype and prove; (2) the root-ownership precondition must cover every source that can contribute the `provider:` section, `config.d/` included (#243); (3) `ROOT_ARTIFACT` forbids group/other *write*, not read — a root-owned `0640` file satisfies it, so "the dev shape cannot register a provider" is too strong, and #242's dev-shape expectation follows #243's actual predicate; (4) the loop cannot distinguish an over-cap request refusal from an undelivered reply — both are a silent close — so a silent close after `session.prompt` is outcome-unknown and never resent, and "shorten and resend" belongs only to the pre-send check (#241) **(2026-09-09, #172: the daemon side now differs in part — a reply the kernel refuses to deliver is answered with `TooLarge` or `Unauthorized`, so that case is distinguishable. A silent close still covers: an over-cap request at the framer; ANY audit-append failure on the prompt path, including the outcome append, which fails AFTER the content left (the daemon withholds the frame rather than serve an unrecorded release); and a response-write timeout or closed connection, which no verb detects yet. The conclusion therefore stands unchanged and matters more: a silent close is outcome-unknown and is never resent. The loop-side fold is #241's.)**; (5) the plane's `read_timeout_ms` (5 s default, 60 s ceiling) already bounds the whole synchronous model turn on the loop's side and must be sized for a real completion (#241/#243) — decision 7's list omits it; (6) `bins/maknae` reaches `reqwest` transitively, but Rust's extern prelude means one *unreviewed manifest line*, not zero, gives the loop its own HTTP client, and `std::process::Command` needs none. Each is folded into the text when its issue lands, dated in place.

## Context

Everything the kernel decides is, today, decided on behalf of a subject that types `maknae read` at a shell. #238 gave the kernel its first mutating verbs and the README described them as "filesystem development commands" — a human tutorial. The operator's question that produced this ADR (2026-09-07): *"How does giving the CLI these commands help a user using Maknae with an LLM as an agentic platform?"* The honest answer was that it does not, yet: the vocabulary is the kernel half of an agent's tools, and the agent — the loop that orchestrates a model and executes its tool calls — has no code and no line on the roadmap. The operational goal has always been what OpenClaw and Hermes Agent *are* ([reference-implementation-autopsy](../reference-implementation-autopsy.md)): an agent, with the one structural inversion that its tools do not touch the OS. **Cooky's MVP is that agent, minimal: configure a model with an OpenAI-compatible endpoint and key, and function as an agent** (operator direction, 2026-09-07).

Three questions had no recorded answer and would otherwise be settled by whoever wrote the first loop:

1. **Which ACP role is the loop?** The [ACP assessment](../references/2026-08-28-acp-protocol-assessment.md) §2 rules that Maknae is the **Client** — the host that provides `fs.*` and decides every call. It did not say who the Agent is, because at the time the answer could have been "any conforming ACP Agent". §5 recorded the trust-model divergence: ACP v2 assumes the Agent is trusted to execute; Maknae's core principle 1 holds the agent runtime untrusted.
2. **Where does the loop run, in what language?** [container-architecture](../container-architecture.md) §3.4 proposes a Python `runtime` container — *proposed*, never ratified — for velocity reasons that assume a broad LLM/MCP SDK footprint the MVP does not need.
3. **Who makes the model call?** `maknae-llm`'s stub said "maknaed-linked; egress terminates there" — which would put outbound TLS and provider-response parsing inside the sole PDP (critical-review round 5 named the cost; corrected in place in the stub); `session.prompt`'s doc in `wire.rs` said "send content to an agent runtime … toward a model endpoint", which conflates the user→loop hop with the loop→model hop; and #172 specifies `session.prompt` as write-ahead egress whose destination is a provider from #153/#169.

A wrong first answer to any of these is expensive: a loop that holds the key, or a loop the kernel does not stand between and the model, is OpenClaw with a nicer README.

## Decision

### 1. Maknae ships its OWN agent. It is the ACP Agent; the trust plane is the ACP Client.

Operator ruling 2026-09-07 (the MCP-tool-surface framing was withdrawn in the same discussion). The loop is Maknae's runtime in the ACP **Agent** role — the process that holds a conversation, presents tools to the model, and executes the model's tool calls. The kernel is the ACP **Client** — the host that provides every capability the Agent uses and decides every use. This is not a third-party Agent plugged into a Maknae host; it is Maknae, and the OpenClaw/Hermes operational goal stated in the project's own protocol vocabulary. A conforming external Agent remains possible later (the assessment's positioning consequence stands); it is not what Cooky builds.

### 2. The loop is UNTRUSTED. It holds no egress credential, no policy, and no durable state.

Core principle 1 and container-architecture §1.3 and §1.5, applied without exception: the loop runs with the **subject's uid**, on the untrusted side of the plane socket, and reaches the kernel only through the existing plane client (`maknae_vault::stream`'s `PlaneConnector` / `AuthenticatedStream` today; #66 records the revisit requirement to cut them out of `maknae-vault` — into `maknae-transport` as that issue names it, or `maknae-plane` — and is not yet a decision). It holds the subject's own plane credential — the CLI SecretID and certificate the [isolation contract](../../packaging/isolation-contract.md) already assigns to the operator uid — and **never the provider credential**, which in Cooky exists only in the `maknae-egress` process (decision 3; the contract's custody row said `maknaed` and carries a dated correction). That custody is a **Vault-policy scoping property, not a linkage property**: the untrusted binary links `maknae-vault` today, and what keeps the provider key out of it is which Vault paths the subject's SecretID may read. The contract **asserts** a custody check — *no egress credential readable by the operator uid, install + CI* — and **no gate implements it today** (`isolation-contract-lint.sh` lints the table's shape, not the property). Cooky is the first milestone with a real credential to check; #242 builds the assertion and binds it to that credential, together.

The loop's transcript is in-memory for the life of one run and never checks in anywhere — §1.5's "a crash loses nothing", not its working-set mechanism. The kernel's audit trail is the durable record **of decisions** — session id, resolved destination, content length or digest, never content (#172's audit contract) — not of the conversation. The session model that would let a conversation outlive a process is Velveteen's, not Cooky's.

### 3. The model call is a capability the trust plane provides to the Agent — decided per turn by the kernel, executed by a separate Rust egress process, and a stated divergence from ACP's method ownership.

Because the Agent is untrusted and holds no egress credential, it cannot make the model call itself. It asks the kernel to: each turn, the loop sends **`session.prompt`** to the trust plane with the messages and the tool schemas; the kernel decides (the grant, the subject, the destination — #172's contract), appends the write-ahead record, hands the turn to **`maknae-egress`**, records the outcome, and returns the model's reply — text or tool calls — on the response leg.

**`maknae-egress` is §3.2's egress proxy as a process, not yet a container (operator ruling 2026-09-07).** A small Rust binary from this workspace, run under **its own service account, `_maknae-egress`, distinct from `_maknae`** on both platforms (Linux: `sysusers`/`postinst`, #240; macOS: #227) — the separation that makes "the PDP does not hold the key" true rather than nominal — reached by `maknaed` over a local socket. It — not `maknaed` — holds the provider credential under **its own Vault AppRole and policy** (a third principal: `maknae enroll`'s policy today enumerates two roles by name, so #240 owns the AppRole, the policy with the KV read, the enroll-policy paths and the SecretID's custody), terminates outbound TLS with the FIPS stack already pinned, makes the chat-completions call, and validates the provider's response into a **bounded reply shape** before anything returns to the PDP. `maknae-llm` is linked into it and nothing else.

**The socket is a second path to the credential, and it is analysed as one.** The socket is created **by the init system, not by the process** — systemd socket activation with `SocketGroup=` (the direction `maknaed.service` already records, #92) and launchd's `SockPathGroup` — so it can be owned `_maknae-egress:_maknae`, mode `0660`, without either account joining the other's group on disk (the cross-membership the packaging forbids). Only the daemon account can connect; `maknae-egress` verifies the connecting peer's uid is `_maknae` before reading a frame; `maknaed` verifies, after connect, that the peer it reached is `_maknae-egress` before writing one — peer credentials read both ways on a connected stream on both platforms (on macOS the client sees the listener's credentials as cached at `listen()`), through `maknae-vault`'s `peercred` module, which #240 exposes rather than duplicates. Frames are `maknae-proto` CBOR, bounded by the same cap discipline as the plane socket. There is **no mTLS** on this channel — both ends are trusted, local, and peer-credential-authenticated — which is a recorded delta against the isolation contract's channel-auth row and the trigger to add it is the moment either end leaves the host (the container). **In the shapes where the accounts do not exist** — the bare dev shape, and macOS before #227 — the uid checks cannot separate the loop from the daemon, and the socket is a PDP-free egress path, exactly as the SecretID is in those shapes; the ADR says so rather than pretending the peer check helps there. The alternative of a host proxy such as Traefik was considered and rejected: it would put a non-Rust, non-FIPS process holding the key into the trust plane, and it would not take the response parsing out of the PDP, which is the larger of the two surfaces. What this buys, stated as the TCB accounting round 5 asked for: the PDP gains **no new** HTTP, TLS or JSON surface — it already links those for Vault, and none of that Vault-facing surface ever sees a provider's bytes; what it decodes from egress is one bounded CBOR frame from a trusted peer, the parser it already has; the trust plane gains a second trusted process designed for exactly that, which the container design already accepts (§1.1, §3.2); and the client and validation code carries forward when the process becomes the container, while the transport does not — a peer-credential Unix socket has no container analogue and the container will speak mTLS per the isolation contract. This ADR is the component ADR `maknae-llm`'s stub was gated on.

**This reverses `session.prompt`'s direction relative to ACP, and the reversal is owned here, not inherited.** In ACP, `session/prompt` is an *agent method*: the Client calls it on the Agent, and the assessment (§3), #172 and #169 all say "Maknae is the caller". In Maknae's vocabulary every verb is a **subject's request to the trust plane**, decided by the PDP — `fs.read` is the subject asking the kernel to let it read, not the kernel reading. `session.prompt` in Cooky is the same shape: the Agent asking the trust plane to send content to the model. The ACP hop the assessment describes — a Client sending `session/prompt` *to* an Agent — is the **user → loop** hop, which Cooky keeps inside one untrusted process (the user types to the loop); the interaction plane that will one day stand between a user and the loop is the gateway (Spinebreaker), and if it speaks ACP to the loop, that is where ACP's `session/prompt` direction lives. The assessment's §5 divergence (the Agent does not execute; the Client does, under a verdict) is the *reason* the reversal is needed; it is not, by itself, the reversal. The `wire.rs` doc for `session.prompt` carries this reversal dated in place, and the bodies of #172 and #169 carry it; the `admin.provider.*`, `session.new`, `session.cancel` and `session.update` docs carry "not built in Cooky" notes that follow from it.

**The response leg is a release and is decided as one.** Model output crossing from the trust plane to the untrusted loop is the relay #172 special-handling 4 describes for `session.update`: decided before it is disclosed onward, audit-then-respond per the #146 invariant, and the content **informs and never authorizes** (core principle 2) — no decision path consumes it. In Cooky the release is to the requesting subject's own loop on the same connection, so the relay decision is the `session.prompt` verdict itself and the record is one write-ahead pair per turn. **What that collapse gives up, stated:** the release verdict is computed before the model output exists, so no content-dependent release rule — a ceiling or releasability check on the *returning* content — can bind in Cooky. It is acceptable only because the audience is the subject that just sent the prompt and nothing stamps markings yet (#229). Triggers to un-collapse it into a decided `session.update`: #229 landing, or any audience other than the requesting subject's own loop. A relay to any other audience is `session.update` today and stays #172's. **A landed-but-undelivered turn** — the egress went out and was recorded, but the reply never reached the loop (an over-cap response refused as `TooLarge`, a response-write timeout, a closed connection) — is treated by the loop exactly as an uncertain write is (decision 4): outcome unknown, **never retried** (#172 special-handling 6: a retried egress that already landed is a duplicate disclosure), and surfaced to the user as such. **(2026-09-09, #172: of these three, the over-cap refusal is recorded as `LandedUndelivered` with the reply's length; #172 adds two causes the three did not anticipate, recorded the same way with the refusal named in `reason`: a reply carrying a block kind the deployment does not admit, and an empty reply. A response-write timeout or a closed connection is not detected on any verb yet, because the write result is discarded for every payload, and detecting it is #240's. The daemon→provider deadline expiring is a different fact, `DeadlineExpired`: delivery to the provider unknown.)**

**One destination, and what keeps it from being chosen by the untrusted side.** `session.prompt` has one destination in Cooky — the provider registered through #243 — and the subject expected to issue it is the loop. "Expected" is the honest word: the plane authenticates **peer credentials** (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` on macOS — only the uid is guaranteed on both; this is the SHIPPED state — ADR-0006's per-process human-session binding is #115, unbuilt), not a binary, so any process of the enrolled subject holding the `session.prompt` grant can issue it, and in Cooky the operator and the loop are the **same uid, hence the same role and the same grants** — role separation between them is unavailable until the second enrolled subject (§8). So the destination is NOT protected by a grant. It is protected by **custody of the registration**: in Cooky the provider is registered by editing `maknaed`'s YAML (#243), which the **Linux** packaging installs as `root:_maknae 0640` under a `0750` directory — and no packaging step adds the operator's uid to `_maknae` (the operator joins the `maknae` group only, `docs/runbook.md`; the daemon is kept out of `maknae` on disk, `postinst` / `maknae.sysusers`), so the subject can neither write nor read the registration. Nothing *enforces* that absence at the OS layer; what #243 enforces at boot is the file: the provider block is a section of `maknae.yaml` — so it reaches `admin.config.show` through the one disclosure path that exists (`ResolvedSettings`, the `DISCLOSABLE`/`SUPPRESSED` tables and their manifest rows, all #243's to add; the drift gate refuses an undecided leaf) — and **#243 adds the precondition** that when the block is present the file must satisfy `ROOT_ARTIFACT`'s requirement (owner root, no group/other write; `loader.rs`), refusing boot otherwise. That is a requirement on #243, not a property `load_root_file` already has: its one caller today, the posture marker, is deliberately fail-soft and does not feed the config view. Root itself can always read it — root and unit control are out of scope by ADR-0006's own assumption, and the custody assertion (#242) proves the *subject* cannot, not that a sudoer cannot. The unprivileged view of the registration is `admin.config.show`, already grantable, under a #162 disclosure decision #243 records (endpoint and model disclosed; the key path `omit`). The key lives in Vault under **`maknae-egress`'s** policy (decision 3); the subject's `maknae-cli` policy grants no KV path at all (`deploy/vault-pki/main.tf`) and the kernel policy gets none — #243 owns the KV mount, #240 the egress principal that reads it. **Custody has a precondition the ADR states rather than assumes: a daemon uid distinct from the subject's.** That exists only on a packaged Linux install (`_maknae`, deb/rpm). On macOS the packaging is unbuilt (`packaging/macos/README.md`: no `.pkg`, no `_maknae` account, no launchd unit), and in the dev shape the runbook describes (`maknaed` run from `~/.maknae` as the operator) the daemons' own Vault SecretIDs are subject-owned `0400` files — so the subject can log in as either and read the KV path, and owns the daemons' YAML besides. In that shape custody does not hold — and once #243's precondition lands, that shape cannot register a provider at all: `~/.maknae/maknae.yaml` is operator-owned `0600`, `ROOT_ARTIFACT` requires owner root, and a root-owned `0600` file is unreadable by an operator-run daemon. So the dev shape boots **without** a provider block (the loop then has nothing to prompt) and #242's dev-shape evidence is "the daemon refuses to boot with a provider block", not "custody fails". The development path for #240 and #241 on a Mac is therefore #227 first. **So the macOS packaging comes into Cooky** (operator ruling 2026-09-07; #227): the `_maknae` and `_maknae-egress` service accounts and launchd units for `maknaed` and `maknae-egress` are what make custody hold on the platform the demonstration runs on — a supported-platform gap, per AGENTS.md, not a footnote. The `.pkg` installer and the Apple signing chain stay behind them, and #227's `lipo`/x86_64 line is corrected there (there are no x86 macOS builds). #242's custody assertion is then evidence on both a packaged Rocky install and a Mac with #227 applied, and an expected, recorded failure on the bare dev shape. **None of `admin.provider.list`, `.set` or `.disable` is built in Cooky.** `.set` and `.disable` because a wire term that could re-target egress from the subject's uid would undo the custody control above; `.list` because it would need the same `GRANTABLE_ACTIONS` extension the other two need (all three are `NotApplicable` today, `decide.rs`) for a view `admin.config.show` already gives. Building any of them is #169's own work. A provider change is therefore a root edit plus a daemon restart, which answers #169's in-flight-retarget requirement the only way Cooky can: every `session.prompt` record names the destination it actually went to, so the trail answers "which content went where" turn by turn; sticky-per-conversation is unachievable without a session object and is not claimed. `session.set_config_option` and `session.set_mode`, which `wire.rs` flags as possible second redirect surfaces, are not implemented in Cooky and stay treated as egress. **`session.cancel` is not built in Cooky**: its operand names a session, and no session identity exists (decision 7). Stopping the loop is the subject stopping its own process. #172's rule — cancel granted wherever prompt is, never the scarcer grant, best-effort, never a recall — applies when a session identity exists.

### 4. Tool calls are executed as the subject, through the kernel's verbs — never by the kernel on the Agent's own authority, and never with a reason on the wire.

When the model asks for `read_file`, the loop sends **`fs.read`** the way the CLI does today: the subject opens, the descriptor is delegated, the kernel verifies the object and decides (ADR-0009). When it asks for `write_file`, the loop sends **`fs.write`** the way #238 shipped it, which has two lanes (the model is told only applied-or-unknown, below — not which lane): **replacement of an existing file** executes in `maknaed` through the subject's delegated non-truncating writable descriptor after a durable intent, and its completion is `KernelObserved` — `Applied`, `NoEffect`, `Partial` or `DurabilityUnknown` in the **trail** (ADR-0019, 2026-09-07 amendment; a fifth, `Incomplete`, recorded with `KernelObserved` origin on either lane when the worker cannot be joined or a report is missing, malformed or rejected — `mutation.rs`); **create-on-absent** executes in the CLI under the subject's credentials after a durable intent authorizes the attempt, and its completion is `ClientReported` — a reported success remains the subject's claim, and a missing report leaves the outcome incomplete. Cooky's demonstration, "reads a file, changes a file, answers", exercises the replacement lane. **What the wire publishes is narrower than the trail, and the ADR does not pretend otherwise:** today the daemon answers a replacement with `MutationComplete` only for a clean `Applied`; `NoEffect`, `Partial` and `DurabilityUnknown` all return the generic `Unauthorized` frame (`mutation.rs`), and a timeout or a failed completion append returns no frame at all. So the loop can tell "applied" from "not applied" and nothing finer — an uncertain write is indistinguishable from a refusal on the wire, though not in the trail. Cooky's rule for the loop follows from that and from ADR-0019's own sentences — for the replacement lane *a completion append failure cannot undo already changed bytes and never produces a success response*, for the client-reported lane *a lost report or deadline yields an incomplete attempt, not a claim of no effect or rollback*: anything but a clean `Applied` is reported to the model as **outcome unknown — the write may have applied; do not retry, and do not assume the prior content**. Whether the wire should distinguish an uncertain write from a denial is #241's question, recorded there.

**Tool results are verdict-shaped and carry only what the wire already publishes.** A refusal reaches the model as the generic refusal the daemon emits for every denied request — `Unauthorized`, "not authorized" — and nothing more: the deny *reason* is audit-only (ADR-0019; the 2026-09-02 operator wire ruling in `handler.rs`; #172's audit contract). A richer refusal for the model would put matched deny-pattern text into model context and thence into the next egress; whether any safe subset exists is an open question #241 records, not a decision here. A clean `Applied` reaches the model as applied; everything else — a refusal, a non-`Applied` completion, a missing frame, an incomplete `ClientReported` outcome — reaches the model as outcome unknown, and the loop does not retry, because on the wire it cannot tell uncertain from refused and must not manufacture certainty either way. The model's text can never authorize anything: it can only ask, and every ask is a request the kernel decides.

### 5. The MVP loop is Rust, a subcommand of the existing untrusted binary: `maknae agent`.

Operator ruling 2026-09-07. The reasons, recorded so the decision can be revisited on evidence rather than taste:

- **Every client-side piece already exists in Rust** — the plane connector, mTLS, the CBOR frames, descriptor delegation, the subject-side write path. A Python loop would have to reimplement the plane client before it could send its first verb; a Rust loop reuses `bins/maknae`'s.
- **The loop adds no packaging surface.** `maknae` is already the unprivileged binary in the isolation contract's matrix; a subcommand adds no row, no image, no SELinux domain. (Cooky's packaging growth is all on the trusted side — the `maknae-egress` binary, its accounts and units — decision 3; the loop itself adds none.) The Python `runtime` container of §3.4 would add all three before the first conversation.
- **The loop's language guarantees are not load-bearing** (§3.4's own words; §1.3 is the principle behind them), so Rust is not chosen for safety here; it is chosen because it is the shortest path to a measured MVP with the project's existing gates (tiers, mutants, drift, `std-fs-drift`) applying unchanged.

**What this does not decide:** the language of the *eventual* runtime container. §3.4's Python rationale — SDK breadth, learning-loop concepts from Hermes — is about capabilities Cooky does not build (MCP client integrations, gap detection, dreaming). That decision is **re-taken on evidence after Cooky**, and the evidence that would move it is named: the first capability whose implementation cost in Rust exceeds the cost of a Python plane client plus a second packaging surface. §3.4 carries a dated note pointing here.

### 6. Exactly two tools, in order: `read_file` first, then `write_file`.

Operator ruling 2026-09-07. `read_file` → `fs.read`; `write_file` → `fs.write`. `fs.delete` and `fs.mkdir` exist in the kernel and are deliberately **not** presented to the model in Cooky: the demonstration is "reads a file, changes a file, answers", and every additional tool is additional attack surface a review must cover.

**What keeps the tool surface honest, stated at its true strength.** The loop's tool bodies are written to send verbs, and the in-repo control is the `std-fs-drift` gate, which inventories exactly what its pattern matches: every production `std::fs` / `File::` / `OpenOptions::` call site plus requirement-free `maknae-io` calls (twelve `std::fs` sites and one `maknae-io` call in `bins/maknae` today, each recording its contract gap), so a tool body that reached for `std::fs` would be a new inventory entry a reviewer sees. It does **not** see `nix::`, `libc::` or `std::process::Command`, and the enroll path alone has at least four filesystem-affecting production calls of that kind — `nix::unistd::chown` and `restorecon` in `enroll/artifact_write.rs`, `setfacl -m u:_maknae:rx` on the subject's home and `apparmor_parser -r` in `enroll/mod.rs` — none in the allowlist because the pattern cannot match them. That uncovered class is #245. The gate governs this repository's source; it says nothing about an untrusted process at runtime, and nothing at the OS layer stops the subject's own process from touching the filesystem directly. The bound is the one core principle 1 gives: **the loop's direct reach is the subject's reach** — direct I/O is not escalation, because the loop is the subject — but it is invisible to the trail, and "every consequential act transits the kernel" is a claim about what the shipped loop *does*, held by review and the gate, not a claim that it *cannot* do otherwise. One consequence is specific enough to name because it is #242's headline evidence: `read_file` on a denied path (`~/.ssh/id_rsa` under the shipped deny) means the loop, as the subject, **opens the file before the verdict** and holds the descriptor — that is ADR-0009's design (the subject's own open is not a Maknae disclosure) — and what the deny prevents is the kernel-mediated disclosure of its bytes into the conversation. The demonstration shows the model never receives them; it does not show the process never touched them. The same honesty applies to the network, and there it is worse: `bins/maknae` already links `reqwest` and a TLS stack transitively through `maknae-vault` (for Vault), so a tool body could make its own model call today with **no** change to `Cargo.toml` and nothing in `deny.toml` or `ci/gates/` would notice; nftables is Linux-only defense-in-depth and macOS has no analogue (the isolation contract marks it deferred). The only controls are review of the loop's source and the deferred egress-network controls — a second argument for #66's transport split, which would take Vault out of the untrusted binary. Recorded, not solved.

### 7. Bounds, on the daemon Cooky actually has: one kernel-enforced, one advisory, and no conversation the kernel can count.

`maknaed` today reads **one request frame per connection** and mints a fresh audit `session_id` per accepted connection (`run.rs`; `admin.session.list`'s doc names connections, "not agent conversations" — the term itself is unbuilt). Multi-frame exchanges within a connection already exist — the `ClientReported` mutation lane runs a bounded, state-machined `MutationExchange` with a kernel-enforced effect counter (#238) — so **the missing thing is not multi-frame capability; it is a conversation identity** the kernel could count turns against across the connections a conversation spans. That identity is a session object, which is Velveteen's, not Cooky's. Stated plainly:

- **The egress deadline** is enforced in `maknaed` per request **(corrected 2026-09-09: #172 bounds the send by the transport's per-peer permit bound, `read_timeout_ms`, and records expiry as `DeadlineExpired`, delivery unknown, never as landed-but-undelivered; the egress-specific deadline, non-blocking, no automatic retry, is #240's)** (#172 item 6: bounded, non-blocking, **no automatic retry** — a retried egress that already landed is a duplicate disclosure).
- **The frame cap is the de facto conversation bound, and the ADR says so rather than pretending otherwise.** Because the loop is stateless and the kernel holds no conversation, every turn re-sends the whole transcript inside one request frame, capped at `transport.frame_max_bytes` (shipped default 64 KiB; hard ceiling 1 MiB). So the cap bounds the *cumulative transcript*, not a turn; a `read_file` result that fills the read budget (the cap minus a 512-byte envelope margin, `handler.rs`) leaves that margin and nothing more for the transcript and tool schemas that must travel with it, so it cannot be relayed back at any legal cap in practice; and a growing conversation would die at an unpredictable turn, after that many egresses had landed. **Operator ruling 2026-09-07: keep the MVP small.** Cooky does not raise the cap and does not make the loop truncate: the loop measures the next request against the cap **before** sending and refuses the turn — telling the user the conversation has reached the platform's bound — rather than sending a frame the daemon will refuse after the fact. **The cap the loop measures against is its own configuration** (`~/.maknae`, the same `transport.frame_max_bytes` the CLI already reads to encode requests), so the pre-send check is **advisory**, and the two caps are independent bounds in both directions. If the loop's cap is the larger and it sends an over-cap request, the daemon's framer refuses it before allocating, writes a `read`-phase deny record and closes the connection — **no** frame comes back, nothing landed (no verdict, no write-ahead pair), and the loop tells the user the turn was refused for size and may be shortened and resent. If the loop's cap is the smaller, the loop refuses turns the platform would have taken; that costs nothing but a conversation cut short. **Landed-but-undelivered** (decision 3) is the *other* case only — the request landed and the *reply* did not arrive (an over-cap response the daemon refuses as `TooLarge`, a response-write timeout, a closed connection) — and that one is never resent. **(2026-09-09, #172: see decision 3's correction — two further causes, a non-text reply and an empty reply, are recorded the same way.)** (The daemon's value is disclosable through `admin.config.show`; making the loop depend on that grant is a decision Cooky does not take.) The demonstration uses a small file and a short conversation and says so. A conversation the kernel holds is Velveteen's, and that is the trigger for a real bound.
- **Steps per prompt and tool calls per step** are enforced in the loop and are **advisory by construction** — a bound applied inside a component this ADR declares untrusted cannot fail closed. What they buy is a well-behaved loop stopping early; nothing in Cooky stops a misbehaving one short of the per-request deadline and the subject's own patience. This is a named gap (§8), not a control.
- **Correlating the turns of one conversation in the trail** is #241's: the loop carries a conversation identifier the kernel records as an **untrusted, informational** attribute — never an input to a verdict — so #242's evidence can group one conversation's records; if the record model cannot carry it without a change, #242 accepts records linked by subject and time window and says so.

All configuration is YAML (ADR-0005 decision 8). The daemon's deadline lives in `maknaed`'s configuration — `root:_maknae 0640` under `0750` on Linux, no other-class access, which is the loader's actual requirement (`mode & 0o007 == 0`; ownership left to OS DAC); the advisory bounds live wherever the loop reads its own configuration, a file the subject owns and may edit, which is fine precisely because they are advisory.

### 8. What Cooky deliberately does not answer

- **Credential scoping — the confused deputy.** In Cooky the provider credential is **platform-scoped, not subject-scoped** (#153 §4's "daemon-scoped"): one key, held by `maknae-egress` and spent at `maknaed`'s direction for any enrolled subject holding the `session.prompt` grant. #153 §4 names this ("credentials are subject-scoped, never daemon-scoped … otherwise the interface becomes a privilege amplifier") and `admin.credential.broker` (#168) is the term that answers it. Cooky accepts the amplifier for a single-user MVP and records it; the trigger to revisit is the second enrolled subject. **This overrides a stated gate:** #153's checklist says *explicitly refuse a daemon-scoped one*, and #172 says its default must not be decided ahead of #153. This ADR proposes the override for the single-subject MVP only; ratifying the ADR is the authority for it, and until then it is a proposal, not a ruling. It is also the ADR that ADR-0006 decision 8 (T0: *any design change that would have the trust plane act with its own privileges for a client is a security decision requiring an ADR*) demands: spending `maknae-egress`'s key on the subject's behalf is exactly that, scoped here to one subject, with the second enrolled subject as the trigger; ADR-0006 carries a dated pointer.
- **Provenance and ceiling across the untrusted hop.** #172 property 4 / special-handling 3 and #170/#171 say the session's high-water mark rises on ingest and never falls. In Cooky nothing stamps `RESOURCE_CLASSIFICATION` (#229), and content the loop reads through `fs.read` returns to the trust plane in the next `session.prompt` **unmarked** — the ceiling operand treats it as the system's lowest level. That is a marking-laundering path from a marked file to egress, and Cooky has no control for it beyond the destination itself: a provider registered for an enclave must be one cleared for that enclave's ceiling (the operator's 2026-09-06 ruling on accredited endpoints), which is #147's destination governance, and ADR-0005 decision 8's **per-endpoint dominance ceiling** is neither honored nor replaced here. Recorded as a gap, owned by #229 (the writer) and #147 (the destination), not solved.
- **#209** — the model as an untrusted caller: what Maknae bounds structurally and what it cannot. This ADR assumes the model is adversarial and lets the kernel decide every ask; it does not claim that is containment.
- **Turn COUNT is unbounded kernel-side; cumulative turn CONTENT is hard-bounded by the frame cap** (decision 7). No conversation identity exists in `maknaed`, so the kernel cannot count turns; it can and does refuse any single frame over the cap. Owned by Velveteen's session object; trigger: a daemon-side conversation identity of any kind.
- **#172's permit conditions, carried and deferred.** #172 permits `session.prompt` on three conditions: the grant; the subject owns the session; the session's provider is in the role's `destinations:` allowlist. Cooky carries the first (which requires `session.prompt` to become decidable — today `Class::Session` decides `NotApplicable` and the grantable set is three `admin.*` terms; that `decide.rs` change is #172's, named in its implementation sites, and Cooky's chain now says so); satisfies the second by construction (no session object — the connection's authenticated subject is the only possible owner); and **defers the third** (no `destinations:` block exists; the single registered provider is the destination).
- **The `egress-proxy` container** is not built; its function ships as the `maknae-egress` process (decision 3). Destination enforcement in Cooky is "the registered provider", decided by `maknaed` and the only route `maknae-egress` is configured with. Triggers to containerize: a second destination of any kind, or the Kubernetes deployment model.
- **#151** — MCP tools presented to the model; **Velveteen** — sessions that outlive a process; **Spinebreaker** — a user reaching the loop from anywhere but the local shell (and the ACP-direction `session/prompt`, if the gateway speaks ACP to the loop).
- **#153's remainder** — several providers, per-user model configuration, capability differences (vision, audio, embeddings — and #172 item 7's finding that non-text content defeats structural marking), OAuth subscription mode. The MVP registers one OpenAI-compatible endpoint (#243).
- **The operand shape.** #172 states `SessionPrompt { session_id, content }`; Cooky's turn carries tool schemas inbound and a reply — text or tool calls — outbound. This ADR fixes that those travel on the `session.prompt` request and response; the concrete shape is #241's, reconciled with #172 there.
