# ADR-0023: Maknae's runtime loop is the ACP Agent and the kernel is the Client — a Rust loop on the untrusted side, model egress brokered by the trust plane

- **Status:** Proposed (operator-directed 2026-09-07, issue #239; milestone Cooky, epic Begin #244). Two of its decisions (5 and 6) are operator **rulings** recorded verbatim; the rest is the author's proposal for ratification. Cooky's implementation issues cite this ADR as their authority while it is Proposed, the way ADR-0010 is cited; ratification is the operator's, at or after #242.
- **Date:** 2026-09-07
- **Deciders:** Alex Ackerman (operator)

## Context

Everything the kernel decides is, today, decided on behalf of a subject that types `maknae read` at a shell. #238 gave the kernel its first mutating verbs and the README described them as "filesystem development commands" — a human tutorial. The operator's question that produced this ADR (2026-09-07): *"How does giving the CLI these commands help a user using Maknae with an LLM as an agentic platform?"* The honest answer was that it does not, yet: the vocabulary is the kernel half of an agent's tools, and the agent — the loop that orchestrates a model and executes its tool calls — has no code and no line on the roadmap. The operational goal has always been what OpenClaw and Hermes Agent *are* ([reference-implementation-autopsy](../reference-implementation-autopsy.md)): an agent, with the one structural inversion that its tools do not touch the OS. **Cooky's MVP is that agent, minimal: configure a model with an OpenAI-compatible endpoint and key, and function as an agent** (operator direction, 2026-09-07).

Three questions had no recorded answer and would otherwise be settled by whoever wrote the first loop:

1. **Which ACP role is the loop?** The [ACP assessment](../references/2026-08-28-acp-protocol-assessment.md) §2 rules that Maknae is the **Client** — the host that provides `fs.*` and decides every call. It did not say who the Agent is, because at the time the answer could have been "any conforming ACP Agent". §5 recorded the trust-model divergence: ACP v2 assumes the Agent is trusted to execute; Maknae's core principle 1 holds the agent runtime untrusted.
2. **Where does the loop run, in what language?** [container-architecture](../container-architecture.md) §3.4 proposes a Python `runtime` container — *proposed*, never ratified — for velocity reasons that assume a broad LLM/MCP SDK footprint the MVP does not need.
3. **Who makes the model call?** `maknae-llm`'s stub says "maknaed-linked; egress terminates there"; `session.prompt`'s doc in `wire.rs` said "send content to an agent runtime … toward a model endpoint", which conflates the user→loop hop with the loop→model hop; and #172 specifies `session.prompt` as write-ahead egress whose destination is a provider from #153/#169.

A wrong first answer to any of these is expensive: a loop that holds the key, or a loop the kernel does not stand between and the model, is OpenClaw with a nicer README.

## Decision

### 1. Maknae ships its OWN agent. It is the ACP Agent; the trust plane is the ACP Client.

The loop is Maknae's runtime in the ACP **Agent** role — the process that holds a conversation, presents tools to the model, and executes the model's tool calls. The kernel is the ACP **Client** — the host that provides every capability the Agent uses and decides every use. This is not a third-party Agent plugged into a Maknae host; it is Maknae, and the OpenClaw/Hermes operational goal stated in the project's own protocol vocabulary. A conforming external Agent remains possible later (the assessment's positioning consequence stands); it is not what Cooky builds.

### 2. The loop is UNTRUSTED. It holds no egress credential, no policy, and no durable state.

Core principle 1 and container-architecture §1.3 and §1.5, applied without exception: the loop runs with the **subject's uid**, on the untrusted side of the plane socket, and reaches the kernel only through the existing plane client (`maknae_vault::stream`'s `PlaneConnector` / `AuthenticatedStream` today; their move to `maknae-plane` is #66). It holds the subject's own plane credential — the CLI SecretID and certificate the [isolation contract](../../packaging/isolation-contract.md) already assigns to the operator uid — and **never the provider credential**, which exists only in `maknaed` per that contract's custody row. That custody is a **Vault-policy scoping property, not a linkage property**: the untrusted binary links `maknae-vault` today, and what keeps the provider key out of it is which Vault paths the subject's SecretID may read. The contract's custody assertion — *no egress credential readable by the operator uid, install + CI* — has, in Cooky, a real credential to bind to for the first time; #242 carries it as acceptance evidence.

The loop's transcript is in-memory for the life of one run (a "working set", §1.5). The kernel's audit trail is the durable record **of decisions** — session id, resolved destination, content length or digest, never content (#172's audit contract) — not of the conversation. The session model that would let a conversation outlive a process is Velveteen's, not Cooky's.

### 3. The model call is a capability the trust plane provides to the Agent — brokered egress, decided per turn, and a stated divergence from ACP's method ownership.

Because the Agent is untrusted and holds no egress credential, it cannot make the model call itself. It asks the kernel to: each turn, the loop sends **`session.prompt`** to the trust plane with the messages and the tool schemas; the kernel decides (the grant, the subject, the destination — #172's contract), appends the write-ahead record, calls the provider through `maknae-llm` (egress terminates in `maknaed`, as the crate's design says), records the outcome, and returns the model's reply — text or tool calls — on the response leg.

**This reverses `session.prompt`'s direction relative to ACP, and the reversal is owned here, not inherited.** In ACP, `session/prompt` is an *agent method*: the Client calls it on the Agent, and the assessment (§3), #172 and #169 all say "Maknae is the caller". In Maknae's vocabulary every verb is a **subject's request to the trust plane**, decided by the PDP — `fs.read` is the subject asking the kernel to let it read, not the kernel reading. `session.prompt` in Cooky is the same shape: the Agent asking the trust plane to send content to the model. The ACP hop the assessment describes — a Client sending `session/prompt` *to* an Agent — is the **user → loop** hop, which Cooky keeps inside one untrusted process (the user types to the loop); the interaction plane that will one day stand between a user and the loop is the gateway (Spinebreaker), and if it speaks ACP to the loop, that is where ACP's `session/prompt` direction lives. The assessment's §5 divergence (the Agent does not execute; the Client does, under a verdict) is the *reason* the reversal is needed; it is not, by itself, the reversal. The `wire.rs` docs for `session.prompt`, `admin.provider.*`, `session.new`, `session.cancel` and `session.update`, and the bodies of #172 and #169, carry this correction dated in place.

**The response leg is a release and is decided as one.** Model output crossing from the trust plane to the untrusted loop is the relay #172 special-handling 4 describes for `session.update`: decided before it is disclosed onward, audit-then-respond per the #146 invariant, and the content **informs and never authorizes** (core principle 2) — no decision path consumes it. In Cooky the release is to the requesting subject's own loop on the same connection, so the relay decision is the `session.prompt` verdict itself and the record is one write-ahead pair per turn; a relay to any *other* audience is `session.update` and stays #172's.

**One destination, and who may set it.** `session.prompt` has one destination in Cooky — the provider registered through #243 — and the subject expected to issue it is the loop. "Expected" is the honest word: the plane authenticates a **uid** (`SO_PEERCRED`, ADR-0005 as amended by ADR-0006), not a binary, so any process of the enrolled subject holding the `session.prompt` grant can issue it; decision 4 says what that does and does not let such a process do. `admin.provider.set` and `.disable` — "egress on the same axis" (`wire.rs`) — are **operator-only in Cooky and denied to the loop's subject role**, so the one destination is never chosen from the untrusted side; `session.set_config_option`, which `wire.rs` flags as a possible second redirect surface, is not implemented in Cooky and stays treated as egress. `session.cancel` is granted wherever `session.prompt` is (#172: never the scarcer grant); in Cooky it stops the loop, and a cancel of an in-flight egress is best-effort and recorded as such — cancel never recalls a disclosure.

### 4. Tool calls are executed as the subject, through the kernel's verbs — never by the kernel on the Agent's own authority, and never with a reason on the wire.

When the model asks for `read_file`, the loop sends **`fs.read`** the way the CLI does today: the subject opens, the descriptor is delegated, the kernel verifies the object and decides (ADR-0009). When it asks for `write_file`, the loop sends **`fs.write`** the way #238 shipped it, which has two lanes and the model sees which one it got: **replacement of an existing file** executes in `maknaed` through the subject's delegated non-truncating writable descriptor after a durable intent, and its completion is `KernelObserved` — `Applied`, `NoEffect`, `Partial` or `DurabilityUnknown` (ADR-0019, 2026-09-07 amendment); **create-on-absent** executes in the CLI under the subject's credentials after a durable intent authorizes the attempt, and its completion is `ClientReported` — a reported success remains the subject's claim, and a missing report leaves the outcome incomplete. Cooky's demonstration, "reads a file, changes a file, answers", exercises the replacement lane.

**Tool results are verdict-shaped and carry only what the wire already publishes.** A refusal reaches the model as the generic refusal the daemon emits for every denied request — `Unauthorized`, "not authorized" — and nothing more: the deny *reason* is audit-only (ADR-0019; the 2026-09-02 operator wire ruling in `handler.rs`; #172's audit contract). A richer refusal for the model would put matched deny-pattern text into model context and thence into the next egress; whether any safe subset exists is an open question #241 records, not a decision here. A `KernelObserved` completion reaches the model as its closed token; an incomplete `ClientReported` outcome reaches the model as incomplete, and the loop does not retry uncertain work. The model's text can never authorize anything: it can only ask, and every ask is a request the kernel decides.

### 5. The MVP loop is Rust, a subcommand of the existing untrusted binary: `maknae agent`.

Operator ruling 2026-09-07. The reasons, recorded so the decision can be revisited on evidence rather than taste:

- **Every client-side piece already exists in Rust** — the plane connector, mTLS, the CBOR frames, descriptor delegation, the subject-side write path. A Python loop would have to reimplement the plane client before it could send its first verb; a Rust loop reuses `bins/maknae`'s.
- **The packaging surface does not grow.** `maknae` is already the unprivileged binary in the isolation contract's matrix; a subcommand adds no row, no image, no SELinux domain. The Python `runtime` container of §3.4 would add all three before the first conversation.
- **The loop's language guarantees are not load-bearing** (§3.4's own words; §1.3 is the principle behind them), so Rust is not chosen for safety here; it is chosen because it is the shortest path to a measured MVP with the project's existing gates (tiers, mutants, drift, `std-fs-drift`) applying unchanged.

**What this does not decide:** the language of the *eventual* runtime container. §3.4's Python rationale — SDK breadth, learning-loop concepts from Hermes — is about capabilities Cooky does not build (MCP client integrations, gap detection, dreaming). That decision is **re-taken on evidence after Cooky**, and the evidence that would move it is named: the first capability whose implementation cost in Rust exceeds the cost of a Python plane client plus a second packaging surface. §3.4 carries a dated note pointing here.

### 6. Exactly two tools, in order: `read_file` first, then `write_file`.

Operator ruling 2026-09-07. `read_file` → `fs.read`; `write_file` → `fs.write`. `fs.delete` and `fs.mkdir` exist in the kernel and are deliberately **not** presented to the model in Cooky: the demonstration is "reads a file, changes a file, answers", and every additional tool is additional attack surface a review must cover.

**What keeps the tool surface honest, stated at its true strength.** The loop's tool bodies are written to send verbs, and the in-repo control is the `std-fs-drift` gate: every direct filesystem call in `bins/maknae` is an exact-inventory exemption (fourteen exist today, each recording its contract gap), so a tool body that reached for `std::fs` would be a new inventory entry a reviewer sees. That gate governs this repository's source; it says nothing about an untrusted process at runtime, and nothing at the OS layer stops the subject's own process from touching the filesystem directly. The bound is the one core principle 1 gives: **the loop's direct reach is the subject's reach** — direct I/O is not escalation, because the loop is the subject — but it is invisible to the trail, and "every consequential act transits the kernel" is a claim about what the shipped loop *does*, held by review and the gate, not a claim that it *cannot* do otherwise.

### 7. Three bounds; the two that matter are enforced in the kernel, the third is advisory and says so.

- **The egress deadline** is enforced in `maknaed` (#172 item 6: bounded, non-blocking, **no automatic retry** — a retried egress that already landed is a duplicate disclosure).
- **Turns per session** is enforced in `maknaed`: the kernel counts `session.prompt` verdicts per connection session and refuses past the configured bound, fail closed. A loop that ignores its own bound is stopped, not merely observed.
- **Tool calls per step** is enforced in the loop and is **advisory by construction** — a bound applied inside a component this ADR declares untrusted cannot fail closed. What it buys is a well-behaved loop stopping early; what limits a misbehaving one is the turn bound above (each tool result goes back to the model only through another `session.prompt`).

All three are YAML configuration (ADR-0005 decision 8). The two kernel-enforced bounds live in `maknaed`'s configuration, operator-owned and root-readable like the rest of `/etc/maknae`; the advisory bound lives wherever the loop reads its own configuration — a file the subject owns and may edit, which is fine precisely because it is advisory.

### 8. What Cooky deliberately does not answer

- **Credential scoping — the confused deputy.** In Cooky the provider credential is **daemon-scoped**: one key, spent by `maknaed` for any enrolled subject holding the `session.prompt` grant. #153 §4 names this ("credentials are subject-scoped, never daemon-scoped … otherwise the interface becomes a privilege amplifier") and `admin.credential.broker` (#168) is the term that answers it. Cooky accepts the amplifier for a single-user MVP and records it; the trigger to revisit is the second enrolled subject.
- **Provenance and ceiling across the untrusted hop.** #172 items 3 and #170/#171 say the session's high-water mark rises on ingest and never falls. In Cooky nothing stamps `RESOURCE_CLASSIFICATION` (#229), and content the loop reads through `fs.read` returns to the trust plane in the next `session.prompt` **unmarked** — the ceiling operand treats it as the system's lowest level. That is a marking-laundering path from a marked file to egress, and Cooky has no control for it beyond the destination itself: a provider registered for an enclave must be one cleared for that enclave's ceiling (the operator's 2026-09-06 ruling on accredited endpoints), which is #147's destination governance, and ADR-0005 decision 8's **per-endpoint dominance ceiling** is neither honored nor replaced here. Recorded as a gap, owned by #229 (the writer) and #147 (the destination), not solved.
- **#209** — the model as an untrusted caller: what Maknae bounds structurally and what it cannot. This ADR assumes the model is adversarial and lets the kernel decide every ask; it does not claim that is containment.
- **The `egress-proxy` container** stays proposed; the MVP's destination check is "the registered provider" inside `maknaed`. Trigger to revisit: a second destination of any kind.
- **#151** — MCP tools presented to the model; **Velveteen** — sessions that outlive a process; **Spinebreaker** — a user reaching the loop from anywhere but the local shell (and the ACP-direction `session/prompt`, if the gateway speaks ACP to the loop).
- **#153's remainder** — several providers, per-user model configuration, capability differences (vision, audio, embeddings — and #172 item 7's finding that non-text content defeats structural marking), OAuth subscription mode. The MVP registers one OpenAI-compatible endpoint (#243).
- **The operand shape.** #172 states `SessionPrompt { session_id, content }`; Cooky's turn carries tool schemas inbound and a reply — text or tool calls — outbound. This ADR fixes that those travel on the `session.prompt` request and response; the concrete shape is #241's, reconciled with #172 there.

## Consequences

- **Cooky's shape follows directly:** #243 (one provider, key via Vault, `admin.provider.set` operator-only) → #169 and #172 (the verbs, with the direction correction) → #240 (`maknae-llm` gets a body: chat completions with tool calling, called only from the `session.prompt` path) → #241 (`maknae agent`; the turn bound in `maknaed`; the operand shape) → #242 (acceptance).
- **Acceptance lanes, stated where they can run.** The hermetic end-to-end against a stub provider runs in the **Linux CI lane** — `bins/maknae`, `bins/maknaed`, `maknae-vault` and `maknae-kernel` are outside `DARWIN_CRATES` and cannot build on the hosted macOS runner (`ci.yml`; the isolation contract's lane note). The macOS end-to-end and the operator-run conversation with a real key on macOS and Rocky are **Wrathion and test-host** criteria, recorded in #242's PR body with the audit lines quoted. The trail — boot composition record, one `session.prompt` write-ahead pair per turn, the `fs.read` verdict, the `fs.write` intent and `KernelObserved` completion — is the artifact, together with the isolation contract's custody assertion holding against the real provider credential.
- **#242 also owns** the README roadmap line for the runtime milestone (the roadmap currently jumps from the kernel to the lake) and the reframing of the README's "Filesystem development commands" section as what it is: the kernel half of the agent's file tools, with the CLI as the reference subject-side executor.
- **`session.prompt`'s wire doc and its four siblings are corrected in place** (decision 3); no wire shape changes and `PROTOCOL_VERSION` is untouched. #172 and #169 carry dated banners in their bodies.
- **Supersedes, in place and dated:** container-architecture §3.4's "Python" for the MVP loop only (the container-level decision is deferred, not reversed); the framing, offered and withdrawn in discussion on 2026-09-07, that the loop's tool surface should be an MCP server.
