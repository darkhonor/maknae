# ADR-0030: Cryptographic libraries are confined to `maknae-crypto`

- **Status:** Accepted (maintainer-ruled 2026-10-27)
- **Date:** 2026-10-27
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#564](https://github.com/darkhonor/maknae/issues/564) (post-quantum TLS key exchange), part of the PQC epic [#569](https://github.com/darkhonor/maknae/issues/569)

> **Amended 2026-10-27 (#573, maintainer).** This record confined the *libraries*, which is narrower than the intent. The intent is one implementation of each cryptographic function, in `maknae-crypto`, so the CBOM (#570) reads one crate and no two implementations can diverge. Crates outside it keep their domain work (for `maknae-vault`, requesting certificates and talking to Vault) and call `maknae-crypto` for the cryptography. #573 moved the plane signature algorithms and `rcgen` here (decisions 1 to 3); decision 5 states the rule; the code that predates it is #578.

> **Amended 2026-10-31 (#589, [ADR-0031](ADR-0031-maknaes-cryptography-comes-from-crypto-profile.md)).** The implementation moved to the public `crypto-profile-awslc4` crate, and `maknae-crypto` is now its adapter. The libraries are confined one level down: `aws-lc-rs`, `rustls` and `rcgen` are declared only by `crypto-profile-awslc4`, which only `maknae-crypto` may depend on. Decision 2's `crypto_provider()`, `install_default_crypto_provider()` and `KX_GROUPS` are replaced by `policy()`, `init()` and the `preferred` profile; `assert_fips_provider()` keeps its name and now refuses with `PolicyDrift`. `signature::SignatureAlgorithm` (decision 2's #578 amendment) is the backend's nine-algorithm type; the plane's three are `plane_key::PlaneKey`. Decision 5 holds: there is still one implementation of each function, and the CBOM reads it from one chain, `maknae-crypto` → `crypto-profile-awslc4`.

## Context

Before this decision, four workspace manifests declared the FIPS cryptographic libraries directly: `maknae-vault` (`aws-lc-rs` and `rustls`, with the posture comment [ADR-0025](ADR-0025-fips-validation-is-a-goal-not-a-constraint.md) records), `maknae-seal`, `maknae-state` and the `maknae` binary (`aws-lc-rs`). The process-wide TLS provider and its start-up assertion lived in `maknae-vault`, so `maknae-llm` and `maknae-deputy` depended on the whole Vault client crate for one function each.

#564 made the TLS key-exchange groups explicit and asserted at start. That added cryptographic policy to the same crate. The PQC epic will next change the seal's key agreement (#565) and needs a cryptographic inventory and CBOM (#570). With the libraries spread over four manifests, an upgrade has four places to edit, and the CBOM has no single manifest to read.

## Decision

1. **`maknae-crypto` is the only workspace member that declares `aws-lc-rs` or `rustls`.** It carries their version requirements and the FIPS posture comment, and re-exports both (`pub use aws_lc_rs; pub use rustls;`). Every other member reaches them through the re-exports. *(Amended 2026-10-27, #573: and `rcgen`, re-exported the same way.)* *(Amended 2026-10-27, #578: it re-exports `rustls` only, because rustls's types are API. `aws-lc-rs` is not re-exported, so a direct aws-lc-rs call outside this crate does not compile; `rcgen` is re-exported only under the `test-support` feature, which `maknae-vault`'s dev-dependencies enable, so an `rcgen` call in production code fails to compile in a per-package build. Every other member calls this crate's functions and uses `maknae_crypto::rustls`. The exact claim: no direct aws-lc-rs API outside `maknae-crypto`, and the rustls entry points listed in `clippy.toml` are refused.)*
2. **It owns the cryptographic policy over them:** `crypto_provider()` (the aws-lc-rs FIPS provider with `KX_GROUPS`), `install_default_crypto_provider()`, `assert_fips_provider()`, and the pure decisions behind the assertion. Its refusals are `CryptoError`; `maknae-vault` maps them to its own variants of the same name. *(Amended 2026-10-27, #573: it also owns the plane identity's signature algorithms, `signature::PlaneKey` with each algorithm's rcgen algorithm, TLS signature scheme and SubjectPublicKeyInfo check, and `generate_csr()`, the keypair and PKCS#10 request a plane sends to Vault.)* *(Amended 2026-10-27, #578: `PlaneKey` is now `signature::SignatureAlgorithm`, whose names state the algorithm: `ml-dsa-87`, `ecdsa-p384-sha384`, `ecdsa-p521-sha512`.)*
3. **Enforcement.** `deny.toml` `[bans]` denies `aws-lc-rs` and `rustls` to every direct dependent except `maknae-crypto` and the third-party crates that wrap them today. `tokio-rustls` re-exports rustls, so it is confined to `maknae-vault` the same way, as is `rcgen`, which selects aws-lc-rs's FIPS backend. *(Amended 2026-10-27, #573: `rcgen` is now confined to `maknae-crypto`, which re-exports it; `maknae-vault` uses the re-export only in test fixtures. Observed red by planting `rcgen` back in `maknae-vault`.)* `[[bans.features]]` denies `reqwest` the features that install a stock provider (`default-tls`, `rustls`, `__rustls-aws-lc-rs`, `native-tls`, `native-tls-no-alpn`); its `rustls-no-provider` leaves the provider to `maknae-crypto`'s process default. `ring` is banned outright (maintainer ruling 2026-10-27): it is a second, non-FIPS crypto library, absent from the graph since #320, and a `ring` feature on rustls or a wrapper would expose `rustls::crypto::ring::default_provider()`, a stock provider a single connection could use while the start-up assertion, which sees only the process default, still passes. `aws-lc-sys` and `aws-lc-fips-sys` are not banned as direct dependencies: their API is `unsafe` to call, which `unsafe_code = "forbid"` refuses outside `maknae-sys` (ADR-0027). `cargo deny --locked check` runs in `build-and-gate`. `clippy.toml` refuses the rustls functions that build or install a stock provider (#564). *(Amended 2026-10-27, #578: decision 1 is now enforced by the compiler, through the re-exports decision 1's amendment names, and by `clippy.toml`, which also refuses the listed rustls entry points, those that reach a cryptographic primitive or build a configuration or verifier on a provider. Those refusals are enforced by clippy, not by the compiler.)*
4. **Mutation.** `maknae-crypto` is a mutation crate; its decisions are T1.
5. **One implementation per cryptographic function** *(added 2026-10-27, #573)*. A cryptographic function (key generation, signing and its algorithm choice, hashing, random bytes, AEAD, key agreement, KDF, TLS configuration) is implemented once, in `maknae-crypto`, and every other crate calls it. A second implementation elsewhere is a defect. Decoding (X.509 and PEM parsing) is not a cryptographic function; a decision over decoded data, such as which algorithm a public key is, is. *(Amended 2026-10-27, #578: met by the code. `maknae-crypto` holds `digest` (SHA-256), `random`, `aead` (AES-256-GCM, sealing only with a nonce the module chooses), `sealbox` (P-384 ECDH, HKDF-SHA384, AES-256-GCM, under a caller-supplied domain label), `fips`, `tls` (the TLS 1.3 builders on the FIPS provider, private-key loading and the WebPKI verifier builders) and `signature::SignatureAlgorithm`. Its API has no Maknae types and it has no message-catalog dependency, so it is shaped for extraction as the public `crypto-profile` crate; its manifest's FIPS-posture comment still cites Maknae's ADR-0025 and `AGENTS.md`, and is replaced at extraction.)*

## Consequences

- An upgrade of `aws-lc-rs` or `rustls` is one manifest. The CBOM reads the algorithms and libraries Maknae ships from one crate.
- `maknae-llm` and `maknae-deputy` no longer depend on `maknae-vault`.
- **Residuals.**
  - Third-party wrappers still name the libraries in their own manifests (`tokio-rustls` and `reqwest` in `maknae-vault`, `reqwest` in `maknae-llm`). A major version bump of either library also moves them. *(Amended 2026-10-27, #573: this listed `rcgen` in `maknae-vault`; it moved here.)*
  - Decision 5 is not yet true of the code that predates it: SHA-256, random bytes, AES-256-GCM, the seal's key agreement and KDF, and the plane TLS configuration are still implemented outside `maknae-crypto`, some more than once. #578 moves them and adds the control that refuses a new one. *(Closed 2026-10-27, #578: decision 5's amendment.)*
  - `maknae-seal` keeps its own FIPS check over aws-lc-rs until #565 decides the seal's shape. *(Closed 2026-10-27, #578: the sealing construction and the FIPS module check live in `maknae-crypto`; `maknae-seal` keeps only the request binding.)*
  - *(Added 2026-10-27, #578.)* rustls's cryptography stays reachable through its public fields and statics, such as a `CryptoProvider`'s own fields, and through unlisted free and associated functions, such as `rustls::crypto::aws_lc_rs::Ticketer::new`, `rustls::crypto::verify_tls12_signature`, `verify_tls13_signature` and `verify_tls13_signature_with_raw_key`, so a member can still reach a primitive without naming a refused function. #581 enumerates that surface and decides whether and how to close it. The `clippy.toml` refusals bind only where clippy runs.
  - The `deny.toml` controls were observed red by planting a direct dependency in a member (normal and dev) `reqwest`'s `rustls` feature in `maknae-llm`, and a `ring` feature on `rustls` and on `tokio-rustls`; no negative-control probe repeats them, because that gate's environment has no `cargo-deny`.
  - `cargo test -p maknae-crypto` builds rustls with `fips` and `std` only; the shipped binaries also unify `tls12` onto it. The decisions this crate tests do not depend on it.
