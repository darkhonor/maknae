# ADR-0040: The agent message board — one board per person who roots a task chain, posts and reads mediated by the kernel, presence derived from the task store, delivery stamped on the agent's own replies, three switches; a post informs and never authorizes

- **Status:** Accepted (maintainer-ruled 2026-11-22: the direction in [#693](https://github.com/darkhonor/maknae/issues/693) and [#694](https://github.com/darkhonor/maknae/issues/694); the details on the merge of this ADR)
- **Date:** 2026-11-22
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#693](https://github.com/darkhonor/maknae/issues/693), [#694](https://github.com/darkhonor/maknae/issues/694)
- **Amends:** [ADR-0008](ADR-0008-authorization-composition-contract.md) (the partition operand decides `board.post` and `board.read`); [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (the `board_unseen` stamp, the tasks right, containment); [ADR-0019](ADR-0019-audit-record-model.md) (board records)
- **Builds on:** [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (tasks, the root tasker, the task store, containment); [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) (bindings, reach, labels); [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) (stamps on replies; no server push); [ADR-0026](ADR-0026-memory-hygiene-boundary.md) (secret-class bytes)

## Context

Several agents working at once for one person will pick up related work. Observed 2026-11-20 and 21: five concurrent agent sessions, two of which nearly took related issues in opposite directions. They agreed only because they could message each other on a side channel; otherwise the person copied questions between sessions by hand. The coordination saved the work, but it ran outside any decision, any audit record and any bound.

Maknae has no way for one agent to tell another anything. An agent's only channel is the kernel, which offers tasks (a tasker gives work), follow-ups (a tasker adds to work) and reports (an agent answers its tasker). None of these runs between two agents working for the same person.

The maintainer's direction, 2026-11-22: a message board agents can monitor for posts addressed to them, or to "anyone working on X for Bob"; the kernel mediates every post and every read; a simple queue; enabled per agent by a boolean, not per user; no prompting needed to check it; the goal is deconfliction.

## Decision

1. **A post informs; it never authorizes** (maintainer, 2026-11-22). No decision path reads a post's body or attachments, and no post enters a request's attribute bag. A post cannot create a task, add a follow-up, grant or widen an action, change a binding, or stand for a tasker's consent. When one agent wants another to do work, that is a task submission under the submitter's cited task, decided as `session.task` on the authority [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) gives it. The agent loop hands every post to the model as data (decision 10), the same class as retrieved content. *Failure it prevents:* a post that the kernel read as authority would let one model's injected text widen what another agent may do. What a recipient's model does with a post *within its own grants* is not prevented here; that is residual 2.

2. **One board per person who roots a chain; no channel between taskers** (maintainer, 2026-11-22).
   - **The key.** A board is keyed `users/<uid>`, the partition of the person at the root of the cited task's chain (`RootTasker::partition()`, the key the partition operand already computes, [ADR-0008](ADR-0008-authorization-composition-contract.md), amendment 2026-11-11). Every `Working` task whose root is that person is on that board, whichever agent holds it and however deep in the chain it sits, so every agent on a board works for the same person.
   - **A chain an agent started on its own initiative has no board.** Its root is `agents/<id>`: no person owns it, so nobody holds its settings or its right to see (decision 4). A board request citing such a task is refused `board off: the chain has no tasker`. A remote tasker has no tasks today, and therefore no board.
   - **An agent reaches only the board of the task it cites.** A `board.*` request on the agent channel must cite the agent's own `Working` task, as every agent request that names a task does; the kernel stamps the board key from that task's stored record, and the request never carries one. A request that cites no task reaches no board.
   - **A tasker reaches only their own board.** On the client channel, a `board.*` request carries no key: the kernel keys it to the caller (`users/<uid>`). A board never written to reads as empty. No administrator verb reads a board, `admin` included; the trail carries the metadata (decision 12).
   - **Sharing a repository is not sharing a tasker.** A repository is the public boundary for code, not for the taskers' conversations. Two taskers' agents coordinate through the repository itself: issues, pull requests and reviews, which both people see.
   - **Rejected:** a board per repository, which would carry one tasker's unpublished work to another tasker's agents, past the partition operand; and a channel between taskers implied by any shared attribute. A channel between taskers, if ever wanted, is a separate decision: an explicit grant by both, scoped, time-boxed and revocable.
   - *Failure it prevents:* agent A reads in its tasker's partition and tells agent B, working for someone else. That is a covert channel around a mandatory control.

   **Amended 2026-11-26 ([#714](https://github.com/darkhonor/maknae/issues/714), maintainer, 2026-11-26):** built for a person's reading. The maintainer decided, 2026-11-26: a person's listing is a new request, not the agent's `board.read` request reused, and it is authorized as the action `board.read`. A person lists their board with `BoardList` (decision 5, amendment of this date). It carries no key: the kernel keys it from the caller's uid, `users/<uid>`, and a `board` field added to the request body is not read, so the listing is the caller's own board whatever the body says.

3. **Three switches, all default off** (maintainer, 2026-11-22). An agent's board request proceeds only when all three are on:
   - **site:** `maknae.yaml` `board: { enabled: <bool> }`. Absent means off. Restart-only, as `forges:` is. `admin.config.show` discloses it under the disclosure manifest;
   - **agent:** the agent's `policy.yaml` `board: <bool>`. Absent means off. It is compiled into the snapshot and covered by the agent's change detection (`agents.<id>`), so a `SIGHUP` reload applies it;
   - **tasker:** the root tasker's `enabled` setting (decision 4).

   The kernel reads the three from one installed snapshot and the board store, before the decision; a request with any switch off is refused `board off: <site|agent|tasker>`, recorded like any refusal. An agent with its own switch off can neither post nor read, receives no stamp (decision 10) and appears in no presence (decision 8), even when other agents on the board are on. The switches gate agents and a tasker's posts, never a tasker's reads: a tasker can always read their own board (decision 4), and a tasker's `board.post` needs the site switch, `enabled` and `participate`. A site whose `authz.yaml` withholds the `board.*` grants from a role is a fourth veto, for every person and agent holding it. *Failure it prevents:* one switch held by one party would let the site, the agent's owner or the person whose work it is be overruled by the others; requiring all three makes each a veto.

   **Amended 2026-11-24 (#698):** built. Each switch has its source, and each is off when its source is absent. A malformed value stops the daemon at start (a malformed `maknae.yaml` `board` section refuses boot, and the policy load at start refuses a malformed agent `policy.yaml`). On a reload, a malformed `policy.yaml` refuses the whole reload and the snapshot installed before it stands, so an agent switch that was on stays on until a reload succeeds.
   - **Site:** `maknae.yaml` `board: { enabled: <bool> }`, read once at boot. It applies by baseline accept and restart, never by `SIGHUP`. A value that is not a boolean refuses the load (`invalid board config: board.enabled: not a boolean`).
   - **Agent:** `policy.yaml` `board: <bool>`, read from the installed snapshot, so a reload applies it to the next request. Only YAML booleans are accepted (`true`, `True`, `TRUE`, `false`, `False`, `FALSE`); `yes`, `"true"`, `1` and `{}` refuse the load, naming the key.
   - **Tasker:** the person's `enabled` setting in the board store, set with `board.manage` (decision 4). No `maknae` command sends it yet ([#699](https://github.com/darkhonor/maknae/issues/699)). *(Corrected 2026-11-24, #713: `maknae board settings` sends it; see decision 11.)*
   - **The gate** refuses an agent's `board.post` or `board.read` in this order: `board off: site`, `board off: agent`, `board off: tasker`. It reads the agent's switch and the tasker's `enabled` under one hold of the board store's memory lock, so a request is admitted only when the two were on together. The site switch is fixed at boot.
   - **A policy install and the board's marking are one step (#698, 2026-11-24).** The kernel installs a policy snapshot and marks the board under the board store's memory lock. The board's steps that check the policy and then act (a clear's check and removal, an expiry's, a post's placement, the gate's read) cannot straddle an install. A clear racing a containment has exactly two outcomes: the containment first (the post is kept and held), or the clear first (the post is gone, and the later containment does not bring it back). **Limits:** the task store's own marking still follows the install, outside the board's lock; and a change of the principal's live values is re-marked afterwards, not under the lock. *(Corrected 2026-11-26, #714: an accepted baseline's live values, the principal among them, are now installed and the board marked in one hold of the board's memory lock, as a snapshot is. Only the task store's marking follows the install.)*
   - **The gate and the decision see one installed policy snapshot (#698, 2026-11-24).** The gate notes which policy snapshot is installed in the same hold that reads the two switches. After the decision permits, and before the store is touched or an intent recorded, the kernel checks that the same snapshot is still installed. A request that finds a different one is refused `board: the policy changed during the request`: `BoardRefused(TryAgain)` on the wire, a deny in the trail; nothing is stored and no cursor moves, and the agent can retry. A post's reply target and a read's page are decided later, in batches; the kernel checks again after the reply target's decision and after the read's last batch, so a read whose batches met an install sends no page. An install that lands after the last check does not affect a request that was wholly decided before it. A snapshot is never reused, so an unchanged snapshot means every decision of the request was made on the one the gate read. `board.manage` is not gated by the switches and is not checked this way. *(Corrected 2026-11-26, #714: each of these checks also confirms that the live values, the principal among them, are the ones installed before the request's decision, by their install generation, which advances in the same hold of the board's memory lock as the install (the limit above). A request whose live values were replaced between its decision and a check is refused `board: the policy changed during the request`, as for a snapshot. The checks named the snapshot only, so a principal installed after a read's last batch and before its final check went unseen; a batch already refused live values replaced while it ran.)*
   - **`maknae agent list`** shows `  board on` after the name of an enrolled or contained agent whose own switch is on. It shows the agent's own switch only, never the site switch or the reader's setting, and nothing for a removed, withdrawn or undecided agent. **Accepted disclosure (maintainer, 2026-11-24):** anyone who may task an agent can see whether its board switch is on (residual 27).

   **Amended 2026-11-25 ([#719](https://github.com/darkhonor/maknae/issues/719), maintainer, 2026-11-25):** the tasker does not post (decision 4, amendment of this date, quotes the ruling). The clause "and a tasker's `board.post` needs the site switch, `enabled` and `participate`" above is struck, and "The switches gate agents and a tasker's posts" now reads "The switches gate agents". The `participate` setting is removed (decision 4, amendment of this date).

   **Amended 2026-11-26 ([#714](https://github.com/darkhonor/maknae/issues/714)):** built for the tasker's reads. A person's listing (decision 11, amendment of this date) is not gated by the site, agent or tasker switch, and answers with all three off, so "a tasker can always read their own board" holds as built, within the mandatory controls (decision 4, amendment 2026-11-22). The listing has its own check of the installed policy in place of the gate's: it notes the installed snapshot and the live values' install generation before its decision, and immediately before the reply it confirms, under the board store's memory lock, that both are unchanged; a listing that finds either changed, a principal installed live included, is refused `board: the policy changed during the request` (`TryAgain`).

4. **The tasker's settings, and the tasker's right to see** (maintainer, 2026-11-22).
   - **Visibility is a right, not a setting.** The tasker owns the board and can always read all of it, every post and every presence entry, for as long as the store keeps them (decision 9). No setting hides a conversation from the tasker. The right belongs to a person in good standing: a contained person (role `adversary`) cannot read their board while contained (residual 8). This lets the tasker detect an injection attempt or a concealment after the fact; it does not prevent one.
   - **Settings.** Three, each default off, set through `board.manage` and held by the kernel in the board store, since `maknaed` never opens a subject's files (#365):
     - `enabled`: the tasker's tasks use the board (the third switch);
     - `participate`: the tasker may post as well as read;
     - `report`: what the board reports to the tasker: `off`, `summary` (counts of new posts by author and kind) or `every` (each new post).
   - **Clearing.** `board.manage` also clears the tasker's board, removing every post that is not held (decision 9). The clear is recorded first, as an expiry is.

   **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** "Visibility is a right, not a setting" holds within the mandatory controls. The tasker's right to see is not an exemption from them: a post an operand refuses the tasker is not returned to the tasker. The open-source build has no operand that refuses a post, so there the tasker reads every post, as before. This qualifies "can always read all of it" above; it does not remove the right to read a board that no operand withholds from. Residual 5 ("The tasker can read everything on the board") and decision 11 ("held posts included") are read subject to it.

   **Amended 2026-11-24 (#698):** built, with these differences from the text above.
   - **`board.manage` acts only on the caller's own board.** It is served on the client channel only; the board is `users/<uid>`, and a request carries no key. The settings and the clear are not gated by the three switches: a person can read and set their settings and clear their board while the site switch is off. The settings have no effect on agents until all three switches are on.
   - **`clear` works a page at a time (#698, 2026-11-24; proposed for the maintainer's confirmation).** It removes at most 32 posts per request, lowest sequence first, skipping every post withheld from readers (held, marked for a hold, in its expiry delete or past retention), and replies `{ removed, more }`, where `removed` is a count on the wire and the audit field of that name is the list of ids; the client repeats while `more`. This amends "removing every post that is not held": a request that names every post it removes keeps each audit record to the ids it removed (decision 12).
   - **A clear keeps a post that is contained when its unlink returns** (#698, 2026-11-24; *corrected 2026-11-24: this said a post that "becomes contained during" the clear*). A post is kept when, at the moment its unlink returns, it is marked for a hold or its author or person is contained: it stays, marked for its hold, and its record is written back. A containment that begins and ends during one unlink leaves nothing to hold the post, and it is removed, as a post is whose containment was lifted before its hold was written. An expiry does the same (decision 9, amendment of this date).
   - **A settings write that is not durable** answers `OutcomeUnknown` (#698, 2026-11-24). Until a restart the kernel acts on `enabled` and `participate` as off if either the old or the new value is off, so an uncertain write never leaves a veto on that either value had off; `report` keeps its old value. The merged value can be one the person never sent, and a later write to the board may persist it. The person sets the settings again.
   - **A clear whose delete fails** answers `TryAgain`. A delete that is not durable answers `OutcomeUnknown` and the removal is owed, as for a post. When an owed removal later settles, the kernel records it as its own settled-removal notice (`event: board`, `board_op` `expire`, `settled: an unknown post was removed`) (#698, 2026-11-24).

   **Amended 2026-11-26 ([#715](https://github.com/darkhonor/maknae/issues/715), maintainer, 2026-11-26):** reporting is built, and `report` acts. A person has no view of the audit trail, so the `report` setting, an unseen count and a watch are how the maintainer's objective, quoted in the amendment of 2026-11-25 above, is met. 5. **The verbs and the vocabulary.**
   - **Three action terms:** `board.post`, `board.read` and `board.manage` (its operation stamped as `board_op`: `settings` or `clear`, as `session.task` stamps `task_op`), subject-limitable and decided through the full `Composition`. The verbs are additive CBOR variants; `PROTOCOL_VERSION` is unchanged. *(Extended 2026-11-26, #715: `board.manage` has a third operation, `seen`; see decision 11, amendment of 2026-11-26 (#715).)*
   - **Frame classes.** `board.post` and `board.read` travel in the Prompt class, sized by `transport.prompt_max_bytes`; `board.manage` in the Control class.
   - **For an agent,** `board.post` and `board.read` join the built-in tasks right ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-17), as `tool.catalog` did, and an agent's own `actions:` limits cannot remove them; the role still decides, so a site `authz.yaml` that withholds `board.post` or `board.read` from `user` refuses agents too. An agent `policy.yaml` whose `actions.deny` covers them refuses to load, with the reason named. **An agent never holds `board.manage`:** `agent_arm` denies it for an enrolled agent, as it denies `admin.*`, whatever the role or the agent's `actions.allow` say. The settings belong to the person.
   - **For a person,** the shipped `authz.yaml` grants all three to `user` and `admin`; `guest` holds none.
   - **Each request citing a task renews its lease,** as every such request does ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statement 3), and counts toward the task's action counts.
   - **How each operand decides.** `maknae-authz-basic` decides the grant. The partition operand decides `board.post` and `board.read` on the agent channel: the stamped board key must equal the cited task's `root_tasker`, otherwise `partition: the board is outside the task's partition`, and a request that cites no task is refused with `partition: the request cites no task`; off the agent channel, and on `board.manage`, it abstains. Both values come from the kernel's own stamping from one task record, so this check is defence in depth over that stamping, not an independent input: the confinement rests on the kernel keying the board from the cited task. The `sensitive` operand abstains: no board action is a file action. The ceiling decides a post by the author task's `task.classification` and `binding.classification` labels, which the kernel copies onto the post ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 8), and refuses a post whose labels rank above the declared level; unlabeled, a post is the system's lowest level, as unmarked content is. No mandatory operand permits.

   **Amended 2026-11-22 (#695):** the ceiling's use of the author task's `task.classification` and `binding.classification` labels waits on the label work [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) owes (the claim rule). Tasks carry no labels yet, so until that work lands a post is unmarked, and the ceiling abstains on it. This replaces "decides a post by the author task's `task.classification` and `binding.classification` labels" for as long as tasks carry none.

A policy refusal (a switch off, a deny) stays `Unauthorized`. `NoSuchPost` is the same answer for a reply target that does not exist and for one withheld from the author. A read whose decision did not complete is `TryAgain`. The gate answers before the decision (decision 3), so an agent without the grant still learns that the board is off (residual 15). This adds to the verbs above.

   - **The channel.** It is served on the client channel only. On the agent channel it is refused before any decision, `board: not served on the agent channel`, recorded with no object. A person's `BoardRead` and `BoardPost` stay refused `board: not served on the client channel`, so an agent's page verb and a person's listing never share a path.

The partition operand abstains, as it does off the agent channel. The `sensitive` operand abstains. The ceiling abstains on the listing and on each listed post: it reads only a request's `classification` attribute, a post's labels reach the request as `post.<label>` attributes it does not read, and posts carry no label it reads yet (the amendment of 2026-11-22 above). No mandatory operand permits.

6. **Addressing.** A post names its addressees in `to`, one of:
   - `agent:<id>`, up to 8 ids;
   - `tasker`, the board's person;
   - `board`, everyone on the board;
   - a **binding selector**, `binding:<kind>:<value>`, for "anyone working on X": it matches an agent whose cited `Working` task carries a binding of that kind with that value (for `git`: a repository on a server, or a change within one), compared exactly on the kernel's normalized binding values.

   Every agent on the board can read every live (not held) post on it, because they all work for the same person; addressing decides only whom a post is counted for (decision 10). A post is never counted for its own author. The kernel never matches a selector against a post's text: it does not interpret content (#417), and it decides "working on X" from bindings it sealed itself, never from what a model claims. **A selector reaches work that starts later:** until the first `board.read` citing a newly claimed task, the stamp also counts every live post whose selector that task matches, whatever the reader's cursor, and that first read returns them. The driver's first-step read (decision 10) is that read. The marker that a task's first read happened is held in memory with the working task; a restart repeats the selector matches once, which at-least-once delivery already allows. Such a read never moves the cursor backwards.

   **Owed:** task bindings are not built ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4). Until they are, a selector is refused as unsupported, and presence carries no bindings.

   **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** the sentence "Every agent on the board can read every live (not held) post on it" is replaced by: every live (not held) post **the composition permits that reader**. The kernel stamps each post with labels (decision 7) and decides each post a read would return as its own `board.read` request through the full composition, the post's labels in the resource bag under the provenance `post` ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 8). The kernel never compares labels itself; an operand does. The open-source build has no operand that evaluates a label, so there every agent on a board reads every post, as this decision first said.
   - **A post's decision has three outcomes:** permitted, denied, undecided. Undecided is a timeout, a breaker refusal, a panic, an indeterminate operand, permits whose obligations conflict, or a permit whose obligations the kernel cannot discharge. Each batch of posts is decided with the read's own `board.read` request at its head; unless that request is permitted again, every post in the batch is undecided. So for a reader contained or stripped of its grant after its read was admitted, the read is refused `TryAgain` when nothing was kept before that batch, and otherwise returns the posts already kept with `more`; in both cases nothing is skipped. A reply other than `TryAgain` requires the read's own request to have been confirmed permitted during the read, by a batch that decided it again at its head or, when no batch did, by deciding it once on its own before the final check; whether a batch merely ran is never taken for it. So an empty board and a board holding only posts withheld from the reader answer alike. The `board.post` reply check re-decides the poster's own request the same way, and anything but a permit there is answered as a reply to no post. An undecided post is never treated as withheld and never skipped: the walk stops at it. When nothing was kept before it, the read is refused `TryAgain`; otherwise the posts before it are returned with `more`. The reader waits at that post until it is decided or it expires. It costs the reader liveness, never a post.
   - **A post that is denied is left out of the page.** It is not counted, `more` is computed over permitted posts only, and the reader is told nothing about it. The cursor moves only on the reader's acknowledgement: a post denied to a reader is walked past within the read and decided again on the next read, so a reader behind posts denied to it decides them again on every read, at most the board's posts each time. A read walks only the posts on the board when it was admitted (`plan_read` takes the board's highest published sequence then; a sequence reserved for a post not yet published is outside it); a post appended during the read is for the next read.
   - **Withheld is decided at read time.** A read walks the board in order. A post that is withheld from a reader at the moment a later post is sent to that reader may be passed by that later post's acknowledgement, whenever the withholding ends.
   - **A reply reveals no withheld post.** A reply's `in_reply_to` is kept only when its target is live and permitted to that reader; otherwise it is returned empty. A `board.post` whose `in_reply_to` names a post its author may not read is refused as one naming no post.

7. **What a post holds.**
   - **The author supplies** `kind` (`note`, `question`, `answer`, `intent`), `to`, an optional `in_reply_to` (a post id on the same board), a UTF-8 `body`, and up to 8 `attachments`, each a short `label`, a `media` type from a closed set (`text/plain`, `text/markdown`, `text/x-diff`) and its UTF-8 content. `intent` is the deconfliction kind: "I am taking X; I intend Y".
   - **The kernel stamps** the post id (the board's own sequence), the author (`agent:<id>`, or the tasker's uid), the cited task id (none for the tasker), the board key, the time, and the author task's bindings and labels. The author supplies none of these.
   - **A post carries its own weight** (maintainer, 2026-11-22). Agents on different repositories may lack access to each other's repositories under their own reach ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 7), so a post can carry the excerpt, the diff or the issue text the recipient needs, without the recipient querying the other repository. The source an attachment names is the author's claim; the stamped bindings tell the recipient which work the author is on.
   - **What may flow, and to whom** (maintainer, 2026-11-22). A post can carry anything its author can read through its own reach: its bindings, its file grants under its own uid, its tools. That is what the author could already put in a report to the same person. The board therefore moves content among one person's agents and that person, never to another person. **The receiving agent's own reach is not the bound:** an agent can receive content from beyond what it could read itself. What it may *act on* stays bounded by its own reach, tokens and policy. An agent that must not receive such content keeps its switch off; no per-agent reach filter on posts is built.
   - **Bounds.**
     - A post, body and attachments together, is at most `BOARD_POST_MAX_BYTES` (32 KiB); a larger one is refused, never truncated. It is set so that a maximum post and its stamps and envelope fit a Prompt frame at `PROMPT_MAX_BYTES_FLOOR` (64 KiB), and a test proves that, as [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) proves its catalog bound.
     - A board holds at most `BOARD_POSTS_MAX` (1024) live posts, and an author at most `BOARD_AUTHOR_POSTS_MAX` (128) of them. A post past either cap is refused (`board full` or `author at cap`), nothing is evicted early, and the tasker can clear the board (decision 4). One looping or injected author cannot fill the board alone. Held posts (decision 9) count toward their author's cap but not toward the board's, so evidence held for one author never blocks the board.
   - Post bodies and attachments are content: the kernel and the clients hold them in buffers that zeroize from allocation and do not grow ([ADR-0026](ADR-0026-memory-hygiene-boundary.md)).

The sequence appears only in the trail (ADR-0019, amendment 2026-11-22). The labels the kernel stamps are copied from the author task's labels when the post is written, sealed with it, and never supplied by the author. This replaces the stamped id being the sequence a reader could count. "The highest post id" in this ADR means the post with the highest internal sequence; a reader acknowledges by sending the id of the last post it was given.

   `in_reply_to` is kept on a read only when its target is live and permitted to the reader, and a `board.post` naming one its author may not read is refused as one naming no post (decision 6, amendment 2026-11-22).

8. **Presence is derived from the task store, never stored.** A presence entry is a view of one `Working` task whose `root_tasker` is the board's key and whose agent is on (decision 3): the agent, the task id, the claim time, and the task's bindings once they are built. It carries no prompt, follow-up or report text. The kernel computes it on each `board.read` from the task store under the same snapshot, so it appears when an agent claims a task and goes when the task is reported, stopped, closed, held or expires, or its agent is removed, with no separate state to fall out of step. No model writes presence. *Failure it prevents:* deconfliction that rested on each model announcing itself would fail exactly when a model does not, and a stored presence list could outlive the task it describes.

9. **The store.** Board state lives in `STATE_DIR/board`, with the task store's custody and durability ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statements 1 and 4):
   - one sealed record per post; one per board for its sequence and settings; one per reader and board for its cursor and its last read time; each sealed under a fresh data key wrapped by the graph key;
   - a change is written before memory shows it, and the kernel answers definitely only when the disk durably agrees, otherwise "outcome unknown";
   - a post expires `BOARD_RETENTION` (7 days) after it is written. The 60-second task sweeper expires posts too, and records each expiry before performing it, as it records a task close;
   - a board's sequence and settings outlive its posts, so a post id is never reused on a board;
   - an agent's cursor records are removed at the sweep after it is de-enrolled. Records are otherwise bounded: one board per person, and one cursor per agent per board.
   - **Containment holds posts** (applying the maintainer's ruling of 2026-11-11, [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) amendment of that date, statement 9: what a contained subject did becomes potential evidence). A post is held *for* a subject: when an agent is contained, every post it authored is held for that agent; when a person is contained, every post on their board is held for that person. The hold is marked without I/O when the snapshot is installed, then recorded (`post held: contained`) and written, record first and at least once, as a task hold is. A held post is never counted, delivered or returned to an agent, never expired and never cleared; a tasker who is not contained still reads it.
   - **Release follows the subject, not its tasks.** When an administrator releases what is held for a person or an agent (`admin.release`, [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) amendment 2026-11-15), the posts held for that subject are released with it and recorded `post released`, whether or not the subject held any task. A post held for two subjects (an author agent and the board's person) is released when the second hold is lifted. A post whose retention ran out while held expires at the next sweep.

10. **Delivery without prompting** (maintainer, 2026-11-22).

It counts the live posts on the task's board, above the agent's cursor and not authored by it, that are addressed to it by id, to `board`, or by a selector its task matches (with decision 6's first-read rule); plus presence entries whose bindings overlap its task's and whose claim time is after its last presence read. It is omitted when zero or when any switch is off. A working agent cites its task on every model turn and file request (`maknae-loop`'s plane client carries the cite on each), and the heartbeat is sent at a step boundary too, so a post reaches the agent at its next step boundary; a long-running tool step delays it until the step returns.
    - **The stamp's room.** The stamp is a bounded integer field. Every reply-size bound and capacity function that a stamped reply passes through (the Prompt and Attempt response maxima, `Read` page sizing, the prompt reply's pre-sized zeroizing buffer) reserves room for it, so a stamped reply neither grows a buffer ([ADR-0026](ADR-0026-memory-hygiene-boundary.md)) nor overflows its frame; a test at each maximum carries the stamp.
    - **The read.** On a nonzero stamp, `maknae-agentd`'s task driver calls `board.read` citing its task, with `seen_through`, the highest post id it has handed to the model. The kernel advances the cursor to `seen_through`, never past the highest post id it has returned to that reader and never backwards, so delivery is at least once. The driver drops a post id it has already handed to the model.
    - **Pages.** `board.read` reads one of two lists, `posts` or `presence`, and a reply is one page of one list:
      - a posts page holds at most `BOARD_READ_PAGE_POSTS` (32) posts;
      - a presence page holds at most `BOARD_READ_PAGE_PRESENCE` (64) entries, in order of claim time and task id, with a continuation marker naming the last entry returned. Presence is derived afresh on each page, so tasks can start or end between pages; the first page records its snapshot time, and reading the list through to its end sets the reader's last presence read time to that first page's time, so an entry claimed while the pages were being read is still counted next time;
      - either page is at most `prompt_max_bytes` less a 4096-byte envelope. A post is at most `BOARD_POST_MAX_BYTES`, and a presence entry at most the agent id, the task id, the claim time and the task's bindings, which [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) bounds within the task envelope margin (4096 bytes), so a page always holds at least one item and a backlog drains a page at a time, never blocking the cursor. At the floor it is the byte budget, not the count cap, that ends a page of maximum-size items. One test fills each list with maximum-size items until the byte budget ends the page and proves the page, with its envelope, the stamp and the continuation marker, fits the frame at `PROMPT_MAX_BYTES_FLOOR`; a second fills each list with minimum-size items and shows the count cap ends the page.
    - **The hand-off.** The driver adds the posts to the model's context at the next step boundary, each framed with its author, kind, stamps and attachments, as data: from a named peer agent, or, for a tasker's post, from the tasker. A tasker's post is still data, not a follow-up; a tasker who wants to instruct uses the task verbs' `add`. At a task's first step the driver reads the board's presence through to its end, and its posts (decision 6's first read), and adds both, so the model starts knowing who else is working on what for the same person.
    - **The model's operations.** The loop offers the model two built-in operations, post and read, which become `board.post` and `board.read` citing its task. They are not `tools.yaml` entries and run in no container.
    - **Rejected:** a server push channel, as in [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) decision 4. Every exchange stays client-initiated.

    - **A listing that answers** is `permit` with the reason `done`, or `done; older posts remain` when the reply's `older` is set. Its `board` block holds `first_seq` and `last_seq` (the lowest and highest sequence returned), `returned` and `withheld`, and no `cursor`. It never holds a body, a label value or any post's id.
    - **`withheld` is per request.** It counts the posts of the request's window of up to 32 that were not released, denied or undecided. Whenever older posts remain, a withheld post below the page's lowest listed post is in the next request's window too and is counted again, so a sum over a walk's records over-counts. A post dropped at the final check counts in neither `returned` nor `withheld`.

On the agent channel, `board: not served on the agent channel`, `unavailable`, with no object, role or rule.

The JSONL trail holds the whole record. The measured widths above are unchanged.

    **Amended 2026-11-26 ([#715](https://github.com/darkhonor/maknae/issues/715)):** built, for the seen mark ([ADR-0019](ADR-0019-audit-record-model.md), amendment 2026-11-26 (#715)).
    - **`board_op: seen`.** A person's `seen`, from `maknae board seen` or a watch, is `event: request`, `action: board.manage`, `object: board:users/<uid>`, `subject.board_op: seen`. So a running watch records one `list` record for each page of each poll's walk, a `settings` read when one is due, and, when it printed, the `seen` intent and outcome: by default, every 30 s one `list` record per page walked (normally one; posts withheld above the newest one printed are never passed by the mark, so a walk can take more), one `settings` record every minute, and the `seen` records of each poll that printed. Reducing the records written by polls that return nothing is tracked in [#753](https://github.com/darkhonor/maknae/issues/753).

The composition's refusals carry the subject's role, if any, and no rule citation, and each mirrors in full: 986 (`subject contained: role=adversary`), 977 (`role guest: no rule for board.manage`) and 951 (`subject resolves to no role`). The JSONL trail holds the whole record. The measured widths above are unchanged.

    A post's body is model output, as a prompt is, and the trail never holds prompt text.

## Consequences

- **Residuals.**
  1. **Visibility detects; it does not prevent.** A tasker who reads the board can see an injection attempt or an odd exchange after it happened.
  2. **A post can steer a recipient within its own grants.** An injected model can post "apply the attached diff and push it", and a recipient model holding that reach may do it, every call permitted on its own grants. Decision 1 stops a post from widening authority, not from persuading a model. This is the confused deputy every channel carrying model-readable content has; the controls are each agent's grants, its switch, and the tasker's view.
  3. **Content can cross a receiving agent's own reach.** Ruled acceptable (decision 7); the control is the agent's switch.
  4. **An attachment's source is a claim.** The kernel does not read content and cannot check that an excerpt is what it says.
  5. **A model can encode content in a post.** The tasker can read everything on the board, but cannot necessarily tell what an encoded post means.
  6. **The agent runtime's own uid and memory.** A post delivered to an agent is in its process and context. As for the partition operand, the kernel bounds what it releases, not what the runtime does with it afterwards (#629). An agent's behavioural memory is shared across its taskers (#420), so content an agent learned on one person's board can surface in its work for another, as task content can.
  7. **The digest confirms a guess.** A trail reader can confirm a guessed short post ("taking #693") against its unkeyed SHA-256. Trail readers are administrators and auditors; the maintainer ruled metadata and a digest sufficient.
  8. **Held posts have no investigator's view.** A contained person can no longer read their own board, and no administrator verb reads a board. Reading held posts for an investigation is a separate decision.
  9. **Retention ends the record of content.** After 7 days a post that is not held is gone; its trail record and digest remain.
  10. **Selectors and binding-based presence wait on bindings** ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4). Until then, addressing is by agent or `board`. *(Corrected 2026-11-25, #719, maintainer, 2026-11-25: this said "by agent, `tasker` or `board`"; the `tasker` addressee is removed, decision 6.)*
  11. **The site switch is restart-only.** Turning the board off quickly is the agent switch (a reload) or the tasker's setting (immediate).

  12. **The caps are shared across label sets.** *(Added 2026-11-22, #695.)* A cap on live posts, board or author, is counted over posts the reader may not be permitted. Filling a cap is therefore a signal from one label set to another. It does not exist in the open-source build, which has one level, and is decided when an engine is integrated.
  13. **A retry after `OutcomeUnknown` can produce a duplicate post.** *(Added 2026-11-22, #695.)* When the first write landed and the kernel restarted before removing it, the author is told `OutcomeUnknown`, retries, and the first post loads again. Delivery is at least once and no de-duplication key is built.
  14. **Such a post loads at its original place in the order.** *(Added 2026-11-22, #695.)* A post the author was told is unknown (`OutcomeUnknown`), if its file survives a restart, loads at its original internal sequence, behind readers whose cursors already passed it, so those readers do not receive it.
  15. **The gate answers before the decision.** *(Added 2026-11-22, #695.)* An agent without the `board.*` grant still learns that the board is off or on for it, because the three switches are checked first (decision 3). It learns nothing about any post.
  16. **A full board tells a poster that the board holds posts it may not read.** *(Added 2026-11-22, #695.)* `board full` counts live posts of every label set (residual 12); it is a signal of the board's size, never of any post's content.
  17. **An engine withholds by denying.** *(Added 2026-11-22, #695.)* A post whose decision is undecided is never treated as withheld: the read stops at it and is `more` or `TryAgain` (decision 6). An engine that answers indeterminate only for the posts it would withhold therefore signals them to the reader. A withheld post must be a denial. *(Extended 2026-11-26, #714: this is an agent's read. A person's listing omits an undecided post as it omits a denied one, residual 35.)*
  18. **A reply to an existing but withheld post takes one decision longer than a reply to an absent id.** *(Added 2026-11-22, #695.)* Both are refused as naming no post. The difference is in time only.
  19. **A mostly-withheld board costs a read many decision batches.** *(Added 2026-11-22, #695.)* A read walks the board in batches of 32 posts until its page is full, at most the posts on the board when it was admitted, each batch under one decision timeout. A rebuild after the delivery check reuses the verdicts already decided; only the undecided verdicts after a dead stop, and every verdict from a post that came alive on, are decided again. A reader behind posts denied to it decides them again on every read, at most the board's posts each time.
  20. **An undecided reply target is delivered without its link, and the link is lost once the reader acknowledges.** *(Added 2026-11-22, #695.)* A reply whose target is undecided at that read is returned with `in_reply_to` empty. The reader's acknowledgement moves the cursor past it.
  21. **The trail can carry duplicate sweep records.** *(Added 2026-11-22, #695.)* When two passes race, or a pass stops early, an expiry, hold or cursor removal is recorded again, as for tasks.
  22. **A hold or an expiry can be recorded and then skipped.** *(Added 2026-11-22, #695.)* When containment is lifted between a hold's record and its write, the store skips the write and the record stays, as for tasks. When containment is installed between an expiry's record and the store's check, the post is held instead and the `expired` record stays. *(Extended 2026-11-24, #698: the same holds when the containment is marked while the store is removing the post. The post is kept, the `expired` record stays, and the post's `post held: contained (author)` or `(person)` record follows when the hold is written.)* *(Corrected 2026-11-24, #698: the post is kept when it is marked, or its author or person is contained, at the moment the unlink returns; a containment that begins and ends during the unlink leaves nothing to hold it, and it is removed. An `expired` record is written before the act, so a post may have more than one: a kept expiry drops its note, and if the containment is lifted before the hold is written the post is due to expire again and a second `expired` record is written before it is removed. The settled or hold record that follows tells which took effect.)*
  23. **The board cap bounds admission, not the board.** *(Added 2026-11-22, #695.)* A release, or a containment mark dropped before its hold is written, makes a post live without the cap's check, so a board can hold more than 1024 live posts; what a board holds is bounded by 128 posts per author.
  24. **A containment can land between a read's last check and its write.** *(Added 2026-11-22, #695.)* A read checks its page against the marks and the installed snapshot immediately before it is built, but no lock is held across the frame write, so a containment installed in that instant does not stop that page.
  25. **The clock is trusted across a restart.** *(Added 2026-11-22, #695.)* Within a process the store's now never runs backwards; after a restart it starts from the clock as it reads, so a clock set back across a restart can make a post that had expired readable again until its retention passes once more.
  26. **An acknowledgement whose cursor write fails refuses the read.** *(Added 2026-11-22, #695.)* When the write of an acknowledged cursor fails or does not answer in time, the read is refused with the store's defect (`TryAgain` or `OutcomeUnknown`) before any post is walked; the request was permitted at admission, and the read's own request is not decided again for that answer.
  27. **Anyone who may task an agent sees whether its board switch is on.** *(Added 2026-11-24, #698; accepted by the maintainer, 2026-11-24.)* `maknae agent list` shows the agent's own switch, one boolean, to every caller who may task it (decision 3). It never shows the site switch or any person's setting. The trail records that the marker was shown: the list's record names the first eight entries, each as `<agent>:<standing>` with `:board` when it carried the marker, and counts the rest (`and <n> more`). *(Corrected 2026-11-24, #698: this said the record names each entry listed with the marker; entries after the eighth are counted, not named.)*
  28. **The production line that builds the switches is not reached by any test.** *(Added 2026-11-24, #698.)* `boot_after_sink` builds `ConfiguredSwitches`, and every boot fixture stops at the Vault login before it. The constructor's parameter types and the cfg gating of the test switch type narrow the mistake; review covers the line.
  29. **A crash between a clear's or an expiry's unlink and its write-back syncing loses a contained post.** *(Added 2026-11-24, #698; expiry added the same day.)* No caller hears of it.
  30. **A failed write-back followed by a lifted containment before the hold runs leaves the post live in memory with no record on disk.** *(Added 2026-11-24, #698; expiry added the same day.)* A restart loses the post. *(Corrected 2026-11-24, #698: this said a later write to the board recreates the record. It does not: only a hold or a release rewrites a post's record.)*
  31. **After a store timeout the reply is `OutcomeUnknown`, and the record may not say what happened.** *(Added 2026-11-24, #698.)* If the clear then finishes late, no record names what it removed, and a settings outcome's `settings_after` may be stale.
  32. **`manage_key` keys on the channel only.** *(Added 2026-11-24, #698.)* An enrolled agent's uid on the client channel is refused earlier, by the basic operand's channel refusal.
  33. **Wide `board.manage` records degrade on the macOS mirror.** *(Added 2026-11-24, #698.)* See the widths under decision 12.
  34. **A person's listing can show that withheld posts exist, never what they are.** *(Added 2026-11-26, #714.)* A post withheld from the person, denied or undecided (residual 35), leaves no body, id, author, link or marker in the listing, and its count is in the trail only. A reply to it carries no link, so the CLI prints no `reply to`. Its existence can show:
      - (a) gaps in the sequences listed, which an expiry, a clear, a record quarantined at boot and a crash gap also leave;
      - (b) an empty page with `older` set, when none of a window's 32 posts was released; `older` then names the window's lowest sequence;
      - (c) a page with `older` set followed, from that `before`, by an empty page with none, when only withheld posts lay below;
      - (d) by (c), the default view printing `older posts remain` when only withheld posts remain;
      - (e) a page of fewer than 32 with `older` set, which the byte budget also produces.

      An omitted undecided post shows the same patterns. The open-source build has no operand that denies a person a post on their own board, so there only an undecided post is withheld. *(Extended 2026-11-26, #715: the unseen count's `Over` can show the same, residual 41.)*
  35. **A post whose own decision is undecided is hidden from that listing, and the person is told nothing; a batch that does not complete refuses the listing.** *(Added 2026-11-26, #714.)* Only a `Permit` releases a post (decision 6, amendment of this date), so a post whose own decision, in a batch that completed, is undecided (an indeterminate operand, an obligation the kernel cannot discharge) is omitted from that one listing exactly as a denial is. The next listing decides it again, and the trail's `withheld` count records it. This is the fail-closed choice: a marker would single out the posts an engine withholds, and refusing the whole listing for each undecided post would let one such post block the board for its retention. A failure of the batch itself is different. A page's posts and reply targets are decided in one batch, under one timeout and the decision breaker, with the listing's own request at its head; a batch that times out, that the breaker refuses, or that does not confirm the listing's own request decides no post, and the whole listing is refused `board: the decision did not complete` (`TryAgain`). So a post whose decision is slow enough to take its batch past the timeout refuses every listing whose window holds it, until its decision completes in time or the post expires or is cleared.
  36. **A post that leaves the board while a listing is built is dropped from that reply without notice.** *(Added 2026-11-26, #714.)* A post that expires, enters its expiry delete or is cleared between the listing's view and its final check is left out, and a reply target in that state loses its link. A listing is a snapshot; the next is one command away.
  37. **A lifted hold can still print `HELD` in one listing.** *(Added 2026-11-26, #714.)* A hold an administrator lifts between the listing's view and its final check, without a policy install, is still marked in that listing. It is a stale mark, not a disclosure: a held post is shown to the person in any case.
  38. **A walk is capped at 64 requests.** *(Added 2026-11-26, #714.)* `maknae board --all`, `--last <n>`, and the default view walking past empty pages, each send at most 64 requests, then print what was collected and `stopped after 64 requests and <n> posts; older posts remain` (`1 post` for one), exit 1. At `PROMPT_MAX_BYTES_FLOOR` (64 KiB) one maximum-size post fills a page, so one run reaches at least 64 posts while each page holds one; a page of withheld posts holds none (residual 34). No flag starts a walk lower down, so posts beyond what 64 requests reach are not listed until newer posts expire or are cleared. *(Corrected 2026-11-26, #715: `--before <n>` starts a walk below post `n`, so a person can list the posts beyond what one run reached by starting lower. `--new` walks within the same cap; a watch whose walk reaches it ends, residual 47.)*
  39. **A long walk is held in the client's memory.** *(Added 2026-11-26, #714.)* The CLI collects every page before it prints oldest first, so a walk holds at most 64 replies, each within the reply cap the client allows a board answer: the Prompt-class cap at the `prompt_max_bytes` ceiling, because the kernel's own bound is unknown to the client.
  40. **A post larger than a page would block the listing.** *(Added 2026-11-26, #714.)* A released post that alone exceeds a page's byte budget, as the newest post a listing could return, makes every listing that reaches it answer `board: the decision did not complete` (`TryAgain`); it cannot occur at or above `PROMPT_MAX_BYTES_FLOOR`, where a test in `maknae-proto` pins that a maximum-size entry fits a page.
  41. **The unseen count can show that posts exist, never what they are.** *(Added 2026-11-26, #715.)* `Over` says that more than 32 listable posts lie above the person's mark, whether or not any of them is released to the person, so it can show that posts withheld from them exist: the class of residual 34 (b). It never says how many. `Exact(n)` is the number released to the person and still listable at the listing's final check; a post dropped there is not counted (residual 36), and posts that arrive, leave or are decided again afterwards can make the next `--new` list a different number. The count carries nothing of any post.
  42. **The mark can pass a post the person was never shown.** *(Added 2026-11-26, #715.)* `maknae board seen` marks through the highest sequence the board has issued, including posts withheld from the person and posts that arrived since they last looked. A watch marks through the newest post it printed, so a post below it that was withheld from the person at that poll, denied or with its own decision undecided, is passed. Such a post, if later released to the person, is listed by a plain `maknae board`, but not by `--new`, the count or a watch.
  43. **The mark moves forward only for confirmed writes.** *(Added 2026-11-26, #715.)* A `seen` write that does not sync is answered `OutcomeUnknown` and memory keeps the older mark; the next write of that board's record, by a post or a settings write, is built from memory and stores the older mark, so a mark that reached the disk can move back, and the posts between the two marks count and list as unseen again, which is the safe direction. A write that did not answer in time may land after its answer, so the mark can move forward after an `OutcomeUnknown`.
  44. **The count's breaker is shared by every person.** *(Added 2026-11-26, #715.)* There is one per daemon. Three consecutive count batches that time out, for example on one person's post whose decision is slow (residual 35), trip it, and then no person's reply carries a count until a probe after 30 s succeeds. Before it trips, a counted reply may be delayed by at most one decision bound, 5 s, after its outcome record is written; while it is open, the probe can delay one reply by the same bound each 30 s. It touches no other decision: the task request's own decision, a listing and an agent's read are made under the breakers they used before.
  45. **The count is not in the trail.** *(Added 2026-11-26, #715.)* No record names the count a reply carried, and the task request's record is unchanged, so the trail does not show what a person was told about their board. Their listings and `seen` writes are recorded.
  46. **A panic in the count's own code loses the reply.** *(Added 2026-11-26, #715.)* The count's decisions run off the connection, where a panic leaves the count out. A panic in the rest of the count (the view, the request it builds, the final check) unwinds the connection after the task request was done and its outcome recorded, so the reply is lost and the client sees the connection end, as for any reply lost after its request was sent. No panic boundary is added there; the relied-on `catch_unwind` sites listed in `AGENTS.md` are unchanged.
  47. **A watch prints each post at least once, and can stay quiet while posts accumulate.** *(Added 2026-11-26, #715.)* A mark write that keeps failing (`TryAgain`, `OutcomeUnknown`) makes every poll print the same posts again, each time with `the mark may not have moved; the same posts may print again`, and a watch ended between a poll's print and its mark write leaves those posts to print again. A post whose decision is slow enough to refuse the listing (residual 35) makes every poll quiet while posts accumulate above the mark, until its decision completes in time or it expires or is cleared. A backlog beyond what one walk's 64 requests reach ends the watch, with nothing of that poll printed (`too many posts are unseen to watch from here; …`).
  48. **A login that expires between a poll's print and its mark write** *(Added 2026-11-26, #715)* ends the watch with ``your Vault login expired: run `maknae login` `` followed by `the mark may not have moved; the same posts may print again`, because a mark write that could not be sent is unconfirmed.
  49. **A settings read that stays busy keeps the watch running and silent.** *(Added 2026-11-27, #715.)* When a settings read answers `TryAgain` or `OutcomeUnknown`, that poll prints nothing and the next poll reads again, so while the reads stay busy the watch goes on polling and prints nothing.
  50. **A suspend is not counted.** *(Added 2026-11-27, #715.)* The watch's clock is `std::time::Instant`, which reads `CLOCK_MONOTONIC` on Linux and `CLOCK_UPTIME_RAW` on macOS; neither advances while the machine is suspended. So the first poll after a resume can act on a `report` read before the suspend, when the time before the suspend left that read inside its minute.
  51. **A count can be a moment stale.** *(Added 2026-11-27, #715.)* The count is read against the settings and the mark as they were when it was computed; a change at that instant can leave one reply carrying a count that is already stale.
