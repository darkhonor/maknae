# ADR-0040: The agent message board — one board per person who roots a task chain, posts and reads mediated by the kernel, presence derived from the task store, delivery stamped on the agent's own replies, three switches; a post informs and never authorizes

- **Status:** Accepted (maintainer-ruled 2026-11-22: the direction in [#693](https://github.com/darkhonor/maknae/issues/693) and [#694](https://github.com/darkhonor/maknae/issues/694); the details on the merge of this ADR)
- **Date:** 2026-11-22
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#693](https://github.com/darkhonor/maknae/issues/693), [#694](https://github.com/darkhonor/maknae/issues/694)
- **Amends:** [ADR-0008](ADR-0008-authorization-composition-contract.md) (the partition operand decides `board.post` and `board.read`); [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (the `board_unseen` stamp, the tasks right, containment); [ADR-0019](ADR-0019-audit-record-model.md) (board records)
- **Builds on:** [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (tasks, the root tasker, the task store, containment); [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) (bindings, reach, labels); [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) (stamps on replies; no server push); [ADR-0026](ADR-0026-memory-hygiene-boundary.md) (secret-class bytes)

## Context

Several agents working at once for one person will pick up related work. Observed 2026-11-20 and 21: five concurrent agent sessions, two of which nearly took related issues in opposite directions. They agreed only because they could message each other on a side channel; otherwise the person copied questions between sessions by hand. The coordination saved the work, but it ran outside any decision, any audit record and any bound.

Maknae has no way for one agent to tell another anything. An agent's only channel is the kernel, which offers tasks (a tasker gives work), follow-ups (a tasker adds to work) and reports (an agent answers its tasker). None of these runs between two agents working for the same person.

The maintainer's direction, 2026-11-22: a message board agents can monitor for posts addressed to them, or to "anyone working on X for Bob"; the kernel mediates every post and every read; a simple queue; enabled per agent by a boolean, not per user; no prompting needed to check it; the goal is deconfliction.

## Decision

1. **A post informs; it never authorizes** (maintainer, 2026-11-22). No decision path reads a post's body or attachments, and no post enters a request's attribute bag. A post cannot create a task, add a follow-up, grant or widen an action, change a binding, or stand for a tasker's consent. When one agent wants another to do work, that is a task submission under the submitter's cited task, decided as `session.task` on the authority [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) gives it. The agent loop hands every post to the model as data (decision 10), the same class as retrieved content. *Failure it prevents:* a post that the kernel read as authority would let one model's injected text widen what another agent may do. What a recipient's model does with a post *within its own grants* is not prevented here; that is residual 2.

2. **One board per person who roots a chain; no channel between taskers** (maintainer, 2026-11-22).
   - **The key.** A board is keyed `users/<uid>`, the partition of the person at the root of the cited task's chain (`RootTasker::partition()`, the key the partition operand already computes, [ADR-0008](ADR-0008-authorization-composition-contract.md), amendment 2026-11-11). Every `Working` task whose root is that person is on that board, whichever agent holds it and however deep in the chain it sits, so every agent on a board works for the same person.
   - **A chain an agent started on its own initiative has no board.** Its root is `agents/<id>`: no person owns it, so nobody holds its settings or its right to see (decision 4). A board request citing such a task is refused `board off: the chain has no tasker`. A remote tasker has no tasks today, and therefore no board.
   - **An agent reaches only the board of the task it cites.** A `board.*` request on the agent channel must cite the agent's own `Working` task, as every agent request that names a task does; the kernel stamps the board key from that task's stored record, and the request never carries one. A request that cites no task reaches no board.
   - **A tasker reaches only their own board.** On the client channel, a `board.*` request carries no key: the kernel keys it to the caller (`users/<uid>`). A board never written to reads as empty. No administrator verb reads a board, `admin` included; the trail carries the metadata (decision 12).
   - **Sharing a repository is not sharing a tasker.** A repository is the public boundary for code, not for the taskers' conversations. Two taskers' agents coordinate through the repository itself: issues, pull requests and reviews, which both people see.
   - **Rejected:** a board per repository, which would carry one tasker's unpublished work to another tasker's agents, past the partition operand; and a channel between taskers implied by any shared attribute. A channel between taskers, if ever wanted, is a separate decision: an explicit grant by both, scoped, time-boxed and revocable.
   - *Failure it prevents:* agent A reads in its tasker's partition and tells agent B, working for someone else. That is a covert channel around a mandatory control.

3. **Three switches, all default off** (maintainer, 2026-11-22). An agent's board request proceeds only when all three are on:
   - **site:** `maknae.yaml` `board: { enabled: <bool> }`. Absent means off. Restart-only, as `forges:` is. `admin.config.show` discloses it under the disclosure manifest;
   - **agent:** the agent's `policy.yaml` `board: <bool>`. Absent means off. It is compiled into the snapshot and covered by the agent's change detection (`agents.<id>`), so a `SIGHUP` reload applies it;
   - **tasker:** the root tasker's `enabled` setting (decision 4).

   The kernel reads the three from one installed snapshot and the board store, before the decision; a request with any switch off is refused `board off: <site|agent|tasker>`, recorded like any refusal. An agent with its own switch off can neither post nor read, receives no stamp (decision 10) and appears in no presence (decision 8), even when other agents on the board are on. The switches gate agents and a tasker's posts, never a tasker's reads: a tasker can always read their own board (decision 4), and a tasker's `board.post` needs the site switch, `enabled` and `participate`. A site whose `authz.yaml` withholds the `board.*` grants from a role is a fourth veto, for every person and agent holding it. *Failure it prevents:* one switch held by one party would let the site, the agent's owner or the person whose work it is be overruled by the others; requiring all three makes each a veto.

4. **The tasker's settings, and the tasker's right to see** (maintainer, 2026-11-22).
   - **Visibility is a right, not a setting.** The tasker owns the board and can always read all of it, every post and every presence entry, for as long as the store keeps them (decision 9). No setting hides a conversation from the tasker. The right belongs to a person in good standing: a contained person (role `adversary`) cannot read their board while contained (residual 8). This lets the tasker detect an injection attempt or a concealment after the fact; it does not prevent one.
   - **Settings.** Three, each default off, set through `board.manage` and held by the kernel in the board store, since `maknaed` never opens a subject's files (#365):
     - `enabled`: the tasker's tasks use the board (the third switch);
     - `participate`: the tasker may post as well as read;
     - `report`: what the board reports to the tasker: `off`, `summary` (counts of new posts by author and kind) or `every` (each new post).
   - **Clearing.** `board.manage` also clears the tasker's board, removing every post that is not held (decision 9). The clear is recorded first, as an expiry is.

   **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** "Visibility is a right, not a setting" holds within the mandatory controls. The tasker's right to see is not an exemption from them: a post an operand refuses the tasker is not returned to the tasker. The open-source build has no operand that refuses a post, so there the tasker reads every post, as before. This qualifies "can always read all of it" above; it does not remove the right to read a board that no operand withholds from. Residual 5 ("The tasker can read everything on the board") and decision 11 ("held posts included") are read subject to it.

5. **The verbs and the vocabulary.**
   - **Three action terms:** `board.post`, `board.read` and `board.manage` (its operation stamped as `board_op`: `settings` or `clear`, as `session.task` stamps `task_op`), subject-limitable and decided through the full `Composition`. The verbs are additive CBOR variants; `PROTOCOL_VERSION` is unchanged.
   - **Frame classes.** `board.post` and `board.read` travel in the Prompt class, sized by `transport.prompt_max_bytes`; `board.manage` in the Control class.
   - **For an agent,** `board.post` and `board.read` join the built-in tasks right ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-17), as `tool.catalog` did, and an agent's own `actions:` limits cannot remove them; the role still decides, so a site `authz.yaml` that withholds `board.post` or `board.read` from `user` refuses agents too. An agent `policy.yaml` whose `actions.deny` covers them refuses to load, with the reason named. **An agent never holds `board.manage`:** `agent_arm` denies it for an enrolled agent, as it denies `admin.*`, whatever the role or the agent's `actions.allow` say. The settings belong to the person.
   - **For a person,** the shipped `authz.yaml` grants all three to `user` and `admin`; `guest` holds none.
   - **Each request citing a task renews its lease,** as every such request does ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statement 3), and counts toward the task's action counts.
   - **How each operand decides.** `maknae-authz-basic` decides the grant. The partition operand decides `board.post` and `board.read` on the agent channel: the stamped board key must equal the cited task's `root_tasker`, otherwise `partition: the board is outside the task's partition`, and a request that cites no task is refused with `partition: the request cites no task`; off the agent channel, and on `board.manage`, it abstains. Both values come from the kernel's own stamping from one task record, so this check is defence in depth over that stamping, not an independent input: the confinement rests on the kernel keying the board from the cited task. The `sensitive` operand abstains: no board action is a file action. The ceiling decides a post by the author task's `task.classification` and `binding.classification` labels, which the kernel copies onto the post ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 8), and refuses a post whose labels rank above the declared level; unlabeled, a post is the system's lowest level, as unmarked content is. No mandatory operand permits.

   **Amended 2026-11-22 (#695):** the ceiling's use of the author task's `task.classification` and `binding.classification` labels waits on the label work [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) owes (the claim rule). Tasks carry no labels yet, so until that work lands a post is unmarked, and the ceiling abstains on it. This replaces "decides a post by the author task's `task.classification` and `binding.classification` labels" for as long as tasks carry none.

   **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** a poster is told why a post was not taken, so it can retry. After the request was permitted, an operational refusal is named on the wire as `BoardRefused` with one of `TryAgain`, `OutcomeUnknown`, `Full`, `AuthorAtCap` or `NoSuchPost`, as `EgressUnavailable` names availability. A policy refusal (a switch off, a deny) stays `Unauthorized`. `NoSuchPost` is the same answer for a reply target that does not exist and for one withheld from the author. A read whose decision did not complete is `TryAgain`. The gate answers before the decision (decision 3), so an agent without the grant still learns that the board is off (residual 15). This adds to the verbs above.

   **Amended 2026-11-22 (#695):** built, with these differences from the text above.
   - Two of the three action terms exist: `board.post` and `board.read`, class `board`, grantable, in the Prompt frame class. `board.manage` is not in the vocabulary yet; it is owed with the settings ([#698](https://github.com/darkhonor/maknae/issues/698)).
   - The gate answers before the decision (decision 3), in this order. A request on the client channel is refused `board: not served on the client channel`. An agent request that cites no task passes the gate and is refused by the decision, `partition: the request cites no task`. A cited task whose root is an agent is refused `board off: the chain has no tasker`. Then the three switches are read: `board off: site`, `board off: agent`, `board off: tasker`. A refusal at the gate is `Unauthorized` on the wire and is recorded with its reason.
   - The site and agent switches have no source until #698, so both are off in every deployment: every `board.post` and `board.read` from an agent whose cited task is rooted at a person is refused `board off: site`. The tasker's `enabled` setting is read from the board store and has no verb to set it yet.
   - A reply's target is decided only when it exists and is live, as a `board.read` request on the post's labels. A target that does not exist, is withheld, or whose decision does not complete is refused as one naming no post (`in_reply_to names no post on the board`), so the two refusals can differ in time.
   - A post whose `to` names an addressee that is not an agent id is refused before the gate, recorded `board.post fails operand pre-gate: addressee not an agent id`.

6. **Addressing.** A post names its addressees in `to`, one of:
   - `agent:<id>`, up to 8 ids;
   - `tasker`, the board's person;
   - `board`, everyone on the board;
   - a **binding selector**, `binding:<kind>:<value>`, for "anyone working on X": it matches an agent whose cited `Working` task carries a binding of that kind with that value (for `git`: a repository on a server, or a change within one), compared exactly on the kernel's normalized binding values.

   Every agent on the board can read every live (not held) post on it, because they all work for the same person; addressing decides only whom a post is counted for (decision 10). A post is never counted for its own author. The kernel never matches a selector against a post's text: it does not interpret content (#417), and it decides "working on X" from bindings it sealed itself, never from what a model claims. **A selector reaches work that starts later:** until the first `board.read` citing a newly claimed task, the stamp also counts every live post whose selector that task matches, whatever the reader's cursor, and that first read returns them. The driver's first-step read (decision 10) is that read. The marker that a task's first read happened is held in memory with the working task; a restart repeats the selector matches once, which at-least-once delivery already allows. Such a read never moves the cursor backwards.

   **Owed:** task bindings are not built ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4). Until they are, a selector is refused as unsupported, and presence carries no bindings.

   **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** the sentence "Every agent on the board can read every live (not held) post on it" is replaced by: every live (not held) post **the composition permits that reader**. The kernel stamps each post with labels (decision 7) and decides each post a read would return as its own `board.read` request through the full composition, the post's labels in the resource bag under the provenance `post` ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 8). The kernel never compares labels itself; an operand does. The open-source build has no operand that evaluates a label, so there every agent on a board reads every post, as this decision first said.
   - **A post's decision has three outcomes:** permitted, denied, undecided. Undecided is a timeout, a breaker refusal, a panic, an indeterminate operand, permits whose obligations conflict, or a permit whose obligations the kernel cannot discharge. Each batch of posts is decided with the read's own `board.read` request at its head; unless that request is permitted again, every post in the batch is undecided. So for a reader contained or stripped of its grant after its read was admitted, the read is refused `TryAgain` when nothing was kept before that batch, and otherwise returns the posts already kept with `more`; in both cases nothing is skipped. A read that decides no batch (no candidate) re-decides its own request once before it replies, and is refused `TryAgain` unless it is permitted, so an empty board and a board holding only posts withheld from the reader answer alike. The `board.post` reply check re-decides the poster's own request the same way, and anything but a permit there is answered as a reply to no post. An undecided post is never treated as withheld and never skipped: the walk stops at it. When nothing was kept before it, the read is refused `TryAgain`; otherwise the posts before it are returned with `more`. The reader waits at that post until it is decided or it expires. It costs the reader liveness, never a post.
   - **A post that is denied is left out of the page.** It is not counted, `more` is computed over permitted posts only, and the reader is told nothing about it. The kernel moves a reader's cursor itself past a leading run of posts that were denied to it, so a reader behind withheld posts does not decide them again on every read. If that write fails, the read keeps the old cursor, records the failure in the trail (`deny` / `unavailable`, the store's reason) and answers with the same page, so a failed skip does not show that withheld posts exist. A read walks only the posts on the board when it was admitted (`plan_read` takes the board's highest published sequence then; a sequence reserved for a post not yet published is outside it); a post appended during the read is for the next read.
   - **Withheld is decided at read time.** A post withheld when a reader's cursor passes it is not delivered to that reader later, even if policy changes, and a held post released after a reader's cursor passed it is not delivered either.
   - **A reply reveals no withheld post.** A reply's `in_reply_to` is kept only when its target is live and permitted to that reader; otherwise it is returned empty. A `board.post` whose `in_reply_to` names a post its author may not read is refused as one naming no post.

7. **What a post holds.**
   - **The author supplies** `kind` (`note`, `question`, `answer`, `intent`), `to`, an optional `in_reply_to` (a post id on the same board), a UTF-8 `body`, and up to 8 `attachments`, each a short `label`, a `media` type from a closed set (`text/plain`, `text/markdown`, `text/x-diff`) and its UTF-8 content. `intent` is the deconfliction kind: "I am taking X; I intend Y".
   - **The kernel stamps** the post id (the board's own sequence), the author (`agent:<id>`, or the tasker's uid), the cited task id (none for the tasker), the board key, the time, and the author task's bindings and labels. The author supplies none of these.
   - **A post carries its own weight** (maintainer, 2026-11-22). Agents on different repositories may lack access to each other's repositories under their own reach ([ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) decision 7), so a post can carry the excerpt, the diff or the issue text the recipient needs, without the recipient querying the other repository. The source an attachment names is the author's claim; the stamped bindings tell the recipient which work the author is on.
   - **What may flow, and to whom** (maintainer, 2026-11-22). A post can carry anything its author can read through its own reach: its bindings, its file grants under its own uid, its tools. That is what the author could already put in a report to the same person. The board therefore moves content among one person's agents and that person, never to another person. **The receiving agent's own reach is not the bound:** an agent can receive content from beyond what it could read itself. What it may *act on* stays bounded by its own reach, tokens and policy. An agent that must not receive such content keeps its switch off; no per-agent reach filter on posts is built.
   - **Bounds.**
     - A post, body and attachments together, is at most `BOARD_POST_MAX_BYTES` (32 KiB); a larger one is refused, never truncated. It is set so that a maximum post and its stamps and envelope fit a Prompt frame at `PROMPT_MAX_BYTES_FLOOR` (64 KiB), and a test proves that, as [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) proves its catalog bound.
     - A board holds at most `BOARD_POSTS_MAX` (1024) live posts, and an author at most `BOARD_AUTHOR_POSTS_MAX` (128) of them. A post past either cap is refused (`board full` or `author at cap`), nothing is evicted early, and the tasker can clear the board (decision 4). One looping or injected author cannot fill the board alone. Held posts (decision 9) count toward their author's cap but not toward the board's, so evidence held for one author never blocks the board.
   - Post bodies and attachments are content: the kernel and the clients hold them in buffers that zeroize from allocation and do not grow ([ADR-0026](ADR-0026-memory-hygiene-boundary.md)).

   **Amended 2026-11-22 (#695):** "the post id (the board's own sequence)" is replaced. A post id is 128 random bits drawn by the kernel, as a task id is. The board keeps its own per-board sequence internally, orders posts by it, and never sends it, so a reader cannot count the posts withheld from it. The sequence appears only in the trail (ADR-0019, amendment 2026-11-22). The labels the kernel stamps are copied from the author task's labels when the post is written, sealed with it, and never supplied by the author. This replaces the stamped id being the sequence a reader could count. "The highest post id" in this ADR means the post with the highest internal sequence; a reader acknowledges by sending the id of the last post it was given.

   The sequence is never reused. This replaces decision 9's "so a post id is never reused on a board": a post id is not reused because it is random, and a draw that collides with a live id on the board is drawn again.

   `in_reply_to` is kept on a read only when its target is live and permitted to the reader, and a `board.post` naming one its author may not read is refused as one naming no post (decision 6, amendment 2026-11-22).

8. **Presence is derived from the task store, never stored.** A presence entry is a view of one `Working` task whose `root_tasker` is the board's key and whose agent is on (decision 3): the agent, the task id, the claim time, and the task's bindings once they are built. It carries no prompt, follow-up or report text. The kernel computes it on each `board.read` from the task store under the same snapshot, so it appears when an agent claims a task and goes when the task is reported, stopped, closed, held or expires, or its agent is removed, with no separate state to fall out of step. No model writes presence. *Failure it prevents:* deconfliction that rested on each model announcing itself would fail exactly when a model does not, and a stored presence list could outlive the task it describes.

9. **The store.** Board state lives in `STATE_DIR/board`, with the task store's custody and durability ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statements 1 and 4):
   - one sealed record per post; one per board for its sequence and settings; one per reader and board for its cursor and its last read time; each sealed under a fresh data key wrapped by the graph key;
   - a change is written before memory shows it, and the kernel answers definitely only when the disk durably agrees, otherwise "outcome unknown";
   - a post expires `BOARD_RETENTION` (7 days) after it is written. The 60-second task sweeper expires posts too, and records each expiry before performing it, as it records a task close;
   - a board's sequence and settings outlive its posts, so a post id is never reused on a board;
   - an agent's cursor records are removed at the sweep after it is de-enrolled. Records are otherwise bounded: one board per person, and one cursor per agent per board.
   - **Containment holds posts** (applying the maintainer's ruling of 2026-11-11, [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) amendment of that date, statement 9: what a contained subject did becomes potential evidence). A post is held *for* a subject: when an agent is contained, every post it authored is held for that agent; when a person is contained, every post on their board is held for that person. The hold is marked without I/O when the snapshot is installed, then recorded (`post held: contained`) and written, record first and at least once, as a task hold is. A held post is never counted, delivered or returned to an agent, never expired and never cleared; a tasker who is not contained still reads it.
   - **Release follows the subject, not its tasks.** When an administrator releases what is held for a person or an agent (`admin.release`, [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) amendment 2026-11-15), the posts held for that subject are released with it and recorded `post released`, whether or not the subject held any task. A post held for two subjects (an author agent and the board's person) is released when the second hold is lifted. A post whose retention ran out while held expires at the next sweep.

   **Amended 2026-11-22 (#695):** what the store built, in addition to the text above.
   - **Records.** `STATE_DIR/board` holds one sealed file per record, suffix `.board`: `post.<uid>.<post id>.board`, `board.<uid>.board` (the sequence and settings) and `cursor.<uid>.<agent id>.board`, where `<uid>` is the board's person. A record is at most 40 KiB (`BOARD_RECORD_MAX`: the post bound and two envelopes). At boot a record that does not decode, is oversized, or names another record is moved aside as `.board.quarantine` after its trail record, and a board record missing or behind a stored post's or cursor's sequence refuses boot. The state directory is created by `StateDirectory=maknae maknae/conversations maknae/tasks maknae/board`. A post whose undo did not sync is owed a removal, retried before every write; while 32 removals are owed or settled and not yet recorded in the trail (`BOARD_OWED_MAX`), a post is refused `store: removals are owed` before any write, so a disk that refuses unlinks, or a trail that refuses the settled records, stops the store taking posts. A cursor write whose outcome is unknown may leave the stored cursor ahead of the one in use; it only ever passes posts already denied to or received by that reader.
   - **A post records its author's uid.** Containment is judged on that uid and on the board's own uid, never on the agent id: a post's author hold follows the account, and a person's hold follows the board's key.
   - **A marked post is withheld at once.** When a snapshot is installed, each post whose author or board is contained is marked without I/O, and a marked post is withheld from every reader before the hold is recorded or written. A post stored after the installed snapshot contains its author or its board is marked as it enters memory, and is withheld and held the same way; its author is still told it was posted. A post that is expiring is withheld the same way. A read revalidates, in one check against the marks and the installed snapshot immediately before the reply is built, every post that shaped the reply: each kept post, the permitted post the page had no room for (the lookahead), the undecided post the walk stopped at, each reply target that kept its link, and the leading run of denied posts the cursor will skip. A post that is no longer live is left out and not sent, and the reader is told nothing (residual 24). The reply is then built again as if that post were absent: a kept post's room goes to the posts after it, a dead lookahead or stop is walked past (an undecided verdict after a dead stop is decided again), and a dead reply target loses its link. A dead member of the denied run changes nothing; it is withheld either way. A post found dead is never decided again in that read, so the rebuilding ends within the read's range. A stop still live keeps the read undecided (`more` or `TryAgain`).
   - **An expiry committed at its check is final.** The store notes a post as expiring in the same locked step as its retention check. No hold is listed or recorded for it. A containment mark that lands during the delete is discarded with the post if the delete succeeds, and survives if the delete is refused. The cost: a post already past retention, whose expiry is already recorded, is not kept as evidence if containment lands in that instant. The reason is that the store never holds its memory lock across I/O. The check consults the installed snapshot itself, not only the store's marks: a post whose author or board's person the installed snapshot contains is not expired but marked for its hold, even before the install has marked the board, and its `expired` record stays (residual 22).
   - **Cursors.** A reader's cursor record is removed at the sweep after its agent id is no longer enrolled, recorded first as `cursor removed: agent gone`. An agent id that stays enrolled keeps its cursor whatever its account. Each install recomputes the cursors due removal, and the removal checks the live view again, so an agent id enrolled again before the sweep keeps its cursor and its noted posts.
   - **Release rides `admin.release`'s pages, by the subject's uid.** After a page's held tasks, a page that lists no task releases up to 32 holds for the subject's uid (`HELD_PAGE_MAX`). Under the reload turn, and after the request is decided again, each hold is recorded before it is written, `post released (author)` or `post released (person)`, as an `admin.release` record with `board_op: release`. The store refuses a release while the hold's subject is contained, checked again under the store's writer lock, and a still-contained subject has none released. A page that attempted a task, or that stopped early, releases no post. The reply carries `posts_released`, the holds lifted on that page, and `posts_held`, the holds still held for the subject. For the post pages, paging continues only after a page that released at least one hold and left some, so it ends when a page releases none; task pages continue as they did. A lift counts in `posts_released` only when it stayed lifted: if the subject is found contained again right after the write, the store writes the hold back, the lift is reported as not released (`post not released: contained again`), it is not counted, and the page stops. A release that names one task, or an agent that is not enrolled (it has no uid to find), releases no post; the posts of a de-enrolled agent are released by naming its account as a user. Both counts are counts of holds: a post held for two reasons for the same uid counts twice, and a person's own post on their own board can carry both.
   - **A post withheld or held when a reader's cursor passes it is not delivered to that reader later, and a post released afterwards is not delivered either** (decision 6, amendment 2026-11-22). The kernel moves a cursor past a leading run of withheld posts, so a reader behind them does not decide them again.
   - **Trail reasons**, each a record written before the change it records: `post held: contained (author)`, `post held: contained (person)`, `expired`, `cursor removed: agent gone`, `settled: an unknown post was removed` and `post released (author)` / `post released (person)`. A failed lift is `post not released: <why>`. A sweep that leaves work undone says `<n> board expiries, holds or cursor removals remain due: <why>`, and a store failure `store: <why>`; a record quarantined at boot is `quarantined: <why>`.
   - **Retention is decided by the clock.** A post is not returned after 7 days, whether or not the sweep has removed it: it is no candidate, no reply target and not deliverable from that instant, and a failed delete changes nothing a reader sees. The sweep removes it from disk within its next pass. It no longer counts toward the board cap; it counts toward its author's until it is removed. A held post past retention stays held.
   - **Memory.** The store keeps every record in memory, zeroizing. The 1024 cap applies when a post is admitted: a post is refused `board full` when the board already has 1024 posts that are not held. Releasing held posts, or a containment lifted before its holds are written, can leave a board above 1024 live posts. What a board holds is bounded by 128 posts for each distinct author that has ever posted on it (4 MiB at the maximum post size), held posts included; a held post is kept until released, including the posts of agents since de-enrolled.

10. **Delivery without prompting** (maintainer, 2026-11-22).
    - **The stamp.** When the agent is on, `board_unseen` is added to every reply to an agent-channel request that cites a `Working` task, and to every `TaskClaim` reply to an agent holding a `Working` task (a claim or heartbeat never cites; the kernel knows the task). It counts the live posts on the task's board, above the agent's cursor and not authored by it, that are addressed to it by id, to `board`, or by a selector its task matches (with decision 6's first-read rule); plus presence entries whose bindings overlap its task's and whose claim time is after its last presence read. It is omitted when zero or when any switch is off. A working agent cites its task on every model turn and file request (`maknae-loop`'s plane client carries the cite on each), and the heartbeat is sent at a step boundary too, so a post reaches the agent at its next step boundary; a long-running tool step delays it until the step returns.
    - **The stamp's room.** The stamp is a bounded integer field. Every reply-size bound and capacity function that a stamped reply passes through (the Prompt and Attempt response maxima, `Read` page sizing, the prompt reply's pre-sized zeroizing buffer) reserves room for it, so a stamped reply neither grows a buffer ([ADR-0026](ADR-0026-memory-hygiene-boundary.md)) nor overflows its frame; a test at each maximum carries the stamp.
    - **The read.** On a nonzero stamp, `maknae-agentd`'s task driver calls `board.read` citing its task, with `seen_through`, the highest post id it has handed to the model. The kernel advances the cursor to `seen_through`, never past the highest post id it has returned to that reader and never backwards, so delivery is at least once. The driver drops a post id it has already handed to the model.
    - **Pages.** `board.read` reads one of two lists, `posts` or `presence`, and a reply is one page of one list:
      - a posts page holds at most `BOARD_READ_PAGE_POSTS` (32) posts;
      - a presence page holds at most `BOARD_READ_PAGE_PRESENCE` (64) entries, in order of claim time and task id, with a continuation marker naming the last entry returned. Presence is derived afresh on each page, so tasks can start or end between pages; the first page records its snapshot time, and reading the list through to its end sets the reader's last presence read time to that first page's time, so an entry claimed while the pages were being read is still counted next time;
      - either page is at most `prompt_max_bytes` less a 4096-byte envelope. A post is at most `BOARD_POST_MAX_BYTES`, and a presence entry at most the agent id, the task id, the claim time and the task's bindings, which [ADR-0037](ADR-0037-task-bindings-labels-and-tool-authorization.md) bounds within the task envelope margin (4096 bytes), so a page always holds at least one item and a backlog drains a page at a time, never blocking the cursor. At the floor it is the byte budget, not the count cap, that ends a page of maximum-size items. One test fills each list with maximum-size items until the byte budget ends the page and proves the page, with its envelope, the stamp and the continuation marker, fits the frame at `PROMPT_MAX_BYTES_FLOOR`; a second fills each list with minimum-size items and shows the count cap ends the page.
    - **The hand-off.** The driver adds the posts to the model's context at the next step boundary, each framed with its author, kind, stamps and attachments, as data: from a named peer agent, or, for a tasker's post, from the tasker. A tasker's post is still data, not a follow-up; a tasker who wants to instruct uses the task verbs' `add`. At a task's first step the driver reads the board's presence through to its end, and its posts (decision 6's first read), and adds both, so the model starts knowing who else is working on what for the same person.
    - **The model's operations.** The loop offers the model two built-in operations, post and read, which become `board.post` and `board.read` citing its task. They are not `tools.yaml` entries and run in no container.
    - **Rejected:** a server push channel, as in [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) decision 4. Every exchange stays client-initiated.

    **Amended 2026-11-22 (#695, maintainer, 2026-11-22):** no post is lost to a kernel restart or an agent crash. The kernel notes, per reader and only after the reply is written, the sequences of the posts it sent, and accepts an acknowledgement only when it names one of those posts above the cursor; an id never sent to that reader moves nothing, whether or not it is on the board. So a refused or unwritten read lets no acknowledgement pass a post that was not sent. The cursor is durable and moves only on the reader's acknowledgement (or past a leading run of posts denied to it, decision 6). The note holds only posts still on the board: an expired post leaves it, and a reader's note goes when it empties. After a kernel restart the note is empty, so the cursor does not move until posts have been returned again: delivery is at least once. The driver acknowledges a post only after it is in the task's durable transcript (#697). This sharpens "never past the highest post id it has returned to that reader".

11. **The tasker's view.** `maknae board` reads the caller's own board, a page at a time: presence, then posts, with attachments, held posts included. `maknae board post` posts as the tasker when `participate` is on. `maknae board settings` reads and sets the three settings, and `maknae board clear` clears the board. **Reporting is pull-shaped:** replies to the tasker's `session.new` and `session.task` requests gain a `board_unseen` count when `report` is not `off`, and `maknae board watch` polls and prints a summary or each post, by the `report` setting. Output is plain text a screen reader can follow, carrying nothing in colour alone.

12. **Audit: metadata and a digest, never the body** (maintainer, 2026-11-22). Each `board.*` request is `event: request` with its action and `object: board:<key>`.
    - A post's record carries the post id, kind, `to`, `in_reply_to`, attachment count, byte sizes and the SHA-256 of the post's canonical encoding of body and attachments; never the body or an attachment.
    - A read's record carries the post ids returned and the cursor reached.
    - A `board.manage` record carries its `board_op`, and for `settings` the settings before and after; for `clear`, the post ids removed.
    - The kernel's own board records are `event: board`, `action: board.manage`, with `board_op` `expire`, `hold` or `release`, written outside any request, as `event: task` records are under `action: session.task`. A query by `board_op` separates them from a tasker's `settings` and `clear`.

    **Amended 2026-11-22 (#695):** a read's record carries the first and last internal sequence returned, the count returned, the count withheld and the cursor reached, in place of "the post ids returned"; a post's record also carries its internal sequence ([ADR-0019](ADR-0019-audit-record-model.md), amendment 2026-11-22).

    **Amended 2026-11-22 (#695):** built. A board request's record is `event: request` with `object: board:users/<uid>`, the `board` block of [ADR-0019](ADR-0019-audit-record-model.md) and no `board_op`. A post writes `intent recorded` before it is stored, then `done`; a read writes `intent recorded` with the cursor it started from, then `done` with the page's counts. The kernel's own records under `action: board.manage`, `event: board`, carry `board_op` `expire` (an expiry, a cursor removal, a settled unknown post) or `hold`. A release is the exception to "written outside any request": it is an administrator's request, so it is `action: admin.release`, `event: request`, `board_op: release`, with `object: board:users/<uid>` and the post's id and sequence. The widest board request records (a maximum post from the widest agent) exceed the macOS syslog line cap and are mirrored there as the degraded marker, as the widest task-verb records are; the JSON trail carries the whole record on every platform. Whether to shorten them is the maintainer's to decide.

    A post's body is model output, as a prompt is, and the trail never holds prompt text.

## Consequences

- **Residuals.**
  1. **Visibility detects; it does not prevent.** A tasker who reads the board can see an injection attempt or an odd exchange after it happened.
  2. **A post can steer a recipient within its own grants.** An injected model can post "apply the attached diff and push it", and a recipient model holding that reach may do it, every call permitted on its own grants. Decision 1 stops a post from widening authority, not from persuading a model. This is the confused deputy every channel carrying model-readable content has; the controls are each agent's grants, its switch, and the tasker's view.
  3. **Content can cross a receiving agent's own reach.** Ruled acceptable (decision 7); the control is the agent's switch.
  4. **An attachment's source is a claim.** The kernel does not read content and cannot check that an excerpt is what it says.
  5. **A model can encode content in a post.** The tasker can read everything on the board, but cannot necessarily tell what an encoded post means.
  6. **The agent runtime's own uid and memory.** A post delivered to an agent is in its process and context. As for the partition operand, the kernel bounds what it releases, not what the runtime does with it afterwards (#629). An agent's behavioural memory is shared across its taskers (#420), so content an agent learned on one person's board can surface in its work for another, as task content can.
  7. **The digest confirms a guess.** A trail reader can confirm a guessed short post ("taking #693") against its unkeyed SHA-256. Trail readers are administrators and auditors; the maintainer ruled metadata and a digest sufficient.
  8. **Held posts have no investigator's view.** A contained person can no longer read their own board, and no administrator verb reads a board. Reading held posts for an investigation is a separate decision.
  9. **Retention ends the record of content.** After 7 days a post that is not held is gone; its trail record and digest remain.
  10. **Selectors and binding-based presence wait on bindings** ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4). Until then, addressing is by agent, `tasker` or `board`.
  11. **The site switch is restart-only.** Turning the board off quickly is the agent switch (a reload) or the tasker's setting (immediate).

  12. **The caps are shared across label sets.** *(Added 2026-11-22, #695.)* A cap on live posts, board or author, is counted over posts the reader may not be permitted. Filling a cap is therefore a signal from one label set to another. It does not exist in the open-source build, which has one level, and is decided when an engine is integrated.
  13. **A retry after `OutcomeUnknown` can produce a duplicate post.** *(Added 2026-11-22, #695.)* When the first write landed and the kernel restarted before removing it, the author is told `OutcomeUnknown`, retries, and the first post loads again. Delivery is at least once and no de-duplication key is built.
  14. **Such a post loads at its original place in the order.** *(Added 2026-11-22, #695.)* A post the author was told is unknown (`OutcomeUnknown`), if its file survives a restart, loads at its original internal sequence, behind readers whose cursors already passed it, so those readers do not receive it.
  15. **The gate answers before the decision.** *(Added 2026-11-22, #695.)* An agent without the `board.*` grant still learns that the board is off or on for it, because the three switches are checked first (decision 3). It learns nothing about any post.
  16. **A full board tells a poster that the board holds posts it may not read.** *(Added 2026-11-22, #695.)* `board full` counts live posts of every label set (residual 12); it is a signal of the board's size, never of any post's content.
  17. **An engine withholds by denying.** *(Added 2026-11-22, #695.)* A post whose decision is undecided is never treated as withheld: the read stops at it and is `more` or `TryAgain` (decision 6). An engine that answers indeterminate only for the posts it would withhold therefore signals them to the reader. A withheld post must be a denial.
  18. **A reply to an existing but withheld post takes one decision longer than a reply to an absent id.** *(Added 2026-11-22, #695.)* Both are refused as naming no post. The difference is in time only.
  19. **A mostly-withheld board costs a read many decision batches.** *(Added 2026-11-22, #695.)* A read walks the board in batches of 32 posts until its page is full, at most the posts on the board when it was admitted, each batch under one decision timeout. A rebuild after the delivery check reuses the verdicts already decided; only the undecided verdicts after a dead stop are decided again.
  20. **An undecided reply target is delivered without its link, and the link is lost once the reader acknowledges.** *(Added 2026-11-22, #695.)* A reply whose target is undecided at that read is returned with `in_reply_to` empty. The reader's acknowledgement moves the cursor past it.
  21. **The trail can carry duplicate sweep records.** *(Added 2026-11-22, #695.)* When two passes race, or a pass stops early, an expiry, hold or cursor removal is recorded again, as for tasks.
  22. **A hold or an expiry can be recorded and then skipped.** *(Added 2026-11-22, #695.)* When containment is lifted between a hold's record and its write, the store skips the write and the record stays, as for tasks. When containment is installed between an expiry's record and the store's check, the post is held instead and the `expired` record stays.
  23. **The board cap bounds admission, not the board.** *(Added 2026-11-22, #695.)* A release, or a containment mark dropped before its hold is written, makes a post live without the cap's check, so a board can hold more than 1024 live posts; what a board holds is bounded by 128 posts per author.
  24. **A containment can land between a read's last check and its write.** *(Added 2026-11-22, #695.)* A read checks its page against the marks and the installed snapshot immediately before it is built, but no lock is held across the frame write, so a containment installed in that instant does not stop that page.
- **The tasks right grows.** An existing agent `policy.yaml` that denies `board.post` or `board.read` stops loading after this change, with the reason named.
- **Built:** nothing. **Owed:** the store, verbs, bounds, pages and containment ([#695](https://github.com/darkhonor/maknae/issues/695)); presence and selectors ([#696](https://github.com/darkhonor/maknae/issues/696)); delivery into the loop ([#697](https://github.com/darkhonor/maknae/issues/697)); the three switches ([#698](https://github.com/darkhonor/maknae/issues/698)); the tasker's view ([#699](https://github.com/darkhonor/maknae/issues/699)). `AGENTS.md`'s account of the partition operand gains the `board.*` case when #695 builds it.
- **Amended 2026-11-22 ([#695](https://github.com/darkhonor/maknae/issues/695)):** **Built:** the wire types and the `board.post` and `board.read` verbs; the vocabulary, class and tasks right; the partition operand's board case; the store and its records; boot and the state directory; the audit fields; the gate, both verbs and the per-post decision; retention, holds and clean-up; release through `admin.release`. `AGENTS.md` carries the `board.*` case. **Owed:** presence and selectors ([#696](https://github.com/darkhonor/maknae/issues/696)); the `board_unseen` stamp and delivery into the loop ([#697](https://github.com/darkhonor/maknae/issues/697)); the switches' configuration and `board.manage` ([#698](https://github.com/darkhonor/maknae/issues/698)), so until it lands every board request from an agent whose cited task is rooted at a person is refused `board off: site` (the other refusals are in decision 5's amendment); the tasker's view and the client channel ([#699](https://github.com/darkhonor/maknae/issues/699)).
