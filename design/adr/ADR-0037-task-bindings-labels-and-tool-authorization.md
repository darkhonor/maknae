# ADR-0037: Task bindings, extensible labels and tool authorization — a task carries intent, never tooling; scope comes from typed bindings the work's own context supplies; reach is the provider-checked intersection of tasker and agent; labels are namespaced, claimed and never lowered by a client

- **Status:** Accepted (maintainer-ruled 2026-11-19)
- **Date:** 2026-11-19
- **Deciders:** Alex Ackerman (maintainer)
- **Raised by:** [#474](https://github.com/darkhonor/maknae/issues/474), [#420](https://github.com/darkhonor/maknae/issues/420) decision 2
- **Amends:** [ADR-0036](ADR-0036-the-tool-model.md) decisions 7 and 13; [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 and its control-mapping row; [ADR-0004](ADR-0004-modular-authorization-architecture.md) decision 2 and §6; [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 7; [ADR-0008](ADR-0008-authorization-composition-contract.md) (the ceiling operand's inputs)
- **Builds on:** [ADR-0036](ADR-0036-the-tool-model.md) (the tool model); [ADR-0035](ADR-0035-policy-enforcement-points-placement-and-trust-tiers.md) (PEP placement); [ADR-0034](ADR-0034-the-models-file-boundary.md) decision 6 (a client-read personal file, snapshotted by the kernel); [ADR-0008](ADR-0008-authorization-composition-contract.md) (the composition the claim rule loads into)

## Context

A task today is a kernel-signed CBOR object holding the target agent, a free-form `ask` (one variant, `Prompt`) and an empty `labels` struct that decodes only an empty map ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 7; `crates/maknae-proto/src/task.rs`). Every request that cites a task is decided on the agent's own role, inside its tasker's partition. [ADR-0036](ADR-0036-the-tool-model.md) decided how tools run and how they are granted (`Tool(<entry> <program> <pattern>)` within `tools.yaml`), and its `github-task` credential class narrows a token to "the task's repositories". The task object carries no repositories. [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 records the consequence as an AC-6 residual: a resource the task does not bound is decided on the agent's role alone, so one tasker could point a shared agent at another tasker's resources. #474 was filed to close it with task classes: a named authority envelope of tools, operations, destinations and scope per kind of work.

The maintainer's direction, 2026-11-19, changes the approach. Models take different paths to the same goal (observed between two reviewing models on this project), so a grammar that names tools or steps chases every new use case. The task carries the business intent; skills shape the procedure and inform, never authorize; tools are an offering to the model, filtered by policy as a coding harness's allow-list filters its commands. The work's own location defines its scope. Identity decides reach. Every kernel engagement is a full policy decision. And the authorization model must stay extensible through Maknae's vocabulary: the in-repo RBAC engine by default, and an external authorization engine that brings a full classification lattice.

## Decision

1. **A task carries intent, never tooling.** A task names what the tasker wants done; it does not name tools, operations or steps, and no grammar defines a procedure per kind of work. **Task classes are rejected**: a named bundle of tools per kind of work encodes one model's procedure and turns every new use case into new grammar. A new use case is a new `tools.yaml` entry and a grant, which is the administrator's data.

2. **Scope comes from typed bindings.** A **binding** has a `kind` and that kind's values. For `git`: every remote (not only `origin`), each a server and a repository path, and optionally a change (a pull or merge request number with its base and head repositories). A binding is **snapshotted onto the conversation** or **sealed into the signed task** when the work starts and is **never re-resolved**: an agent clones into its task directory from the binding, and a later `git remote set-url` or `git remote add`, by workspace code or the model, moves nothing. **Wire.** The task object and `session.new` gain an additive `bindings` field, and the task object a kernel-written `reach` field holding the intersection result (decision 7). Both are omitted from the encoding when empty, so a task signed before they existed still re-encodes to the bytes that were signed and its signature verifies after the change (`task_signing_bytes` re-serializes the decoded object). Bindings and `reach` are bounded together, in count and in bytes, against the signed task's envelope margin ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 8), and a submission whose bindings could exceed it is refused at submission, never at signing. **Per-repository allow lists are rejected**, in `/etc/maknae` and in `~/.maknae` alike: they do not scale, and a personal list fails open when a private repository is forgotten.

3. **Where bindings come from.**
   - **A person's own CLI session:** the client runs the resolvers that the session's usable tool entries declare against the working directory (for `git`, the remotes in `.git/config`) and sends the result at `session.new`. `.git/config` is local, not cloned, so at that moment it is the person's own file. The kernel never reads a home directory (#365); it validates each binding (well formed; its server authorized by site configuration) and snapshots it, as [ADR-0034](ADR-0034-the-models-file-boundary.md) decision 6 does with the personal `sensitive.yaml`. An edit applies to the next conversation.
   - **On the agent channel,** `session.new` bindings come only from the cited task; a `session.new` carrying any other binding is refused. An agent's own-initiative task takes its bindings from the Agent Daemon's own parse, an untrusted client's; that is accepted because such a task intersects with the agent's own reach only (decision 7).
   - **A task:** the submission carries explicit bindings. Each resolver brings **link recognizers** for its kind (for `git`: `https://<server>/<owner>/<repo>/pull/<n>` and the GitLab merge-request form). The tasker's client runs them over the tasker's own prompt before submission, so the kernel still never reads content (#417), and **shows the tasker what it bound**. A link to a server the site configuration does not authorize is refused at the client, with the reason. Nothing is bound that the tasker did not submit. Intake does not trust the client's parse ([ADR-0009](ADR-0009-subject-side-os-dac-evaluation.md)'s untrusted client): it re-validates each binding, and the intersection call (decision 7) resolves what a link cannot show, such as the head repository of a pull request from a fork. A remote tasker (`Tasker::Remote`) has no local provider login, so a task of theirs with a `git` binding is refused until the gateway ([#117](https://github.com/darkhonor/maknae/issues/117)) supplies one.
   - **A sub-task's** bindings must be a subset of its parent's sealed bindings.
   - Maknae never translates intent into commands. The tasker's request becomes a binding, deterministically; the binding becomes `gh pr view 155 -R <owner>/<repo>` only by the model's own choice, inside the patterns and the token the binding shaped.

4. **Tool entries declare what they bind.** A `tools.yaml` entry gains `binds:`, naming the binding kinds it consumes and, for each, a resolver chosen from a closed list in Maknae's code. A new resolver is a Maknae change; a new entry using an existing resolver is administrator data. **Missing binding, missing tool:** an entry whose binding kind the conversation or task does not carry is not offered to the model and is refused if called. A credential class's narrowing uses the binding (the `github-task` class mints for the bound repositories at the permission decision 7 allows). Command patterns may reference bound values (`gh pr view {git.change} -R {git.base}`). `network.sites` stays host-level: the proxy sees a host and a port, never a path, so after intake a repository is bounded by the site, through the narrowed token.

5. **The model sees a filtered view, never `tools.yaml`.** The front end offers the model what the subject may call now: entries that are enabled, allowed by the subject's `Tool(...)` grants (for a task, the agent's), and whose binding kinds are present. For each, the model sees the entry's name and description and the granted program patterns with bound values filled in. It never sees an entry it cannot call (a refusal says "not available", never "exists but not granted"), nor the fence: image references, credential classes, sites, volumes, resources or argument denials. The file lies under `/etc/maknae/**` in the shipped `sensitive.yaml`. The offering follows the model protocol in use, through the single invocation tool of [ADR-0036](ADR-0036-the-tool-model.md) decision 21; it is a convenience, and the control is the per-call decision. Administrators see the full configuration through `admin.config.show`'s disclosure rules.

6. **Identity decides reach.** A person's CLI session uses the person's own credential, and the provider enforces the person's reach; Maknae keeps no copy of it. An agent uses its own identity (a GitHub App installation, a bot user), whose reach its owner grants at the provider. Who may use that reach is the agent's `taskers:` list. A task never runs on the tasker's credential.

7. **The intersection: a task reaches only what both its tasker and its agent can reach.**
   - **The tasker side is #168 scope item 4, adopted.** At submission the tasker's client reads the tasker's own token, seals it to the Egress Daemon, and `maknaed` carries it unopened ([ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md)). The Egress Daemon calls `GET /repos/{owner}/{repo}` for each bound repository as the tasker and as the agent; the result is the lower of the two, per repository and per operation, against the repository that operation touches (the base for reading, reviewing and merging; the head for pushing to the change's branch). Whether one token carries every permission set or one token is minted per set stays open (`design/egress-and-tool-execution.md` §10 item 13). The tasker's token serves that read only and is never stored. A missing login, an expired token, a 401 or a 404 refuses the task. The tasker side was measured on 2026-10-19 for user OAuth tokens and on 2026-10-22 for fine-grained personal tokens.
   - **The agent side for a GitHub App installation is unmeasured and owed**: whether `GET /repos` returns `permissions` for an installation token, and otherwise derivation from the installation's repository list and the App's granted permissions. So is the mapping from a role level (`pull`, `push`) to an installation-token permission set.
   - **A credential class's `kind` implements the reach check.** `github-app-installation` does the pair above; another kind brings its own. **A tool entry whose `credential` names a class whose kind implements no reach check is refused in tasks** (fail closed). Entries with `credential: none` are unaffected.
   - **Agents as taskers.** An agent's own-initiative task (root `agents/<id>`) intersects with the agent's own reach only. A sub-task's tasker half comes from its parent's sealed result, restricted to the sub-task's bindings, because its submitter is an agent and holds no tasker token. Its agent half is checked afresh for the sub-task's own agent, which needs only that agent's identity. The sealed result is the lower of the two, per repository and operation, so a task chain never reaches beyond any agent in it or its root tasker.
   - **Timing.** The intersection is observed at submission and sealed as `reach`. The installation token is minted at hand-out from that sealed result, and every re-mint during the task re-runs the agent-side check. Hand-out re-decides the tasker's role and the agent's `taskers:` ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statement 10), not the tasker's provider reach.

8. **Labels are extensible security attributes, separate from bindings, and fail closed.**
   - **Separate concerns.** Bindings say what the work is about; labels are attributes an operand evaluates (classification, releasability, compartments, or whatever an engine brings). **Overloading `labels` with bindings is rejected.**
   - **Keys name a provenance and a namespace.** A label key is `<provenance>.<namespace>.<key>`, where the provenance is `entry` (a `tools.yaml` entry), `task` or `binding`. Maknae's core enumerates no namespace. Labels reach the request's resource bag. The existing bare `classification` resource key is unchanged: it is the object's own marking, written only by the kernel from the object's own label (`crates/maknae-security/src/request.rs`), and no label ever writes it.
   - **Who may write which label.** Entry labels are administrator data. Task and binding labels are supplied by a client and can only add refusals: an operand that claims `task.classification` refuses when that label ranks above the system's declared level, and refuses a token it cannot rank (a foreign system's level is refused by name, [ADR-0022](ADR-0022-classification-policy-as-data.md)). A client label never stands in for the object's own marking, so it cannot lower or widen it. An entry's accreditation (the most its environment may receive) is the opposite relation to a marking (a property of what is sent), so it is carried as an `entry` label and evaluated only by an operand that decides destination dominance (`design/egress-and-tool-execution.md` §9); the default build has none.
   - **The claim rule.** Each operand declares the (provenance, namespace) pairs it evaluates. A `tools.yaml` entry carrying a pair no loaded operand claims is disabled with a load warning, so one entry never takes the file down; a task or a session carrying one is refused. An unclaimed label is a refusal, never an abstention. A claimed label is evaluated on every request that cites its task or conversation, never once at intake. The default build's ceiling claims `task.classification` and `binding.classification` and nothing else, so an entry carrying an accreditation label is disabled until an operand that decides dominance claims it. An external authorization engine claims its own pairs when it is loaded. Mandatory operands still never permit ([ADR-0008](ADR-0008-authorization-composition-contract.md)).
   - **Values flatten into the contract's `AttrValue`**: a level as `Str`, compartments and releasability as `Set`. The contract's `List` carries ordered values such as a tool's arguments, which labels never use. The claim declaration is an additive change to the `Authorizer` contract under [ADR-0004](ADR-0004-modular-authorization-architecture.md) §6.
   - Site attributes (`design/egress-and-tool-execution.md` §9) use the same namespaces, so an engine sees one vocabulary across tools, tasks and sites.

9. **Side effects are their own grants.** Posting is a separate pattern on a separate entry that the site defines for it (for example `Tool(github-post gh pr review --comment *)`), and each review decision (comment, request changes, approve) is its own shape, so a site grants or withholds each one. Who may approve whose pull request, and whether an approval counts toward a merge, is the forge's policy, not Maknae's. Merging is a separate act again ([#676](https://github.com/darkhonor/maknae/issues/676)). This satisfies [#480](https://github.com/darkhonor/maknae/issues/480).

10. **Every request is decided in full.** Bindings, labels and the intersection result are inputs to each decision, never a cached verdict. Each tool call cites its conversation or task and is decided on the subject's grants (for a task, the agent's role), the bindings and labels in the resource bag, and the mandatory operands.

### A pull-request review, worked end to end

Alice is in hobi's `taskers:`. She runs `maknae agent hobi -p "Review https://github.com/darkhonor/maknae/pull/345"`.

1. Her client recognizes the link and binds `git`: server `github.com`, base `darkhonor/maknae`, change 345. It shows her the binding, seals her GitHub token to the Egress Daemon and submits.
2. Intake decides `session.task` on her role and hobi's `taskers:`, re-validates the binding against site configuration, checks that every label the task carries is claimed, and runs the intersection: the change's head is `darkhonor/maknae` too; alice holds `pull`, hobi's App installation covers `darkhonor/*`; the result is `pull` on `darkhonor/maknae`. The binding and the result are sealed into the task.
3. Hobi claims the task; the installation token is minted for `darkhonor/maknae` at `pull`. The model is offered `rust-fetch` (whose `gh` patterns, with the bound values filled in, read `gh pr view 345 -R darkhonor/maknae` and `gh pr diff 345 -R darkhonor/maknae`), because hobi's grants allow it and its `git` binding is present, and `rust-build`, which binds nothing and holds no credential. A posting entry is offered only if hobi holds its grant, and each posting call is still decided against that grant and the sealed result.
4. Each call is decided in full. The launch obligation carries the bound values; `gh` runs as hobi's uid, in a container whose only workspace mount is the task's directory, with the narrowed token.
5. A model that also reads the repository's ADRs or `AGENTS.md`, or searches the web, works inside the same fence: the same workspace, the same token, and only the sites hobi's entries allow.
6. The report returns to alice through the kernel.

**A fork variant.** Had the change come from `contributor/maknae`, the link would still name only the base. The intersection call reads the head from the pull request, checks reading against the base and pushing against the head, and finds hobi's App not installed on the contributor's fork. The task can read and review; any push to the change's branch is refused.

## Consequences

- **Residuals.**
  1. The tasker's provider reach is observed at submission only. Hand-out re-decides the role and `taskers:`, and each re-mint re-checks the agent's reach, but nothing re-checks the tasker's. The window runs from submission until the task's outcome is recorded; nothing bounds the queue time or the working time today.
  2. In a person's own CLI session a binding bounds servers and command patterns, not repositories: the person's credential is broad and the proxy sees hosts. It bounds the model, not the person, who could reach the repository anyway.
  3. Shared behavioural memory is not bound; it is not built. AC-6 stays partial for memory, described, not decided, in [`design/intent/behavioural-memory.md`](../intent/behavioural-memory.md); no issue tracks it (maintainer, 2026-11-19).
  4. An agent's taskers share its reach by its owner's choice; each reaches at most the intersection of their own access with the agent's.
  5. Every installation token can read public repositories (`design/egress-and-tool-execution.md` §10 item 13).
  6. Patterns that reference bound values bind the model, not a compromised Agent Daemon, whose own account can run a tool with any token it reaches (`design/egress-and-tool-execution.md` §5.4).
  7. The agent side of the intersection for a GitHub App installation is unmeasured until measured (decision 7).
- **Some tools stop working in tasks until their credential kind has a reach check.** ADR-0036's own `vault` example (`vault-child-token`) is refused in tasks from the day this lands, and so is any stored-token class until its kind implements a check. A person's CLI session is unaffected.
- **#474 is satisfied** by this ADR. **#420 decision 2 is settled.** **#480 is satisfied** (decision 9).
- **Owed, none built:** the `bindings` and `reach` fields on the task object and `bindings` on `session.new`, omitted when empty, with a test that a task signed without them still verifies; the bound on bindings; `binds:` and the resolvers; link recognizers and the binding echo; the claim declaration on `Authorizer` and its registry; the intersection in the Egress Daemon (#168 slice 4), the App-side measurement and the re-mint check; the mapping from a role level to an installation-token permission set; bound-value patterns in the `Tool(...)` parser.
- **Amended in place:** [ADR-0036](ADR-0036-the-tool-model.md) (`binds:`; credential classes narrow from bindings; the filtered view); [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) (task classes rejected; the envelope is the sealed bindings and intersection; the AC-6 row); [ADR-0004](ADR-0004-modular-authorization-architecture.md) (the claim declaration as an additive contract change); [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (the task object's `bindings`, `reach` and evaluated `labels`); [ADR-0008](ADR-0008-authorization-composition-contract.md) (the ceiling operand's two new inputs).
