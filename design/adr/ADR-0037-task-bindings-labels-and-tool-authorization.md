## Context

A task today is a kernel-signed CBOR object holding the target agent, a free-form `ask` (one variant, `Prompt`) and an empty `labels` struct that decodes only an empty map ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 7; `crates/maknae-proto/src/task.rs`). Every request that cites a task is decided on the agent's own role, inside its tasker's partition. [ADR-0036](ADR-0036-the-tool-model.md) decided how tools run and how they are granted (`Tool(<entry> <program> <pattern>)` within `tools.yaml`), and its `github-task` credential class narrows a token to "the task's repositories". The task object carries no repositories. [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 records the consequence as an AC-6 residual: a resource the task does not bound is decided on the agent's role alone, so one tasker could point a shared agent at another tasker's resources. #474 was filed to close it with task classes: a named authority envelope of tools, operations, destinations and scope per kind of work.

The maintainer's direction, 2026-11-19, changes the approach. Models take different paths to the same goal (observed between two reviewing models on this project), so a grammar that names tools or steps chases every new use case. The task carries the business intent; skills shape the procedure and inform, never authorize; tools are an offering to the model, filtered by policy as a coding harness's allow-list filters its commands. The work's own location defines its scope. Identity decides reach. Every kernel engagement is a full policy decision. And the authorization model must stay extensible through Maknae's vocabulary: the in-repo RBAC engine by default, and an external authorization engine that brings a full classification lattice.

## Decision

1. **A task carries intent, never tooling.** A task names what the tasker wants done; it does not name tools, operations or steps, and no grammar defines a procedure per kind of work. **Task classes are rejected**: a named bundle of tools per kind of work encodes one model's procedure and turns every new use case into new grammar. A new use case is a new `tools.yaml` entry and a grant, which is the administrator's data.

2. **Scope comes from typed bindings.** A **binding** has a `kind` and that kind's values. For `git`: every remote (not only `origin`), each a server and a repository path, and optionally a change (a pull or merge request number with its base and head repositories). A binding is **snapshotted onto the conversation** or **sealed into the signed task** when the work starts and is **never re-resolved**: an agent clones into its task directory from the binding, and a later `git remote set-url` or `git remote add`, by workspace code or the model, moves nothing. **Wire.** The task object and `session.new` gain an additive `bindings` field, and the task object a kernel-written `reach` field holding the intersection result (decision 7). Both are omitted from the encoding when empty, so a task signed before they existed still re-encodes to the bytes that were signed and its signature verifies after the change (`task_signing_bytes` re-serializes the decoded object). Bindings and `reach` are bounded together, in count and in bytes, against the signed task's envelope margin ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 8), and a submission whose bindings could exceed it is refused at submission, never at signing. **Per-repository allow lists are rejected**, in `/etc/maknae` and in `~/.maknae` alike: they do not scale, and a personal list fails open when a private repository is forgotten.

   **Amended 2026-11-22 ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4 PR A), as built.** This names what is built and what this decision left open.
   - **What is built.** The `bindings` field exists on the task submission, the signed task object and the task view (`crates/maknae-proto/src/task.rs`). `bindings` on `session.new` is not built ([#479](https://github.com/darkhonor/maknae/issues/479)), and `reach` lands with slice 4 PR B. A task signed before the field existed re-encodes to its signed bytes and verifies; a test pins it.
   - **The shape.** A `git` binding is `server` (a lowercase `host[:port]` of at most 255 bytes, the `forges:` host grammar), `base` (a repository path of at most 255 bytes: two or more segments of `[A-Za-z0-9._-]`, none `.` or `..` or starting with `-`, and no `.git` suffix), an optional `change` (a pull or merge request number, at least 1) and `head`. **`change` is optional**: a binding without one names the repository only. **A submission carries no `head`**, and decode refuses one; `head` is the kernel's to write. PR A writes none: a top-level task seals `head: null`, and a sub-task's binding is its parent's, `head` included. "Every remote" reads as one binding per repository, up to the bound below.
   - **The bound.** A task carries at most `TASK_BINDINGS_MAX` (8) bindings, bounded in encoded bytes **on the sealed form**: the sealed list encodes to at most `TASK_BINDINGS_MAX_BYTES` (1024). A sealed binding always encodes `head` (`null` when absent), 6 bytes a request does not carry, so a submission's list is bounded at `TASK_BINDING_REQUESTS_MAX_BYTES` (976 = 1024 − 6 × 8), and a test proves a request set at that bound seals within 1024. Intake measures the sealed list again and refuses one over 1024, which matters once a sub-task copies a `head` PR B writes. A further `TASK_REACH_MAX_BYTES` (1024) is reserved for `reach`. Decode refuses a ninth binding, a duplicate and a list over its bound; it never deduplicates, reorders or normalizes, because `task_signing_bytes` re-serializes the decoded object. Measured 2026-11-22: a delivered task's envelope is 436 bytes, 1469 with bindings at the bound and 2493 with the reach reserve, within the 4096-byte margin of [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 8; a page of 32 held views with maximal bindings is 50,606 bytes and of 32 task views 40,269, within the 65,536-byte control frame. *The failure the request bound prevents:* a client that cut on the sealed bound would let a set of long bindings pass the client and fail decode whole.
   - **What the PDP sees.** Bound values reach the PDP as resource keys `bound.git.server`, `bound.git.base`, `bound.git.head` and `bound.git.change`, beside `binding.kinds`. Each is a `List`, index-aligned with the task's bindings, with `""` for an absent field and `change` in decimal. There is one encoding, `encode_git_bound` and `decode_git_bound` in `crates/maknae-security/src/request.rs`, which the kernel's writer and the PDP's reader both call. The keys are vocabulary in the existing `AttrValue`, not a change to the [ADR-0004](ADR-0004-modular-authorization-architecture.md) contract. A `binding.kinds` naming `git` without the lists, lists without `git` in `binding.kinds`, or lists that do not decode are `Indeterminate`.
   - **The matching rule.** A pattern that references bound values matches within one binding, for an allow and for a deny alike, so values from two bindings never combine into one match; but no production caller builds a tool request until [#479](https://github.com/darkhonor/maknae/issues/479), so neither the `tools.yaml` ceiling's nor the `Tool(...)` grants' use of bound values is reachable in production today, and only tests exercise it. *The failure it prevents:* with `alpha` change 1 and `beta` change 2 bound, a match that took each placeholder from any binding would admit `pr review 1 -R beta`.
   - **Classification.** A binding's coordinates (server, base, head, change) are grammar-validated repository coordinates. They are shown to the tasker, listed in task status and recorded in the audit trail ([ADR-0019](ADR-0019-audit-record-model.md), amendment 2026-11-22) by design, so they are not secret-class content under [ADR-0026](ADR-0026-memory-hygiene-boundary.md), and the buffers that hold them are outside its zeroizing rule. The same holds for a host named in a client's "not bound" line, which passes the same host grammar first. The prompt they are read from stays secret-class: a fragment of it is copied only once it is admitted as a binding or a nameable host, or, when a shorthand or bare name that is not bound is listed in the echo, into a zeroizing buffer allocated at its exact length. A link whose authority carries userinfo is neither bound nor named.

   **Amended 2026-11-24 ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4 PR B), as built.** This replaces the 2026-11-22 banner's bound and measurements, and names what PR B built.
   - **Sealed when the work starts, plus tasker-added addenda.** A binding is still never re-resolved, and the signed task never changes. A working task's own tasker may add bindings with `TaskAdd` (`/add`). The kernel seals them as it seals a submission's, observes their reach (decision 7), and writes them into a separate, cumulative `TaskAddendum` (`schema` `maknae.task.addendum`, `version` 1, the task id, a sequence number, the added bindings and their reach), signed under its own context `maknae.task.addendum.v1\0` ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-24). The task and its addendum hold at most 8 bindings together, and a duplicate on (server, base, change) is refused. A task sealed without `reach` (PR A era) takes no addendum. An agent that submitted a task on its own initiative cannot add to it while it holds a working task, the rule a submission already follows. The agent verifies the addendum against its task before it takes any added binding. Every reader of a task's bindings (the sub-task parent match, the view, the stamped tool request and the Agent Daemon's sub-task candidates) reads the task's own bindings followed by the addendum's.
   - **`head` is written.** Intake writes `head` from what the tasker's observation of the change reports (decision 7): the head repository's full name, or `null` for a binding without a change and for a change whose head repository was deleted.
   - **`reach` is built.** `TaskObject.reach` holds one entry per binding, index-aligned, omitted when empty (`crates/maknae-proto/src/reach.rs`, `task.rs`). Each entry holds the tasker side (base and head operation sets), its basis, the agent side (observed sets, `AtHandOut` or `NoForgeCredential`) and an optional reason the effective reach is empty. Decode refuses an unknown operation bit, `PushHead` in a base set, head operations on a binding with no head, `reach` without bindings and a length that differs from the bindings'. An empty `reach` beside bindings still decodes: that is a PR A task, and its effective reach is empty. `TaskView.reach` carries only the effective summary, one `(ops, why)` pair per binding, with base operations in bits 0-4 and head operations in bits 5-9.
   - **The bound.** The sealed list is bounded at `TASK_BINDINGS_MAX_BYTES` = **1280**, so that a sealed `head` fits. A submission's list stays at `TASK_BINDING_REQUESTS_MAX_BYTES` = **976**, its own constant: 976 + 6 × 8 + 256 = 1280, so a maximal request set seals with one 255-byte head, and a test pins it. A sealed list over 1280, which long fork heads can produce, refuses the task by name. `TASK_REACH_MAX_BYTES` = **1024** is now enforced on decode. **Measured 2026-11-23**, replacing the 2026-11-22 numbers: a delivered task's envelope is 436 bytes bare, 1725 with 8 bindings at 1280 (each with a 40-byte head), 2492 with the largest reach as well (761 bytes for 8 entries), and 2755 with bindings and the full 1024-byte reach reserve, within the 4096-byte margin of [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) decision 8. A page of 32 held views with maximal bindings and summaries is 60,302 bytes, and of 32 task views 49,965, within the 65,536-byte control frame, so the held view keeps `reach`.

3. **Where bindings come from.**
   - **A person's own CLI session:** the client runs the resolvers that the session's usable tool entries declare against the working directory (for `git`, the remotes in `.git/config`) and sends the result at `session.new`. `.git/config` is local, not cloned, so at that moment it is the person's own file. The kernel never reads a home directory (#365); it validates each binding (well formed; its server authorized by site configuration) and snapshots it, as [ADR-0034](ADR-0034-the-models-file-boundary.md) decision 6 does with the personal `sensitive.yaml`. An edit applies to the next conversation.
   - **On the agent channel,** `session.new` bindings come only from the cited task; a `session.new` carrying any other binding is refused. An agent's own-initiative task takes its bindings from the Agent Daemon's own parse, an untrusted client's; that is accepted because such a task intersects with the agent's own reach only (decision 7).
   - **A task:** the submission carries explicit bindings. Each resolver brings **link recognizers** for its kind (for `git`: `https://<server>/<owner>/<repo>/pull/<n>` and the GitLab merge-request form). The tasker's client runs them over the tasker's own prompt before submission, so the kernel still never reads content (#417), and **shows the tasker what it bound**. A link to a server the site configuration does not authorize is refused at the client, with the reason. Nothing is bound that the tasker did not submit. Intake does not trust the client's parse ([ADR-0009](ADR-0009-subject-side-os-dac-evaluation.md)'s untrusted client): it re-validates each binding, and the intersection call (decision 7) resolves what a link cannot show, such as the head repository of a pull request from a fork. A remote tasker (`Tasker::Remote`) has no local provider login, so a task of theirs with a `git` binding is refused until the gateway ([#117](https://github.com/darkhonor/maknae/issues/117)) supplies one.
   - **A sub-task's** bindings must be a subset of its parent's sealed bindings.
   - Maknae never translates intent into commands. The tasker's request becomes a binding, deterministically; the binding becomes `gh pr view 155 -R <owner>/<repo>` only by the model's own choice, inside the patterns and the token the binding shaped.

   **Amended 2026-11-21 ([#674](https://github.com/darkhonor/maknae/issues/674), [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md) decision 6):** "the server authorized by site configuration" and "a server the site configuration does not authorize" mean an entry in `maknae.yaml` `forges:` (name, binding kind, `host[:port]`, provider). The client learns the list from its subject's tool catalog, never from `/etc/maknae`. Forge hosts are link servers, not fenced sites, and grant no network reach.

   **Amended 2026-11-22 ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4 PR A), as built, for tasks.** Bindings on `session.new` (the first bullet) are not built ([#479](https://github.com/darkhonor/maknae/issues/479)); what follows is where a task's bindings come from. The recognizers and the chooser are `crates/maknae-agent/src/hints.rs`; the working-directory read is `crates/maknae-loop/src/workdir.rs`; intake is `seal_bindings` in `crates/maknae-kernel/src/task.rs`.
   - **The site authorizes hosts only.** `forges:` names a `host[:port]` and a provider, never a repository or a path, and nothing else authorizes a binding's server. Which repository on an authorized host a task may reach is PR B's reach check (decision 7), never a list (decision 2).
   - **A link to a host that is not a forge is not bound, and the task is still submitted.** This replaces "refused at the client, with the reason". The client binds a link only to the host of a `git` forge in its subject's catalog, matched exactly (ASCII case-insensitive, port included), over `https` only. Any other link is left out of the bindings, the echo says why (for example `not bound: evil.example: unknown server`, `not https`, or `no forge list` when the catalog was refused or failed its digest), and the task is submitted without it. The echo lists at most 32 candidates not bound and counts the rest on one line. Intake still refuses a *submitted* binding whose server is not the host of a current `git` forge (`task not bound: server <s> is not the host of a git forge`), so a client that ignores the hint gains nothing. *The failure it prevents:* a prompt that quotes an unrelated link would otherwise refuse the whole task.
   - **The repository-only forms.** On a `github` forge, `https://<host>/<owner>/<repo>/pull/<n>` binds the change, and any other link into a repository binds its first two path segments, the repository only. On a `gitlab` forge, `https://<host>/<group>/…/<project>/-/merge_requests/<n>` binds the change, and any other link binds the project path before the first `/-/`; a path with no `/-/` that contains one of GitLab's route segments is not bound (`ambiguous GitLab path`). The client drops a repository-only candidate when a change candidate names the same repository; intake refuses only an exact duplicate.
   - **Reserved first segments.** A first path segment that is the forge's own page, not an owner, never binds. GitLab's list is the "Reserved group (top-level) names" of its documentation (`docs.gitlab.com/user/reserved_names`). GitHub publishes no such list, so its list (55 entries, `GITHUB_RESERVED`) is maintained in code; an organization whose name is on it does not bind, which fails closed. *The failure it prevents:* `https://github.com/settings/tokens` bound as the repository `settings/tokens`.
   - **Shorthand and bare names.** `owner/repo#N` and `owner/repo!N` bind only when the catalog names exactly one distinct `git` forge, counted by host and provider (with more than one, `ambiguous shorthand`). On GitHub, `#N` is the change and `!N` is not a form; on GitLab, `!N` is the merge request and `#N`, an issue, binds the repository only. A bare `owner/repo` binds only inside backticks, to the one forge, or when it equals a working-directory remote's repository, to that remote's forge. **Bare numbers (`#12`, `PR 12`) are context, not bindings.** *The failure it prevents:* with one forge, `and/or`, `src/main.rs`, `TCP/IP` and `N/A` bound as repositories, and once PR B refuses a task whose repository answers 404 (decision 7), a misread word would refuse a legitimate task.
   - **The tasker's working-directory remotes.** `maknae agent <name>` reads the remotes of the checkout it was started in, once per session, and offers each forge repository they name as a binding of every task the session submits. It is built into the client, not yet a `binds:` resolver (decision 4). The walk takes the nearest `.git`, never through a symlinked `.git`, and follows a `.git` file's `gitdir:` and `commondir` (worktrees and submodules). Every file and directory it reads, the checkout directory that holds `.git` included, must be owned by the tasker and not world-writable; group-writable is accepted (ruling 2026-11-22, put to the maintainer): RHEL and Rocky's user-private-group umask `002` makes git write `0664` configs and `0775` directories, and refusing group write would refuse every checkout on those hosts. The `.git` file, `commondir` and `config` must each have exactly one link, and `config` is at most 64 KiB. Only `remote.<name>.url` is read, in ssh, scp, `git` and `http(s)` forms; `include` and `insteadOf` are not followed, and userinfo (a token in a URL) never leaves the parser. A remote matches a forge on its hostname, port aside, and **the sealed server is the forge's configured `host`**; a hostname that matches more than one forge is not bound (`ambiguous forge`). A checkout that cannot be read is said once, on stderr, and binds nothing; outside a checkout nothing is said. **Residual:** a member of the tasker's group who can write the checkout's git configuration can change which repository the task names. The kernel checks only the host, and PR B's reach check bounds the repository.
   - **The bound at the client.** The client keeps at most 8 candidates and cuts at `TASK_BINDING_REQUESTS_MAX_BYTES` (decision 2), as a prefix; each candidate cut is echoed `over the bound of 8 bindings or 976 bytes`. After submission the echo names what the kernel sealed (`bound: <server>/<base>[ change <n>]`), never what was sent.
   - **Sub-tasks match exactly, and the Agent Daemon reads no working directory.** It runs the link recognizers over the sub-task's prompt only, and keeps a candidate that equals one of the parent's sealed bindings on (server, base, change); intake refuses any other, and refuses one whose server is no longer the host of a `git` forge. The sealed binding is the parent's own. **Residual:** a repository-only candidate does not match a parent's change binding on the same repository, so it is not carried.
   - **A remote tasker.** `Tasker::Remote` does not reach intake today; the sealing function refuses a remote tasker's binding, and is unit-tested there.
   - **Residual: an agent's own-initiative task may bind any repository on an authorized host** until PR B's reach check exists, because nothing bounds the repository but the host. Until [#479](https://github.com/darkhonor/maknae/issues/479) no tool request reads bound values (decision 2), so it has no production effect.

   **Amended 2026-11-24 ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4 PR B): the own-initiative residual above is closed by failing closed.** An agent's own-initiative task may still bind any repository on an authorized host, but its reach is bounded. Its tasker side is the submitting agent's own observed reach: a reach frame for the submitter's GitHub App, base operations only, with no head. When the submitter's credential is not observed at submission (`AtHandOut`, such as a machine user) or it has none, the tasker side is empty, so the task's effective reach is empty: the task is stored, and once reach is enforced (PR C, [#479](https://github.com/darkhonor/maknae/issues/479)) it can act on nothing. A sub-task whose parent was sealed without `reach` (a PR A task) is refused (`task not reached: parent task has no reach`). An agent-channel submission carries no forge token, and one that does is refused.

4. **Tool entries declare what they bind.** A `tools.yaml` entry gains `binds:`, naming the binding kinds it consumes and, for each, a resolver chosen from a closed list in Maknae's code. A new resolver is a Maknae change; a new entry using an existing resolver is administrator data. **Missing binding, missing tool:** an entry whose binding kind the conversation or task does not carry is not offered to the model and is refused if called. A credential class's narrowing uses the binding (the `github-task` class mints for the bound repositories at the permission decision 7 allows). Command patterns may reference bound values (`gh pr view {git.change} -R {git.base}`). `network.sites` stays host-level: the proxy sees a host and a port, never a path, so after intake a repository is bounded by the site, through the narrowed token.

5. **The model sees a filtered view, never `tools.yaml`.** The front end offers the model what the subject may call now: entries that are enabled, allowed by the subject's `Tool(...)` grants (for a task, the agent's), and whose binding kinds are present. For each, the model sees the entry's name and description and the granted program patterns with bound values filled in. It never sees an entry it cannot call (a refusal says "not available", never "exists but not granted"), nor the fence: image references, credential classes, sites, volumes, resources or argument denials. The file lies under `/etc/maknae/**` in the shipped `sensitive.yaml`. The offering follows the model protocol in use, through the single invocation tool of [ADR-0036](ADR-0036-the-tool-model.md) decision 21; it is a convenience, and the control is the per-call decision. Administrators see the full configuration through `admin.config.show`'s disclosure rules.

   **Amended 2026-11-21 ([#674](https://github.com/darkhonor/maknae/issues/674), [ADR-0039](ADR-0039-the-per-subject-tool-catalog-and-forges.md)):** the filtered view reaches the clients as the per-subject tool catalog: `maknaed` compiles it from the site's `tools.yaml`, `forges:` and the subject's grants, serves it through `tool.catalog` and stamps its digest on `TaskClaim` and `session.new` replies. Its patterns are the entry's own ceiling patterns that the subject's grants overlap, less those a deny provably covers, so enumeration is conservative: the catalog can list a pattern a concrete call still refuses, which this decision's "never sees an entry it cannot call" did not allow for. The front end filters it further by the bindings present. It is a hint; the control is still the per-call decision.

6. **Identity decides reach.** A person's CLI session uses the person's own credential, and the provider enforces the person's reach; Maknae keeps no copy of it. An agent uses its own identity (a GitHub App installation, a bot user), whose reach its owner grants at the provider. Who may use that reach is the agent's `taskers:` list. A task never runs on the tasker's credential.

7. **The intersection: a task reaches only what both its tasker and its agent can reach.**
   - **The tasker side is #168 scope item 4, adopted.** At submission the tasker's client reads the tasker's own token, seals it to the Egress Daemon, and `maknaed` carries it unopened ([ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md)). The Egress Daemon calls `GET /repos/{owner}/{repo}` for each bound repository as the tasker and as the agent; the result is the lower of the two, per repository and per operation, against the repository that operation touches (the base for reading, reviewing and merging; the head for pushing to the change's branch). Whether one token carries every permission set or one token is minted per set stays open (`design/egress-and-tool-execution.md` §10 item 13). The tasker's token serves that read only and is never stored. A missing login, an expired token, a 401 or a 404 refuses the task. The tasker side was measured on 2026-10-19 for user OAuth tokens and on 2026-10-22 for fine-grained personal tokens.
   - **The agent side for a GitHub App installation is unmeasured and owed**: whether `GET /repos` returns `permissions` for an installation token, and otherwise derivation from the installation's repository list and the App's granted permissions. So is the mapping from a role level (`pull`, `push`) to an installation-token permission set.

     **Amended 2026-11-19:** Measured 2026-11-19 ([ADR-0038](ADR-0038-the-egress-daemon-mints-trust-plane-credentials.md)): an installation token's `GET /repos` `permissions` block is present and all `false`; the agent side is derived from the installation's repository list and the App's granted permissions, never from that block.
   - **A credential class's `kind` implements the reach check.** `github-app-installation` does the pair above; another kind brings its own. **A tool entry whose `credential` names a class whose kind implements no reach check is refused in tasks** (fail closed). Entries with `credential: none` are unaffected.
   - **Agents as taskers.** An agent's own-initiative task (root `agents/<id>`) intersects with the agent's own reach only. A sub-task's tasker half comes from its parent's sealed result, restricted to the sub-task's bindings, because its submitter is an agent and holds no tasker token. Its agent half is checked afresh for the sub-task's own agent, which needs only that agent's identity. The sealed result is the lower of the two, per repository and operation, so a task chain never reaches beyond any agent in it or its root tasker.
   - **Timing.** The intersection is observed at submission and sealed as `reach`. The installation token is minted at hand-out from that sealed result, and every re-mint during the task re-runs the agent-side check. Hand-out re-decides the tasker's role and the agent's `taskers:` ([ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md), amendment 2026-11-11, statement 10), not the tasker's provider reach.

   **Amended 2026-11-24 ([#168](https://github.com/darkhonor/maknae/issues/168) slice 4 PR B), as built: reach is observed at submission and sealed; nothing enforces it yet.** The forge-specific code is `crates/maknae-forge` (one module per forge: link recognizers, sans-I/O reach observers, mint dispatch); the Egress Daemon drives the observers (`crates/maknae-deputy/src/reach/`); intake is `crates/maknae-kernel/src/reach.rs`. GitHub is the only forge that observes reach.
   - **Nothing consumes `reach` yet.** It is sealed into the task, shown to the tasker, listed in the task view and recorded in the trail. No tool request, no mint and no hand-out reads it until PR C and [#479](https://github.com/darkhonor/maknae/issues/479).
   - **The operations.** Reach is a set of neutral operations per binding, on two sides: `Read`, `Review`, `IssueWrite` and `Merge` against the base, and `PushHead` against the head. The effective reach is the tasker side intersected with the agent side, per side and per operation (`effective_reach`, `crates/maknae-proto/src/reach.rs`). An agent side of `AtHandOut` or `NoForgeCredential` gives an empty effective reach, so a task chain is never wider than any agent in it.
   - **The tasker's token.** The tasker stores it once with `maknae forge login <server>`, a wrapped write to `<kv_mount>/data/<user_prefix>/<username>/forges/<host>`, field `token` ([ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md), amendment 2026-11-24). At submission the client does a wrapped read with the person's own Vault login and seals the wrapping token to the Egress Daemon under its own associated-data domain, `maknae-seal-aad-forge-v1`, binding the purpose, a nonce, the server, the expected path and the field. `TaskSubmit` and `TaskAdd` carry one sealed token per bound server whose forge observes reach, spelled as the binding spells it, at most 8. The kernel refuses a token for a server no binding names and any token on the agent channel. Tokens travel on the verb, never in `TaskSubmission`, and are never stored. The client no longer reads `gh`'s store.
   - **The tasker side on GitHub.** `GET /repos/{base}`, whose five `permissions` booleans give the tasker's role: `pull` or `triage` gives `Read`, `Review` and `IssueWrite`; `push`, `maintain` or `admin` adds `Merge`. For a change, `GET /repos/{base}/pulls/{n}` gives the head repository, and `GET /repos/{head}` gives `PushHead` at `push` or above; a head equal to the base reuses the base's role. A deleted head repository gives no head operations, with the reason `HeadGone`. All five booleans `false` is an observation, and seals empty base operations. **Every other answer refuses the task:** a missing login, an expired token, 401, 404, 403 or 429, a redirect, a 5xx, a malformed body, no answer or the reach deadline. That includes a 404 for a working-directory remote and for `pulls/{n}` when `#N` names an issue (maintainer, 2026-11-23: "if the repo doesn't exist or access was revoked outside of Maknae, then the task is denied").
   - **The agent side for a GitHub App installation**, on the measured basis (2026-11-19). With the App's Transit-signed JWT, `GET /app/installations/{id}` gives the App's granted permissions: `Read` needs `contents`, `metadata`, `pull_requests` and `issues` all at `read` or above; `Review` needs `pull_requests: write`; `IssueWrite`, `issues: write`; `Merge`, `contents: write` and `pull_requests: write`; `PushHead`, on the head, `contents: write` (`admin` counts as `write`). A suspended installation refuses. Coverage comes from one installation-wide `metadata: read` token ([ADR-0038](ADR-0038-the-egress-daemon-mints-trust-plane-credentials.md) decision 3, amendment 2026-11-24), `GET /installation/repositories` (100 per page, at most 10 pages) and an immediate revoke. A base not listed gives an empty agent side with the reason `AgentNotCovered`, not a refusal; a head not listed gives no head operations. `GET /repos` is never called with an installation token.
   - **Which kinds are observed.** The kernel classifies each of the agent's granted `git` credentials through `maknae-forge` at boot: `github-app-installation` is observed; `github-machine-user` is `AtHandOut`, so its effective reach is empty until PR C observes it at hand-out; GitLab kinds implement no reach check, so a GitLab binding seals empty reach with the reason `NoReachCheck` and its tools stay refused in tasks. More than 8 observed credentials on one server, or two Apps on one host for one agent, refuse the task.
   - **Where the API is.** The Egress Daemon finds a forge's API base in `minting.yaml` `apis:` ([ADR-0038](ADR-0038-the-egress-daemon-mints-trust-plane-credentials.md) decision 7, amendment 2026-11-24). The tasker side needs only that map; the agent side also needs the App and a ready minter, without which it is `NoForgeCredential`. A server with no `apis:` entry, and a host with no `minting.yaml`, refuse every task bound to a GitHub forge, because the tasker side cannot be observed.
   - **Sub-tasks.** The tasker side is the parent's effective reach for the same binding, with the reach of an addendum binding included; the agent side is observed afresh for the sub-task's agent.
   - **Bounds.** `egress.reach_deadline_ms` (default 20,000, 1,000 to 300,000) bounds one submission's reach, starting when reach starts; each frame carries the time left as `deadline_ms`, which the Egress Daemon enforces. After reach the store steps get a fresh `decide × 2`. At most 4 reach exchanges run at once on each side of the egress socket (`REACH_CONCURRENCY_MAX`), and waiting for one counts against the deadline (`reach outcome unknown: at capacity`). Reach shares the egress connection pool and is not counted in the prompt breaker.
   - **The trail** records an intent before each frame and its outcome after it, and the submission's records carry `subject.reach` ([ADR-0019](ADR-0019-audit-record-model.md), amendment 2026-11-24). The wire still answers only "refused"; the class is in the trail (`task not reached: …`).
   - **Residuals.** The tasker's reach is observed at submission only (residual 1). A stale working-directory remote refuses every task from that checkout. A fork head the tasker cannot read (a private fork answering 404) refuses the whole task. An installation with more than 1000 repositories is under-covered, which fails closed. `Read` needs all four App permissions, so an App granted only `metadata` and `pull_requests` gets no `Read`. `PushHead` is under-approximated for a fork whose pull request allows maintainer edits. An own-initiative task through an App has no head, so no `PushHead`. Nothing ties the stored token to the local user's GitHub identity. A compromised kernel can use a tasker's single-use sealed token to probe repositories of its choosing, because the associated data binds no asks. Classification is per provider, not per host, so a GitHub Enterprise Server machine user makes github.com bindings `AtHandOut` too; both outcomes are empty. GitHub Enterprise Server is unmeasured.

   **Amended 2026-11-26 ([#746](https://github.com/darkhonor/maknae/issues/746), [#168](https://github.com/darkhonor/maknae/issues/168), maintainer ruling in the walkthrough of `design/diagrams/generated-task-tool-lifecycle.svg`): a stored-token side is observed through `forge_auth` before the task is claimable, and the Egress Daemon computes the intersection.** A target decision, not built. The task-store side of it is [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md)'s amendment of the same date.
   - **Which sides.** Every side whose credential is a stored token held by an agent (`github-machine-user`) is observed through `forge_auth` to that agent:
     - the target agent's side, always;
     - for an own-initiative task, also the submitting agent's side, which is that task's tasker side.
     - A sub-task's tasker side still comes from its parent's sealed reach. Its agent side uses `forge_auth` when the sub-agent's credential is a stored token.
     - An agent holding both an App and a stored-token credential on one server refuses the task, as two Apps on one host do.
   - **The flow.**
     1. At submission the Egress Daemon opens the tasker's wrapping token at once and observes the tasker side, as before. The token is single use with a 60 s TTL (`USER_KEY_WRAP_TTL`), so it cannot wait for the agent.
     2. The kernel assigns the task id before the first reach frame, so every sealed copy can bind it. It stores the submission `AwaitingReach`, answers the tasker, and queues `forge_auth` (the task id and the forge servers, no credential) for the agent. The agent receives it on its notice poll, every 5 s in every state.
     3. The agent does a wrapped read of its own stored token per named server and seals each wrapping token to the Egress Daemon under `maknae-seal-aad-forge-v1`. The associated data carries its own purpose (agent side), a nonce, the server, the expected path (`<kv_mount>/data/<agent_prefix>/<id>/forges/<host>`, field `token`: the tasker's layout under the agent's own tree, which [ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md)'s amendment of 2026-11-13 lets only that agent's AppRole read) and the field. The Egress Daemon checks the purpose and the wrapping token's `creation_path`, as it does for the tasker side, so neither side's token can be replayed as the other's.
     4. The kernel relays the sealed tokens, unopened, with the Egress Daemon's sealed copy of the first-observed side. The Egress Daemon calls `GET /repos/{base}` (and the head, as for the tasker side) as the machine user, maps the `permissions` booleans as it does the tasker's, and computes the intersection.
     5. The kernel decides on the result, signs the task with it once, and queues it. **A task is never claimable before its reach is decided.**
   - **The Egress Daemon computes the intersection, for every reach frame** (App included). It returns both sides and the effective reach, and the kernel decides on them. Every observation it returns comes with a copy sealed to itself, as `for_revocation` is, whose associated data binds the task id and the sealed bindings. The kernel stores that copy and relays it in the frame that completes the other side. The Egress Daemon checks both bindings, so the kernel can neither alter an observation nor swap in another task's. When both sides are stored tokens, the frame carrying the second answer intersects.
   - **Outcomes follow the App side's rules.**
     - An observation seals, an empty one included.
     - A 404, or a 403 without rate-limit headers, on the base as the machine user gives an empty agent side, `AgentNotCovered`.
     - No stored token for the server gives `NoForgeCredential`. That includes a GitHub Enterprise Server machine user bound to github.com.
     - A 401, an expired or mismatched wrapping token, a redirect, a 429, a 403 carrying rate-limit headers, a 5xx, a malformed body or the deadline refuses. Because no caller waits on it, a refusal closes the task `NotReached`, which the tasker collects.
   - **Bounds.** Each agent-side frame gets its own `egress.reach_deadline_ms`, and the agent's 60 s wrapping-token TTL bounds it too.
   - **Addenda.** A `TaskAdd` with a new binding to a working task whose agent's credential is a stored token is held as a unit, the addendum with that add's follow-up, until its reach is decided.
     - While held, the follow-up does not count toward the task's follow-ups, so the report check (ADR-0033 amendment 2026-11-11, statement 7, amended 2026-11-13) never waits on it. The kernel accepts the `forge_auth` answer for the held add (ADR-0033, amendment 2026-11-26, statement 3).
     - On a refused agent side the unit is discarded and the task keeps working. The tasker sees "add not reached" in `status` and `list`, and the trail records it.
     - Any `TaskAdd` while one awaits is refused.
   - **What the tasker sees.** `TaskSubmit` answers at once with the bindings, the tasker side and "awaiting the agent's reach". The effective reach shows in `status` and `list` once decided. A `NotReached` close is collected.
   - **Rejected alternatives.**
     - *A Vault KV read for the Egress Daemon over agents' tokens.* It would reverse [ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md) decision 6 and ADR-0038 decision 5: no process acting for many users holds a standing grant over their credentials.
     - *A second leg after hand-out.* It queues a task its agent cannot act on, and adds a path for a frame that never arrives.
     - *Holding the tasker's wrapping token until the agent answers.* It dies at 60 s, behind a busy or offline agent.
   - **This replaces:**
     1. In the tasker-side bullet, "The Egress Daemon calls `GET /repos/{owner}/{repo}` for each bound repository as the tasker and as the agent; the result is the lower of the two". The Egress Daemon still computes the lower of the two, now returning it with both sides, and a stored-token side is observed through `forge_auth`.
     2. In "Agents as taskers.", "Its agent half is checked afresh for the sub-task's own agent, which needs only that agent's identity". A stored-token sub-agent needs its `forge_auth` answer.
     3. In "Timing.", "The intersection is observed at submission and sealed as `reach`". A stored-token side is observed when its agent answers, and the task is sealed then.
     4. In the 2026-11-24 "The operations.", "The effective reach is the tasker side intersected with the agent side … (`effective_reach`, `crates/maknae-proto/src/reach.rs`)". The Egress Daemon computes it. In "An agent side of `AtHandOut` or `NoForgeCredential` gives an empty effective reach", `AtHandOut` stays decodable for stored tasks and is never written again.
     5. In "The tasker's token.", "The kernel refuses a token for a server no binding names and any token on the agent channel". The `forge_auth` answer is the one exception, for the servers its notice named.
     6. In "Which kinds are observed.", "`github-machine-user` is `AtHandOut`, so its effective reach is empty until PR C observes it at hand-out". It is observed through `forge_auth`.
     7. In "Bounds.", "bounds one submission's reach, starting when reach starts". It also bounds each agent-side frame.
     8. In "The trail", "the submission's records carry `subject.reach`". An awaiting task's reach is recorded when it is decided, with the notice, the answer and each agent-side frame.
     9. In "Residuals.", "a GitHub Enterprise Server machine user makes github.com bindings `AtHandOut` too; both outcomes are empty". The agent holds no token for that server, so `NoForgeCredential`.
     10. In decision 3's own-initiative amendment, "When the submitter's credential is not observed at submission (`AtHandOut`, such as a machine user) … the tasker side is empty". It is observed through `forge_auth` to the submitting agent.
   - **Residuals.**
     - A 403 for SSO enforcement seals an empty agent side without a refusal.
     - A fine-grained token's `permissions` block was measured on 2026-10-22; a classic token is unmeasured.

8. **Labels are extensible security attributes, separate from bindings, and fail closed.**
   - **Separate concerns.** Bindings say what the work is about; labels are attributes an operand evaluates (classification, releasability, compartments, or whatever an engine brings). **Overloading `labels` with bindings is rejected.**
   - **Keys name a provenance and a namespace.** A label key is `<provenance>.<namespace>.<key>`, where the provenance is `entry` (a `tools.yaml` entry), `task` or `binding`. Maknae's core enumerates no namespace. Labels reach the request's resource bag. The existing bare `classification` resource key is unchanged: it is the object's own marking, written only by the kernel from the object's own label (`crates/maknae-security/src/request.rs`), and no label ever writes it.
   - **Who may write which label.** Entry labels are administrator data. Task and binding labels are supplied by a client and can only add refusals: an operand that claims `task.classification` refuses when that label ranks above the system's declared level, and refuses a token it cannot rank (a foreign system's level is refused by name, [ADR-0022](ADR-0022-classification-policy-as-data.md)). A client label never stands in for the object's own marking, so it cannot lower or widen it. An entry's accreditation (the most its environment may receive) is the opposite relation to a marking (a property of what is sent), so it is carried as an `entry` label and evaluated only by an operand that decides destination dominance (`design/egress-and-tool-execution.md` §9); the default build has none.
   - **The claim rule.** Each operand declares the (provenance, namespace) pairs it evaluates. A `tools.yaml` entry carrying a pair no loaded operand claims is disabled with a load warning, so one entry never takes the file down; a task or a session carrying one is refused. An unclaimed label is a refusal, never an abstention. A claimed label is evaluated on every request that cites its task or conversation, never once at intake. The default build's ceiling claims `task.classification` and `binding.classification` and nothing else, so an entry carrying an accreditation label is disabled until an operand that decides dominance claims it. An external authorization engine claims its own pairs when it is loaded. Mandatory operands still never permit ([ADR-0008](ADR-0008-authorization-composition-contract.md)).
   - **Values flatten into the contract's `AttrValue`**: a level as `Str`, compartments and releasability as `Set`. The contract's `List` carries ordered values such as a tool's arguments, which labels never use. The claim declaration is an additive change to the `Authorizer` contract under [ADR-0004](ADR-0004-modular-authorization-architecture.md) §6.
   - Site attributes (`design/egress-and-tool-execution.md` §9) use the same namespaces, so an engine sees one vocabulary across tools, tasks and sites.
   **Amended 2026-11-22 ([#695](https://github.com/darkhonor/maknae/issues/695), [ADR-0040](ADR-0040-the-agent-message-board.md) decision 6):** the provenances are `entry`, `task`, `binding` and a fourth, `post`. This replaces "the provenance is `entry`, `task` or `binding`". A post carries the labels the kernel stamps on it, copied from the author task's labels when it is written. On a `board.read` decision of that post, they reach the resource bag as `post.<namespace>.<key>`. The reader's own task is the cited task, so its labels are `task.*`; the post needs names of its own for an operand to compare the two. Until tasks carry labels, no post carries any.

9. **Side effects are their own grants.** Posting is a separate pattern on a separate entry that the site defines for it (for example `Tool(github-post gh pr review --comment *)`), and each review decision (comment, request changes, approve) is its own shape, so a site grants or withholds each one. Who may approve whose pull request, and whether an approval counts toward a merge, is the forge's policy, not Maknae's. Merging is a separate act again ([#676](https://github.com/darkhonor/maknae/issues/676)). This satisfies [#480](https://github.com/darkhonor/maknae/issues/480).

10. **Every request is decided in full.** Bindings, labels and the intersection result are inputs to each decision, never a cached verdict. Each tool call cites its conversation or task and is decided on the subject's grants (for a task, the agent's role), the bindings and labels in the resource bag, and the mandatory operands.

### A pull-request review, worked end to end

Alice is in hobi's `taskers:`. She runs `maknae agent hobi -p "Review https://github.com/darkhonor/maknae/pull/345"`.

1. Her client recognizes the link and binds `git`: server `github.com`, base `darkhonor/maknae`, change 345. It shows her the binding, seals her GitHub token to the Egress Daemon and submits.
2. Intake decides `session.task` on her role and hobi's `taskers:`, re-validates the binding against site configuration, checks that every label the task carries is claimed, and runs the intersection: the change's head is `darkhonor/maknae` too; alice holds `pull`, hobi's App installation covers `darkhonor/*`; the result is `pull` on `darkhonor/maknae`. The binding and the result are sealed into the task.
3. Hobi claims the task; the installation token is minted for `darkhonor/maknae` at `pull`. The model is offered `rust-fetch` (whose `gh` patterns, with the bound values filled in, read `gh pr view 345 -R darkhonor/maknae` and `gh pr diff 345 -R darkhonor/maknae`), because hobi's grants allow it and its `git` binding is present, and `rust-build`, which binds nothing and holds no credential. A posting entry is offered only if hobi holds its grant, and each posting call is still decided against that grant and the sealed result.
4. Each call is decided in full. The launch obligation carries the bound values; `gh` runs as hobi's uid, in a container whose only workspace mount is the task's directory, with the narrowed token.
5. A model that also reads the repository's ADRs or `AGENTS.md`, or searches the web, works inside the same fence: the same workspace, the same token, and only the sites hobi's entries allow.
6. The report returns to alice through the kernel.

**A fork variant.** Had the change come from `contributor/maknae`, the link would still name only the base. The intersection call reads the head from the pull request, checks reading against the base and pushing against the head, and finds hobi's App not installed on the contributor's fork. The task can read and review; any push to the change's branch is refused.

## Consequences

- **Residuals.**
  1. The tasker's provider reach is observed at submission only. Hand-out re-decides the role and `taskers:`, and each re-mint re-checks the agent's reach, but nothing re-checks the tasker's. The window runs from submission until the task's outcome is recorded; nothing bounds the queue time or the working time today.
  2. In a person's own CLI session a binding bounds servers and command patterns, not repositories: the person's credential is broad and the proxy sees hosts. It bounds the model, not the person, who could reach the repository anyway.
  3. Shared behavioural memory is not bound; it is not built. AC-6 stays partial for memory, described, not decided, in [`design/intent/behavioural-memory.md`](../intent/behavioural-memory.md); no issue tracks it (maintainer, 2026-11-19).
  4. An agent's taskers share its reach by its owner's choice; each reaches at most the intersection of their own access with the agent's.
  5. Every installation token can read public repositories (`design/egress-and-tool-execution.md` §10 item 13).
  6. Patterns that reference bound values bind the model, not a compromised Agent Daemon, whose own account can run a tool with any token it reaches (`design/egress-and-tool-execution.md` §5.4).
  7. The agent side of the intersection for a GitHub App installation is unmeasured until measured (decision 7). *(Amended 2026-11-19: Measured 2026-11-19 ([ADR-0038](ADR-0038-the-egress-daemon-mints-trust-plane-credentials.md)): an installation token's `GET /repos` `permissions` block is present and all `false`; the agent side is derived from the installation's repository list and the App's granted permissions, never from that block.)*
- **Some tools stop working in tasks until their credential kind has a reach check.** ADR-0036's own `vault` example (`vault-child-token`) is refused in tasks from the day this lands, and so is any stored-token class until its kind implements a check. A person's CLI session is unaffected.
- **#474 is satisfied** by this ADR. **#420 decision 2 is settled.** **#480 is satisfied** (decision 9).
- **Amended in place:** [ADR-0036](ADR-0036-the-tool-model.md) (`binds:`; credential classes narrow from bindings; the filtered view); [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) (task classes rejected; the envelope is the sealed bindings and intersection; the AC-6 row); [ADR-0004](ADR-0004-modular-authorization-architecture.md) (the claim declaration as an additive contract change); [ADR-0033](ADR-0033-agent-identity-admission-and-tasks.md) (the task object's `bindings`, `reach` and evaluated `labels`); [ADR-0008](ADR-0008-authorization-composition-contract.md) (the ceiling operand's two new inputs).
