# ADR-0006: Client authentication (AuthN) model — the trust plane is the sole client-facing door; clients never reach Vault; local peer-cred now, OIDC-federated gateway later

- **Status:** Accepted (operator-ratified 2026-08-22)
- **Date:** 2026-08-22
- **Deciders:** Alex Ackerman (operator)
- **Relates to:** ADR-0005 (enforcement locus & TCB boundary — `maknaed` is the sole PDP; the gateway is "owed"; *amends* it with a bootstrap exception to the client-leaf requirement, Decision 6); ADR-0018 (local-plane authorization & deployment model — *amends* its operator-CLI standing-SecretID); ADR-0019 (audit record model — the authenticated uid is captured per request); ADR-0020 (access-control model — the **authorization** counterpart this AuthN model feeds). Issues: #66 (the gateway / remote-client boundary), #73 (el9 operator-CLI `0400` seal residual — OPEN; *superseded on broker-landing*, see Consequences), #89 (`--user` cannot use `--with-key=tpm2` — already **patched** via `--with-key=auto`, closed 2026-08-16).

> **Scope: authentication, not authorization.** This ADR fixes *who a client is and how it proves that* (the IA family). It does **not** decide what an authenticated client may do — that is the reference monitor's per-request call, deny-by-default (ADR-0020, the AC family). AuthN establishes identity and hands it to the PDP; establishing a session is never itself an authorization.

> **Number-reuse note.** Per the registry convention (2026-08-22) an ADR takes a number at authoring and freed numbers are reused; `0006` previously held the (unwritten, since-embodied-in-AGENTS.md) single-source-of-truth doctrine. The filename and registry topic are the identity — the bare number is a handle.

## Context

Today Maknae is a single host: the `maknae` CLI and `maknaed` daemon run on the same box, talking over an mTLS UDS (ADR-0005). In the shipped design the CLI authenticates to **Vault** directly (its own AppRole SecretID → mint a `cli`-plane leaf → mTLS to the daemon), which forced a per-platform at-rest seal for that standing SecretID — the `systemd-creds --user` / Keychain split, and the RHEL-9 residual gap (#73, #89).

Two forces make that model wrong going forward:

1. **The client is untrusted by design, and will become *remote*.** The daemon will grow a network listener; the target is controlling Maknae from an iOS app over 5G/VPN. A remote, untrusted client must **not** be assumed to have — or need — a network path to Vault. Punching Vault out toward untrusted networks, and issuing every client a Vault identity, is the opposite of the reference-monitor posture.
2. **Short-lived, brokered credentials are the idiomatic model.** The current design handed a *human operator* a *machine credential* (a standing AppRole SecretID). AppRole+SecretID is for machines; humans authenticate via a human method and receive short-lived tokens.

## Decision

1. **The trust plane is the sole client-facing authentication endpoint.** A client — local or remote — authenticates to and transacts only with the trust plane (`maknaed` locally; the **gateway**, #66, remotely). Clients **never** reach Vault, the lake, model endpoints, or any other trust infrastructure directly. The trust plane is the sole broker to Vault. This is the reference-monitor principle (ADR-0005, AC-25) projected onto the network boundary: one authenticated door, everything trusted behind it.

2. **Clients hold no standing Vault credential at rest.** Client credentials are **short-lived and trust-plane-brokered**. (The *daemon's own* machine identity — a standing AppRole SecretID, HRoT-sealed — is a separate concern and is unchanged; ADR-0018. This ADR governs *client/operator* authentication only.)

3. **Local (on-host) client authentication = OS host-login + `maknae`-group membership + peer-cred uid.** The operating system has already authenticated the user at host login; membership in the `maknae` group over the `0660` UDS is the gate, and `SO_PEERCRED` binds the principal (uid). That authenticated uid is captured in **every** AU-3 audit record (ADR-0019), so attribution of who did what on the trusted host is already exact. The on-server CLI therefore holds **no** Vault credential and needs no separate `maknae login` — the OS session is the login; the trust plane brokers everything else. Leaning on host-login is a stated, accepted assumption for the on-server CLI. The mTLS `cli`-plane leaf that ADR-0005 requires on the channel is unchanged as a requirement — under this model the trust plane **brokers a short-lived leaf** for the client off the peer-cred bootstrap, rather than the CLI minting it from a standing SecretID.

4. **Remote client authentication = OIDC federation through the gateway.** The remote client authenticates natively to an external identity provider (e.g. GitHub, Azure AD) and presents the resulting **trusted token** to the gateway (#66) over TLS; the gateway validates it (federated identity, IA-8) and brokers a **short-TTL session** to the trust plane. No Maknae standing secret is stored on the client. The mobile benefit — a lost, stolen, or seized device forfeits only an expiring session, not a standing Maknae credential — holds **only if the device's IdP credentials are also short-lived exposure**: native OIDC devices commonly retain a refresh token or a reusable IdP browser session that can mint fresh access tokens, so the model REQUIRES those to be **sender-constrained (e.g. DPoP / mTLS-bound) and gateway-revocable**, and MUST NOT rely on long-lived bearer refresh tokens. Absent that, a retained refresh token is a longer-lived exposure — so the gateway MUST be able to revoke a device's sessions (and, where the IdP allows, its tokens) on report of loss (#66). The Maknae side stores nothing durable regardless.

5. **The client stays untrusted across the boundary.** A client is authenticated **per session** and authorized **per request** by the sole PDP (deny-by-default, ADR-0020). A valid session is identity, never entitlement.

6. **Bootstrap — issuing the client credential cannot itself require that credential.** A fresh client holds no `cli` leaf, yet ADR-0005/ADR-0018 require a verified `cli`-plane leaf to serve a normal request — so **leaf issuance must be a distinct, credential-optional handshake**, or the model is circular (it cannot). The trust plane therefore exposes a **credential-optional issuance step**, and the counterpart, credential, and TLS termination differ by boundary — the two are **not** one flat tunnel to the daemon:
   - **Local** — the counterpart is `maknaed` over the UDS. The channel is TLS 1.3 with `maknaed` presenting its `plane/kernel` server cert; the client is authenticated by `SO_PEERCRED` (uid ∈ `maknae` group), no leaf presupposed. `maknaed` then brokers the short-lived `cli` leaf and returns it, after which **every subsequent request uses full mutual mTLS** with that leaf (ADR-0005, unchanged on the wire). **Brokering requires a Vault signing capability the daemon does not hold today** — ADR-0005 scopes each plane's policy to its *own* `pki/sign/<plane-role>` and forbids the kernel identity from signing the `cli` role (custody-by-secret-absence); see the owed-decision note below.
   - **Remote** — the counterpart is the **gateway** (#66), which presents its **own** server identity — **never the daemon's `plane/kernel` key** (TLS does not terminate by impersonating the daemon) — and authenticates the client by the OIDC-federated token (Decision 4). The gateway is itself a trust-plane component that reaches `maknaed` over a **separate internal `gateway↔daemon` session**; the remote client **does not reach `maknaed` directly and holds no `cli` leaf** — its session is `client↔gateway`. Two distinct identities, two distinct sessions; the gateway both validates OIDC independently *and* speaks the internal channel — neither is sacrificed to a pass-through tunnel.

   This **refines, not weakens, ADR-0005's "mTLS from the start"**: the channel is never plaintext, the trust plane is always server-authenticated, and only the *client-auth factor* for the single issuance handshake differs from steady state (peer-cred / OIDC instead of a not-yet-existent client leaf). The issuance path carries the **same fail-closed + AU-3 audit** as the normal gate — a non-`maknae`-group peer is refused and audited (ADR-0018 decision 1(b), ADR-0019) — and locally the `SO_PEERCRED` uid is a **kernel-attested** factor, unforgeable over the `0660` UDS. On the local plane **any `maknae`-group member** may obtain a leaf via issuance, with per-request attribution by that uid (AU-3); finer *per-member* authorization is deferred to the gateway/PDP (ADR-0018's accepted "group = local authorization, multi-user deferred" model), not the bare-metal local plane. The concrete issuance wire protocol is implementing-spec / gateway (#66) work; an append-only note is added to ADR-0005 and ADR-0018.

   **Owed decision — the broker signing capability (blocks the local brokered path, and thus #73's closure).** For `maknaed` to broker a `cli` leaf it needs a Vault capability its current kernel-only policy scope denies — the daemon's *authentication* to Vault (AppRole SecretID, HRoT-sealed, periodic token) is unchanged, but a scoped *signing* grant is new and must be ratified. Because the leaf is now **plane-generic and not the authorization principal** (Decision 7), letting the trust plane mint it is **not** the escalation the original custody criterion guarded against: the forbidden direction — a `cli` identity signing a `kernel` leaf — is untouched, and the authz principal remains the kernel-attested peer-cred uid. **Recommended resolution:** grant `maknaed` a **narrowly-scoped `pki/sign/cli-role` (issuance-only) capability** and update ADR-0005's per-plane-policy acceptance criterion accordingly; the alternative is a **separate broker identity** scoped to cli issuance (keeps the kernel role pristine at the cost of a second secret to custody). This changes an operator-ratified ADR-0005 property, so it is **owed to the operator to ratify** before the brokered local path is implemented; until then the standing operator-CLI SecretID and its el9 `0400` residual (#73, OPEN) remain in effect.

7. **The authenticated principal is carried into every PDP decision — the `cli` leaf is not an operator identity.** Per ADR-0005 the `cli` leaf's URI-SAN binds the *plane* (`maknae://<deployment_id>/plane/cli`), not the operator; but authorization (ADR-0020: sole PDP, deny-by-default, **per request**) needs the *principal* on every call, or an operator authenticated once at bootstrap silently becomes indistinguishable afterward. **Locally** the principal is the `SO_PEERCRED` uid — present on every connection, already captured in AU-3 (ADR-0019) — so per-operator attribution and authorization hold with no extra mechanism. **Remotely** there is no peer-cred and — per Decision 6 — the client holds no `cli` leaf at all (its session is `client↔gateway`), so the validated OIDC principal (and its claims → subject attributes) MUST be carried into each request, through the gateway to the sole PDP, by a **cryptographically channel-bound session / subject context** — never inferred from plane membership. Two consequences follow and are load-bearing: a `cli` leaf is **never sufficient identity for authorization** (it proves plane membership, not who), and a `cli` leaf **cannot be lifted to impersonate its holder** — locally the daemon binds the actual `SO_PEERCRED` uid, not the leaf; remotely the client holds no leaf to lift (Decision 6) and authorization rides the channel-bound session regardless. The concrete envelope — a per-operator leaf identity vs. a bound subject-context token, with audience + replay binding — is owed **subject-context work tracked as issue #19** (an *issue*, not a reserved ADR number, per this registry's number-at-creation rule); the *requirement* that the principal reach every PDP call is fixed here.

## Consequences

- **The per-platform CLI-seal problem is superseded — once the brokered path lands.** In the target model the on-server CLI holds no Vault credential (the trust plane brokers a short-lived one), so there is nothing to seal at rest. This **supersedes** the CLI-seal requirement rather than patching it — but the change is prospective, not accomplished: **#73 (the RHEL-9 `0400` plaintext CLI-SecretID residual) is OPEN and resolves *by removal* only when the brokered local path (owed, below) lands.** Until then the residual and the ADR-0018 standing operator-CLI SecretID **remain in force** — do not close #73 or strip the residual before the broker replaces it. **#89** (`--user` cannot use `--with-key=tpm2`) was already **patched** (`--with-key=auto`, commit `56dd0ab`, closed 2026-08-16); this model removes the seal *class* it lived in going forward. A cleartext SecretID on disk was the symptom of the wrong model — the endpoint of this model removes the credential, not just the seal.
- **Vault stays private, behind the trust plane** — never exposed to clients or to untrusted networks. The edge attack surface shrinks to one authenticated door.
- **Supersedes (in target model) ADR-0018's operator-CLI standing SecretID.** ADR-0018's daemon-side model (standing AppRole SecretID, HRoT-sealed, periodic token) is unchanged; only the *operator CLI* credential model moves here. An append-only amendment is added to ADR-0018.
- **Local and remote are one model, differing only in the authentication factor** (peer-cred uid vs. OIDC-federated token) — so the local implementation built now is forward-compatible with the gateway, not a throwaway.
- **Owed work:** the trust plane grows a client-facing authenticate-and-broker path — locally a peer-cred bootstrap that brokers a short-lived cred, remotely the gateway's OIDC front door (#66). The on-server brokered path is the near-term implementation that resolves #73 the right way.
- **Per-operator remote identity is native** via OIDC (each human is their own IdP identity); on-host, per-user attribution comes from the peer-cred uid. Multi-operator is therefore a property of the model, not a bolt-on.

## Scope boundary

Fixes the **authentication model**: the sole-door principle, credential lifetime (short-lived, brokered, none-at-rest-on-client), and the local (peer-cred) vs. remote (OIDC) authentication factors. It does **not** specify: the concrete **gateway** mechanism or wire protocol (#66's implementing spec); the OIDC integration detail (providers, token validation, claim mapping); the local bootstrap wire protocol (implementing spec); or **authorization** — what an authenticated client may do (ADR-0020, the reference monitor). The daemon's own machine authentication (ADR-0018) is out of scope and unchanged.
