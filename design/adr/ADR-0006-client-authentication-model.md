> **Scope: authentication, not authorization.** This ADR fixes *who a client is and how it proves that* (the IA family). It does **not** decide what an authenticated client may do — that is the reference monitor's per-request call, deny-by-default (ADR-0020, the AC family). AuthN establishes identity and hands it to the PDP; establishing a session is never itself an authorization.

> **Number-reuse note.** Per the registry convention (2026-08-22) an ADR takes a number at authoring and freed numbers are reused; `0006` previously held the (unwritten, since-embodied-in-AGENTS.md) single-source-of-truth doctrine. The filename and registry topic are the identity — the bare number is a handle.

> **Implementation status — the code does NOT yet implement this ADR.** The shipped code implements the pre-ADR model: the CLI holds an AppRole SecretID (per-platform sealed at rest), self-mints a `cli`-plane leaf, and speaks mutual mTLS to the daemon. ## Context

Today Maknae is a single host: the `maknae` CLI and `maknaed` daemon run on the same box, talking over an mTLS UDS (ADR-0005). In the shipped design the CLI authenticates to **Vault** directly (its own AppRole SecretID → mint a `cli`-plane leaf → mTLS to the daemon), which forced a per-platform at-rest seal for that standing SecretID — the `systemd-creds --user` / Keychain split, and the RHEL-9 gap where enroll cannot complete at all (#73, #89).

Two forces make that model wrong going forward. First, **the client is untrusted by design, and will become *remote*** — the daemon will grow a network listener; the target is controlling Maknae from an iOS app over 5G/VPN. A remote, untrusted client must not be assumed to have — or need — a network path to Vault; punching Vault out toward untrusted networks, and issuing every client a Vault identity, is the opposite of the reference-monitor posture *(for local users, ADR-0028 issues each a userpass Vault identity, by maintainer ruling; see decision 1's note)*. Second, **the current design handed a *human operator* a *machine credential*** (a standing AppRole SecretID). AppRole+SecretID is for machines; humans authenticate via a human method and receive short-lived sessions.

An earlier draft of this ADR fixed the symptom (no standing SecretID) but kept the client credential as a Vault-issued X.509 leaf, brokered by the daemon — which required granting the trust plane a `cli`-signing capability ADR-0005 deliberately withholds (custody-by-secret-absence), and made local and remote clients mechanically asymmetric. The operator directed a ground-up threat assessment of the authentication strategy (2026-08-22); three candidate strategies were evaluated against the trust assumptions and threat model below and against DoD ZT RA v2.0 / NIST SP 800-207 / SP 800-63. The selected strategy (this ADR) removes the client X.509 requirement instead of working around it.

## Trust assumptions (operator-ratified, 2026-08-22)

1. **The OS host posture is STIG'd and access is limited to authorized individuals.** Host login is a trustworthy authentication event; Maknae *inherits* OS authentication (IA-2 satisfied by the platform's login; AC-2 account management by the platform) rather than re-implementing it. This is an explicit, documented external authority, not implicit trust — see §Alignment.
2. **`maknae`-group membership is a root-gated administrative act.** Nobody drifts into the trust boundary; an administrator deliberately enrolled them — and removal from the group is, symmetrically, the local de-enrollment/revocation act (Decision 4).
3. **An *externally achieved* OS compromise (root obtained by non-Maknae means) is outside Maknae's threat model** — root owns the daemon's memory, sealed secrets, and socket; no scheme Maknae runs on that host survives its own root. These are things the platform (STIG, access control, scanning) handles and Maknae never can.
4. **Maknae as the escalation *vector* is squarely inside the threat model — it is threat #1.** A user authenticated *to Maknae* must never be able to escalate to *host-level* access through any Maknae component. Direction matters: host→Maknae compromise is the OS's failure; Maknae→host escalation is *our* failure and must be impossible. (This is a primary reason the kernel is Rust — ADR-0002.)
5. **When the remote boundary exists, the gateway is in the TCB for remote principal assertion.** The gateway (#117) validates OIDC and *asserts* the resulting principal to the PDP over its machine channel; a compromised gateway can therefore impersonate **enrolled remote subjects** to the PDP. That risk is *bounded*, not defeated (T10): gateway compromise never yields the **daemon's** `plane/kernel` identity or local principals, and no Vault authority beyond the gateway's **own** scoped credential (its own AppRole + `pki/sign/<gateway-role>` under ADR-0005's per-plane pattern — final grant design at #117 — whose compromise also inherits ADR-0005's honest mount-wide-revoke DoS residual, now reachable from a network-facing component — therefore **#117 MUST scope the gateway's Vault policy to exclude `pki` revoke, or place gateway credentials on a separate mount**, so the residual does not extend to the network boundary); every asserted principal still faces the per-request deny-by-default PDP. Admitting a second trust-plane component is a deliberate TCB expansion, named in the ADR-0005 amendment — it is the price of never exposing `maknaed` to untrusted networks, and it is why the gateway carries its own scoped identity and policy. *(Narrowed 2026-11-05, decision 11: the gateway no longer asserts a principal on its own say-so. It forwards the IdP's signed assertion, and `maknaed` verifies it on every request. The gateway stays in the TCB for what it alone enforces: the client↔gateway channel binding and sender-constraint, its visit clock, and revocation on report of loss. A compromised gateway can act only for subjects whose assertions it holds and that are still live, until they expire or the per-request check sees them revoked. The Vault-policy rule above is unchanged.)*

## Decision

**The strategy in one sentence:** *every human client, local or remote, is an admin-enrolled principal, authenticated at its boundary's door by that boundary's native factor, and carried in a **bounded** session (connection-scoped locally, short-TTL remotely) to the sole PDP on every request.* (Non-human and channel-mediated surfaces are explicitly out of scope — see §Scope boundary.) *(Scoped 2026-10-23, #550: one non-human subject is now in scope. The Agent Daemon authenticates as a workload, by decision 9.)*

1. **The trust plane is the sole client-facing authentication endpoint.** A client — local or remote — authenticates to and transacts only with the trust plane (`maknaed` over the UDS locally; the **gateway**, #117, remotely). Clients **never** reach Vault, the instance's local Knowledge Lake (the KLC's tiered store — the *external* standalone lake is never read at runtime, ADR-0005), model endpoints, or any other trust infrastructure directly. This is the reference-monitor principle (ADR-0005, AC-25) projected onto the network boundary: one authenticated door per boundary, everything trusted behind it. *(Amended 2026-10-01 by ADR-0028, for local users only: a local user's CLI reaches Vault with the user's own userpass identity, to read the user's own provider key and, while the local channel still uses a client certificate, to mint it. Remote clients are unchanged.)*

2. **X.509 / Vault PKI is machine identity only; client authentication is a session, never a certificate.** Plane leaves (ADR-0005) identify *workloads* — the daemon, and later the gateway's internal channel. Humans and client apps never hold a Maknae certificate or any Vault credential. A client's credential is a **bounded session** minted by its boundary's door after the boundary-native factor authenticates — **connection-scoped locally** (Decision 4), **short-TTL and revocable remotely** (Decision 5). This dissolves the prior draft's central defect — no client leaf exists, so no issuance bootstrap exists, and **no new Vault or PKI capability is granted to anyone**: ADR-0005's machine-plane policy scoping and custody-by-secret-absence are unchanged, and retiring the `cli` client role strictly *narrows* the PKI grant surface. Session-minting authority is boundary-local, and the normative contract is: **locally, no token is issued at all** — the session is a daemon-side record (Decision 4), so there is no key-custody question and nothing survives a daemon restart (clients re-establish transparently from peer-cred); a **token-shaped session exists only where a client must hold a handle — the remote boundary** — where it is gateway-held state or a gateway-keyed token whose custody is #117 implementing work, constrained here: sender-constrained, revocable, and **MUST NOT introduce a new Vault grant** for session purposes. To be precise about what already exists: this is not the platform's first identity-shaped capability — the kernel already links the *privileged* subject-context mint (`maknae-subject-ctx-mint`, ADR-0005) for scoped task identities — but this ADR adds **no new** minting or signing authority, and a session forged by a compromised daemon is honoured only by that same daemon: it confers nothing off-daemon and nothing at the host layer (T0, T5). *(Amended 2026-10-01 by ADR-0028, for local users only: a local human holds a userpass Vault identity and a token at rest under the CLI credential's custody. The certificate half of this decision is unchanged: while the local channel still uses a client certificate (until #114/#116), that identity mints it. This decision remains the target model for remote clients.)* *(Scoped 2026-10-23, #550: "no new Vault or PKI capability is granted to anyone" holds for client authentication. Decision 9 gives the Agent Daemon, a workload, its own `pki/sign` role under ADR-0005 decision 4's per-plane pattern, as assumption 5 already does for the gateway. It also gives the administrator who enrolls and de-enrolls agents a Vault policy scoped to agent credentials, as `maknae enroll` already has for `maknaed`. Humans still never hold a certificate.)* *(Amended 2026-11-05: decision 11 adds one Vault grant for remote client authentication, to `maknaed` itself: the IdP client credential `maknaed` holds for introspection: one secret path it can read, used for introspection only. That the IdP client is configured without the client-credentials grant is a deployment requirement Maknae cannot check, which #117's documentation must state. It is a read, not a minting or signing capability.)*

3. **Enrollment precedes authentication, on both boundaries, as an explicit administrative act.** Locally, root adds the user to the `maknae` group (assumption 2). Remotely, the Maknae Admin **enrolls the OIDC subject** — a merely *valid* IdP identity is refused (T9). Nobody can authenticate whom an administrator did not first ratify — and symmetrically, **de-enrollment is the revocation act**: group removal locally (enforced by Decision 4's re-check), enrollment-list removal + session revocation remotely (Decision 5). Authorization-to-authenticate is never implicit.

4. **Local (on-host) authentication = a live OS host-login session + current `maknae`-group membership + kernel-attested peer-cred, with the session daemon-side and uid-bound.** *(Amended 2026-10-23, [#550](https://github.com/darkhonor/maknae/issues/550): this decision authenticates **human** clients on the client socket, and it is unchanged for them. It refuses a service by design, and that refusal stands. The Agent Daemon is not admitted here under any factor. It authenticates on its own socket, by decision 9, and an agent account is never a `maknae`-group member. That is not enforced today: the shipped gate admits any process that presents a verified `plane/cli` leaf and is in the `maknae` group, and the human-session check is #115. ADR-0024 decision 6's ordering constraint keeps the Agent Daemon (#472) from shipping before this is enforced.)* The STIG'd OS is the local identity provider (assumption 1); `SO_PEERCRED` re-attests the uid on **every connection** — a kernel-attested, non-replayable, non-exfiltratable factor. The channel is TLS 1.3 over the `0660` UDS with `maknaed` server-authenticated (`plane/kernel` cert); the client presents no certificate. On **every connection — and re-evaluated on every request over that connection** — the daemon verifies that (i) the live peer-cred uid equals the session's bound uid, (ii) that uid is **currently** a member of `maknae` — membership re-resolved from the host's user database, *not* trusted from the client process's snapshotted supplementary groups — **and (iii) that the connecting *process* belongs to a live *human* login session** — the binding is **per-process, not per-uid**: on Linux/logind, resolve the peer PID's **own** session (`sd_pid_get_session`, cgroup-derived) and require **that session** to have `Class=user` and `State ∈ {active, online}`; a process with no session is refused. A uid-scoped search ("does this uid have *any* qualifying session") is **forbidden**: it admits a cron job, lingering unit, or logout leftover whenever the same user happens to be concurrently logged in elsewhere — the connecting process's own context, not its owner's best session, is what authenticates (deny-by-default). The peer-PID→session resolution must be race-hardened against PID recycling (e.g. pidfd; #115 implementation detail). The `Class` field of the process's own session is the discriminator that makes this a *human*-login check: `Class=background` sessions do **not** qualify (on RHEL-family hosts `pam_systemd` in the `crond` stack registers a real logind session for cron/at jobs — distinguished by Class, not State), `Class=manager` does not qualify (a lingering user's manager; `Linger` is a logind *User* property, not a session state — a lingering user typically has no qualifying session at all), `State=closing` (post-logout leftovers) does not qualify, and no-qualifying-session is refused. Because peer-cred proves *process ownership*, not that the login premise still holds, this refuses a leftover `nohup`/`tmux`-after-logout process, a lingering user unit, and a cron job wearing an enrolled uid (operator-ratified addition, 2026-08-22; autonomous scheduled work is deliberately *not* a human session — it belongs to the scope-excluded task-identity surface (c), never to a human's uid). Running the CLI as another uid (`sudo -u <user> maknae`) yields no qualifying session for the *target* uid and is **deliberately refused** — authenticate as yourself. **Platform scope — decidable, config-driven, fail-closed:** the platform branch is selected by an explicit **deployment-mode key in the daemon's config** (exact key: implementing spec, #115), read at boot and **fail-closed on absence or ambiguity** (ADR-0005's config posture: any config error → exit non-zero). The runtime never *infers* its platform from the presence or absence of a registry — "logind is down on a bare-metal host" and "we are in a pod" are observationally identical yet MUST resolve in opposite directions, so the branch must come from ratified configuration, never from observation. **Linux host mode:** the logind predicate above; an unavailable registry **denies** (the infrastructure-denial class). **macOS host mode:** the factor is retained, and *equivalent* is a **criterion, not a mechanism** — the check MUST **(1)** distinguish a **human login session** (console, tty, *or* SSH — all qualify, matching Linux) from a **background/scheduled context** (launchd jobs, cron, daemons), and **(2)** report *absent* after logout. **No single macOS mechanism supplies both properties, so the check is two-part:** the peer's **BSM audit token** (read off the socket via `LOCAL_PEERTOKEN`; `auid ≠ AU_DEFAUDITID`) supplies **(1)** — human-vs-background, kernel-attested exactly like peer-cred, launchd/cron contexts carry `-1` — but **not (2)**: `auid` is set once at login and **inherited immutably**, so a post-logout `nohup`/`tmux` process retains it (precisely the T11 leftover case). Liveness **(2)** MUST come from a registry that *clears at logout* — a current `utmpx` entry for the uid (tty/SSH) or the `SCDynamicStore` console user (GUI). **Known platform asymmetry, stated:** the macOS liveness half is uid-scoped (no per-process logout-clearing registry exists), so a post-logout leftover under a uid that is *concurrently* logged in elsewhere passes on macOS where the Linux per-process binding refuses it — the residual is a live-human-owned uid, per-request-attributed, bounded by the visit clock; #115 MAY tighten it if a per-session mapping proves practical. #115 implements both parts, and the "logged-out uid refused at the next request" negative MUST run on **macOS as well as Linux** — it is the test that tells these mechanisms apart. **Container mode (Kubernetes / Compose-Podman):** the local human client path is removed by **construction in depth** (operator-ratified 2026-08-22), each layer catching what the previous cannot: **(1) packaging — the OCI image ships `maknaed` only; no `maknae` client binary exists in the image** (the everyday guarantee — enforced at build by a **shipped-artifact inventory witness** in `ci/gates/`, mirroring ADR-0005 decision 3's witness pattern: the OCI image MUST NOT contain a `maknae` client binary; owed with #81/#116); **(2) the client listener is not bound at all** — container mode binds only the machine-mTLS listener (#114's per-listener split), so there is **no client socket to connect to**: a `kubectl exec` / `podman exec` shell — or a binary copied in with `kubectl cp`, which defeats layer 1 — has nothing to reach, and **no human-vs-workload discrimination is required**, keeping the branch decidable purely from config; in-cluster workloads use the machine listener with platform identity (ADR-0018's "multi-user collapses into the Kubernetes/gateway case"). Human access on the container path is the gateway (#117) — enforced by schedule as well: the operator has **shelved OCI builds until the gateway lands** (#81/#117), so a gateway-less container deployment cannot ship. **Boot self-verification (operator-ratified 2026-08-22): the environment verifies the declaration; it never selects the branch.** At startup `maknaed` cross-checks the declared mode against environment characteristics and **refuses to boot on contradiction** (exit non-zero, audited — ADR-0005's config posture): `linux-host` requires a systemd boot signature (`sd_booted()` / `/run/systemd/system`) **and** the absence of any *filesystem* container marker; `container` requires at least one container marker; on a macOS build, any declared value other than `macos-host` is itself a mismatch and refuses boot (and vice versa) — so the refusal holds in either direction on all three modes. **Marker evidence is ranked:** *filesystem/mount* markers — the Kubernetes serviceaccount mount (`/var/run/secrets/kubernetes.io/serviceaccount/`), `/run/.containerenv` (Podman), `/.dockerenv` (Docker) — are created inside the container's own mount namespace, cannot appear at host level, and are **authoritative**; *environment* markers — `KUBERNETES_SERVICE_HOST`, `container=` — are ordinary inherited process environment and are **corroborating only**: they MAY satisfy the `container` requirement (they only ever permit) but MUST NOT alone refuse a `linux-host` declaration (a hand-run `maknaed` on a k8s worker node with `KUBERNETES_SERVICE_HOST` exported for `kubectl` convenience must not self-outage). The marker list is **non-exhaustive and maintained by #115** — measured on the production-path cluster (RKE2/containerd, 2026-08-22): a real pod carries **only** `KUBERNETES_SERVICE_HOST` and the serviceaccount mount; `/run/.containerenv`, `/.dockerenv`, and `container=` are all absent under containerd, and `/run/systemd/system` is absent in-pod (so the `linux-host` rule correctly fails there). A systemd-inside-container image declared `container` is tolerated by design (the `container` rule requires a marker, not the absence of systemd — the asymmetry is deliberate and does real work). The reverse case is likewise deliberate: a **`systemd-nspawn`** container — whose only marker is the corroborating-class `container=` and which runs its own systemd *and logind* — boots as `linux-host` by design, because the Linux predicate functions normally inside it; reclassification, if ever wanted, is a #115 marker-list update, not an ADR change. Observation can *stop* the daemon, never *choose* its mode — a host config baked into an image, or a container config on bare metal, dies loudly at boot instead of surfacing as mysterious runtime denials. Spoofing these markers requires root/unit control (assumption 3, out of scope). So **de-enrollment — and logout — terminates access at the next request, even over a connection that is already open**: a long-lived connection never outruns its enrollment (today's per-invocation CLI makes the per-connection and per-request checks coincide, but the per-request rule is what makes the guarantee hold for any future long-lived client); group removal and logout *are* the local session-termination mechanisms (AC-12). **Lookup-failure semantics are fail-closed:** on a domain-joined host the membership lookup may traverse SSSD/LDAP, so a directory outage denies local connections **and in-flight requests** — an accepted availability trade, consistent with ADR-0018's "genuine external failure is a legitimate fail-closed trigger" (its anti-self-outage stance rejects *self-inflicted* shutdowns, which this is not); *(qualified 2026-11-05, decision 11 residual (1): an SSSD host answering from its offline cache does not deny, so this holds only where the host identity stack is configured to fail rather than serve cached entries)*; the denial is audited (AU-3) as an **infrastructure denial, distinguishable from a de-enrollment or logout denial**; an unavailable session registry (logind) is the same fail-closed infrastructure-denial class. Because the checks are per-request, **two lookups** sit on every PDP call's hot path — the group resolution (possibly remote, via SSSD/LDAP) and the logind liveness query (a local D-Bus round trip) — so #115 **SHOULD** adopt a bounded-TTL *positive* cache for either lookup where cost demands it (remote membership sources especially); **a cache TTL bounds both the de-enrollment latency and the logout latency — it MUST be stated by #115 and MUST NOT exceed an operator-configured maximum (default 60 s)**. *(Struck 2026-11-05, decision 11, maintainer: no positive cache is permitted for either lookup. Zero Trust inspects every request on current facts, so de-enrollment and logout take effect at the next request as far as Maknae is concerned; the host identity stack's own caches still apply, decision 11 residual (1).)* One precision for the implementer: the `SO_PEERCRED` uid is kernel-captured at connect and cannot change for the connection's lifetime, so the per-request re-validation is genuinely dynamic for the two revocable factors — **group membership and login-session liveness** — while the uid check is fixed by the kernel at connect (Decision 7). Check (i) is therefore a **defensive session-map integrity assertion, not an authentication factor**: it has no adversarial failure mode by construction (the session's uid is derived from the same kernel fact it is compared against). The authenticating facts are the kernel's peer-cred, the per-request group re-resolution, and the per-request session-liveness check, and the negative tests target those — a non-member refused at connect, a de-enrolled member refused at the next request, a logged-out uid refused at the next request (**on both Linux and macOS**), no client socket existing in container mode (a connect attempt finds nothing to reach — fail-closed by absence; note this is the one denial in this ADR `maknaed` itself cannot AU-3-record: an unbound socket yields a client-side error with nothing daemon-side to log — platform-layer audit only), a **request written by a foreign uid over a delegated fd refused** (Linux: `SCM_CREDENTIALS` mismatch), and a **boot refusal on a declared-mode/environment mismatch in either direction** — not an unconstructible uid mismatch (ADR-0016 / AGENTS.md: every assertion must be able to go red). **Per-request sender verification (Linux, closes T13):** the daemon sets **`SO_PASSCRED`** on the client socket, so every request message carries **kernel-verified `SCM_CREDENTIALS` of its *actual sender*** — which MUST match the session's bound uid. A connected fd passed to another uid (`SCM_RIGHTS`) therefore does **not** transfer identity even while the original connector stays alive: the recipient's own writes carry the recipient's kernel-attested credentials, mismatch the session, and are refused and audited. **Attribution is per-message, not per-connection.** macOS has no per-message sender-credential facility (`LOCAL_PEERCRED`/`LOCAL_PEERTOKEN` are connection-scoped): the fd-delegation residual there is equivalent to **voluntary credential sharing** (T4 class — a willing or compromised principal can always proxy by other means), documented as an attribution caveat, bounded by the visit clock; #115 MAY explore stronger macOS bindings. **Evidence note (measured 2026-08-22, Rocky 10 / systemd 257 + RKE2 cluster + macOS):** the predicate's discriminators were verified on live systems, not inferred — a cron job fired with its own logind session of **`Class=background`** (confirming `pam_systemd` in the RHEL `crond` stack and that `Class`, not `State`, is what refuses it); an SSH session showed `Class=user, State=active`; a lingering user's manager showed `Class=manager`; `sudo -u <user>` yielded **no** logind session for the target uid (and Linux `loginuid` stayed sticky at the invoker — the exact analog of macOS `auid` immutability); a logged-out session holding a surviving `nohup` process showed **`State=closing`** (refused as specified); host-level `/run/.containerenv` and `/.dockerenv` remained absent with podman installed and running; a production-path pod carried only the two markers noted above; and on macOS a login-session process carried `auid = uid` with `LOCAL_PEERTOKEN` present in the SDK (the `auid = -1` background half is #115's macOS negative test). Measurements are from el10/systemd 257; el9 shares the same RHEL PAM layout (`pam_systemd` via `password-auth`), and #115's test matrix MUST include el9 confirmation. **The normative local session contract (one sentence): the session is a daemon-side subject-context record keyed to (uid, connection), established at connect after all checks pass, re-validated on every request, and discarded at disconnect; no token or handle is ever issued to the client** — nothing session-shaped exists on the client, at rest or otherwise (T2), which is what actually retires the seal problem (#73); local session lifetime *is* connection lifetime — itself bounded by the visit clock below and by per-request re-validation; there is no separate session-*credential* TTL locally (credential-TTL semantics apply only to the remote boundary, Decision 5) — and locally a daemon restart simply drops connections, the same event as disconnect. **The daemon also owns the visit clock (operator-ratified addition, 2026-08-22):** `maknaed` imposes an **idle timeout** and an **absolute maximum connection lifetime** on every client connection — trust-plane-owned termination authority, independent of any client-held state (SC-10). Expiry *is* the disconnect event (the session record dies with the connection), and re-establishment re-runs the full gate **including a fresh kernel peer-cred capture** — defense-in-depth behind the per-message `SCM_CREDENTIALS` check on Linux, and the *primary* bound on the fd-delegation residual on macOS, which lacks per-message sender credentials. The timer values are #115's to fix and MUST be stated; the clock bounds the *connection*, not cumulative use — an immediate reconnect is acceptable precisely because re-establishment re-runs the full gate with fresh captures. Its value over bare peer-cred is *uniformity* — the same session/subject-context contract the remote boundary uses (Decision 7) — not additional authentication strength. The on-server CLI (the Maknae Admin's surface for admin functions, troubleshooting, and AI-harness testing) therefore holds no credential at rest and needs no separate `maknae login` — the OS session is the login. *(Amended 2026-10-01 by [ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md), for local users only: the CLI holds a userpass Vault token at rest and `maknae login` obtains it, for Vault; the certless plane channel described here is unchanged.)* There is no bootstrap problem: the first connection authenticates exactly like every other, by peer-cred; no credential is presupposed.

5. **Remote authentication = OIDC federation through the gateway, hardened.** The remote client authenticates natively to an external IdP (e.g. GitHub, Azure AD) and presents the assertion to the **gateway** (#117) over TLS; the gateway validates it against the **enrolled-subject list** (Decision 3) and mints a **short-TTL, channel-bound session** that the gateway holds and can revoke. REQUIREd properties: **(a)** the IdP MUST enforce MFA / conditional access (AAL2, SP 800-63B) — Maknae delegates the factor, not the requirement; **(b)** assertion presentation MUST be injection-protected — REQUIREd concretely: back-channel presentation **and, where the deployment claims SP 800-63C-3 FAL2, assertion encryption to the gateway as well** (under 800-63C-**3**, FAL2 = signed *and encrypted-to-RP* assertions; 800-63C-**4** §5 frames the FAL2 bar as injection protection via back-channel presentation or encryption — this model REQUIREs the protections either way; a signed *bearer* assertion alone is only FAL1 under both revisions); **(c)** sender-constraint (DPoP / mTLS-bound keys — the SP 800-63C holder-of-key / FAL3 direction) applies to **both legs**: the device-retained IdP credential (refresh token / IdP session) *and* the client↔gateway session itself; long-lived bearer refresh tokens MUST NOT be relied on; **(d)** the gateway MUST be able to revoke a device's sessions (and, where the IdP allows, its tokens) on report of loss (T7); **(e)** the gateway owns the same **visit clock** as the local plane (Decision 4, operator-ratified 2026-08-22): an idle timeout and an absolute maximum session/connection lifetime **in addition to** short TTL and revocation-on-demand — client-independent termination authority (SC-10); expiry forces full re-authentication at the door, re-evaluating every connect-time-fixed fact (channel binding, session keys), with no per-request IdP round-trip in steady state. *(Amended 2026-11-05, decision 11: struck "no per-request IdP round-trip in steady state". Every request now carries the IdP's assertion, which `maknaed` verifies and whose subject's account state it checks against the IdP. The visit clock is unchanged.)* The gateway presents its **own** machine identity (never the daemon's `plane/kernel` key), reaches `maknaed` over a **separate internal mutual-mTLS machine channel**, asserts the validated principal per assumption 5, and the remote client **never reaches `maknaed`** — its session is `client↔gateway`. *(Amended 2026-11-05, decision 11: the gateway forwards the IdP's signed token instead of asserting the principal; `maknaed` verifies it.)* A lost, stolen, or seized device forfeits an expiring, revocable, sender-constrained session — no durable Maknae credential exists on any client.

6. **The client stays untrusted across the boundary.** A client is authenticated **per session and re-validated per request** (locally: current group membership and live host-login session on every request, Decision 4; remotely: bounded by session TTL, gateway revocation, and the gateway's visit clock — **no per-request IdP round-trip**, Decision 5) and authorized **per request** by the sole PDP (deny-by-default, ADR-0020). A valid session is identity, never entitlement. *(Amended 2026-11-05, decision 11: remotely, the assertion and the subject's account state are now checked on every request, as the local factors already are.)*

7. **The authenticated principal is carried into every PDP decision.** Locally the principal is the `SO_PEERCRED` uid — kernel-captured at connect and immutable for the connection's lifetime, present on every connection, captured in every AU-3 record (ADR-0019). Remotely the validated OIDC principal (and its claims → subject attributes) rides the gateway-held session and is asserted, with the gateway's own identity, into each request to the sole PDP — never inferred from plane membership, network location, or content self-labeling (inform-but-not-authorize, AGENTS.md). The session is the **carrier** of identity and subject context (the concrete envelope is the subject-context work, issue #19 — an *issue*, not a reserved ADR number, per the registry's number-at-creation rule); the *requirement* that the principal reach every PDP call is fixed here. This is also the designed insertion point for later attribute enrichment — device posture (#112), DCS clearance — without changing the model. *(Amended 2026-11-05, decision 11: remotely, what is carried into each request is the IdP's signed assertion, verified by `maknaed`, not a principal the gateway asserts. The channel identifies the component that carried the request; it never identifies the principal.)*

8. **Maknae is never the privilege-escalation vector (T0).** No Maknae component performs an action on a client's behalf that exceeds that client's own authority on the host or in the policy model: the daemon does not proxy host access, exposes no setuid-like surface, and a Maknae session confers exactly zero host-level rights. Any design change that would have the trust plane act with its own privileges *for* a client is a security decision requiring an ADR, not a convenience (AGENTS.md core principle 3). **Found violated in shipped code, 2026-08-30 — this assumption is load-bearing, not aspirational.** The `fs.read` path resolves a client-supplied name with the daemon's own `_maknae` credentials and never evaluates the subject's access to the target ([#186](https://github.com/darkhonor/maknae/issues/186)); `peer_uid` reaches the PDP as an attribute but never reaches the filesystem. [ADR-0009](ADR-0009-subject-side-os-dac-evaluation.md) is the ADR this clause demands, and it **restores** the assumption — the subject opens the object itself and delegates the descriptor — rather than carving an exception into it. *(Dated pointer 2026-09-07: [ADR-0023](ADR-0023-runtime-loop-role-and-placement.md) §8 is the ADR this clause requires for the one exception taken so far — the `maknae-egress` process spending a daemon-held provider credential on an enrolled subject's behalf, scoped to the single-subject Cooky MVP, trigger to revisit: the second enrolled subject.)* *(Resolved 2026-10-01 by [ADR-0028](ADR-0028-per-user-model-providers-and-kernel-blind-credentials.md): the Egress Daemon holds no provider credential; it spends a user's key only through that user's own single-use wrapping token, so the exception no longer exists.)*

9. **The Agent Daemon authenticates as a workload: its own plane leaf, presented on a machine channel, bound to its own uid on a host, with its enrollment decided on every request** *(added 2026-10-23, [#550](https://github.com/darkhonor/maknae/issues/550))*. [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6 makes the Agent Daemon a subject with its own uid, role and Vault AppRole. It is a service, so decision 4's human-session factor refuses it. It is a workload, so decision 2 already names its credential class: a plane leaf. **None of this is built.** #472 builds it, with #114's per-listener verifier split.
   - **The factor.**
     - A plane leaf issued under ADR-0005 decision 4's per-plane pattern: the agent's own AppRole, a Vault policy scoped to `pki/sign` on its own role, and a key generated locally and held in memory only. More than one Agent Daemon may be enrolled, so the leaf's URI-SAN names the specific agent, not only the plane class (for example `maknae://<deployment_id>/plane/agent/<agent_id>`; *dated pointer 2026-11-05, #114: plane identities are now SPIFFE IDs, so the example reads `spiffe://<trust_domain>/plane/agent/<agent_id>`, per ADR-0005 decision 4's amendment*). Each agent's Vault credential can sign only its own name. An `agent_id` is restricted to a character set that cannot widen the role's `allowed_uri_sans` pattern, the invariant `deploy/vault-pki` already enforces for `deployment_id`. #472 fixes the exact SAN and role layout.
     - It is presented over mutual TLS 1.3 on a machine channel, never on the human client socket. On that channel, `maknaed`'s verifier accepts only a leaf whose SAN names an enrolled agent. A `plane/cli` or `plane/kernel` leaf is refused there. In the other direction, the agent pins the Maknae CA bundle and requires `maknaed`'s `plane/kernel` leaf, as each plane does under ADR-0005 decision 4.
     - **Host modes (Linux and macOS): the channel is a Unix domain socket of its own,** separate from the client socket, owned by `maknaed`'s account, mode `0660`, and reachable only by agent accounts through a group that holds no human (never `maknae`). The peer-cred uid must equal the uid enrolled for that agent. This adapts ADR-0005 decision 2's split (*"the cert binds the plane; the peer-cred binds the principal"*): here the leaf names the agent and the uid binds it to the account. The caveat carries over: both facts fall to a compromise of the agent's account.
     - **Container mode:** the channel is TCP across pods, so no peer-cred exists and the leaf alone is the factor. The agent's first Vault credential comes from the platform (Vault's Kubernetes auth), not from a SecretID at rest. De-enrolling there also removes the agent's Kubernetes auth role. Container builds are shelved until #117, so this is target model only.
   - **Enrollment precedes authentication (decision 3).** An agent is admitted only when an administrator has enrolled it. The enrollment maps the agent's id to its uid on a host, and it lives in the kernel's identity layer ([ADR-0029](ADR-0029-kernel-enforcement-state-graph.md)), so every request is decided against the current snapshot. **An enrolled agent's uid MUST be a service account, never one a human logs in as:** it is not a `maknae`-group member and it has no login shell. The check runs at enrollment and again whenever the identity layer is rebuilt (each reload or restart, and any live identity transition ADR-0029 decision 5 may add), and an enrollment that fails it is refused. An agent enrolled "as" a human would merge two subjects, and its SecretID would sit at rest under a human's uid, within reach of that human's cron jobs.
   - **De-enrollment, and what it does not depend on.** A root edit that removes the enrollment applies at the next reload or restart (ADR-0029), or at a live identity transition if one is added. From then on every request is refused, including over an open connection, whatever leaf the agent still holds. The de-enrollment act also destroys the agent's SecretIDs **and revokes its outstanding Vault tokens**: destroying a SecretID blocks new logins only, and a live token can keep signing leaves. The token revocation MUST be scoped to that one agent: for example by disabling its Vault identity entity, by its tracked token accessors, or through an auth mount of its own. It MUST NOT use a lease prefix that also covers `maknaed`'s token or another agent's, because `maknaed`'s AppRole shares today's mount and revoking it would be a self-inflicted outage (ADR-0018). #472 picks the mechanism. The administrator performs this with a Vault policy scoped to agent credentials, not with `maknaed`'s identity. The agent's token MUST have a stated `token_max_ttl` (#472), unlike `maknaed`'s periodic token, so a revocation that was missed still ends. Re-enrolling an agent id after a compromise issues new credentials. Vault's revoke is mount-wide (ADR-0005 decision 4), so certificate revocation is never the off switch: the enrollment check is, and the leaf's TTL bounds only a leaf stolen from a still-enrolled agent.
   - **Connection lifetime.** The visit clock (decision 4) applies to agent connections, and `maknaed` also ends a connection no later than the leaf's expiry, so a connection never outlives the certificate that opened it. On Linux, the per-message `SCM_CREDENTIALS` check of decision 4 applies to the agent's socket. On macOS, the same connection-scoped residual applies, bounded by the visit clock.
   - **What the Agent Daemon's Vault grant excludes.** The agent runtime is untrusted by design. Its policy **MUST NOT** grant certificate revocation on any mount: on the plane mount it could revoke `maknaed`'s leaf, and on a mount shared by agents it could revoke another agent's. This is assumption 5's rule for the gateway, tightened for a component outside the TCB. Today only the kernel plane's policy can revoke; `maknae-user` cannot (`deploy/vault-pki`). The agent keeps token `revoke-self`, so its shutdown revokes its own token as the `maknae-vault` client does. Its leaf's TTL MUST NOT exceed the deployment's `leaf_ttl_seconds`, and #472 states it. Its role sets `no_store`, or #472 states why not, so an untrusted signer cannot grow Vault's certificate store without bound.
   - **It asserts only itself.** The channel carries the agent's own principal (decision 7). Unlike the gateway (assumption 5), the Agent Daemon never asserts another principal, and it joins no TCB. *(Amended 2026-11-05, decision 11: the gateway no longer asserts a principal either; it forwards the IdP's token.)* A tasker's identity reaches the record from the kernel's own intake decision ([#475](https://github.com/darkhonor/maknae/issues/475)), never from the agent's say-so. Decision 8 is unchanged.
   - **A cron job running under a human's uid is still refused (T11).** On the client socket, decision 4's session check refuses it, unchanged. On the agent socket, the verifier refuses any leaf that does not name an enrolled agent, and an account a human logs in as is never an enrolled agent's (above). Until #114 and #116 retire the client certificate, a human can still mint a `plane/cli` leaf; it is refused on the agent socket all the same.
   - **macOS parity.** A launchd daemon running under the agent's account presents the same leaf, and `LOCAL_PEERCRED` supplies the uid. No launchd job identity is needed, and macOS offers no public API for one.
   - **Secret 0.** On a host, the agent's standing AppRole SecretID is placed in OS custody by `sudo maknae enroll agent <id> --account <user> --bind-cidr <cidr>…`, the pattern ADR-0018 uses for `maknaed`: on Linux a TPM2-bound `systemd-creds` credential named `maknae-agent-secret-id` at `/etc/maknae/private/agent-<id>-secret-id.cred`, with no plaintext opt-out; on macOS a System keychain item (service `io.maknae.maknae-agentd`, account `<id>`) trusted only to the Developer ID-signed `/usr/local/bin/maknae-agentd`. The SecretID is minted with `cidr_list` and `token_bound_cidrs` set to the enrolled addresses, so Vault refuses it and its tokens from any source address outside them (as Vault sees the address, so behind NAT the binding is to the translated address). Enrollment refuses an account whose shell is not one of the non-login shells `/usr/sbin/nologin`, `/sbin/nologin`, `/usr/bin/nologin`, `/bin/false` and `/usr/bin/false`, Maknae's own daemon accounts, and an account another agent already holds. `--rotate` mints and seals the new SecretID before destroying the old, and an accessor stays recorded until its destroy succeeds; after sealing, enrollment also lists the role's accessors in Vault and retires every one but the new SecretID's, so an accessor minted and never recorded is reconciled rather than orphaned. Each agent id is therefore enrolled on exactly one host: enrolling or rotating it on another host destroys the first host's SecretID. **Residual (macOS):** the keychain trusts the binary, not a uid, so the boundary between two agents on one host is the agent binary reading only its own enrolled id's item, gated on its euid; that reader is #472's. Decision 4's "nothing at rest" is about human clients and is unchanged.
   - **What mutual TLS gives.** Mutual authentication and the integrity of the channel. It does not give non-repudiation (ADR-0005 decision 2); durable non-repudiation is an ADR-0007 audit control.
   - **Not decided here:** SPIFFE/SPIRE workload attestation as an Enterprise option, selected by configuration ([#554](https://github.com/darkhonor/maknae/issues/554)). It would change how the leaf is issued, not the checks above.

10. **Each party is authenticated by the strongest proof available for it, and a control is claimed only for the property it proves** *(added 2026-11-05, [#114](https://github.com/darkhonor/maknae/issues/114))*. The question asked of every channel is which security property it must prove — server authenticity, peer (component) authentication, principal authentication, confidentiality, integrity — and what mechanism actually proves it. A mechanism that proves nothing for a party is removed, not kept for appearance: a false sense of security is worse than a named gap, because no one goes looking for the gap. Every residual is stated.
    - **Per party.**

      | Party | Proof | What it does not prove |
      |---|---|---|
      | `maknaed` | Its `plane/kernel` server certificate, on every TLS channel it serves; peers pin the Maknae CA bundle. On the Egress Daemon's socket, its uid (below) | That its code is unmodified: no workload attestation exists; its sealed SecretID (ADR-0018) binds the host, not the binary |
      | Local human | The kernel-attested peer uid (`SO_PEERCRED`; per message on Linux, `SCM_CREDENTIALS`), plus decision 4's per-request group and live-login checks, plus decision 11's account-state check. Separately, to Vault: the user's own userpass identity and a token at rest (ADR-0028) | Presence at the keyboard within a live session (§Alignment) |
      | Remote human | The IdP's signed token, verified by `maknaed` on every request (decision 11), carried by the gateway | Device health (#112); that this request came from the subject: sender-constraint (decision 5(c)) is proved to the gateway, so from `maknaed`'s side the forwarded token is a bearer token, and a compromised gateway can replay a live one (T10) |
      | Workload holding a Vault identity (Agent Daemon; the gateway's machine channel) | A plane leaf held by its service account, presented over mutual TLS; for the Agent Daemon on a host, also the peer uid bound to its enrollment (decision 9) | That its code is unmodified: no workload attestation exists (SPIFFE/SPIRE, #554, is undecided) |
      | Workload with no Vault identity (the Egress Daemon, ADR-0028) | Uids, checked in both directions on a local socket: `maknaed` checks before writing that the listener belongs to `_maknae-egress` or root (`listener_uid_is`; on Linux systemd binds the socket, so root is what is seen, trusted per assumption 3), and the Egress Daemon checks before reading that the connecting uid is exactly `maknaed`'s | Confidentiality beyond the OS's socket isolation (no TLS on this channel; below) |
      | An Agent Daemon task's tasker | The kernel's own intake record and the envelope bound there (ADR-0024 decision 6, #475), never the agent's say-so | Unbuilt (#475) |
      | The client binary (CLI, mobile app) | **Nothing.** It runs as the user, so any secret it holds the user can extract. It is untrusted by design, as the agent runtime is: the PDP decides every request, so a modified client gains nothing | Everything; it is not asked to prove anything |

    - **Per channel class.**

      | Channel | Server authenticity | Peer authentication | Principal | Confidentiality and integrity |

Descriptors delegated under ADR-0009 travel as `SCM_RIGHTS` beneath TLS; their integrity is the OS kernel's, and the per-message sender check (decision 4) binds them to the session on Linux; on macOS that is the T13 residual |

      Channels that do not terminate at `maknaed` or the Egress Daemon's socket are governed elsewhere and are not claimed by this table: the CLI → Vault userpass channel (ADR-0028), the Egress Daemon → Vault unwrap and the Egress Daemon → model-provider TLS (ADR-0023, ADR-0028). The rows for the IdP and the directory are decision 11's, not built.

    - **Why the client certificate goes (the rationale for decision 2).** The shipped `plane/cli` leaf is minted per invocation by the CLI, from the user's own Vault token. It proves that the connecting process could use that user's Vault identity, which any process running as that user can. That is nothing beyond what the peer uid already proves, and the peer uid is attested by the OS kernel rather than by possession. As a proof of the binary it proves nothing, because the binary runs as the user. Keeping it would claim client authentication the channel does not provide. Retiring it removes that claim and the `pki/sign` capability from the user's Vault policy. **It does not remove a credential at rest:** the user's userpass token stays at rest under ADR-0028, for reading the user's own provider key. The channel itself is not weakened: it stays TLS 1.3, server-authenticated, with the peer uid as the principal.
    - **On a channel that carries other principals' requests, the certificate never identifies a principal.** There, a channel's certificate or uid identifies the component that carried a request. (Where a workload is itself the principal, as the Agent Daemon is for its own actions under decision 9, its leaf is that principal's credential.) The principal travels inside the request and is proved by something that component cannot forge: the peer uid, the IdP's signature, or the kernel's intake record. A principal is never inferred from the channel, its plane, its network location, or what the content says about itself (decision 7; inform-but-not-authorize, applied to identity).
    - **A home install uses the same mechanisms as an enterprise one.** A single-user host differs in defaults (which listeners are bound, which account-state source answers), never in which checks run.

11. **Every request is a full inspection; Maknae holds no cache of subject state between requests** *(added 2026-11-05, [#114](https://github.com/darkhonor/maknae/issues/114), [#117](https://github.com/darkhonor/maknae/issues/117))*. Zero Trust, and the data-centric decisions ADR-0020 grows toward, need every request decided on current facts: the component that carried it, the principal, any task envelope, and the data's own attributes.
    - **Account state is checked on every request.** The PDP asks an authoritative source whether the subject's account is currently active, and refuses when the source cannot answer. It applies to every subject, the Agent Daemon included; for a service account, the account state is its enrollment and its Vault identity, not an OS login policy (a macOS login-policy check of a hidden service account may report "not allowed"). This is the current direction, to be tested when the Agent Daemon is built (#472) and revised if it does not hold. The proposed model, not yet decided, is `Active | Disabled | Locked | Expired | Unknown`: everything but `Active` denies, missing data is `Unknown`, and password expiry is a separate flag, not a deny state. Which source answers for which kind of account — the host for the accounts it owns, the directory for a directory-backed account even at the local console — is open in [#117](https://github.com/darkhonor/maknae/issues/117), with the measured evidence. No PAM module is loaded into `maknaed` (ADR-0002), which never runs as root. On Linux the measured local source is a protocol call from Rust (Varlink to `systemd-userdbd`, #117); on macOS the proposed source is an OpenDirectory framework call, through FFI in `maknae-sys` (ADR-0027). That would load Apple's framework client, C and Objective-C, into `maknaed` on a shipping platform: a larger surface than ADR-0027's single-operation libc calls, so it is proposed, not decided, and #117 must justify it against ADR-0002 or find a source outside the process. **Stated residual:** `maknaed` resolves users and groups through glibc NSS today (`crates/maknae-kernel/src/groupres.rs`, `crates/maknae-authz-basic/src/binding.rs`), and glibc loads the configured NSS modules into the calling process, so C NSS modules (`libnss_sss` on an SSSD host, `libnss_systemd` on a stock one) run inside `maknaed` now. Whether to replace NSS resolution is owed with #117. **Not covered by any non-PAM path, stated:** `pam_access`, `pam_time`, `pam_faillock` and site-specific account modules.
    - **A remote principal's IdP token is verified by `maknaed` on every request,** checking signature, audience and expiry, and the subject's account state is checked against the IdP (token introspection, RFC 7662, is the baseline). Introspection's `active` describes the token, not the account: whether disabling or locking an account makes an IdP report its live tokens inactive is up to the IdP, so #117 must verify it for each IdP enrolled, or the per-request account check is only a token-validity check under another name. Those checks together need a signed token that can also be introspected, which means a JWT access token (RFC 9068), not an ID token (RFC 7662 does not introspect ID tokens) and not an opaque token (it has no signature). A pushed revocation feed (OpenID Shared Signals / CAEP) may be added later behind the same check, for scale. It is a source of current state, not a cache of decisions. Introspection responses are not cached, although RFC 7662 §4 allows it. Which audience `maknaed` requires, who the SP 800-63C relying party is when the assertion is encrypted to the gateway (decision 5(b)), and how 800-63C's assertion-based FAL terms carry over to the forwarded access token, are #117's to fix. An IdP that offers no account-state source cannot be enrolled, since every request would be `Unknown`; whether decision 5's GitHub example qualifies is #117's to establish. This amends decisions 2, 4, 5, 6, 7 and 9, assumption 5, T5 and T10. It governs the #117 gateway; channel adapters (Discord and the like, §Scope boundary (a)) are still owed their own decision.
    - **Decision 4's bounded positive cache for group membership and logind liveness is struck.** Maknae caches no subject state between requests: group membership, login liveness, account state, the remote token and its introspection response are all asked of their source for every request. The IdP's signing keys may be cached: they are facts about the IdP, not the subject. **Stated residuals:** (1) the sources keep their own caches. SSSD caches entries (`entry_cache_timeout`, 5400 s by default) and answers from cache while the directory is offline; nscd and macOS's directory services cache too; `systemd-userdbd` answers through NSS. So the real de-enrollment latency, and whether a directory outage denies, are set by the host identity stack's configuration. #115 and #117 decide whether Maknae requires settings for it or bypasses it, and the deployment documentation states it either way. (2) Two snapshots are per load, not per request: a service account's enrollment, its account state above, which decision 9 applies at the next reload or restart (ADR-0029); and `maknae-authz-basic`, which resolves `bindings.yaml` usernames to uids once per policy load (`crates/maknae-authz-basic/src/binding.rs`), so a deleted account whose uid is reused keeps the old name's binding until the next reload; per-request resolution is owed by #439. (3) With introspection uncached, the IdP's request rate equals the PDP's: the IdP is the scaling limit, which a pushed feed (below) relieves.
    - **It scales by components, not principals.** Thousands of remote principals share a few long-lived gateway channels. A request's non-policy inputs travel with it as verifiable artifacts (the IdP token; for an agent task, the intake-bound envelope), so more than one PDP instance can decide them. Making the envelope a signed artifact would be a new kernel signing authority, which decision 2 says this ADR does not add; it is owed with the fleet design, not claimed here. That is the target for a container deployment; it is not built, and its interaction with the kernel enforcement state graph (ADR-0029) is owed work, not claimed here.
    - **The TCB boundary moves in three places.** (1) `maknaed` gains token-verification code (OIDC/JWT parsing and signature checks, in Rust, with its cryptography through `maknae-crypto`, ADR-0030/0031): a deliberate expansion of the kernel's code. (2) **`maknaed` gains outbound network channels and a credential:** it calls the IdP (introspection and its signing-key set) and, for directory-backed accounts, the directory, and it holds the IdP client credential that introspection requires (RFC 7662 §2.1), in its own Vault custody. Today `maknaed`'s SELinux policy names Vault's labelled port as its one network destination (`packaging/common/maknae.te`; `auth_use_nsswitch` also admits what the host's NSS configuration needs, such as LDAP under the `authlogin_nsswitch_use_ldap` boolean), and ADR-0023 places outbound internet TLS in the Egress Daemon; this adds the IdP and directory endpoints as named, labelled destinations of the kernel. This is the current direction (maintainer, 2026-11-05). Nothing built today depends on it, and the alternative — the Egress Daemon makes the calls while `maknaed` verifies signatures against signing keys configured into the kernel, which would make the Egress Daemon trusted for the account-state answer — stays open until #117 builds it. (3) The gateway's trust narrows from principal-asserter to channel binder (assumption 5, T10). The current direction puts outbound TLS and response parsing inside the PDP, which ADR-0023 decision 3 kept out of it for model calls. The cost is accepted here because the responses are small, structured and schema-bound, unlike a model's output, and because the introspection and account-state answers can only deny or confirm a decision, never widen it. **The signing-key set is different:** it defines which tokens verify, so a substituted key set lets an attacker forge a token for any enrolled remote principal. It is trusted only through TLS to the IdP's configured trust (T15); keys configured into the kernel, the alternative above, would not have this exposure. Whether keys are fetched at runtime or pinned in configuration is #117's to decide, and this exposure is the deciding factor. The account-state sources — the host's identity services, the directory, the IdP — join Vault and the host login (assumption 1) as external authorities Maknae relies on and does not contain: their answers are trusted, their unavailability denies, and their compromise is outside what Maknae can defeat.

## Alignment — DoD Zero Trust RA & NIST (strengths and honest gaps)

Assessed 2026-08-22 against **NIST SP 800-207** (*Zero Trust Architecture*), the **DoD Zero Trust Reference Architecture v2.0**, and **NIST SP 800-63-3/-63B/-63C**. Strengths first, then the gaps an assessor would write up — kept here deliberately so they are owed work, not surprises.

**Where this model is strong (the load-bearing ZT properties):**

- **Per-session access, exceeded.** 800-207 Tenet 3: *"Access to individual enterprise resources is granted on a per-session basis."* This model authenticates per session, **re-validates the local enrollment factors per request**, and authorizes **per request** at the sole PDP (Decisions 4 & 6) — stricter than the tenet demands.
- **Strict pre-access enforcement.** Tenet 6: *"All resource authentication and authorization are dynamic and strictly enforced before access is allowed."* Deny-by-default, fail-closed, enrolled-principals-only (Decision 3), per-request PDP (ADR-0020).
- **All resources behind the door.** Tenet 1 (all data sources and services are resources) — the trust plane fronts Vault, the instance's local Knowledge Lake, and model endpoints; no client touches a resource directly (Decision 1). PDP/PEP separation per 800-207 §3 (logical components): `maknaed` is the policy engine + local enforcement point; the gateway is the remote PEP — a named TCB expansion (assumption 5), not an implicit one.
- **Identity-based, not location-based, trust.** Tenet 2 (*"all communication is secured regardless of network location"*): TLS on both boundaries, including over the local UDS. Being local grants nothing — it only selects *which factor* authenticates you (peer-cred vs. OIDC); the `0660` socket is segmentation defense-in-depth, never the access decision.
- **Dynamic policy with an attribute conduit.** Tenet 4 (access decided by dynamic policy including client identity and environmental attributes): the session-as-subject-context-carrier (Decision 7) is precisely the conduit for RBAC→ABAC enrichment (ADR-0020, DCS) — the carrier exists even where today's attributes are minimal.
- **PDP-subversion minimization.** 800-207 §5.1 names subversion of the ZT decision process as a principal threat; this model keeps the PDP's grant surface *minimal* — no new Vault/PKI capability, session authority boundary-local (Decision 2, T5). Least privilege for the crown jewel. *(Amended 2026-11-05: decision 11 adds one Vault read to the PDP, the IdP client credential `maknaed` holds for introspection: one secret path it can read, used for introspection only. That the IdP client is configured without the client-credentials grant is a deployment requirement Maknae cannot check, which #117's documentation must state.)*
- **Assurance mapping (800-63), stated honestly.** Local: AAL is inherited from the STIG'd host's login policy (CAC/smartcard on a DoD host → AAL2/3) and is **bounded by the host's own session/reauthentication policy** — `SO_PEERCRED` attests *process ownership*, not subscriber presence; Maknae adds **no presence reauthentication** of its own, though the **visit clock forces periodic re-establishment** and **logout is enforced at the next request** via the session-liveness check (Decision 4) — what remains unattested is presence at the keyboard *within* a live session (an owed gap, noted below). Remote: a signed bearer assertion alone is FAL1; this model **REQUIREs the FAL2 bar** (63C-3 / 63C-4, Decision 5b) and pushes the **FAL3 / holder-of-key direction** via sender-constraint on both legs (Decision 5c).

**Honest gaps (deliberate MVP deferrals, owed as tracked work — this is an AI-agent platform and will grow against them):**

- **Device posture (DoD ZT RA Device pillar; 800-207 Tenet 5** — *"the enterprise monitors and measures the integrity and security posture of all owned and associated assets"*)**.** Channel-binding proves device *identity* (a key), not device *health/compliance*. Locally, "STIG'd host" is a governed platform assumption, not a signal Maknae measures. **Deferral rationale:** single-host MVP; the platform owns host posture. **Insertion point when built:** device-posture claims enter as session subject-context attributes (Decision 7). **Tracked: #112.**
- **Visibility & Analytics pillar (Tenet 7).** AU-3 per-request with the exact principal (ADR-0019) is the foundation; SIEM export / analytics on top is future work. **Tracked: #113.**
- **Automation & Orchestration pillar.** Revocation-on-report and fail-closed exist; SOAR-class orchestration is out of scope for a local platform at MVP (response wiring tracked under #113's scope).
- **MFA and conditional access are delegated**, not owned — to the STIG'd host's login policy locally and to the IdP remotely. **Session reauthentication is now partly owned**: the visit clock forces periodic re-establishment and the liveness check enforces logout (Decision 4); what stays delegated is presence-within-a-live-session (the AAL bullet above). All delegations are stated as explicit REQUIREs or assumptions with the trust boundary named (assumption 1; Decision 5a; the AAL bound above) rather than left for an assessor to discover.

## Consequences

- **The per-platform CLI-seal problem is superseded — once the local session path lands.** In the target model the on-server CLI holds nothing at rest — no SecretID, no certificate, and **no session handle** (Decision 4) — so there is nothing to seal on any platform. This **supersedes** the CLI-seal requirement rather than patching it — but the change is prospective, not accomplished: **#73 (operator enroll cannot complete on RHEL 9 — `systemd-creds --user` needs systemd ≥ 256, el9 ships 252; enroll fails closed there today) is OPEN and resolves *by removal* only when the session path lands.** Until then the shipped model (CLI SecretID + self-minted leaf, per ADR-0005/0018) remains the design of record on the platforms where it works — do not close #73 or alter the shipped path before the session path replaces it. **#89** was already patched (`--with-key=auto`, closed 2026-08-16); this model removes the seal *class* it lived in going forward. *(Amended 2026-10-01 by ADR-0028: for local users the CLI holds a userpass token at rest, so the per-platform seal remains required for it.)*
- **No new Vault capabilities; the signing-grant decision is dissolved.** *(Scoped 2026-10-23, #550: for client authentication. Decision 9's grants to the Agent Daemon and to the administrator who enrolls it are in the bullet "The Agent Daemon gets a plane role" below.)* The prior draft's owed decision (grant `maknaed` `pki/sign/cli-role`, or stand up a broker identity) is **dissolved, not deferred** — sessions need no PKI, and the constraint is normative: locally no token exists at all (the session is a daemon-side connection-scoped record, Decision 4); the remote session's key custody is #117 work and **MUST NOT introduce a new Vault grant** for session purposes (Decision 2). Custody-by-secret-absence (ADR-0005) is preserved for machine planes; retiring the `cli` client role strictly narrows the PKI grant surface. The daemon's machine identity (ADR-0018: standing AppRole SecretID, HRoT-sealed, periodic token) is untouched. *(Amended 2026-11-05: one new Vault read is granted to `maknaed`, the IdP client credential `maknaed` holds for introspection: one secret path it can read, used for introspection only. That the IdP client is configured without the client-credentials grant is a deployment requirement Maknae cannot check, which #117's documentation must state.)*
- **ADR-0005 is amended (append-only):** the *client* channel's mutual-mTLS requirement is superseded in target model — the local client channel becomes server-authenticated TLS 1.3 + kernel-attested peer-cred + daemon-side uid-bound session; mutual mTLS remains for **machine (plane-to-plane) channels** — today that is the shipped daemon↔CLI plane channel (until #114/#116 land); in target model, the `gateway↔daemon` link (#117) and the Agent Daemon's own socket (decision 9, added 2026-10-23). ## Scope boundary

Fixes the **authentication strategy for human clients** *(and, since 2026-10-23, for the Agent Daemon as a workload: decision 9)*: the sole-door principle, the machine-vs-human credential split (X.509 vs. sessions), enrollment-precedes-authentication, the boundary-native factors (peer-cred local; OIDC remote), session custody/binding/termination properties, and the principal-to-PDP contract. It does **not** specify: the concrete session wire format or the subject-context envelope (#19, implementing spec); the deployment-mode config key's name and values (#115, implementing spec); the gateway mechanism (#117); OIDC integration detail (providers, validation, claim mapping); or **authorization** (ADR-0020). The daemon's own machine authentication (ADR-0018) is out of scope and unchanged.

**Explicitly out of scope — adjacent client-shaped surfaces, each owed its own decision (tracked work, not reserved ADR numbers):** (a) **channel-adapter operators** (Discord/Matrix et al. — the container architecture's channel gateway authenticates operators by a fail-closed allowlist; whether that component and the #117 gateway converge is an open operator decision); (b) **multi-operator agent-runtime delegation** (the KLC's one-runtime-serving-N-operators case — the runtime's own uid is *not* an operator identity, and per-operator attribution through the runtime needs the subject-context envelope, #19); (c) **autonomous task identities** (scheduler/dreaming tasks under scoped task identities via the kernel's privileged subject-context mint, ADR-0005). This ADR's two boundary factors cover the human CLI and the human remote app; it deliberately claims nothing about (a)–(c) beyond the invariant that *whatever* their identities are, they reach the PDP as explicit principals (Decision 7) and never escalate (Decision 8). *(2026-10-22, #471: for the Agent Daemon, the identity half of (b) and (c) is decided by [ADR-0024](ADR-0024-tenancy-model-and-agent-identity.md) decision 6. It is a subject with its own uid; per-tasker attribution on the intake record is owed by #475. How it authenticates is still undecided here: decision 4's human-session factor refuses a service by design, and the replacement factor is [#550](https://github.com/darkhonor/maknae/issues/550).)* *(2026-10-23, #550: decided. The Agent Daemon authenticates by decision 9. Every other non-human surface in (a)–(c) is still owed its own decision.)*
