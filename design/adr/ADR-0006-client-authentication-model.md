# ADR-0006: Client authentication (AuthN) model — sole trust-plane door; boundary-native factors; uniform bounded sessions; X.509 is machine identity only

- **Status:** Accepted (operator-ratified 2026-08-22; strategy selected after an objective threat assessment against the DoD Zero Trust Reference Architecture and NIST guidance — see §Alignment)
- **Date:** 2026-08-22
- **Deciders:** Alex Ackerman (operator)
- **Supersedes (in target model, via append-only amendments to the affected ADRs):** ADR-0005's client-channel mutual-mTLS clause — including, *for the client channel only* (machine channels retain each): the mTLS negative suite's "absent client cert → reject" and "uid mismatch" criteria, the "`maknaed` requires `plane/cli`" peer-verifier rule, and the `maknae-vault` crate-contract's client-side leaf-minting path — and the `cli` plane leaf as a client credential; ADR-0018's operator-CLI standing SecretID, its decision-1 client gate (clause (a) for local clients), its "mTLS plane cert is the real per-user credential" phrasing (decision body, Consequences, acceptance-test framing, and both cert-as-authenticator control-mapping rows), and its per-platform CLI-seal apparatus. All prospective until the session path lands — see Consequences.
- **Relates to:** ADR-0002 (Rust kernel — the T0 memory-safety substrate); ADR-0005 (enforcement locus & TCB boundary — amended); ADR-0018 (local-plane authorization & deployment model — amended); ADR-0019 (audit record model — gains owed field work, see Consequences); ADR-0020 (access-control model — the **authorization** counterpart this AuthN model feeds). Issues: #66 (gateway / remote-client boundary), #73 (operator enroll cannot complete on el9 — `systemd-creds --user` needs systemd ≥ 256, RHEL 9 ships 252; OPEN, superseded on session-path landing), #89 (`--user` cannot use `--with-key=tpm2` — **patched** via `--with-key=auto`, closed 2026-08-16), #19 (subject-context envelope — the session payload's implementing work), #112 (device-posture epic), #113 (audit export / analytics epic).

> **Scope: authentication, not authorization.** This ADR fixes *who a client is and how it proves that* (the IA family). It does **not** decide what an authenticated client may do — that is the reference monitor's per-request call, deny-by-default (ADR-0020, the AC family). AuthN establishes identity and hands it to the PDP; establishing a session is never itself an authorization.

> **Number-reuse note.** Per the registry convention (2026-08-22) an ADR takes a number at authoring and freed numbers are reused; `0006` previously held the (unwritten, since-embodied-in-AGENTS.md) single-source-of-truth doctrine. The filename and registry topic are the identity — the bare number is a handle.

> **Implementation status — the code does NOT yet implement this ADR.** The shipped code implements the pre-ADR model: the CLI holds an AppRole SecretID (per-platform sealed at rest), self-mints a `cli`-plane leaf, and speaks mutual mTLS to the daemon. Per the authority order (code → KLC → ADRs), the code remains authoritative for what *is*; this ADR fixes what is *ratified to become*. The delta is tracked as specific convergence issues: **#114** (`maknaed` channel split — certless client listener, mutual mTLS retained for machine planes, negative-suite split by channel class), **#115** (daemon-side uid-bound session records, in-memory, group-membership re-check per connection **and per request** — de-enrollment terminates access even over an open connection), **#116** (CLI credential-path removal — resolves #73 by removal; enroll and doc sweep). Do not treat any target-model statement below as a description of current behavior until those issues close.

## Context

Today Maknae is a single host: the `maknae` CLI and `maknaed` daemon run on the same box, talking over an mTLS UDS (ADR-0005). In the shipped design the CLI authenticates to **Vault** directly (its own AppRole SecretID → mint a `cli`-plane leaf → mTLS to the daemon), which forced a per-platform at-rest seal for that standing SecretID — the `systemd-creds --user` / Keychain split, and the RHEL-9 gap where enroll cannot complete at all (#73, #89).

Two forces make that model wrong going forward. First, **the client is untrusted by design, and will become *remote*** — the daemon will grow a network listener; the target is controlling Maknae from an iOS app over 5G/VPN. A remote, untrusted client must not be assumed to have — or need — a network path to Vault; punching Vault out toward untrusted networks, and issuing every client a Vault identity, is the opposite of the reference-monitor posture. Second, **the current design handed a *human operator* a *machine credential*** (a standing AppRole SecretID). AppRole+SecretID is for machines; humans authenticate via a human method and receive short-lived sessions.

An earlier draft of this ADR fixed the symptom (no standing SecretID) but kept the client credential as a Vault-issued X.509 leaf, brokered by the daemon — which required granting the trust plane a `cli`-signing capability ADR-0005 deliberately withholds (custody-by-secret-absence), and made local and remote clients mechanically asymmetric. The operator directed a ground-up threat assessment of the authentication strategy (2026-08-22); three candidate strategies were evaluated against the trust assumptions and threat model below and against DoD ZT RA v2.0 / NIST SP 800-207 / SP 800-63. The selected strategy (this ADR) removes the client X.509 requirement instead of working around it.

## Trust assumptions (operator-ratified, 2026-08-22)

1. **The OS host posture is STIG'd and access is limited to authorized individuals.** Host login is a trustworthy authentication event; Maknae *inherits* OS authentication (IA-2 satisfied by the platform's login; AC-2 account management by the platform) rather than re-implementing it. This is an explicit, documented external authority, not implicit trust — see §Alignment.
2. **`maknae`-group membership is a root-gated administrative act.** Nobody drifts into the trust boundary; an administrator deliberately enrolled them — and removal from the group is, symmetrically, the local de-enrollment/revocation act (Decision 4).
3. **An *externally achieved* OS compromise (root obtained by non-Maknae means) is outside Maknae's threat model** — root owns the daemon's memory, sealed secrets, and socket; no scheme Maknae runs on that host survives its own root. These are things the platform (STIG, access control, scanning) handles and Maknae never can.
4. **Maknae as the escalation *vector* is squarely inside the threat model — it is threat #1.** A user authenticated *to Maknae* must never be able to escalate to *host-level* access through any Maknae component. Direction matters: host→Maknae compromise is the OS's failure; Maknae→host escalation is *our* failure and must be impossible. (This is a primary reason the kernel is Rust — ADR-0002.)
5. **When the remote boundary exists, the gateway is in the TCB for remote principal assertion.** The gateway (#66) validates OIDC and *asserts* the resulting principal to the PDP over its machine channel; a compromised gateway can therefore impersonate **enrolled remote subjects** to the PDP. That risk is *bounded*, not defeated (T10): gateway compromise never yields the **daemon's** `plane/kernel` identity or local principals, and no Vault authority beyond the gateway's **own** scoped credential (its own AppRole + `pki/sign/<gateway-role>` under ADR-0005's per-plane pattern — final grant design at #66 — whose compromise also inherits ADR-0005's honest mount-wide-revoke DoS residual, now reachable from a network-facing component — therefore **#66 MUST scope the gateway's Vault policy to exclude `pki` revoke, or place gateway credentials on a separate mount**, so the residual does not extend to the network boundary); every asserted principal still faces the per-request deny-by-default PDP. Admitting a second trust-plane component is a deliberate TCB expansion, named in the ADR-0005 amendment — it is the price of never exposing `maknaed` to untrusted networks, and it is why the gateway carries its own scoped identity and policy.

## Decision

**The strategy in one sentence:** *every human client, local or remote, is an admin-enrolled principal, authenticated at its boundary's door by that boundary's native factor, and carried in a **bounded** session (connection-scoped locally, short-TTL remotely) to the sole PDP on every request.* (Non-human and channel-mediated surfaces are explicitly out of scope — see §Scope boundary.)

1. **The trust plane is the sole client-facing authentication endpoint.** A client — local or remote — authenticates to and transacts only with the trust plane (`maknaed` over the UDS locally; the **gateway**, #66, remotely). Clients **never** reach Vault, the instance's local Knowledge Lake (the KLC's tiered store — the *external* standalone lake is never read at runtime, ADR-0005), model endpoints, or any other trust infrastructure directly. This is the reference-monitor principle (ADR-0005, AC-25) projected onto the network boundary: one authenticated door per boundary, everything trusted behind it.

2. **X.509 / Vault PKI is machine identity only; client authentication is a session, never a certificate.** Plane leaves (ADR-0005) identify *workloads* — the daemon, and later the gateway's internal channel. Humans and client apps never hold a Maknae certificate or any Vault credential. A client's credential is a **bounded session** minted by its boundary's door after the boundary-native factor authenticates — **connection-scoped locally** (Decision 4), **short-TTL and revocable remotely** (Decision 5). This dissolves the prior draft's central defect — no client leaf exists, so no issuance bootstrap exists, and **no new Vault or PKI capability is granted to anyone**: ADR-0005's machine-plane policy scoping and custody-by-secret-absence are unchanged, and retiring the `cli` client role strictly *narrows* the PKI grant surface. Session-minting authority is boundary-local, and the normative contract is: **locally, no token is issued at all** — the session is a daemon-side record (Decision 4), so there is no key-custody question and nothing survives a daemon restart (clients re-establish transparently from peer-cred); a **token-shaped session exists only where a client must hold a handle — the remote boundary** — where it is gateway-held state or a gateway-keyed token whose custody is #66 implementing work, constrained here: sender-constrained, revocable, and **MUST NOT introduce a new Vault grant** for session purposes. To be precise about what already exists: this is not the platform's first identity-shaped capability — the kernel already links the *privileged* subject-context mint (`maknae-subject-ctx-mint`, ADR-0005) for scoped task identities — but this ADR adds **no new** minting or signing authority, and a session forged by a compromised daemon is honoured only by that same daemon: it confers nothing off-daemon and nothing at the host layer (T0, T5).

3. **Enrollment precedes authentication, on both boundaries, as an explicit administrative act.** Locally, root adds the user to the `maknae` group (assumption 2). Remotely, the Maknae Admin **enrolls the OIDC subject** — a merely *valid* IdP identity is refused (T9). Nobody can authenticate whom an administrator did not first ratify — and symmetrically, **de-enrollment is the revocation act**: group removal locally (enforced by Decision 4's re-check), enrollment-list removal + session revocation remotely (Decision 5). Authorization-to-authenticate is never implicit.

4. **Local (on-host) authentication = OS host-login + current `maknae`-group membership + kernel-attested peer-cred, with the session daemon-side and uid-bound.** The STIG'd OS is the local identity provider (assumption 1); `SO_PEERCRED` re-attests the uid on **every connection** — a kernel-attested, non-replayable, non-exfiltratable factor. The channel is TLS 1.3 over the `0660` UDS with `maknaed` server-authenticated (`plane/kernel` cert); the client presents no certificate. On **every connection — and re-evaluated on every request over that connection** — the daemon verifies both that (i) the live peer-cred uid equals the session's bound uid **and** (ii) that uid is **currently** a member of `maknae` — membership re-resolved from the host's user database, *not* trusted from the client process's snapshotted supplementary groups — so **de-enrollment terminates access at the next request, even over a connection that is already open**: a long-lived connection never outruns its enrollment (today's per-invocation CLI makes the per-connection and per-request checks coincide, but the per-request rule is what makes the guarantee hold for any future long-lived client); group removal *is* the local session-termination mechanism (AC-12). **Lookup-failure semantics are fail-closed:** on a domain-joined host the membership lookup may traverse SSSD/LDAP, so a directory outage denies local connections **and in-flight requests** — an accepted availability trade, consistent with ADR-0018's "genuine external failure is a legitimate fail-closed trigger" (its anti-self-outage stance rejects *self-inflicted* shutdowns, which this is not); the denial is audited (AU-3) as an **infrastructure denial, distinguishable from a de-enrollment denial**. Because the check is per-request, the lookup sits on every PDP call's hot path, so #115 **SHOULD** adopt a bounded-TTL *positive* cache (fail-closed on expiry) on hosts whose membership source is remote — **the cache TTL is the de-enrollment latency bound — it MUST be stated by #115 and MUST NOT exceed an operator-configured maximum (default 60 s)**. One precision for the implementer: the `SO_PEERCRED` uid is kernel-captured at connect and cannot change for the connection's lifetime, so the per-request re-validation is genuinely dynamic only for **group membership** — the uid check is fixed by the kernel at connect (Decision 7). Check (i) is therefore a **defensive session-map integrity assertion, not an authentication factor**: it has no adversarial failure mode by construction (the session's uid is derived from the same kernel fact it is compared against). The authenticating facts are the kernel's peer-cred and the per-request group re-resolution, and the negative tests target those — a non-member refused at connect, a de-enrolled member refused at the next request — not an unconstructible uid mismatch (ADR-0016 / AGENTS.md: every assertion must be able to go red). **The normative local session contract (one sentence): the session is a daemon-side subject-context record keyed to (uid, connection), established at connect after both checks pass, re-validated on every request, and discarded at disconnect; no token or handle is ever issued to the client** — nothing session-shaped exists on the client, at rest or otherwise (T2), which is what actually retires the seal problem (#73); local session lifetime *is* connection lifetime bounded by per-request re-validation, TTL semantics apply only to the remote boundary (Decision 5), and locally a daemon restart simply drops connections — the same event as disconnect. **The daemon also owns the visit clock (operator-ratified addition, 2026-08-22):** `maknaed` imposes an **idle timeout** and an **absolute maximum connection lifetime** on every client connection — trust-plane-owned termination authority, independent of any client-held state (SC-10). Expiry *is* the disconnect event (the session record dies with the connection), and re-establishment re-runs the full gate **including a fresh kernel peer-cred capture** — bounding the one staleness per-request re-validation cannot reach: a connect-time-fixed uid on a socket whose fd was later handed to another process (`SCM_RIGHTS`). The timer values are #115's to fix and MUST be stated. Its value over bare peer-cred is *uniformity* — the same session/subject-context contract the remote boundary uses (Decision 7) — not additional authentication strength. The on-server CLI (the Maknae Admin's surface for admin functions, troubleshooting, and AI-harness testing) therefore holds no credential at rest and needs no separate `maknae login` — the OS session is the login. There is no bootstrap problem: the first connection authenticates exactly like every other, by peer-cred; no credential is presupposed.

5. **Remote authentication = OIDC federation through the gateway, hardened.** The remote client authenticates natively to an external IdP (e.g. GitHub, Azure AD) and presents the assertion to the **gateway** (#66) over TLS; the gateway validates it against the **enrolled-subject list** (Decision 3) and mints a **short-TTL, channel-bound session** that the gateway holds and can revoke. REQUIREd properties: **(a)** the IdP MUST enforce MFA / conditional access (AAL2, SP 800-63B) — Maknae delegates the factor, not the requirement; **(b)** assertion presentation MUST be injection-protected — REQUIREd concretely: back-channel presentation **and, where the deployment claims SP 800-63C-3 FAL2, assertion encryption to the gateway as well** (under 800-63C-**3**, FAL2 = signed *and encrypted-to-RP* assertions; 800-63C-**4** §5 frames the FAL2 bar as injection protection via back-channel presentation or encryption — this model REQUIREs the protections either way; a signed *bearer* assertion alone is only FAL1 under both revisions); **(c)** sender-constraint (DPoP / mTLS-bound keys — the SP 800-63C holder-of-key / FAL3 direction) applies to **both legs**: the device-retained IdP credential (refresh token / IdP session) *and* the client↔gateway session itself; long-lived bearer refresh tokens MUST NOT be relied on; **(d)** the gateway MUST be able to revoke a device's sessions (and, where the IdP allows, its tokens) on report of loss (T7); **(e)** the gateway owns the same **visit clock** as the local plane (Decision 4, operator-ratified 2026-08-22): an idle timeout and an absolute maximum session/connection lifetime **in addition to** short TTL and revocation-on-demand — client-independent termination authority (SC-10); expiry forces full re-authentication at the door, re-evaluating every connect-time-fixed fact (channel binding, session keys), with no per-request IdP round-trip in steady state. The gateway presents its **own** machine identity (never the daemon's `plane/kernel` key), reaches `maknaed` over a **separate internal mutual-mTLS machine channel**, asserts the validated principal per assumption 5, and the remote client **never reaches `maknaed`** — its session is `client↔gateway`. A lost, stolen, or seized device forfeits an expiring, revocable, sender-constrained session — no durable Maknae credential exists on any client.

6. **The client stays untrusted across the boundary.** A client is authenticated **per session and re-validated per request** (locally: current group membership on every request, Decision 4; remotely: bounded by session TTL, gateway revocation, and the gateway's visit clock — **no per-request IdP round-trip**, Decision 5) and authorized **per request** by the sole PDP (deny-by-default, ADR-0020). A valid session is identity, never entitlement.

7. **The authenticated principal is carried into every PDP decision.** Locally the principal is the `SO_PEERCRED` uid — kernel-captured at connect and immutable for the connection's lifetime, present on every connection, captured in every AU-3 record (ADR-0019). Remotely the validated OIDC principal (and its claims → subject attributes) rides the gateway-held session and is asserted, with the gateway's own identity, into each request to the sole PDP — never inferred from plane membership, network location, or content self-labeling (inform-but-not-authorize, AGENTS.md). The session is the **carrier** of identity and subject context (the concrete envelope is the subject-context work, issue #19 — an *issue*, not a reserved ADR number, per the registry's number-at-creation rule); the *requirement* that the principal reach every PDP call is fixed here. This is also the designed insertion point for later attribute enrichment — device posture (#112), DCS clearance — without changing the model.

8. **Maknae is never the privilege-escalation vector (T0).** No Maknae component performs an action on a client's behalf that exceeds that client's own authority on the host or in the policy model: the daemon does not proxy host access, exposes no setuid-like surface, and a Maknae session confers exactly zero host-level rights. Any design change that would have the trust plane act with its own privileges *for* a client is a security decision requiring an ADR, not a convenience (AGENTS.md core principle 3).

## Alignment — DoD Zero Trust RA & NIST (strengths and honest gaps)

Assessed 2026-08-22 against **NIST SP 800-207** (*Zero Trust Architecture*), the **DoD Zero Trust Reference Architecture v2.0**, and **NIST SP 800-63-3/-63B/-63C**. Strengths first, then the gaps an assessor would write up — kept here deliberately so they are owed work, not surprises.

**Where this model is strong (the load-bearing ZT properties):**

- **Per-session access, exceeded.** 800-207 Tenet 3: *"Access to individual enterprise resources is granted on a per-session basis."* This model authenticates per session, **re-validates the local enrollment factors per request**, and authorizes **per request** at the sole PDP (Decisions 4 & 6) — stricter than the tenet demands.
- **Strict pre-access enforcement.** Tenet 6: *"All resource authentication and authorization are dynamic and strictly enforced before access is allowed."* Deny-by-default, fail-closed, enrolled-principals-only (Decision 3), per-request PDP (ADR-0020).
- **All resources behind the door.** Tenet 1 (all data sources and services are resources) — the trust plane fronts Vault, the instance's local Knowledge Lake, and model endpoints; no client touches a resource directly (Decision 1). PDP/PEP separation per 800-207 §3 (logical components): `maknaed` is the policy engine + local enforcement point; the gateway is the remote PEP — a named TCB expansion (assumption 5), not an implicit one.
- **Identity-based, not location-based, trust.** Tenet 2 (*"all communication is secured regardless of network location"*): TLS on both boundaries, including over the local UDS. Being local grants nothing — it only selects *which factor* authenticates you (peer-cred vs. OIDC); the `0660` socket is segmentation defense-in-depth, never the access decision.
- **Dynamic policy with an attribute conduit.** Tenet 4 (access decided by dynamic policy including client identity and environmental attributes): the session-as-subject-context-carrier (Decision 7) is precisely the conduit for RBAC→ABAC enrichment (ADR-0020, DCS) — the carrier exists even where today's attributes are minimal.
- **PDP-subversion minimization.** 800-207 §5.1 names subversion of the ZT decision process as a principal threat; this model keeps the PDP's grant surface *minimal* — no new Vault/PKI capability, session authority boundary-local (Decision 2, T5). Least privilege for the crown jewel.
- **Assurance mapping (800-63), stated honestly.** Local: AAL is inherited from the STIG'd host's login policy (CAC/smartcard on a DoD host → AAL2/3) and is **bounded by the host's own session/reauthentication policy** — `SO_PEERCRED` attests *process ownership*, not subscriber presence, and Maknae adds no reauthentication of its own (a long-lived host session retains access until logout or de-enrollment; an owed gap, noted below). Remote: a signed bearer assertion alone is FAL1; this model **REQUIREs the FAL2 bar** (63C-3 / 63C-4, Decision 5b) and pushes the **FAL3 / holder-of-key direction** via sender-constraint on both legs (Decision 5c).

**Honest gaps (deliberate MVP deferrals, owed as tracked work — this is an AI-agent platform and will grow against them):**

- **Device posture (DoD ZT RA Device pillar; 800-207 Tenet 5** — *"the enterprise monitors and measures the integrity and security posture of all owned and associated assets"*)**.** Channel-binding proves device *identity* (a key), not device *health/compliance*. Locally, "STIG'd host" is a governed platform assumption, not a signal Maknae measures. **Deferral rationale:** single-host MVP; the platform owns host posture. **Insertion point when built:** device-posture claims enter as session subject-context attributes (Decision 7). **Tracked: #112.**
- **Visibility & Analytics pillar (Tenet 7).** AU-3 per-request with the exact principal (ADR-0019) is the foundation; SIEM export / analytics on top is future work. **Tracked: #113.**
- **Automation & Orchestration pillar.** Revocation-on-report and fail-closed exist; SOAR-class orchestration is out of scope for a local platform at MVP (response wiring tracked under #113's scope).
- **MFA, conditional access, and session reauthentication are delegated**, not owned — to the STIG'd host's login/session policy locally and to the IdP remotely. All delegations are stated as explicit REQUIREs or assumptions with the trust boundary named (assumption 1; Decision 5a; the AAL bound above) rather than left for an assessor to discover.

## Consequences

- **The per-platform CLI-seal problem is superseded — once the local session path lands.** In the target model the on-server CLI holds nothing at rest — no SecretID, no certificate, and **no session handle** (Decision 4) — so there is nothing to seal on any platform. This **supersedes** the CLI-seal requirement rather than patching it — but the change is prospective, not accomplished: **#73 (operator enroll cannot complete on RHEL 9 — `systemd-creds --user` needs systemd ≥ 256, el9 ships 252; enroll fails closed there today) is OPEN and resolves *by removal* only when the session path lands.** Until then the shipped model (CLI SecretID + self-minted leaf, per ADR-0005/0018) remains the design of record on the platforms where it works — do not close #73 or alter the shipped path before the session path replaces it. **#89** was already patched (`--with-key=auto`, closed 2026-08-16); this model removes the seal *class* it lived in going forward.
- **No new Vault capabilities; the signing-grant decision is dissolved.** The prior draft's owed decision (grant `maknaed` `pki/sign/cli-role`, or stand up a broker identity) is **dissolved, not deferred** — sessions need no PKI, and the constraint is normative: locally no token exists at all (the session is a daemon-side connection-scoped record, Decision 4); the remote session's key custody is #66 work and **MUST NOT introduce a new Vault grant** for session purposes (Decision 2). Custody-by-secret-absence (ADR-0005) is preserved for machine planes; retiring the `cli` client role strictly narrows the PKI grant surface. The daemon's machine identity (ADR-0018: standing AppRole SecretID, HRoT-sealed, periodic token) is untouched.
- **ADR-0005 is amended (append-only):** the *client* channel's mutual-mTLS requirement is superseded in target model — the local client channel becomes server-authenticated TLS 1.3 + kernel-attested peer-cred + daemon-side uid-bound session; mutual mTLS remains for **machine (plane-to-plane) channels** (daemon↔Vault today; gateway↔daemon later). Consequently three further clauses split **by channel class** (superseded for the client channel, retained for machine channels): the **mTLS negative suite's** "absent client cert → reject" criterion, the "**`maknaed` requires `plane/cli`**" peer-verifier rule, and the **`maknae-vault` crate-contract's** client-side leaf-minting path — in the target model `maknaed` runs distinct verifier configurations per listener (mutual-mTLS machine channels; server-auth + peer-cred client channel), and acceptance tests must assert each class separately. The amendment also **names the TCB expansion**: when #66 lands, the gateway joins the trust plane as the remote PEP and principal-asserter (assumption 5). The `cli` PKI role is **retired as a client credential**; its disposition (reuse as the gateway's internal machine identity, or removal) is decided with #66.
- **ADR-0018 is amended (append-only):** decision 1's gate for local clients becomes *(b) current `maknae`-group membership (re-resolved at connect and on every request) + live peer-cred uid + daemon-side uid-bound session*; ADR-0018's **Scope-boundary** "gates *connections*, not *operations*" line is likewise superseded **for the enrollment gate only** (the AuthN re-check moves to per-request; the per-request PDP *authorization* decision remains out of ADR-0018's scope); clause (a) (verified `cli`-plane leaf) is superseded in target model for clients, retained for machine planes. The "mTLS plane cert is the real per-user credential" phrasing is superseded **everywhere it appears** — the decision-1 body, the Consequences echo, and both cert-as-authenticator control-mapping rows — the per-user credential is the OS login attested per connection by peer-cred. The acceptance-test framing built on "a valid `cli` plane cert" is superseded for the client channel per the negative-suite split above.
- **ADR-0019 gains owed field work (not amended yet):** its client-facing `source`/`subject` fields are defined around the peer plane URI-SAN + uid — in the target model the client channel has no client cert (the URI-SAN half goes vestigial for clients), and the remote path needs fields for the **OIDC principal and the asserting gateway's identity**. Owed with #66/#19; the daemon/machine-channel audit fields are unaffected.
- **Local and remote share the model's invariants — with named deltas.** Invariant on both boundaries: enrollment-precedes-authentication, a bounded session as the identity carrier (connection-scoped locally; short-TTL remotely), nothing durable **of Maknae's** on the client, and the principal-to-PDP contract (Decision 7). Deliberate deltas: minting/holding authority (daemon vs. gateway), binding (uid vs. channel/sender-constraint), revocation mechanism (group removal + per-request re-check vs. gateway revocation), and PEP locus (`maknaed` vs. gateway). The local implementation built now is the pattern the gateway instantiates — same invariants, its boundary's deltas.
- **Owed work (specific, filed):** code convergence — **#114** (`maknaed` per-channel verifier split), **#115** (daemon-side session records + de-enrollment re-check), **#116** (CLI credential-path removal + enroll rework + doc sweep — resolves #73 by removal; covers `packaging/isolation-contract.md`'s runtime-plane CLI credential rows and the runbook's CLI-credential sections). Platform growth — the gateway (#66); the subject-context envelope (#19); device posture (#112); audit export / analytics (#113).

## Scope boundary

Fixes the **authentication strategy for human clients**: the sole-door principle, the machine-vs-human credential split (X.509 vs. sessions), enrollment-precedes-authentication, the boundary-native factors (peer-cred local; OIDC remote), session custody/binding/termination properties, and the principal-to-PDP contract. It does **not** specify: the concrete session wire format or the subject-context envelope (#19, implementing spec); the gateway mechanism (#66); OIDC integration detail (providers, validation, claim mapping); or **authorization** (ADR-0020). The daemon's own machine authentication (ADR-0018) is out of scope and unchanged.

**Explicitly out of scope — adjacent client-shaped surfaces, each owed its own decision (tracked work, not reserved ADR numbers):** (a) **channel-adapter operators** (Discord/Matrix et al. — the container architecture's channel gateway authenticates operators by a fail-closed allowlist; whether that component and the #66 gateway converge is an open operator decision); (b) **multi-operator agent-runtime delegation** (the KLC's one-runtime-serving-N-operators case — the runtime's own uid is *not* an operator identity, and per-operator attribution through the runtime needs the subject-context envelope, #19); (c) **autonomous task identities** (scheduler/dreaming tasks under scoped task identities via the kernel's privileged subject-context mint, ADR-0005). This ADR's two boundary factors cover the human CLI and the human remote app; it deliberately claims nothing about (a)–(c) beyond the invariant that *whatever* their identities are, they reach the PDP as explicit principals (Decision 7) and never escalate (Decision 8).
