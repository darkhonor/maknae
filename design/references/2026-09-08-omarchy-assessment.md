## 1. Provenance disposition (read first)

Provenance is **favorable and adoption is still off the table**, on the Agent Deck pattern rather than the DeepSeek one:

- **US-origin, permissive, well-funded, and now foundation-held.** Incubated at 37signals; the Omacom Foundation (announced 2026-08-21, $8M then $12.6M from Lütke, Collison, Dell, Dorsey, Prince, Fried, DHH and others) holds the trademarks and funds infrastructure. MIT throughout (`LICENSE`; the package-build repo and the archived Chromium fork likewise). Cloning for read-only study needed no special clearance. The foundation's jurisdiction, legal form and board are **not published** (§6, unverified).
- **Artifact adoption is foreclosed by domain and platform, not provenance.** Omarchy is an Arch Linux desktop distribution delivered as an ISO and two pacman packages. Maknae's supported platforms are Linux (amd64/arm64) on STIG baselines and macOS on Apple Silicon (AGENTS.md conventions); Arch is not one of them, and nothing here is a Rust dependency. There is no shell script in this tree Maknae would vendor.
- **Its engineering process is the opposite of Maknae's on the axes Maknae cares most about**, and that is precisely why it is worth a record: `omarchybot` (Claude Opus 5 plus Codex) reviews *and merges* pull requests; there is no CI workflow and no shellcheck; the v4.0.0 to v4.0.2 window (2026-08-14 to 08-31) shipped two security fast-follow releases closing injection bugs that a published critique attributes to *"AI-generated bash scripts to process untrusted input without meaningful review."* Ideas and patterns are safe to learn from. The process is a validating contrast for principles 5 and 6.

This record exists so the "agent-first OS" question is not re-derived from scratch when Cooky reaches the loop, and so the contrast is not silently softened later.

## 2. Where Omarchy sits (center of gravity)

Against the reference set on record:

| | Center of gravity |
|---|---|
| **OpenClaw** | Breadth of channels; single-user, local-first control plane. |
| **Hermes** | The learning loop. |
| **DeepSeek Harness** | Everything hot-swappable, no privileged core. |
| **Agent Deck** | A trusted meta-tool observing trusted agents from a trusted host. |
| **Omarchy** | **The host itself, redesigned around the assumption that an agent will act on it.** Fourteen coding-agent CLIs pre-wired as lazy stubs, one chosen as *the* default agent, launched from a keybinding with that harness's own "don't stop to ask" flag, a 15-minute passwordless-`sudo` toggle *"useful for AI agents"*, skills symlinked into every harness's config directory, and the one LLM-assisted OS feature (crash diagnosis) implemented as "hand the crash to your agent." |

**The inversion is the lens.** Omarchy and Maknae start from the same premise, that agents will act on the machine, and resolve it in opposite directions. Omarchy's answer is *trust the chef, then trust the agent*: remove the friction between the agent and root, and rely on the user's judgment and snapshot-rollback. Maknae's answer is *the agent is untrusted by design*: put a reference monitor between the agent and every consequential action, and let nothing prompt-level authorize anything ([ADR-0005](../adr/ADR-0005-enforcement-locus-tcb-boundary.md), principle 2). Omarchy is what the market ships when the second answer is absent. Every finding below reads off that line.

## 3. Findings and dispositions

Dispositions are **proposed characterizations only** — nothing is decided, scheduled, or ticketed.

### 3.1 Agent launch with every harness's permission bypass, from the user's unsandboxed session — DO NOT ADOPT; record as the canonical form of the threat Maknae's PDP exists for.

`bin/omarchy-agent:54-55` states the design plainly: *"Agents launched from the keybinding or menu run unattended, so each one starts with its own spelling of 'don't stop to ask'"*, then enumerates them: `opencode --auto` (58), `agy --dangerously-skip-permissions` (62), `copilot --allow-all` (66), `crush --yolo` (74), `claude --permission-mode auto` (78), `grok --permission-mode bypassPermissions` (82), `codex --approve-for-me` (95), `cursor-agent --yolo --trust` (103), `hermes --yolo` (110), `muse --approval-mode never` (115), `omp --auto-approve` (119). The launcher is `setsid uwsm-app -- xdg-terminal-exec … -e "$1"` (`bin/omarchy-launch-tui:13`): the user's own session, no namespace, no mount restriction, no policy. Shell aliases repeat it (`default/bash/aliases:46-49`). The companion is `bin/omarchy-sudo-passwordless:49-61`, which writes `${USER} ALL=(ALL) NOPASSWD: ALL` to `/etc/sudoers.d/99-omarchy-nopasswd-${USER}` for 15 minutes behind a confirmation whose own text says it *"significantly weakens the security of your system"*; the manual lists it under Setup > Security as being there *"so AI agents can perform system tasks."*

- **What it demonstrates, and this is the useful part:** the harness's permission prompt is treated by the OS vendor as **UX friction, not a control**, and is switched off at the first opportunity. Maknae already holds that prompt-level markers cannot authorize (principle 2). Omarchy is field evidence that they will not even be *present* on a real machine: a governance design that assumes the harness will ask is designing for a machine nobody ships.
- **Fit to Maknae:** none as a mechanism. As a threat model it is exact. The Cooky loop (ADR-0023) is the agent that Omarchy would launch with `--yolo`; the difference is that Maknae's loop has no permission prompt to bypass because the decision was never the loop's to make. This is the sentence to keep.
- **One detail worth stealing anyway:** `bin/omarchy-agent:34-36` changes directory from `$HOME` to `$HOME/Work` because *"Agents refuse to remember trust for $HOME."* Even a trust-the-agent OS narrows the agent's working scope to a directory. Maknae narrows it to delegated descriptors ([ADR-0009](../adr/ADR-0009-subject-side-os-dac-evaluation.md)); the instinct is the same, the enforcement is not.

### 3.2 The crash-diagnosis path: event → bounded prompt → read-only skill → gated reporting — LEARN FROM the shape; DO NOT ADOPT the data path.

This is Omarchy's only LLM-assisted troubleshooting feature, and it is well shaped. `default/systemd/user/omarchy-crash-watch.service` tails `systemd-coredump` (`bin/omarchy-crash-watch:49`), stays silent unless a default agent is configured (`:69`) and only for the user's own UID (`:73`), and raises a toast *"Click to diagnose with AI"* (`:40-45`). Clicking runs `bin/omarchy-agent-crash:33-49`, which builds a twelve-line prompt of exactly five facts (process, PID, binary, signal, time) and hands it to the default agent with *"Use the diagnose-crash skill."* The skill (`default/agents/skills/diagnose-crash/SKILL.md`) directs the agent to `coredumpctl info`, the journal, `free -h`, and `gdb` against `debuginfod.archlinux.org` (`:56-64`), carries the line *"Diagnosis reads; it does not fix, tidy, or reconfigure"* (`:88`), and warns that *"a core is a verbatim copy of the process's memory and can hold passwords, tokens, and private documents"* (`:67-69`). Its `reporting.md:28-36` gates any upstream issue on three conditions (a verified bug in Omarchy's sphere, explicit user agreement, a working `gh auth`) and requires the filing to be signed *"Filed by <model name> via <agent harness>"* (`:73-76`). DHH's merge message: *"It stays quiet until an agent is configured, since a diagnosis is all it offers."* There is no `omarchy-doctor`, no "ask AI" menu, and no script that sends logs or hardware facts to a model; the non-LLM `omarchy-debug` uploads to `logs.omarchy.org` with a 24-hour expiry **only** on an explicit menu choice (`bin/omarchy-debug:73-78`).

- **Problem it solves that Maknae will hit:** an agent as a **read-first responder to a system event** with an explicit "reads, does not fix" boundary and an explicit consent gate before anything leaves the machine is, almost line for line, the Cooky MVP (ADR-0023: two tools, read first). The prompt-as-five-facts discipline, the skill-carried boundary, the signed attribution of machine-filed reports, and the "silent unless configured" default are all transferable as design, and cheap.
- **Why the data path is not:** Omarchy gathers five fields and transmits nothing; *everything after that is whatever the user's agent does*, and the agent has just been told to read a core dump that may hold credentials. Whether that memory reaches a remote model is decided by nobody. In Maknae the same scenario is a classification decision the ceiling operand makes about content (the dump) flowing to a destination (the provider), and the egress process (#240) is the only path it can take. **This is a concrete acceptance test for #240/#242**: a crash dump marked above the declared level must be refused before the loop can quote it to the model.

### 3.3 Skills as symlinks into seven harnesses, and OS widgets that read harness credentials — CONTRAST on credential custody.

`bin/omarchy-provision-user:87-104` symlinks every directory under `default/agents/skills/` into `~/.agents/skills`, `~/.claude/skills`, `~/.codex/skills`, `~/.pi/agent/skills`, `~/.gemini/config/skills`, `~/.hermes/skills` and per-profile Hermes dirs. Theme sync writes into agent settings files (`bin/omarchy-theme-set-claude:9-12,54`, templates under `default/themed/`). The bar's usage widget (`shell/plugins/agents/manifest.json`, every 900 s) reads `~/.claude/.credentials.json` (`bin/omarchy-agent-usage-claude:586`), extracts the OAuth `accessToken` (`:593`) and calls `https://api.anthropic.com/api/oauth/usage` with it (`:36,715-716`); the Codex collector spawns an app-server and reads `~/.codex/sessions`; the Fireworks collector falls back to `~/.fireworks/auth.ini` and opencode's `auth.json` (`bin/omarchy-agent-usage-fireworks:199-209`).

- **The contrast:** the OS treats harness credentials in the home directory as ambient data a status widget may read and replay. Maknae's provider registration (#243) refuses a key in configuration by name and reaches it only through Vault; ADR-0023 gives the model call its own process and its own Vault principal so the loop never holds the credential at all. Omarchy shows the default a desktop converges on when custody is not designed: every agent's token is one `jq` away from every other process in the session.
- **Transferable:** the *distribution* mechanism for skills (one source tree, symlinked into each harness's discovery path) is a reasonable answer to "how does the OS teach the agent about itself," and the shipped `omarchy` skill's instruction to always run `omarchy debug --no-sudo --print` (`SKILL.md:222-228`) is an agent-facing least-privilege rule written where the agent will read it. Maknae's AGENTS.md is the same idea for contributors; a subject-facing equivalent for the loop is worth a thought when #241 lands.

### 3.4 Unpinned agent binaries at provisioning, and `curl | sh` for toolchains — DO NOT ADOPT; a direct contrast with this week's supply-chain work.

`install/user/mise.sh:5-29` provisions stubs for `codex`, `claude`, `crush`, `antigravity-cli`, `gh`, `copilot`, `opencode`, `npm:playwright`, `pi`, `github:can1357/oh-my-pi`, `npm:@xai-official/grok`, `cursor-agent`, `ghui`, `hunk`, `hey`, `github:OpenRouterLabs/ori-releases`, a pipx Hermes, and Meta's Muse via `http:muse[url=https://api.meta.ai/muse-launcher.sh…]`. The stub (`bin/omarchy-mise-install:52-57`) sets `MISE_MINIMUM_RELEASE_AGE=0` and runs `mise use -g --quiet <pkg>` on first invocation: latest at that moment, no pin, no checksum, and `bin/omarchy-update-mise:11` repeats `MISE_MINIMUM_RELEASE_AGE=0 mise up` on every update. Toolchains arrive by `curl -fsSL https://astral.sh/uv/install.sh | sh`, `bash -c "$(curl … sh.rustup.rs)"`, and the same for opam (`bin/omarchy-install-dev-env:100,122,135`). The 3.x→4 upgrader fetches `refs/heads/master.tar.gz` unverified (`bin/omarchy-upgrade-to-quattro:968`); the dev channel is `git pull --ff-only` of a moving branch (`bin/omarchy-update-dev:15`) whose `bin/` is then placed in sudo's `secure_path` (`bin/omarchy-dev-link:22`).

- **Fit to Maknae:** none. Maknae now pins actions by SHA with the repository refusing unpinned ones, runs every CI cargo command `--locked`, holds a 5/5/5/10-day cooldown on crates and 7 on actions, and pins the FIPS module below the in-process release. `MISE_MINIMUM_RELEASE_AGE=0` is the exact inverse of a cooldown, and the foundation that ships it is a mise sponsor. Record the contrast; the reasoning is already on the shelf in `dependabot.yml` and `crates/maknae-vault/Cargo.toml`.

### 3.5 Package trust: a first-party repo rebuilding AUR, a keyserver-bootstrapped root, and a year of `TrustAll` — CONTRAST, with one validating detail.

`pkgs.omarchy.org` (from v2.0.0, 2025-08-25) rebuilds AUR PKGBUILDs in containers, signs, and rsyncs to production; the key lives in 1Password (`omacom/omarchy-pkgs`). From August 2025 to August 2026 the repo ran `SigLevel = Optional TrustAll` (packages carried SHA-256 only) until migration `1787589206.sh` (2026-08-24) removed the override; today `default/pacman/pacman-stable.conf` has `Required DatabaseOptional`. The trust root is fetched from `keys.openpgp.org` and locally signed (`bin/omarchy-update-keyring:5-6`); the internal plan `plans/nix.md` concedes *"our signature chain roots outside our infrastructure"* and that the AUR path *"executes unsigned build scripts fetched live from aur.archlinux.org."* Two weakenings persist: `SigLevel = Never` for a GitHub-release-hosted repo on Apple T2 Macs (`install/hardware/pacman.sh:7-9`), and the 3.x→4 upgrader writing `Optional TrustAll` (`bin/omarchy-upgrade-to-quattro:417,430`) without restoring it in that script. The base install uses no AUR; optional browsers do, via `yay --noconfirm` (`bin/omarchy-install-browser:44-86`). No evidence links Omarchy to the July 2025 AUR malware packages.

- **The validating detail:** the stable channel *"runs one month behind"* Arch (`manual/30-updates.md:13`), with edge→rc→stable promotion. That is a supply-chain delay identical in spirit to Maknae's cooldown, adopted for the same reason, by a project otherwise indifferent to pinning. Worth one sentence in the Dependabot rationale if it is ever questioned.
- **For a DoD host the rest is disqualifying**, and it is the reason Omarchy is not a candidate operating environment for Maknae under the OS exploration: a trust root that must be fetched at install, a rebuild pipeline with no published vetting policy, and `--noconfirm` on every transaction (`bin/omarchy-pkg-add:8,10`, `omarchy-update-system-pkgs:20-21` with `--overwrite '/usr/share/omarchy/*'`).

### 3.6 Migrations: timestamp-keyed, idempotent, per-user markers, ordered, never silent, and *taught to agents* — LEARN FROM.

`migrations/<unix timestamp>.sh` (111 files, 2026-05-13 to 2026-09-07), mode 0644 with no shebang, executed by `bash -euo pipefail` (`bin/omarchy-migrate:73`), marked per user on success (`:74-75`), strictly ordered with the queue halting on failure, and announced at login by a notifier that *"prompts, never runs silently."* Privilege is not inherited: *"privileged operations should invoke the appropriate helper or privilege prompt themselves. Migrations must be idempotent"* (`agents/skills/migrations.md:29-31`). That file is a **skill written for the agents that author migrations**, alongside `AGENTS.md` (DHH, 2026-02-06: *"Let's help our agent friends a little to understand the Omarchy code base"*).

- **Problem it solves that Maknae will hit:** `config.d/` and the boot-selected classification system will need schema migrations eventually, and the loop's own state will too. The discipline here (key by time, idempotent, per-principal marker, halt on first failure, announce, escalate explicitly) is a good default and costs nothing to write down now.
- **Fit to Maknae's process:** the agent-facing task skills are the same instinct as AGENTS.md's decision-record rules, aimed one level lower. Where Omarchy keeps `plans/` in the repository, Maknae's standing rule is that plans never live there; the contrast is deliberate and should stay.

### 3.7 Engineering process: bot merges, no CI, and a security wave after a rewrite — DO NOT ADOPT; validating contrast for principles 5 and 6.

`.github/` holds `CODEOWNERS` (`* @dhh @ryanrhughes`), `SECURITY.md` (added 2026-08-30), and issue templates; **no workflows**, no shellcheck configuration. There is a substantial in-repo bash test suite (236 shell tests, a 714-line CLI test, a VM acceptance suite including `security-test.sh` that asserts key-only SSH and the `ufw limit 22` rule), but nothing runs it on a pull request. DHH authored roughly 78% of commits and 51 of 64 releases; Quattro landed as a single DHH PR (#6231); `omarchybot` reviews and merges. The v4.0.0 release (2026-08-14) was followed by v4.0.1 (08-25: themes could execute code, USB device names executed as Hyprland Lua, predictable `/tmp` in FIDO2 setup, git transport-helper abuse) and v4.0.2 (08-31: shell injection in theme and app installers, CUPS hardening, remote image injection, SSH password auth off by default). Separately, the default user sat in the `docker` group, root-equivalent, from 2025-06-01 until PR #8056 on 2026-08-24. A Security Team was formed around 2026-08-19. **No CVE has been assigned to any Omarchy issue** and no GitHub Security Advisory has been published; the credits page lists seven reporters.

- **Why it matters here:** Maknae is also built largely by AI agents. The difference is not the authorship; it is that Maknae's suite is mutation-proofed, every gate has a negative control, fresh-context review is mandatory, and no agent merges (principles 5 and 6; CONTRIBUTING). Omarchy is what the same authorship produces without those controls, and it produced two security releases in seventeen days. The record is worth citing the next time the blind-review cost is questioned.

### 3.8 Security defaults on the host — CONTRAST; Omarchy is not a candidate host for the OS exploration.

LUKS is default-on with a Ctrl+C opt-out (`manual/02-getting-started.md:3,35`), `cryptsetup … --pbkdf argon2id` on passphrase change (`bin/omarchy-drive-password:25`), ufw deny-in/allow-out with 53317 open for LocalSend (`install/config/firewall.sh:2-7`), sshd off until an opt-in wizard that pulls keys from `https://github.com/$username.keys` (`bin/omarchy-setup-security-sshd:106`) and writes `PasswordAuthentication no` (`:161-162`), FIDO2 for `sudo` and polkit opt-in (`bin/omarchy-setup-security-fido2:23,29`), LLMNR and mDNS off, one hardened unit (`cups-browsed`). Against that: *"You must turn off Secure Boot and/or TPM in the BIOS… They're Microsoft security schemes"* (`manual/02-getting-started.md:7`), so no measured boot and no TPM-bound LUKS; SDDM autologin is **permanent on encrypted installs** (`bin/omarchy-provision-owner:776-779`, *"the LUKS prompt is the auth boundary"*); the default GNOME keyring is created passwordless with `lock-on-idle=false` (`install/user/default-keyring.sh:6-13`); faillock `deny` raised from 3 to 10 and `passwd_tries=10` (`etc/security/faillock.conf:7`, `etc/sudoers.d/omarchy-passwd-tries:1`); three shipped scoped `NOPASSWD` rules; the Docker socket enabled by default; the install log `chmod 666`.

- **Disposition:** the OS exploration asks *"which supported hosts can establish those guarantees."* Omarchy answers for itself: it is a single-user developer workstation that trades measured boot, session authentication and lockout policy for convenience, by design and in writing. Several of those are CAT I or CAT II findings on the baselines Maknae deploys to. It is a fine machine to *develop* Maknae on and a wrong machine to *enforce* Maknae from.

### 3.9 Diagnostics consent model and the absence of telemetry — LEARN FROM.

No analytics or telemetry strings exist in `bin/`, `install/`, `etc/`, `default/` or `config/`. Outbound runtime calls are enumerable: weather (`wttr.in`), an AUR reachability probe, a speed test, an update check every six hours, and the two user-initiated log uploads with 24-hour expiry. The upgrade failure path is an ERR trap that prints a Discord URL (`bin/omarchy-update:19`), not a phone-home.

- **Fit to Maknae:** the property "every outbound destination is enumerable from the tree" is one Maknae should be able to state about itself, and after #240 it will be able to state it as a policy fact rather than a grep. The 24-hour-expiry, explicit-choice upload is a sensible consent shape for whatever #223 (audit offload) becomes.

### 3.10 Documentation as the product surface — LEARN FROM, selectively.

A 51-chapter manual (`manual/`, mirrored at omarchy.org), `docs/update-process.md`, `docs/file-layout.md`, `docs/theming.md`, `docs/testing.md`, and per-task agent skills. The manual is the reason a distribution built on bash is usable by 200,000 people; it is also where the security posture is stated candidly (*"Omarchy takes security extremely seriously"* in the same chapter that documents the passwordless-sudo toggle). Maknae's [`docs/configuration.md`](../../docs/configuration.md) and runbook are the seed of the same thing; the lesson is that the manual should say what the system *refuses* as plainly as what it does.

## 4. The agentic-OS question, answered from the record

The maintainer's added focus was **how Omarchy handles agentic tool integration and LLM integration on the OS for troubleshooting.** The short answer, with the evidence above:

1. **Integration is wide and shallow.** Fourteen agents are one keybinding away, every one launched with permissions bypassed, in the user's session, with credentials readable from `$HOME` by any process. The OS offers *access*, not *governance*. There is no MCP server, no shipped permission allowlist, no hook, no sandbox; the only shipped Claude Code or Codex configuration is theming and skill discovery.
2. **LLM troubleshooting is one feature, well bounded, ungoverned past its edge.** Crash diagnosis is a model of restraint in what the OS itself collects and sends (five facts, nothing transmitted). It then hands a possibly credential-bearing core dump to an agent whose egress nobody mediates. The boundary is documentary (*"reads; does not fix"*), not enforced.
3. **The trajectory is toward more of the same.** The agent-facing surfaces landed in order: a skill (2026-01), unpinned stubs and the sudo danger mode (2026-03), usage widgets reading credentials (2026-05 to 08), the default agent and crash diagnosis (2026-08), and the tagline change to "agentic" (2026-09-01). Each step lowers friction between the agent and the machine; none adds a decision point.

**What that means for Cooky.** The loop Maknae ships (ADR-0023) will be judged next to this. Its answer to the same three items is: one loop, no bypass flag because the loop never held the decision; credentials in a separate process under a separate principal; and egress that is a policy outcome, not a side effect of which agent the user picked. Omarchy has made the market's default legible. The acceptance evidence for #242 should include the crash-dump case from §3.2, stated as "a thing Omarchy would have sent, and Maknae refused, with the record to show it."

## 5. Scope and limits of this assessment (honesty)

- **Read-only, two shallow clones, no execution.** Surveyed at `quattro` HEAD `d5040617`; line numbers move. History dating used a blob-less unshallow of the second clone.
- **The self-hosted search instance returned zero results for every query** (its upstream engines were suspended or rate-limited on the day), so the external record fell back to direct fetches and the public GitHub API. Every external claim in §6 carries the URL it was read from.
- **Unverified, stated as such:** the exact date the repository moved from `basecamp/` to `omacom/`; star count over time (the stargazer listing was refused); the foundation's jurisdiction, legal form, and board; any DHH statement using the words "secure enough."
- **Not assessed:** the Quickshell desktop shell's own code (42k lines of QML/JS), the ISO builder in `omarchy-pkgs`, and the `omarchy-chromium` fork (archived 2026-05-07).
- **No dispositions ratified.** Nothing above opens an issue or changes a plan. The one concrete suggestion, a crash-dump acceptance case for #240/#242, is a candidate for the Cooky acceptance issue, not a commitment.
